# 21. Polling (опрос) и паттерны синхронизации

Про то, что такое поллер, зачем его используют, чем он плох, чем его заменяют. С примерами из ИСНА.

---

## 1. Что такое polling

**Polling (опрос)** — приёмник **периодически спрашивает** источник «есть новые данные?». Инициатор — приёмник. Источник просто отвечает на запросы, ничего сам никуда не пушит.

Аналогия: ты каждые 5 минут проверяешь почтовый ящик — есть письма? Ящик сам тебе не звонит.

### 1.1 Простейшая схема

```
┌────────────┐    "Есть новости?"    ┌──────────────┐
│  Приёмник  │ ────────────────────▶ │  Источник    │
│ (poller)   │ ◀──────────────────── │  (сервер БД, │
│            │    "Держи, вот эти"    │   API, etc)  │
└────────────┘                        └──────────────┘
       │
       │  каждые N секунд повторяем
       ▼
     цикл
```

### 1.2 Что делает поллер в коде

Типичный псевдокод:

```java
@Scheduled(fixedDelay = 30_000)   // каждые 30 сек
public void poll() {
    long lastOffset = repo.getLastOffset();          // где остановились
    List<Item> batch = source.fetch(lastOffset, 200); // спросить у источника
    for (Item item : batch) {
        try {
            apply(item);                              // применить
            lastOffset = item.getOffset();            // сдвинуть курсор
        } catch (Exception e) {
            log.error("failed on {}", item.getId(), e);
            break;                                    // или continue, зависит от логики
        }
    }
    repo.saveLastOffset(lastOffset);                  // запомнить прогресс
}
```

Три ключевых элемента:
- **Планировщик** (`@Scheduled`, `taskScheduler`, cron) — запускает цикл раз в N секунд.
- **Курсор** (`last_offset`, timestamp, ID) — точка «докуда докатились».
- **Батч** — сколько тянуть за один тик (200, 1000, unlimited).

## 2. Виды polling

### 2.1 Short polling (обычный)

Приёмник спрашивает — источник **сразу отвечает** (даже если ничего нового нет: `[]` пустой массив). Пауза до следующего запроса.

- **Плюсы**: примитивно, HTTP-friendly, работает через любые прокси/файрволы.
- **Минусы**: пустых запросов много (нагрузка на источник), latency = interval.

Именно это — **AS-IS в ИСНА**: `isnanzsync` каждые 30 сек дёргает tax-rep-sync через SOAP `IBSyncChannelClient.syncData(...)`, даже если ничего нового.

### 2.2 Long polling

Приёмник спрашивает — источник **держит соединение открытым**, пока не появится новое (или таймаут ~30-60 сек). Как только появилось — сразу отдаёт.

- **Плюсы**: latency ≈ 0, меньше пустых запросов.
- **Минусы**: держит подключения → плохо масштабируется, файрволы могут рвать длинные соединения.
- Пример: Slack RTM API до перехода на WebSocket.

### 2.3 Adaptive polling

Интервал **зависит от нагрузки**: пусто → увеличиваем интервал (30с → 1мин → 5мин), нашли что-то → уменьшаем (30с → 5с). Разумный компромисс.

### 2.4 Batch polling

Собираем данные пачками, а не по одному:
```
GET /events?since=12345&limit=200
```
`last_offset` двигается по всей пачке. Один запрос — 200 записей.

Все виды выше используют одну и ту же идею — **инициатива на приёмнике**, разница только в том, как часто и как много.

## 3. Как выглядит поллер в синхронизации ИСНА (пример AS-IS)

Пример полного цикла синхронизации статуса НЗ из tax-rep в isna-nz.

### 3.1 Источник — tax-rep

- Бизнес-процесс: приёмка НЗ → создание строки статуса.
- В **той же транзакции** INSERT в таблицу-outbox `nz_notification_sync (id, nz_id, status, ...)`. `id` — монотонно возрастает через sequence.
- Готовый REST/SOAP-эндпоинт: `GET /api/nz-sync/get/{lastOffset}` → возвращает до 200 строк с `id > lastOffset`.

### 3.2 Приёмник — isna-nz

- Хранит свой курсор: `universal_sync_history.last_offset` (для `data_type = NZ_NOTIFICATION`).
- Каждые 30 сек:
  - читает `last_offset` из БД,
  - шлёт SOAP-запрос `IBSyncChannel/syncData(offset=last_offset)` — с ЭЦП-подписью,
  - получает JSON-массив событий,
  - применяет каждое событие (создать запись `nz_status_history`, обновить `nz`, добавить в очередь генерации PDF-уведомления),
  - сохраняет новый `last_offset` в БД,
  - шедулит следующий вызов через 30 сек.

### 3.3 Ключевой код

`isna-nz-sync/.../service/NotificationSyncService.java`:

```java
@EventListener(ApplicationReadyEvent.class)
public void sync() {
    Long lastOffset = universalSyncHistoryService.getLastOffsetByDataType("NZ_NOTIFICATION");
    SyncDataRequest req = ...;
    req.setOffset(lastOffset);
    String signed = kalkanGlobalService.serializeAndSign(req);
    Object resp = client.syncData(serviceId, senderId, password, signed);
    processResponse(messageId, lastOffset, resp);
    taskScheduler.schedule(this::sync, now + syncDelay);   // ← вот и планировщик
}
```

Обрати внимание — schedule сам себя рекурсивно, а не через `@Scheduled(fixedDelay)`. Работает так же, только чуть менее декларативно.

## 4. Плюсы и минусы polling

### 4.1 Плюсы

- **Простота реализации** — работает на HTTP/REST/SOAP, никаких брокеров, WebSocket, специальных протоколов.
- **Понятная восстановимость** — упал приёмник, перезапустился, прочитал `last_offset`, продолжил.
- **Нет требований к источнику** — источник просто отдаёт данные по запросу, не должен знать про подписчиков.
- **Файрвол-friendly** — обычный HTTP-запрос, ни NAT, ни закрытые порты не мешают.
- **Скорость разработки** — часто это первая версия синхронизации, потому что «быстро сделать».

### 4.2 Минусы

- **Latency** — задержка ≈ interval. При 30-сек интервале статус НЗ едет в среднем 15 сек, максимум 30 сек. Для realtime не годится.
- **Пустые запросы** — 90% циклов «пусто». Нагрузка на источник и сеть даже при отсутствии данных.
- **Один общий курсор — точка отказа**:
  - если приёмник упал на записи N → следующий тик снова возьмёт с N → застревает вся очередь;
  - если админ вручную сдвинул `last_offset` вперёд (для «разморозки») → **записи между старым и новым offset тихо пропадают**;
  - именно так в ИСНА 1236 документов NZ 016 остались в статусе `in-processing` вместо `accepted`.
- **Нет обратной связи** — источник не знает, реально ли приёмник применил, или упал на середине.
- **Batch-эффект** — задержка накапливается, если N событий пришло между тиками.
- **Не масштабируется по подписчикам** — если приёмников 10, они все синхронно долбят источник. Push-модель распределяет нагрузку броктером.

### 4.3 Классические ошибки при написании поллера

1. **`catch (Exception) { break; }` без rollback** — курсор сохраняется на последней успешной, все следующие в батче теряются молча. AS-IS ИСНА страдает именно этим.
2. **`findById(id).isEmpty()` → тихий return** — запись потеряна, но курсор двинулся вперёд.
3. **`@Transactional` без `rollbackFor=Exception.class`** — checked-исключения не откатывают транзакцию, курсор коммитится с частичным состоянием.
4. **Курсор в БД + apply в другой транзакции** — если apply прошёл, а сохранение курсора — нет (или наоборот), рассинхрон.
5. **Отсутствие идемпотентности на приёмнике** — при ретрае то же событие применяется дважды (два уведомления клиенту, дубли в БД).
6. **Фиксированный batch size без backpressure** — источник может быть перегружен, приёмник продолжает долбить.

## 5. Альтернативы polling

### 5.1 Push (webhook, callback)

Источник **сам** зовёт приёмник, когда есть новое:

```
Источник --(HTTP POST /webhook)-->  Приёмник
```

- **Плюсы**: latency миллисекунды, нет пустых запросов.
- **Минусы**: источник должен знать про подписчиков, при недоступности приёмника нужен retry на источнике.

Пример: GitHub webhook, платёжные шлюзы Stripe/Kaspi.

### 5.2 Message broker (Rabbit, Kafka)

Источник **публикует** в брокер, приёмник **подписан** и получает push от брокера. Между ними развязка.

```
Источник → [брокер] → Приёмник
```

- **Плюсы**: latency миллисекунды, гарантии доставки (persistent queues), retry, DLQ, fan-out на много подписчиков.
- **Минусы**: инфраструктурная сложность (брокер надо держать живым), другой протокол (AMQP/Kafka вместо HTTP).

Пример: в ИСНА все внутренние очереди типа `PDF_CENTRAL`, `NOTIFICATION_CENTRAL` — через Rabbit. Межконтурная связь для генерации PDF ФНО (`isna-to-knp-pdf-direct`) — тоже Rabbit.

### 5.3 CDC (Change Data Capture)

Отдельный процесс читает **WAL PostgreSQL** и публикует изменения в Kafka. Приложение не знает про синхронизацию — просто пишет в свою БД.

```
Источник → INSERT → WAL → [Debezium] → Kafka → Приёмник
```

- **Плюсы**: приложение вообще ни при чём, CDC-агент сам всё поймает. Zero-impact на код.
- **Минусы**: операционная сложность (Kafka + Kafka Connect + Debezium + мониторинг).

Пример: Netflix, Uber, крупные fintech, где latency важна, а нагрузка миллионы событий/сек.

### 5.4 Server-Sent Events / WebSocket

Долгоживущее соединение источник → приёмник, источник шлёт по нему события.

- **Плюсы**: realtime.
- **Минусы**: только пока соединение живо, нужен reconnect с backoff, не подходит для гарантированной доставки.

## 6. Push vs pull — когда что выбирать

| Критерий | Pull (polling) | Push (broker) |
|---|---|---|
| Задержка | interval (секунды-минуты) | миллисекунды |
| Пустые запросы | много | нет |
| Инициатор | приёмник | источник |
| Знание про подписчиков на источнике | нет | да (через брокер) |
| Файрвол-friendly | да | нужен открытый порт брокера |
| Инфраструктура | HTTP хватит | нужен брокер |
| Fan-out | плохо (каждый долбит) | хорошо (одно событие → N подписчиков) |
| Восстановление после сбоя | легко (перечитал курсор) | легко (durable queue) |
| Гарантия доставки | on-demand (пока приёмник спрашивает) | at-least-once / exactly-once (durable + ack) |
| Ordering | естественный (по offset) | естественный per-partition |
| Backpressure | приёмник контролирует | брокер буферизует |
| Простота разработки | высокая (можно за час) | средняя (нужны продюсер/консюмер/DLQ) |

**Правило большого пальца:**
- **Прототип / low-throughput / внутренний cron-job**: polling ок.
- **Что-то видит пользователь и ждёт результат** (принятие документа, статус платежа): push.
- **Высокая нагрузка (десятки тысяч событий/сек)** или **fan-out**: message broker обязательно.
- **Разные системы разных владельцев**: webhook (если pushing side управляем) или polling (если нет).

## 7. Как из polling переехать в push (общий рецепт)

Не «удалить старое, включить новое» — а поэтапно:

### Этап 1. Dark launch (обе схемы параллельно)

- Источник продолжает вести outbox (`nz_notification_sync` / `queue_message`), но **дополнительно** пушит каждое событие в брокер после commit.
- Приёмник: включаем новый `@RabbitListener`, но старый poller тоже работает.
- **Идемпотентность на приёмнике обязательна** — иначе события применятся дважды. Классически: таблица `inbox(source_id UNIQUE)` + `INSERT ... ON CONFLICT DO NOTHING`.
- Мониторим неделю: сравниваем сколько применилось через push и сколько через pull. В идеале push должен покрывать 100%, pull — 0.

### Этап 2. Отключение poller'а

Убираем `@Scheduled` / `taskScheduler.schedule(this::sync)` на приёмнике. Push остаётся единственным каналом.

### Этап 3. Уборка

- Удалить SOAP/REST-эндпоинт синхронизации на источнике.
- Удалить курсор-таблицу (или оставить архивно).

## 8. Как из polling'а сделать «безстрятного» push с гарантиями (паттерн из ИСНА)

Просто «уйти на брокер» недостаточно — Rabbit сам по себе может потерять сообщение при рестарте, консюмер может упасть между receive и apply, ack может не долететь до продюсера. **Правильный паттерн — Transactional Outbox + шедулер-восстановитель + inbox**.

### 8.1 На источнике

1. **Outbox-таблица в той же БД, что и бизнес-данные**. В `NzService.processNz` INSERT в `queue_message` идёт **в одной транзакции** с INSERT в `nz_status_history`. Атомарно.
2. **После commit** — publish в Rabbit. Если broker недоступен → status в outbox остаётся `WAIT`.
3. **`@Scheduled` producer** каждые ≤ 2 мин: SELECT `WAIT`/`FAILED` c `next_attempt_date_time < now()` → re-publish. **Не polling источника — polling своей же outbox-таблицы, что кардинально другое** (там всегда мало строк — те что не доехали).
4. **Stuck-recovery шедулер** каждые ≤ 10 мин: SELECT `IN_PROGRESS` со `status_date_time` старше 30 мин → переводит в `FAILED` + `attempts++` → producer подхватит.

### 8.2 На приёмнике

1. `@RabbitListener` принимает сообщение.
2. INSERT в `inbox(source_id UNIQUE)` с `ON CONFLICT DO NOTHING` — если 0 rows, значит уже применяли → сразу ack.
3. Иначе — применить (та же логика что раньше в `updateNz`).
4. Отправить ack-сообщение обратно источнику через отдельную ack-очередь.

### 8.3 Ack-очередь обратно

- Приёмник → `TAX_REP_TO_NZ_NOTIFICATION_SYNC_ACK_QUEUE` → консюмер на источнике → `queueMessageService.success(qm)` или `failed(qm, error)`.
- Если ack не пришёл → outbox-запись висит в `IN_PROGRESS` → stuck-recovery через 30 мин вернёт в `FAILED` → producer перезапушит → приёмник видит inbox-запись → мгновенно шлёт ack `applied=true` → outbox финализируется.

### 8.4 Что это даёт

**Ничего не пропадает, даже если:**
- broker падает → outbox держит, producer ретраит;
- consumer падает → Rabbit re-deliver или producer re-publish, inbox спасает от двойного применения;
- ack теряется → stuck-recovery + retry-round trip;
- бизнес-транзакция откатывается → outbox-запись откатывается вместе с ней (одна tx);
- админ ошибся с offset → offset больше не единая точка отказа, каждое сообщение независимо.

**Максимальное время восстановления** — 30 мин (stuck-recovery threshold) + ≤ 2 мин (producer interval) + `SimpleRedeliveryStrategy` backoff. То есть ≈ 30-40 мин worst case, но не «навсегда».

## 9. Метрики и мониторинг поллера

Что смотреть, если у тебя всё же остался polling:

- **Возраст `last_offset`** — насколько отстаёт от источника. `MAX(source.id) - last_offset` → должно быстро возвращаться к нулю после каждого тика.
- **Duration тика** — сколько занимает один цикл. Если растёт → приёмник не успевает.
- **Errors per cycle** — сколько записей в батче упало.
- **Cycles per hour** — реально запускается ли шедулер (если 0 — виновник в самом Spring).
- **Cursor stuck detector** — если `last_offset` не двигается более чем X минут, при том что источник INSERT-ит → алёрт.

Для push через outbox+broker:

- **Количество `WAIT`/`FAILED`/`IN_PROGRESS`** в outbox по queue_name → должно быть близко к нулю большую часть времени.
- **Возраст самой старой `IN_PROGRESS`** → должно быть < 30 мин.
- **Attempts distribution** → если большинство доезжают на 1-2 попытки, ок; если 5+ — есть системная проблема.
- **DLQ / dead-letter counts** → должно быть 0.

## 10. Итог

- **Polling** — приёмник опрашивает источник по расписанию. Просто, но с latency и точками отказа.
- Работает через курсор (`last_offset`) в БД приёмника + периодический вызов.
- Слабости: latency ≈ interval, при сбое → застревание или тихий пропуск.
- **Push через broker** — источник публикует, приёмник подписан. Realtime + отказоустойчиво.
- Правильный push реализуется через **Transactional Outbox + retry + stuck-recovery + inbox** — иначе broker сам по себе не спасает от потери.
- Переход pull → push — обязательно поэтапно (dark launch), с идемпотентностью на приёмнике.

### Что в ИСНА сейчас

- Синхронизация статусов НЗ (`nz_notification_sync`) — **polling каждые 30 сек** через SOAP.
- Внутренние очереди сервисов (`PDF_CENTRAL`, `NOTIFICATION_CENTRAL`, `REGISTRIES_CENTRAL`) — **push через Rabbit + Transactional Outbox** (таблица `queue_message`).
- Межконтурная генерация PDF ФНО (`isna-to-knp-pdf-direct`) — **push через Rabbit КНП** (без outbox, только Rabbit-durable).

Синхронизацию НЗ имеет смысл переводить в тот же режим — Transactional Outbox через `queue_message` + push в Rabbit КНП + inbox на приёмнике. См. `isna-tax-rep/docs/nz-notification-sync-rabbit-migration.md`.
