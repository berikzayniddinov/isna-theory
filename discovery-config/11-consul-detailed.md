# 11. Consul: service discovery в enterprise микросервисах

## Зачем Consul если есть Kubernetes

Первый вопрос, возникающий у разработчика после знакомства с Kubernetes — зачем в системе ещё Consul, если K8s уже даёт service discovery через встроенные ClusterIP Service и внутренний DNS. Вопрос разумный, и понимание ответа помогает разобраться в архитектуре enterprise микросервисной системы вроде КНП, где присутствуют оба механизма одновременно.

Первый уровень объяснения — исторический. Много enterprise систем построены на Spring Cloud стеке, разработанном до массового внедрения Kubernetes. Spring Cloud появился примерно в 2015 году, изначально работал с Netflix Eureka, потом добавил поддержку Consul. Kubernetes тогда только начинал набирать популярность, service mesh как концепция ещё не существовал. Компании строили микросервисные архитектуры на Spring Cloud, использовали Consul для service discovery. Когда Kubernetes стал стандартом инфраструктуры, приложения мигрировали в кластер, но исторический механизм service discovery оставался. Полное удаление Consul из работающей системы — задача на месяцы, не всегда оправданная. Так и в КНП: Spring Cloud плюс Consul появились раньше, K8s пришёл позже, оба существуют параллельно и работают вместе.

Второй уровень — client-side load balancing как принципиальный архитектурный выбор. Kubernetes Service работает на четвёртом уровне сетевой модели, через iptables или IPVS правила, настраиваемые kube-proxy на каждой ноде. Балансировка простая round-robin — трафик направляется к следующему backend в списке, никакая информация о состоянии этого backend не учитывается. Это работает для простых случаев, но не даёт гибкости. Consul поддерживает совершенно другой подход — клиент сам получает список инстансов сервиса и выбирает по своему алгоритму. Возможны веса на отдельных инстансах (для canary deployments), теги для фильтрации (только определённая версия или регион), retry на другой инстанс при ошибке первого, custom эвристики выбора вроде географической близости или sticky sessions по идентификатору пользователя. Всё это невозможно с простой server-side балансировкой Kubernetes Service.

Третий уровень — качество health checks. Kubernetes probes проверяют TCP порт или HTTP endpoint, возвращающий определённый код. По сути "приложение отвечает на порту". Consul может делать более сложные проверки с учётом бизнес-логики. Не просто "приложение живо", а "приложение живо и БД доступна и очередь не переполнена и внешний сервис отвечает в разумное время". Custom health indicators, зависящие от реального состояния системы, а не только от того, слушает ли контейнер на порту.

Четвёртый уровень — распределённое хранилище ключ-значение. Consul предоставляет KV store, доступный из любого сервиса через простой HTTP API. Feature flags, глобальные конфигурации, координация между сервисами, распределённые локи — всё это можно реализовать через KV. Kubernetes ConfigMap для той же задачи негибок, потому что при изменении конфигурации требуется перезапуск pods, чтобы новые значения подхватились. Consul KV работает с механизмом Spring Cloud Config Refresh, позволяющим менять конфигурацию в runtime без рестарта приложения.

Пятый уровень — multi-datacenter federation. Consul умеет объединять кластеры в разных датацентрах в единую сеть, сервисы могут находить друг друга через границы датацентров. Kubernetes Service работает только внутри одного кластера — сервисы разных кластеров общаются через внешние endpoints, что усложняет discovery.

Итог такой. Для нового проекта, полностью построенного на Kubernetes, обычно достаточно встроенного Service механизма. Но в КНП, где Spring Cloud плюс Consul появились раньше Kubernetes, они остались как дополнительный слой. Знание обоих механизмов необходимо для практической работы с существующей системой, для диагностики проблем сетевого взаимодействия между микросервисами и для разработки новых сервисов, интегрирующихся с существующей инфраструктурой.

## Что такое Consul технически

Consul — продукт компании HashiCorp, известной также инструментами Terraform, Vault, Nomad. Написан на языке Go, распространяется одним бинарным файлом без сторонних зависимостей. Может работать на любой платформе, поддерживающей Go — Linux, Windows, macOS.

Внутри Consul сочетает несколько функциональных ролей. Первая роль — service registry, каталог сервисов и их запущенных инстансов. Приложение регистрируется в этом каталоге при старте, отменяет регистрацию при shutdown. Другие приложения запрашивают у каталога список активных инстансов конкретного сервиса, чтобы отправить им запросы. Вторая роль — активная проверка здоровья зарегистрированных сервисов. Consul периодически дёргает специальный health check endpoint каждого инстанса, определяет живой ли он. Инстансы, не проходящие health check, помечаются как проблемные и исключаются из результатов discovery. Третья роль — распределённое хранилище ключ-значение с простым HTTP API для put и get операций. Значения могут быть до 512 килобайт, произвольный набор байтов.

Дополнительно Consul предоставляет несколько специализированных возможностей. DNS интерфейс на отдельном порту позволяет резолвить имена сервисов в IP адреса через стандартный протокол DNS, что даёт возможность использовать Consul без специальных клиентских библиотек, даже из shell скриптов. Consul Connect — встроенный service mesh с mutual TLS между сервисами через sidecar proxies на основе Envoy, обеспечивает шифрование всего inter-service трафика без изменения кода приложений. В КНП эта возможность не используется, вся коммуникация происходит по обычному HTTP внутри доверенной сети кластера. Multi-datacenter federation позволяет объединять несколько кластеров Consul в разных датацентрах для распределённого service discovery.

## Архитектура Consul

Consul использует классическое разделение узлов на серверы и агенты, дополненное gossip протоколом для эффективного распространения информации о состоянии кластера.

Consul server — узел, хранящий состояние системы. В production обычно развёртывают три или пять серверов на датацентр. Между собой они используют алгоритм консенсуса Raft для согласования состояния. Один сервер в каждый момент времени является лидером, остальные — followers. Все операции записи проходят через лидера, реплицируются на followers через Raft log. Если лидер падает, followers обнаруживают отсутствие heartbeats и проводят выборы нового лидера. Raft гарантирует, что любое подтверждённое изменение видно всем серверам, обеспечивая strong consistency. Скорость записи ограничена скоростью Raft consensus, что в типичной сети составляет единицы миллисекунд. Чтение может идти с любого сервера параллельно, что даёт хорошую масштабируемость для read-heavy нагрузок.

Три сервера в кластере дают отказоустойчивость единицы — один сервер может упасть, кластер продолжает работать. Пять серверов дают отказоустойчивость двойки. Чётное количество серверов бесполезно, поскольку не улучшает отказоустойчивость по сравнению с ближайшим нечётным меньшим числом, но добавляет overhead на дополнительный узел.

Consul agent — узел на каждой физической машине или в каждом pod Kubernetes кластера. Агент не хранит состояние самостоятельно, он проксирует запросы к серверам. Основные функции агента — выполнение health checks для локально зарегистрированных сервисов и предоставление HTTP API на localhost для приложений. Приложение всегда общается с локальным агентом, а не напрямую с сервером, что упрощает конфигурацию (адрес агента известен и стабилен — это всегда localhost) и добавляет уровень изоляции от отказов серверов.

Между узлами кластера используется gossip protocol для распространения информации о состоянии друг друга. Consul реализует SWIM (Scalable Weakly-consistent Infection-style process group Membership) — peer-to-peer протокол, при котором каждый узел периодически "болтает" со случайными соседями, распространяя информацию о живости других узлов. Такой подход не требует централизованной координации, естественно масштабируется до тысяч узлов, устойчив к частичным сетевым сбоям. Есть два уровня gossip — LAN gossip внутри одного датацентра для быстрого обнаружения новых узлов и failures, и WAN gossip между датацентрами для multi-datacenter federation.

Полная топология Consul кластера в КНП выглядит примерно так. Три или пять серверов координируют состояние через Raft consensus, обеспечивая strong consistency для service registry и KV store. Десятки или сотни агентов работают на нодах Kubernetes кластера, обслуживают локальные приложения и общаются с серверами через gRPC для операций записи и HTTP для чтения. Gossip протокол держит всех участников в курсе живости друг друга.

## Регистрация Spring Boot приложения в Consul

Механика регистрации автоматизируется через Spring Cloud Consul. Разработчику достаточно подключить соответствующий starter и настроить несколько параметров, всё остальное происходит автоматически при старте приложения.

Подключение зависимости `spring-cloud-starter-consul-discovery` в build.gradle приводит к появлению в classpath автоконфигурационных классов, которые Spring Boot обнаруживает при старте. Часто вместе с discovery starter подключают ещё `spring-cloud-starter-consul-config` для чтения конфигурации из Consul KV store и `spring-cloud-starter-openfeign` для декларативных HTTP клиентов, использующих Consul discovery для поиска целевых сервисов.

Конфигурация обычно находится в файле `bootstrap.yml`, который читается до обычного `application.yml`. Это необходимо потому, что настройки Consul нужны для загрузки конфигурации из KV store, а сама эта конфигурация может влиять на всё остальное. В bootstrap указывается адрес Consul agent (обычно localhost или внутренний DNS имя вроде consul.isna.internal), порт, имя сервиса под которым приложение регистрируется, путь к health check endpoint (обычно /actuator/health от Spring Boot Actuator), интервал проверки, префикс IP-адрес использования вместо hostname (важно в контейнерной среде, где hostname бесполезен для сетевых обращений), опции регистрации и деregistration, идентификатор экземпляра и произвольные теги для фильтрации.

Особое внимание требует настройка query-passing со значением true. Этот параметр определяет, какие инстансы возвращаются клиентам при discovery. По умолчанию значение false — возвращаются все инстансы независимо от их health статуса. Клиент может получить в списке инстанс, помеченный как critical (не проходит health check), попытаться к нему подключиться и получить connection refused или timeout. При query-passing true в результате остаются только инстансы в состоянии passing. Правильная настройка для production — всегда true. Реальный кейс из КНП — при подготовке к масштабной миграции обнаружили, что в пятидесяти трёх модулях эта настройка не была явно прописана, использовалось значение по умолчанию false, что потенциально приводило к попыткам подключения к нездоровым инстансам. Массовая правка через миграционный pull request исправила ситуацию.

Что происходит при старте приложения. Spring Boot автоконфигурация регистрирует beans ConsulServiceRegistry и ConsulAutoServiceRegistration в контексте. Эти beans подписаны на событие WebServerInitializedEvent, которое публикуется после того как embedded HTTP сервер (обычно Tomcat) стартовал и знает свой актуальный порт. Когда событие приходит, ConsulAutoServiceRegistration формирует HTTP запрос к локальному Consul agent на регистрацию сервиса. Запрос содержит имя сервиса, уникальный идентификатор экземпляра, IP адрес и порт этого экземпляра, список тегов, спецификацию health check с URL и интервалом проверки. Consul agent сохраняет информацию, начинает периодически дёргать указанный health check URL. Ответ с кодом 200 — статус passing, сервис включён в результаты discovery. Ответ с кодом 4xx или 5xx или отсутствие ответа за timeout — статус critical, сервис исключён из результатов до восстановления. Есть промежуточное состояние warning, редко используемое.

При корректном shutdown приложения Spring через механизм SmartLifecycle вызывает метод deregister у ConsulServiceRegistry, который отправляет соответствующий HTTP запрос в Consul agent на снятие регистрации. Сервис немедленно исключается из discovery.

Важная деталь работает не так гладко, как хотелось бы. Когда pod убивается сигналом SIGKILL, например через kubectl delete pod с force флагом или после превышения grace period, приложение не успевает выполнить shutdown hooks. Deregister не отправляется. Consul продолжает считать сервис зарегистрированным, но health check начинает fail из-за отсутствия ответа. Через параметр DeregisterCriticalServiceAfter, обычно установленный в одну минуту, Consul сам вычистит запись после того как сервис провалил все health checks за этот период. До этого момента списки инстансов, возвращаемые клиентам, могут содержать несуществующий адрес. Клиент, попытавшийся к нему обратиться, получит connection refused, что должно обрабатываться через retry на другой инстанс.

## Реальные проблемы Consul в КНП

Два кейса из практики КНП хорошо иллюстрируют типичные проблемы работы с Consul в production и показывают как думать о таких системах.

Первый кейс называется в внутренней документации "Consul deregister after DB flap". Ситуация была следующая. Приложение работало нормально, БД тоже работала. В какой-то момент произошёл кратковременный сбой сетевой доступности между приложением и БД — network flap длительностью несколько секунд. Приложение осталось живым и здоровым как процесс, но health check endpoint зависел от доступности БД (readiness probe проверял способность выполнить простой SQL запрос). В момент flap health check вернул ошибку. Consul пометил сервис как critical, исключил из discovery. Другие сервисы, обращавшиеся к нему через discovery, начали получать ошибку "No servers available: isnaKnpFs". После восстановления БД приложение снова могло обслуживать запросы, но не было надёжного механизма автоматического восстановления регистрации. Consul оставался с закешированным critical статусом до следующего successful health check, что могло занимать различное время в зависимости от таймингов. Плюс некоторые клиенты кэшировали список инстансов и не сразу подхватывали изменения. Оперативный fix оказался простым — kubectl rollout restart deployment пересоздал pods, которые заново прошли всю цепочку регистрации в Consul с нуля, и всё восстановилось. Урок для команды был двойной. С одной стороны, важно правильно настраивать health checks — readiness может зависеть от external systems, но liveness должен быть независимым. С другой стороны, нужен мониторинг разрыва между Kubernetes статусом (все pods Running и Ready) и Consul статусом (сервисы могут быть critical), потому что эти два состояния не всегда синхронизированы.

Второй кейс — "LoadBalancer case sensitivity after Java 21 migration". При миграции части сервисов на Java 21 и обновлении Spring Cloud до совместимой версии произошла замена LoadBalancer implementation. Раньше использовался Ribbon от Netflix, который был deprecated много лет и наконец удалён. Заменил его Spring Cloud LoadBalancer. API остался тот же для конечного пользователя — Feign клиенты работали без изменений, RestTemplate с балансировкой тоже. Но semantic поведение изменилось. Ribbon был case-insensitive при поиске сервисов — если код обращался к "isnaKnpUser", Ribbon находил зарегистрированный "isnaknpuser". Spring Cloud LoadBalancer строгий, case-sensitive. Если в коде "isnaKnpUser", а в Consul "isnaknpuser" — сервис не найден, ошибка. В кодовой базе с давних времён накопились разночтения в case имени одного и того же сервиса в разных местах. Ribbon это молчаливо прощал, никаких проблем не было заметно. Миграция на SC LB обнажила проблему — 500 ошибки от того что клиент не может найти сервис по неверному в case имени. Fix — унифицировать case имён сервисов везде через search-and-replace. Урок общий — миграция библиотек может менять semantic поведение даже когда API остаётся идентичным. Регрессионное тестирование должно быть достаточно строгим чтобы ловить такие изменения до prod.

## Client-side load balancing детально

Классический подход к балансировке — server-side. Клиент обращается к виртуальному IP адресу (VIP), за которым скрыт балансировщик — nginx, HAProxy, Kubernetes Service. Балансировщик выбирает конкретный backend и проксирует к нему трафик. Клиент никогда не знает какой конкретно backend его обслуживал.

Consul вместе со Spring Cloud реализует принципиально другой подход — client-side load balancing. Балансировщик работает внутри клиентского приложения. Клиент напрямую обращается к выбранному backend без промежуточного прокси.

Работает это следующим образом. Приложение isnaKnp хочет позвать другой сервис isnaKnpUser. Клиентская библиотека, реализующая LoadBalancer интерфейс, обращается к локальному Consul agent с запросом на получение списка живых инстансов сервиса isnaKnpUser. Consul agent проксирует запрос к серверу, получает актуальный список зарегистрированных и passing инстансов. LoadBalancer выбирает один инстанс из полученного списка по своему алгоритму — по умолчанию round-robin, но возможны weighted, sticky по идентификатору пользователя, географическая близость, произвольная custom логика. Клиент делает HTTP запрос напрямую на IP и порт выбранного pod. Никаких промежуточных VIPs или балансировщиков, полностью прямая коммуникация.

Преимущества такого подхода несколько. Отсутствие лишнего сетевого hop через VIP уменьшает latency. Клиент видит топологию сервисов, что позволяет реализовать умные стратегии — retry на другой инстанс при ошибке первого без обращения к балансировщику, интеллектуальный выбор based on latency history, custom алгоритмы под специфические нужды. Балансировка близка к бизнес-логике, что даёт больше гибкости.

Есть и недостатки. Логика балансировки должна быть реализована в каждом клиенте, что усложняет централизованное изменение стратегии. Все клиенты должны уметь service discovery — это добавляет зависимость от Consul для каждого сервиса. Пришлось обучать команду работе с новой концепцией, которая для многих была непривычной после traditional server-side балансировки.

В Spring Cloud исторически было две основных реализации client-side балансировки. Ribbon от Netflix был первым в этой нише, широко использовался с 2015 по 2018 годы. Netflix перевёл его в maintenance режим в 2018, разработка практически прекратилась. Ещё встречается в legacy приложениях, но не рекомендуется для новых. Spring Cloud LoadBalancer — современная замена, разработанная командой Spring. Проще устроенный, полностью reactive под капотом, интегрируется с Consul, Eureka и другими discovery clients. С версии Spring Cloud 2020.0 используется по умолчанию. API одинаковый для конечного пользователя, различия проявляются только в edge cases вроде обсуждённой case sensitivity.

## Feign как декларативный HTTP клиент

Использование client-side балансировки напрямую через LoadBalancer API получается многословным. Стандартный подход в Spring Cloud микросервисах — Feign, декларативный HTTP клиент. Разработчик описывает целевой HTTP API через Java интерфейс с аннотациями Spring MVC, Spring генерирует прокси реализацию этого интерфейса с автоматической интеграцией service discovery и load balancing.

Без Feign работа с HTTP выглядит через RestTemplate. Разработчик пишет строку URL с именем сервиса вместо hostname, полагается на Spring Cloud конфигурацию RestTemplate для превращения имени сервиса в реальный IP через LoadBalancer. Формирует параметры, отправляет запрос, получает ответ, парсит из JSON в Java объект вручную или через сериализатор. Обрабатывает возможные ошибки. Всё это работает, но требует явного HTTP кода в бизнес-логике.

С Feign код меняется радикально. Разработчик определяет интерфейс с аннотациями похожими на аннотации Spring MVC контроллеров. FeignClient annotation указывает имя целевого сервиса — то самое имя, под которым он зарегистрирован в Consul. GetMapping и PostMapping определяют HTTP методы и пути. PathVariable, RequestParam, RequestBody позволяют мапить параметры Java методов на элементы HTTP запроса. Реализация интерфейса не пишется — Spring генерирует прокси через reflection автоматически.

Что происходит при вызове метода такого интерфейса. Feign проксирует вызов, извлекает информацию о целевом сервисе из FeignClient аннотации, обращается к LoadBalancer с запросом на инстанс этого сервиса. LoadBalancer получает список инстансов от Consul, выбирает один, возвращает адрес. Feign формирует HTTP запрос, сериализуя параметры согласно аннотациям. Через HTTP клиентскую библиотеку (обычно Apache HttpClient или OkHttp) отправляет запрос на выбранный адрес. Получает ответ, десериализует тело через Jackson в возвращаемый тип Java метода. Обрабатывает HTTP статус — по умолчанию бросает FeignException для 4xx и 5xx ответов.

Всё это скрыто за одним вызовом метода Java интерфейса. Разработчик работает с бизнес-логикой, детали HTTP полностью абстрагированы. Активация Feign в Spring Boot требует одной аннотации EnableFeignClients на главном классе приложения.

Feign поддерживает механизм fallback для graceful degradation при недоступности целевого сервиса. Разработчик может указать fallback класс, реализующий тот же интерфейс, но возвращающий безопасные значения по умолчанию. Если основной вызов упал по любой причине, вместо exception возвращается результат от fallback. Механизм требует осторожности — легко скрыть реальные проблемы, которые лучше было бы видеть в логах и метриках.

Дополнительно можно подключить circuit breaker паттерн через spring-cloud-starter-circuitbreaker-resilience4j. При превышении заданного процента ошибок в некотором окне времени цепь размыкается — все последующие вызовы сразу возвращают fallback без реальных попыток обращения к сервису. Через настраиваемый период цепь пробует восстановиться. Механизм защищает от каскадных отказов, когда медленный или упавший сервис затягивает все свои клиенты в timeout.

В КНП Feign — стандарт для inter-service коммуникации. В коде десятки FeignClient интерфейсов, каждый для одного целевого сервиса. Стандартные примеры имён — IsnaKnpUserFeignClient для доступа к пользователям, IsnaFnoDictionaryFeignClient для справочников форм налоговой отчётности. Все написаны как интерфейсы с аннотациями, реализация автогенерируется.

## Consul KV store и Spring Cloud Consul Config

Consul предоставляет распределённое key-value хранилище через простой HTTP API. Значения могут быть до 512 килобайт произвольных байтов. Ключи организуются в иерархическую структуру через слэши, что позволяет группировать связанную конфигурацию.

Через HTTP API можно положить, прочитать, удалить или получить список ключей с определённым префиксом. Всё через стандартные HTTP методы PUT, GET, DELETE. Значения хранятся в base64 при возврате через API, есть параметр raw для получения исходного значения без кодирования.

KV store используется для широкого спектра задач. Feature flags — включение и выключение функциональности без изменения кода и без пересборки приложения. Глобальные конфигурации — параметры, общие для множества сервисов. Координация между сервисами — распределённые локи, лидер выборы. В простых случаях можно даже использовать как lightweight config server для приложений.

Spring умеет читать конфигурацию из Consul KV на старте через spring-cloud-starter-consul-config. Настройка происходит в bootstrap.yml — потому что настройки самого механизма чтения конфигурации из Consul должны быть доступны до загрузки этой конфигурации. Указывается format (обычно yaml), префикс ключей и default context.

Ключи организованы иерархически. По пути config/application/data лежит общая конфигурация для всех сервисов. По пути config/isnaKnpIntegration/data — специфичная для конкретного сервиса. По пути config/isnaKnpIntegration,prod/data — только для profile prod у этого сервиса. Значение по каждому ключу — YAML документ. Spring на старте читает все применимые ключи в порядке приоритета, парсит YAML, мержит результат в Environment. С этого момента свойства из Consul KV становятся доступны как обычные Spring properties — через @Value, @ConfigurationProperties, env.getProperty.

Ключевая особенность механизма — возможность refresh конфигурации без рестарта приложения. Beans, помеченные аннотацией RefreshScope, при событии refresh пересоздаются с новыми значениями из обновлённой конфигурации. Триггер — POST запрос на actuator/refresh endpoint. Это позволяет менять поведение работающих сервисов на лету, что критично для feature flags и других dynamic конфигураций. Beans без RefreshScope остаются с исходными значениями, так что для них требуется перезапуск для применения новой конфигурации.

Consul также поддерживает механизм watches — подписка на изменения ключей. При изменении ключа Consul может пушить уведомление подписчикам или запускать shell скрипт. Через Spring Cloud Consul Config можно настроить автоматический refresh при обнаружении изменения — приложение периодически проверяет хэш значений в KV, при изменении автоматически запускает refresh. В КНП обычно используется явный refresh через POST на actuator endpoint — предсказуемее, меньше сюрпризов от неожиданного обновления в неподходящий момент.

## DNS интерфейс и другие возможности

Consul запускает встроенный DNS сервер на порту 8600 по умолчанию. Через стандартный DNS протокол можно резолвить имена сервисов в IP адреса живых инстансов. Формат имени включает имя сервиса, datacenter и суффикс consul. Резолв возвращает SRV records с полными адресами включая порт для каждого passing инстанса.

Преимущество DNS интерфейса — работает с любым языком программирования через стандартные сетевые функции, не требует специальных клиентских библиотек. Bash скрипт может использовать dig или nslookup для service discovery. Приложение на Python или Go, не имеющее готовой интеграции с Consul, может резолвить сервисы через обычный getaddrinfo. Однако DNS не поддерживает продвинутые возможности Consul — нет фильтрации по тегам, health status учитывается ограниченно, нет weighted balancing. Для полноценной работы обычно используются нативные Consul клиенты.

В КНП DNS интерфейс не используется активно, потому что все Java сервисы работают через Spring Cloud Consul discovery, а не-Java интеграции минимальны.

## Практические аспекты health checks

Consul поддерживает несколько типов проверок здоровья, каждый со своей семантикой и trade-offs.

HTTP check делает периодические HTTP запросы на указанный URL, ответ с кодом от 200 до 399 считается успехом. Это стандарт для web приложений, работающих через Spring Boot Actuator health endpoint. В КНП именно этот тип используется повсеместно. Consul дёргает /actuator/health каждые 15 секунд (типичное значение), проверяя что приложение живо и обрабатывает запросы.

TCP check делает простое TCP соединение на порт. Success если удалось подключиться. Тип легковесный, не требует специального endpoint в приложении. Но не показывает готовность приложения реально работать — порт может быть открыт даже если приложение внутри в broken state. Реальный кейс из КНП показал опасность — TCP check на Hazelcast порт возвращал success даже когда Hazelcast был в невалидном состоянии из-за несовместимости версий, приложение принимало трафик, но обработать не могло, получались 500 ошибки. Правильно было использовать HTTP check на Actuator health, который проверяет полную готовность включая внутренние компоненты.

Script check запускает произвольную shell команду, exit code ноль считается успехом. Гибко, но требует чтобы Consul agent мог запускать команды в правильном окружении. Обычно для нестандартных проверок.

Docker check похож на script, но запускает команду внутри указанного Docker контейнера. Специфично для Docker deployments.

gRPC check использует стандартный gRPC health protocol. Для gRPC сервисов.

TTL check работает в push модели вместо pull. Сервис сам должен периодически отправлять уведомление в Consul о том что он жив, через специальный API endpoint. Если за указанный TTL не пришло уведомление, статус меняется на critical. Полезно для сервисов, которые не могут отвечать на входящие health check запросы, но могут сами говорить о своей живости.

Один сервис может иметь несколько health checks одновременно. Общий статус — passing только если все checks passing. Any failure переводит в warning или critical в зависимости от настроек.

## Диагностика типичных проблем

Работа с Consul в production регулярно даёт возможность разбирать типовые проблемы, понимание которых помогает быстро локализовать источник.

Ошибка "No servers available: isnaKnpUser" в логах клиентского сервиса означает что при попытке discovery получен пустой список инстансов. Причины могут быть несколько. Ни одного инстанса сервиса не зарегистрировано — проверить что сам сервис работает, что регистрация настроена в bootstrap.yml. Все зарегистрированные инстансы находятся в состоянии critical — проверить через Consul API или UI health статусы всех инстансов, разобраться почему health checks fail. Consul недоступен на момент discovery запроса — проверить сетевую связность между клиентским сервисом и Consul agent или server. Параметр query-passing со значением false и все инстансы critical — проверить конфигурацию, установить query-passing в true.

Диагностика ведётся через Consul HTTP API. Запрос catalog/services покажет все зарегистрированные сервисы. Запрос catalog/service с указанием имени вернёт зарегистрированные инстансы. Запрос health/service вернёт то же с health статусами каждого инстанса. Добавление параметра passing равного true фильтрует только живые. Через UI Consul на порту 8500 доступна визуализация того же, что удобнее для быстрого просмотра.

Проблема "приложение долго стартует потому что не может достучаться до Consul" возникает при недоступности Consul во время старта приложения. По умолчанию Spring Cloud Consul пробует зарегистрироваться при старте, если fail-fast установлено в true — приложение падает если Consul недоступен, если в false — работает без регистрации до восстановления Consul. Выбор зависит от требований. Fail-fast разумен когда без Consul приложение не может корректно работать. Otherwise удобно fail-fast false, чтобы приложение стартовало даже при временных проблемах с Consul, продолжало обрабатывать локальные запросы, а регистрация произошла позже автоматически.

Дубли инстансов в Consul возникают когда pod убивается SIGKILL без отправки deregister. Consul продолжает считать pod зарегистрированным. Как обсуждалось, автоматическая очистка происходит через параметр DeregisterCriticalServiceAfter, но до этого момента дубли видны. Ручная очистка возможна через API запрос на deregister endpoint с указанием service ID.

Ложные положительные health checks — когда сервис помечен passing, но реально не может обслуживать запросы. Обычно связано с TCP check вместо HTTP check. Fix — переход на HTTP check с endpoint, проверяющим реальную готовность (Actuator health).

## Заключение

Consul — стандарт service discovery в enterprise Java микросервисной архитектуре, дополняющий или заменяющий встроенные механизмы Kubernetes. Три роли в одном продукте — service registry, health checking, KV store — плюс DNS интерфейс, multi-datacenter federation, опционально service mesh через Consul Connect.

Архитектурно Consul использует классическое разделение на серверы с Raft consensus для согласования состояния и агенты на каждой ноде для локального обслуживания приложений. Gossip protocol обеспечивает эффективное распространение информации о живости узлов кластера без централизованной координации.

Spring Boot интеграция происходит через spring-cloud-starter-consul-discovery. Автоматическая регистрация при событии WebServerInitializedEvent, автоматический deregister при graceful shutdown. При SIGKILL deregister не происходит — Consul сам чистит критичные записи через настраиваемый timeout.

Client-side load balancing принципиально отличается от server-side балансировки Kubernetes Service. Клиент получает список инстансов, сам выбирает по алгоритму, обращается напрямую к выбранному backend. Даёт гибкость custom алгоритмов и меньше latency, но усложняет клиенты и делает их зависимыми от discovery системы.

Feign как декларативный HTTP клиент — стандарт в КНП для inter-service коммуникации. Разработчик описывает целевой API через Java интерфейс с аннотациями, Spring генерирует прокси реализацию с интеграцией service discovery и load balancing. Опциональные fallback и circuit breaker для устойчивости к отказам.

KV store для конфигураций, feature flags, координации. Spring Cloud Consul Config читает конфигурацию из KV при старте, поддерживает refresh без рестарта через RefreshScope и actuator endpoint. Watches для реактивного обновления при изменениях.

Критичные настройки для production включают query-passing true (только живые инстансы в результатах discovery), prefer-ip-address true для контейнерной среды, правильный health-check-path на Actuator, deregister true для корректного shutdown.

Реальные проблемы КНП показывают важность правильных архитектурных решений. Consul deregister after DB flap решается разделением readiness и liveness probes и правильным мониторингом разрыва между Kubernetes и Consul статусами. LoadBalancer case sensitivity после миграции Java 21 показал важность регрессионного тестирования при обновлении инфраструктурных библиотек.

Знание Consul обязательно для senior разработчика в КНП, потому что все inter-service вызовы идут через Feign с Consul discovery дополнительно к Kubernetes Service инфраструктуре. Понимание обоих механизмов необходимо для диагностики сетевых проблем и разработки новых сервисов, корректно интегрирующихся с существующей архитектурой.

Дальше обсуждается работа с БД через JPA и Hibernate. Все сервисы КНП используют PostgreSQL через JPA, что делает знание слоя ORM критически важным для performance и корректности приложений.
