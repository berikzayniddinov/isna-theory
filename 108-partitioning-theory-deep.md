# 108. Партиции: теория, механика, ловушки в разных системах

## Зачем это знать

Партиция — одно из самых перегруженных слов в инженерии. В PostgreSQL это подтаблица внутри partitioned table. В Kafka — упорядоченный лог сообщений внутри топика. В Cassandra — единица размещения данных на ноде. В Hadoop/Spark — блок данных для параллельной обработки. В CAP-теореме — состояние когда сеть между узлами разорвана. Одно слово, пять разных смыслов, но за всеми стоит одна и та же идея: **разбиение большого целого на части, которые можно обрабатывать независимо**.

Понимать эту идею глубоко надо потому что каждый scale-up в системе рано или поздно упирается в вопрос «как это разделить». Таблица выросла до сотен миллионов строк — партиционировать по датам. Kafka топик получает миллион сообщений в секунду — увеличивать число партиций. Cassandra кластер разросся до 20 нод — правильно выбрать partition key чтобы данные размазались равномерно. Микросервис уперся в CPU — партиционировать нагрузку по user_id между инстансами. Одни и те же концепции: partition key, hash function, hotspot, rebalancing, replication factor. Один и тот же класс ошибок: неудачный partition key → одна партиция несёт 90% данных → hotspot → вся система тормозит из-за одной ноды.

Разберём партиции как общую концепцию. Что даёт партиционирование (масштабирование, изоляция, локальность, fault domains). Три классических стратегии выбора партиции: range, hash, list — и в каких системах какая работает. Consistent hashing и почему он ключевой для динамического добавления/удаления нод. Проблема hotspots и как её обходят (composite keys, salting). Rebalancing и его стоимость. Partition как unit of parallelism в аналитических системах (Spark, MapReduce). Partition в контексте CAP-теоремы — network partition как проблема консистентности. Разница между партицией и шардом. Плюс — практические ловушки: неправильный partition key, cross-partition queries, миграция при изменении схемы партиционирования. Postgres-специфика уже разобрана в файле 91, здесь — уровень выше, теория, применимая ко всем распределённым системам.

## Что такое партиция и зачем она

Партиция — это подмножество данных или работы, которое можно обрабатывать независимо от других подмножеств. Ключевое слово — **независимо**. Если для обработки партиции A нужно постоянно ходить в партицию B, никакого выигрыша нет — вы просто добавили сложности.

Партиционирование даёт четыре класса выгод, и их полезно различать, потому что разные задачи требуют разных из них:

**Масштабирование данных**. Одна таблица PostgreSQL с миллиардом строк — плохо: индексы огромны, VACUUM тянется часами, ALTER TABLE блокирует всё. Разбитая на 100 партиций по месяцам — каждая по 10 миллионов строк, обслуживается независимо. Один Kafka топик с 10 TB данных на одном брокере — не поместится. Разбитый на 20 партиций по 500 GB на 20 брокерах — работает.

**Масштабирование throughput**. Один consumer в Kafka читает топик последовательно — потолок в тысячи сообщений в секунду. 20 consumers, по одному на партицию — 20x throughput. Один PostgreSQL insert-запрос на большую таблицу с индексом — потолок в тысячи в секунду (упирается в индексы). Партиционированная таблица с 12 партициями по месяцам — инсерты в текущий месяц идут в одну партицию, старые не трогаются вовсе, hot working set индекса — только текущая партиция.

**Изоляция**. Долгий запрос по партиции 2020 года не мешает быстрым запросам по 2025-й, потому что физически это разные таблицы, разные страницы в shared_buffers, независимые autovacuum. Consumer из партиции 5 не блокирует consumer из партиции 6. Развалилась одна партиция БД — остальные работают.

**Локальность и fault domains**. Партиция целиком живёт на одной ноде — обработка «локальна», не требует сети. Партиция может быть реплицирована на N нод — падение одной не убивает партицию. Партиции равномерно раскиданы — падение ноды теряет только фрагмент, не всё.

Одна и та же техника используется от уровня отдельной таблицы до уровня всего датацентра. Отсюда универсальность концепции.

## Три стратегии: range, hash, list

Три классических способа определить, в какую партицию попадёт конкретная запись. Каждый со своими сильными и слабыми сторонами.

**Range partitioning** — по непрерывному диапазону значений partition key. Партиция A: `date BETWEEN 2024-01-01 AND 2024-01-31`. Партиция B: `date BETWEEN 2024-02-01 AND 2024-02-29`. И так далее.

Плюсы range: **partition pruning** для range-запросов работает идеально. `WHERE date >= '2024-03-15' AND date < '2024-04-10'` затрагивает ровно 2 партиции, не все. Drop старых данных мгновенный — `DROP TABLE orders_2020_01` вместо `DELETE FROM orders WHERE date < '2020-02-01'` который сжирает часы. Естественно для time-series данных: логи, метрики, ордера, транзакции.

Минусы range: **потенциальный hotspot на текущую партицию**. Все новые записи (INSERT) идут в текущую (самую свежую) партицию. Одна партиция — hot, остальные — cold. Для write-heavy workloads с равномерной нагрузкой это плохо. Плюс — при неравномерном распределении по временной оси (например, всплеск активности в Black Friday) одна партиция может стать намного больше других.

**Hash partitioning** — партиция определяется через `hash(partition_key) mod N`. Партиция A получает записи где `hash(user_id) mod 100 = 0`. Партиция B — где `= 1`. И так далее.

Плюсы hash: **равномерное распределение**. Если ключ распределён равномерно и hash хорошая — данные размажутся по партициям одинаково. Нет hotspot на конкретную партицию.

Минусы hash: **partition pruning работает только для точного совпадения ключа**. `WHERE user_id = 42` — знаем hash, знаем партицию, читаем одну. `WHERE user_id > 100` — не знаем, надо читать все партиции. Range queries по partition key становятся дорогими. Изменение числа партиций — сложное, потому что `mod N` меняется для всех ключей (см. consistent hashing ниже).

**List partitioning** — партиция для явного списка значений. Партиция A: `country IN ('KZ', 'RU', 'BY')`. Партиция B: `country IN ('US', 'CA')`. Партиция C: остальные.

Плюсы: логичное разделение по бизнес-смыслу (регионы, категории). Каждая партиция может быть на своей ноде с локальным compliance (GDPR — европейские данные только в Европе).

Минусы: неравномерное распределение (партиция с крупной страной больше). Ограниченный набор значений — не подходит для непрерывных данных.

**Composite partitioning** — комбинация. Postgres поддерживает subpartitioning: сначала по range (месяц), потом по hash (user_id внутри месяца). MySQL умеет partition-by-hash-subpartition-by-key. Combines преимущества, добавляет сложности.

## Consistent hashing: почему обычный `mod N` — плохо

Наивный hash partitioning: `partition = hash(key) mod N`. Работает пока N не меняется. Как только добавили ноду или убрали — `mod N` меняется, **все ключи** переезжают на новые партиции. Массовая миграция данных, downtime, headache.

Пример. Было 3 ноды, `hash(user_1) mod 3 = 0` → нода A. Добавили 4-ю: `hash(user_1) mod 4 = 1` → нода B. И так для 99% ключей — они переехали. Кластер стал недоступен на время rebalance.

**Consistent hashing** решает эту проблему. Придумана в Akamai в 1997 году, сейчас используется практически везде где есть динамическое количество нод: Cassandra, DynamoDB, Riak, распределённые кеши (memcached в облаках), балансировщики нагрузки.

Идея. Представь себе кольцо — окружность значений от 0 до 2^32 (или другого большого числа). Каждая нода хэшируется в одну (или несколько) точку на этом кольце. Каждый ключ тоже хэшируется в точку на кольце. Ключ принадлежит той ноде, которая **ближайшая по кольцу против часовой стрелки** (или другое соглашение).

```
        Nodes on ring
              A
        ↙         ↘
       key1        C
       ↓
       (hash lands here, belongs to A next)
        
       key2         
        ↓
        ↘        ↗
             B
```

Что происходит когда добавили ноду D между A и C: только ключи, попавшие между C и D по кольцу, переезжают с A на D. Все остальные — на своих местах. Rebalance затрагивает `1/N` данных вместо всех.

Что происходит когда убрали ноду C: её ключи мигрируют к следующей по кольцу (тоже примерно `1/N` данных).

**Virtual nodes** — усовершенствование consistent hashing. Каждая физическая нода регистрирует не одну точку на кольце, а несколько сотен (**vnodes**). Так распределение становится ровнее — при физическом добавлении/удалении ноды данные размазываются между всеми остальными равномерно, а не идут одному «соседу» на кольце. Cassandra по умолчанию использует 256 vnodes на физическую ноду.

Consistent hashing — не единственный подход. **Rendezvous hashing** (Highest Random Weight, HRW) даёт похожие свойства через другой алгоритм: для каждого ключа считаем `hash(key + node)` для каждой ноды, ключ принадлежит ноде с наибольшим значением. Проще реализовать, работает без кольца. Используется в CDN routing, некоторых системах кеширования.

## Проблема hotspots

Hotspot — партиция (или нода), которая получает непропорционально большую нагрузку. Классическая проблема любой партиционированной системы. Стоит инцидентов.

**Причины hotspot'ов**:

1. **Плохо выбранный partition key**. Партиционировали по `country`, все запросы приходят из Казахстана (наш прод) — партиция KZ несёт 95% нагрузки, партиции RU/US/CN — пустые. Distribution неравномерное по бизнес-смыслу.

2. **Timestamp как partition key при hash-based распределении** — не проблема сама по себе, но если данные читаются последовательно по времени (типичный analytics query), все читатели упираются в одну текущую партицию.

3. **Естественная временная неравномерность** для range-partitioning. В bank API 90% транзакций в рабочие часы. Партиция за пятницу с 15:00 до 18:00 огромная, партиция за субботу с 3:00 до 6:00 — крохотная.

4. **Один «hot» ключ**. В таблице `events` есть системный user_id = 0 для служебных событий, туда пишется 50% всех событий. Хэш этого одного ключа всегда попадает на одну партицию, она горячая, остальные простаивают.

**Обход hotspot'ов**:

**Composite partition key**. Вместо `partition_by = user_id` использовать `partition_by = (user_id, event_type)` или `(user_id, timestamp_bucket)`. Одна и та же комбинация даст ту же партицию, но разные события одного user'а размазываются.

**Salting**. Искусственно добавить случайность к partition key. `partition_by = concat(random_prefix(0..9), user_id)`. Один hot user превращается в 10 равномерно нагруженных партиций. Минус: чтение по user_id теперь требует опроса всех 10 salt-вариантов.

**Sub-partitioning**. Внутри одной range-партиции сделать hash-подпартиционирование. Range даёт локальность по времени, hash — распределение внутри временного окна.

**Read/write splitting**. Hot ключи выделить в отдельную партицию с отдельной репликацией — больше реплик, читать со всех. Классический подход в системах читающих сессионные данные.

## Rebalancing: цена изменения топологии

Rebalancing — процесс перераспределения данных между партициями при изменении их числа или конфигурации. Дорогая операция, но неизбежная.

Три сценария, требующих rebalance:

**Добавление нод для scale-up**. Кластер вырос из 5 нод в 10 — половину данных надо переселить, чтобы каждая нода несла свою честную долю.

**Удаление нод** (плановое или из-за сбоя). Данные с уходящей ноды надо распределить по остальным.

**Изменение partition scheme**. Было hash по user_id — стало по (user_id, region). Весь ключевой fingerprint меняется, все данные надо переразбить.

**Стоимость rebalance** зависит от системы:

- **Cassandra** — вpartial availability во время rebalance, скорость ограничена сетью, для крупного кластера дни-недели. Streaming данных между нодами напрямую.
- **Kafka** — reassignment партиций между брокерами (`kafka-reassign-partitions.sh`), тоже сетевой пропускной способностью ограничено. Consumer group rebalancing — секунды, но с паузой обработки.
- **DynamoDB** (managed) — прозрачно, но splits/joins партиций происходят автоматически при росте throughput. Иногда провоцирует temporary throttling.
- **PostgreSQL partitioning** — практически невозможно без даунтайма для существующих данных. Обычно так: создаётся новая партиционированная таблица с новой схемой, данные перекачиваются в неё, потом атомарный SWAP.

**Минимизация impact rebalance**:

- **Throttling**: ограничение скорости, чтобы не убить production I/O. Cassandra `stream_throughput_outbound_megabits_per_sec`, Kafka `--throttle 100000000`.
- **Off-hours**: rebalance ночью или в выходные.
- **Gradual rollout**: не переселять всё разом, а по 10% в час.
- **Consistent hashing с virtual nodes** — уже описано, минимизирует объём переселения.

Из этого — важное правило: **выбор partition key на старте важнее, чем кажется**. Rebalance при неправильном выборе — очень дорогая операция. Пересматривать partition scheme через год после запуска — почти всегда болезненно.

## Партиция как unit of parallelism

Отдельный смысл партиций — в аналитических системах. Здесь партиция не столько про размещение данных, сколько про **единицу параллельной обработки**.

**Spark / MapReduce**. Большой датасет разбивается на партиции (обычно по 100-200 MB каждая). Каждая партиция обрабатывается отдельным executor'ом параллельно. Число партиций = degree of parallelism. Мало партиций → низкая параллельность, кластер простаивает. Много партиций → overhead на управление, каждая слишком маленькая, накладные расходы съедают выигрыш.

Правило Spark: партиций должно быть примерно **2-4x** число CPU cores в кластере. При 100 cores — 200-400 партиций. Позволяет parallelism полностью использовать железо + буфер для work stealing (когда одна партиция обработалась быстрее — executor берётся за следующую из очереди).

**Ключевой момент — shuffle**. Если операция требует данные из разных партиций (JOIN, GROUP BY по не-partition-key), Spark делает shuffle: перераспределение данных между партициями по новому ключу. Это дорого — данные ходят по сети между executor'ами. Оптимизация Spark queries почти всегда сводится к **минимизации shuffle**: партиционировать заранее по join-key, использовать broadcast joins для маленьких таблиц, colocate таблицы с одинаковым partition key.

**Kafka partitions как parallelism**. Consumer group читает топик, каждый consumer получает свой набор партиций. Число consumer'ов не может быть больше числа партиций — иначе часть будет простаивать. Число партиций — потолок параллельности. Поэтому топики создают с запасом (например, 30 партиций для 3 consumer'ов сейчас — на будущее).

**Cassandra concurrent reads**. Каждая партиция читается независимо. Много мелких партиций — можно читать 100 параллельно, суммарный throughput высокий. Одна огромная партиция — один read за раз, никакой параллельности.

## Partition в контексте CAP-теоремы

Отдельная семантика слова «партиция», путающая новичков. CAP-теорема Эрика Брюера (2000) говорит о трёх свойствах распределённой системы: **Consistency** (все ноды видят одну и ту же версию данных), **Availability** (система отвечает на запросы), **Partition tolerance** (система работает при разрыве сети между нодами).

Здесь **partition = network partition** — состояние когда часть нод не может связаться с другой частью. Не связано с partitioning данных! Одноимённые термины из разных доменов.

Теорема: в момент network partition можно сохранить или C или A, но не оба. Либо ноды на изолированной стороне отказываются отвечать (сохраняют C, теряют A), либо продолжают работать со своим устаревшим состоянием (сохраняют A, теряют C).

Практика:
- **CP-системы** (Cassandra в strong-consistency mode, Zookeeper, etcd, PostgreSQL с synchronous replication): при network partition minority-сторона становится read-only или недоступной. Consistency сохраняется, availability частично теряется.
- **AP-системы** (Cassandra в eventual-consistency mode, DynamoDB, Riak): обе стороны продолжают отвечать, состояния расходятся, потом мержатся при восстановлении связи (conflict resolution через last-write-wins, vector clocks, CRDT).

CAP-теорема — не абсолют, PACELC уточняет: **если** есть partition, выбирай P/A/C; **иначе** выбирай L (latency) vs C. То есть даже без partition вопрос consistency vs latency остаётся.

Связь с data partitioning: чем больше данных партиционировано между нодами, тем выше вероятность что network partition затронет некоторое подмножество данных. Больше распределение = больше поверхность для network partition.

## Партиция vs шард — терминологическая гигиена

Термины часто взаимозаменяемы, но принято такое различение (см. также файл 91):

**Партиция** — обычно означает разбиение внутри одной системы/базы/сервера. PostgreSQL partitioned table — партиции живут на одном сервере. Kafka partitions одного топика могут быть на разных брокерах, но всё в одном Kafka-кластере.

**Шард** — обычно означает физически отдельные, самостоятельные экземпляры системы. Шард PostgreSQL — это своя инсталляция PostgreSQL со своими данными, работающая независимо. MongoDB shard, MySQL sharding — то же.

Разница практически:
- Партиции обычно управляются самой системой автоматически (partition pruning, автоматический роутинг).
- Шарды часто требуют внешнего слоя роутинга (application-level, прокси типа Vitess или ProxySQL, или встроенный distributed layer типа Citus).
- Партиции легче переконфигурировать (в пределах одной системы).
- Шардинг сложнее, но даёт большее масштабирование.

Иногда термины смешивают. Cassandra называет свои единицы разбиения «partition» хотя они физически на разных нодах — то есть в терминологии PostgreSQL это шарды. DynamoDB тоже говорит «partition». Sharding — исторически MySQL-communityшный термин.

Практическое правило: если система сама роутит запрос без вашего участия — партиция. Если приложение или прокси должны знать где данные — шард.

## Практические ловушки

**Неправильный partition key**. Самая частая и самая дорогая ошибка. Выбрали `country` для глобального SaaS, а 90% клиентов из одной страны. Выбрали `user_id` hash для чат-приложения, где 20% чатов — с ботами (одинаковый bot_user_id для всех). Выбрали timestamp для logs, а нужно фильтровать по service — каждый запрос читает все партиции по времени, потом фильтрует.

Правило: partition key должен обеспечивать **и равномерное распределение** (нет hotspot'ов), **и локальность типичных запросов** (partition pruning работает). Выбор — по анализу access patterns, не только по интуиции.

**Cross-partition queries**. Если запрос не содержит partition key в условиях — приходится читать все партиции. `SELECT * FROM orders WHERE amount > 1000` при партиционировании по `user_id` — сканирует все партиции. Часто fatally дорого.

Обход: либо вводить composite partition key где второй компонент часто в запросах; либо создавать отдельные проекции/materialized views с другим partition key для конкретных запросов; либо переносить такие запросы в OLAP-систему (Clickhouse, BigQuery), где сканирование эффективнее.

**Изменение partition scheme**. Через год после запуска понимаешь что выбрал не тот ключ. Что делать? Идеальный сценарий: параллельно поднять новую партиционированную таблицу с правильной схемой, `INSERT INTO new_orders SELECT * FROM orders`, потом атомарный SWAP (переименование). Плохой сценарий: миграция на живой системе с даунтаймом. Реальный сценарий: 6 месяцев миграции с dual-write pattern (пишем в обе схемы, читаем из старой, потом переключаем чтение, потом убираем старую).

**Транзакции через партиции**. Транзакция затрагивающая несколько партиций часто требует distributed transaction (2PC/XA), что медленно и хрупко. Правило дизайна: **транзакция должна ложиться в одну партицию**. Если бизнес-логика требует изменять данные нескольких сущностей одновременно — партиционировать их так чтобы они оказались в одной партиции.

Классический пример: в банковской системе если User и его Accounts партиционированы по разным ключам — перевод денег требует cross-partition transaction. Правильно: `Account.partition_key = user_id` — все счета одного пользователя в одной партиции, transfer между ними — локальная транзакция.

**Небольшое количество данных**. Партиционирование имеет overhead: metadata, планировщик оптимизирует по каждой партиции отдельно, множество мелких файлов. Для таблицы в 100 тысяч строк партиционирование только замедлит работу. Порог — обычно **10+ миллионов строк** или **10+ GB** данных.

## Диагностика в проде

**Симптом: одна нода/партиция нагружена в 10 раз больше остальных.**

PostgreSQL — узнать размеры партиций:

```sql
SELECT 
  child.relname AS partition,
  pg_size_pretty(pg_relation_size(child.oid)) AS size,
  pg_stat_get_live_tuples(child.oid) AS live_rows
FROM pg_inherits
JOIN pg_class parent ON pg_inherits.inhparent = parent.oid
JOIN pg_class child ON pg_inherits.inhrelid = child.oid
WHERE parent.relname = 'orders'
ORDER BY pg_relation_size(child.oid) DESC;
```

Одна партиция в 10x больше — hotspot по данным. Одна в 10x по queries — hotspot по нагрузке, смотреть `pg_stat_statements` и `pg_stat_user_tables.n_tup_ins/upd/del` по партициям.

Kafka — распределение партиций по брокерам:

```bash
kafka-topics.sh --describe --topic orders --bootstrap-server ...
# смотреть колонку Leader — сколько партиций где
kafka-consumer-groups.sh --describe --group my-group
# смотреть lag per partition — где отстаёт consumer
```

Cassandra — размер партиций:

```bash
nodetool tablehistograms my_keyspace my_table
# смотреть 99% percentile row count и size — если сильно больше среднего, есть fat partition
nodetool status
# смотреть Load per node — равномерно или один нагружен
```

**Симптом: cross-partition query медленный.**

PostgreSQL — `EXPLAIN ANALYZE` покажет сколько партиций реально сканировалось. Если много — либо добавлять partition pruning через `WHERE partition_key = ...`, либо создать индекс покрывающий условие, либо признать что запрос по своей природе не подходит для этой схемы партиционирования.

Kafka — если consumer один, а надо параллелить: увеличить количество партиций топика и добавить consumers. `kafka-topics.sh --alter --partitions 30 --topic orders` (только увеличение, уменьшение невозможно).

**Симптом: rebalance постоянно, кластер нестабильный.**

Kafka consumer group — проверить `session.timeout.ms` (слишком короткий → частые ложные rebalance при GC-паузах), `max.poll.interval.ms` (слишком короткий → consumer помечается мёртвым если долго обрабатывает батч). Cassandra — проверить `nodetool netstats` на постоянный streaming, значит топология нестабильна.

## Заключение

Партиция как концепция — универсальный способ разбить большое целое на независимо обрабатываемые части. Применяется везде: PostgreSQL partitions, Kafka partitions, Cassandra partitions, Spark partitions, sharding. Одни и те же идеи повторяются на разных уровнях абстракции.

Даёт четыре класса выгод: масштабирование данных (индексы, VACUUM, ALTER работают на партициях), масштабирование throughput (параллельная обработка партиций), изоляция (нагрузка не пересекается), fault domains (падение одной партиции не убивает остальные).

Три стратегии выбора: **range** (natural для time-series, но hotspot на текущей), **hash** (равномерное распределение, но нет pruning для range-queries), **list** (по бизнес-категориям, часто неравномерно). **Composite** и **sub-partitioning** комбинируют.

**Consistent hashing** решает проблему `mod N` при изменении числа нод — при добавлении ноды переселяется только `1/N` данных, а не почти всё. Virtual nodes делают распределение ровнее. Rendezvous hashing — альтернативный алгоритм с похожими свойствами.

**Hotspots** — фундаментальная проблема партиционирования. Причины: плохой ключ, естественная неравномерность, один hot ключ. Обход: composite key, salting, sub-partitioning, read/write splitting.

**Rebalancing** — дорогая операция. Минимизация impact через throttling, off-hours, gradual rollout, consistent hashing с vnodes. Отсюда важность правильного выбора partition key **на старте** — пересматривать через год почти всегда болезненно.

Партиция как **unit of parallelism** в аналитических системах (Spark: 2-4x cores). Ключевая оптимизация — **минимизация shuffle**, партиционирование заранее по join-key.

**CAP-теорема** — здесь partition = network partition (не data partition!). При разрыве сети выбираешь либо consistency либо availability. PACELC уточняет: даже без partition остаётся trade-off latency vs consistency.

**Партиция vs шард** — партиция обычно управляется системой автоматически (в одном сервере/кластере), шард — отдельная инсталляция, требует external routing. Границы размыты, разные системы называют одно и то же по-разному.

**Практические ловушки**: неправильный partition key (стоит инцидентов и сложных миграций); cross-partition queries (сканируют всё); транзакции через партиции (требуют distributed transactions); партиционирование маленьких таблиц (только замедляет).

Диагностика в проде через размеры партиций, per-partition метрики, распределение нагрузки. Hotspot ловится по 10x-разнице в размере или queries между партициями.
