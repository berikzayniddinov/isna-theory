# 17. Java 11 к 21: JVM, GC, производительность

## Что изменилось под капотом

Синтаксические изменения между Java 11 и 21 видны непосредственно в коде, но не менее важные преобразования произошли на уровне JVM — виртуальной машины, исполняющей этот код. Сборщики мусора, механизмы работы в контейнерах, ускорение старта приложений, оптимизации JIT компилятора — всё это эволюционировало параллельно с языком, и понимание этих изменений критично для senior разработчика работающего с production приложениями. Одно дело написать код на современном Java, другое — настроить JVM правильно чтобы этот код эффективно выполнялся в реальном окружении.

Для КНП контекста тема особенно актуальна потому что миграция части сервисов на Java 21 идёт через параллельные ветки master-21. Каждый мигрируемый сервис попадает в новую версию JVM с изменившимися дефолтами, новыми возможностями и удалёнными опциями. Понимание что изменилось помогает избегать сюрпризов в production и использовать новые возможности осознанно.

## Эволюция сборщиков мусора

Между Java 11 и Java 21 подсистема garbage collection претерпела значительные изменения. Одни сборщики были удалены как устаревшие, другие получили статус production ready, третьи — существенные улучшения работы.

В Java 11 набор доступных сборщиков включал G1 как основной по умолчанию с Java 9, Parallel GC для batch задач ориентированных на throughput, Serial GC для маленьких приложений с ограниченными ресурсами, устаревающий Concurrent Mark-Sweep, и экспериментальные ZGC и Shenandoah только начинающие свой путь. По умолчанию все приложения использовали G1, что было разумным компромиссом для большинства нагрузок.

К Java 21 картина существенно изменилась. Concurrent Mark-Sweep был удалён в Java 14 после многих лет постепенного выведения из эксплуатации — сборщик устарел, замену выполнял G1. ZGC получил статус production ready в Java 15, а в Java 21 появилась его generational версия — это принципиальное улучшение делающее ZGC значительно более эффективным для типичных нагрузок enterprise приложений. Shenandoah также стал production ready в Java 15. G1 остался сборщиком по умолчанию, но получил многочисленные улучшения в эффективности использования памяти и скорости старта.

G1 работает на основе разделения heap на регионы фиксированного размера от одного до тридцати двух мегабайт. Каждый регион в определённый момент времени играет роль Eden, Survivor или Old generation. Концурентные фазы работы сборщика перемежаются с короткими stop-the-world паузами. Целевая максимальная длительность пауз задаётся параметром MaxGCPauseMillis со значением по умолчанию двести миллисекунд. G1 хорошо работает на heap размером от четырёх до шестидесяти четырёх гигабайт. Между версиями 11 и 21 в G1 существенно уменьшилось потребление памяти на метаданные, ускорился старт, улучшилось поведение при всплесках аллокации. Появились concurrent full GC операции которые раньше всегда были stop-the-world.

ZGC как радикально другой подход к сборке мусора использует colored pointers — специальные биты в самих указателях для отметок метаданных сборщика. Это позволяет ZGC выполнять compaction concurrent с работой приложения, без остановки. Паузы у ZGC составляют менее миллисекунды даже на heap размером в терабайты. Это делает ZGC идеальным выбором для low latency сервисов вроде торговых систем, real-time обработки, любых приложений где даже сотня миллисекунд паузы неприемлема. Ценой преимуществ является больший memory footprint — ZGC требует дополнительной памяти для служебных структур, что делает его невыгодным для маленьких heap до восьми гигабайт. В таких случаях G1 работает эффективнее.

Появление generational ZGC в Java 21 — большое улучшение. Оригинальный ZGC не разделял heap на поколения, что было теоретически чистым решением но упускало возможность оптимизации типичных паттернов аллокации где большинство объектов умирают молодыми. Generational ZGC вводит разделение на young и old generation, применяя специфичные для каждого стратегии сборки. Результат — существенное сокращение потребления памяти и CPU при том же качестве латентности.

Shenandoah представляет собой альтернативу ZGC от Red Hat, также фокусирующуюся на concurrent compaction. Использует другой механизм чем colored pointers, работает на архитектурах где ZGC ограничен. Не является сборщиком по умолчанию в OpenJDK, но доступен для использования.

Выбор сборщика для типичного Spring Boot микросервиса в КНП с heap размером от пятисот двенадцати мегабайт до двух гигабайт — G1 без обсуждения. Он справляется отлично, паузы приемлемые для web приложений, оверхеда минимум. Для случаев с более крупным heap и требованиями к сверхнизкой латентности ZGC становится оправданным выбором.

## Container awareness JVM

Одна из самых важных практических тем для микросервисной архитектуры — как JVM видит ресурсы контейнера. В Java 8 существовала фундаментальная проблема — JVM смотрела на физические ресурсы хоста, полностью игнорируя ограничения контейнера. Если в контейнере с memory limit пятьсот двенадцать мегабайт запустить JVM без явного Xmx, она бы взяла двадцать пять процентов от хостовой памяти, что могло составлять шестнадцать гигабайт на большом сервере. Результат — мгновенный OOMKilled при первой попытке выделить существенное количество памяти.

Начиная с Java 10 JVM научилась видеть ограничения cgroups. С Java 15 добавилась поддержка cgroups v2. Это делает работу в контейнерах значительно предсказуемее — JVM автоматически определяет доступную память и CPU из ограничений контейнера, использует их для выбора размера heap и настройки внутренних thread pools.

Автоматический выбор размера heap работает через процентные параметры от cgroup memory limit. MaxRAMPercentage задаёт какой процент доступной памяти использовать под heap. По умолчанию двадцать пять процентов, но для контейнеров обычно устанавливается семьдесят пять процентов чтобы более полно использовать выделенные ресурсы. InitialRAMPercentage и MinRAMPercentage контролируют начальный и минимальный размер heap. Явное задание этих параметров через JAVA_TOOL_OPTIONS в Dockerfile гарантирует предсказуемое поведение независимо от версии JDK и её defaults.

Более классический подход — явно указывать Xms и Xmx в мегабайтах или гигабайтах. Разница в том что фиксированные размеры не адаптируются при изменении memory limit контейнера, тогда как процентные автоматически подстраиваются. Для К8s deployments где memory limit меняется через изменение манифеста, процентный подход даёт большую гибкость.

CPU awareness работает аналогично памяти. JVM видит cgroup CPU quota и использует её для определения availableProcessors — метода Runtime возвращающего количество доступных процессоров. Это число влияет на многие внутренние структуры — количество GC threads, размер ForkJoinPool.commonPool используемого parallelStream и async operations, количество threads в различных пулах auto-configured Spring компонентами. Правильное определение количества доступных CPU критично для эффективной работы всех этих механизмов. Параметр ActiveProcessorCount позволяет явно переопределить если автоматическое определение работает неправильно.

## Ускорение старта через Class Data Sharing

Одна из существенных проблем Java приложений — время холодного старта. Загрузка тысяч классов из JAR файлов, парсинг байткода, инициализация метамодели — всё это занимает секунды даже для относительно небольшого приложения. Для микросервисной архитектуры с частыми деплойментами и автоскейлингом это существенно ограничивает agility.

Class Data Sharing или CDS — механизм ускорения загрузки классов через предкомпилированный архив метаданных. Стандартные классы JDK не меняются между запусками приложения, поэтому их метаданные можно один раз проанализировать, сохранить в специальный файл, и использовать при последующих запусках без повторной работы. С Java 12 стандартный CDS архив поставляется вместе с JDK и используется автоматически, ускоряя старт всех Java приложений на десятки процентов без каких-либо действий разработчика.

AppCDS расширяет идею на классы конкретного приложения. Разработчик прогоняет приложение с параметром ArchiveClassesAtExit, получает архив содержащий метаданные всех загруженных классов включая классы приложения и зависимостей. При последующих запусках с параметром SharedArchiveFile указывающим на этот архив, загрузка классов происходит существенно быстрее. Ускорение cold start составляет десять-тридцать процентов для типичного Spring Boot приложения. Для больших приложений с сотнями зависимостей эффект более заметен.

В контейнерной архитектуре AppCDS архив может генерироваться в multi-stage Docker build — один stage прогоняет приложение для генерации архива, другой stage запускает production контейнер с готовым архивом. Для Spring Boot layered JAR архив можно вынести в отдельный layer, что позволяет кэшировать его между сборками при изменении только application code.

Coordinated Restore at Checkpoint или CRaC — ещё более радикальный подход, представленный как preview в Java 21. Идея заключается в сохранении полного состояния JVM после warmup — включая JIT compiled code, инициализированные структуры, прогретые кэши — в файл. При старте нового instance восстановление из checkpoint занимает миллисекунды вместо секунд полного старта. Технология пока в preview статусе и в production используется редко, но потенциально может кардинально изменить время старта JVM приложений.

## GraalVM Native Image как альтернативный путь

GraalVM Native Image представляет принципиально другой подход к компиляции Java. Вместо runtime исполнения байткода на JVM с JIT компиляцией, GraalVM выполняет полную ahead-of-time компиляцию в нативный executable для целевой платформы. Результат — обычный бинарный файл без зависимости от JVM.

Преимущества native image впечатляют. Cold start составляет от ста до трёхсот миллисекунд против пяти-пятнадцати секунд классической JVM. Потребление памяти в разы меньше — обычно от пятидесяти до ста мегабайт против четырёхсот и больше у типичного Spring Boot приложения. Это делает native image идеальным выбором для serverless функций, edge computing, ограниченных ресурсов IoT.

Обратной стороной является ряд существенных ограничений. Сборка native image занимает минуты — процесс полной AOT компиляции существенно дольше обычного JAR билда. JIT оптимизаций нет — компилятор не имеет profile-guided информации о реальных паттернах выполнения. Reflection и dynamic class loading требуют явной конфигурации через файлы указывающие какие классы будут доступны в runtime. Многие фичи Spring и Hibernate требуют специальной поддержки для native image, что ограничивает возможности использования.

Spring Boot начиная с версии 3.0 включает специальный AOT processing через spring-boot-maven-plugin process-aot goal. Он подготавливает приложение к компиляции через GraalVM, обрабатывая метаданные Spring контекста и конфигурируя необходимые reflection hints. Это делает миграцию на native image значительно проще, но всё равно требует внимания к специфичным для приложения деталям.

В КНП native image массово не используется. Причины включают большое количество legacy кода с активным использованием reflection, сложности с Hibernate которые не всегда полностью поддерживаются в native image, инженерные затраты на подготовку к переходу. Классический JVM подход остаётся стандартом для enterprise приложений где cold start в секунды приемлем.

## Улучшения JIT компилятора

JIT компилятор HotSpot использует двухуровневую tiered compilation. C1 обеспечивает быструю компиляцию с базовыми оптимизациями для быстрого прогрева. C2 выполняет более медленную но глубокую оптимизацию для стабильно горячего кода. Между Java 11 и 21 обе стадии получили существенные улучшения.

C2 стал эффективнее в inlining методов, escape analysis для стековой аллокации коротко живущих объектов, pattern-based оптимизациях специфичных для новых языковых конструкций. Особенно заметны улучшения для кода использующего lambdas, method references, stream operations. Оптимизации подстраиваются под типичные паттерны современного Java кода делая его практически эквивалентным по производительности написанному в старом императивном стиле.

Отдельная тема связанная с JIT — pinning virtual threads. Virtual threads из Project Loom обсуждаются подробно в отдельном файле, но с точки зрения JIT важен факт что определённые операции блокируют освобождение carrier thread. Synchronized блоки и native code вызовы приводят к pinning когда virtual thread не может быть отсоединён от OS thread. Это ломает основное преимущество virtual threads. Диагностика через параметр jdk.tracePinnedThreads позволяет находить проблемные места и заменять synchronized на ReentrantLock который совместим с virtual threads.

GraalVM можно использовать не только для native image, но и как JIT компилятор внутри обычной JVM. Начиная с Java 11 в OpenJDK доступен Graal JIT через специальные experimental флаги. Иногда он даёт лучшую производительность чем C2, иногда хуже — реальный эффект зависит от конкретного workload и требует бенчмаркинга. Массового применения в enterprise Java не получил, но остаётся интересной опцией для специфичных случаев.

## Java Flight Recorder как встроенный профилировщик

JFR — мощный инструмент для профилирования Java приложений с минимальным overhead. Раньше был коммерческой фичей Oracle JDK, но с Java 11 доступен в OpenJDK бесплатно. Это существенно расширило доступность профессионального профилирования для всех Java разработчиков.

Механически JFR собирает события работы JVM — CPU sample points, GC pauses, memory allocations, thread state transitions, IO operations, lock contentions. Все события идут в буфер в памяти с минимальным overhead — обычно менее одного процента при типичной конфигурации. Запись может активироваться заранее через параметр StartFlightRecording или через jcmd в runtime, что позволяет включать профилирование только при возникновении проблем.

Полученный recording файл открывается в JDK Mission Control (JMC) — GUI инструменте от Oracle. JMC визуализирует все собранные события — flame graphs для CPU hotspots, timeline GC pauses, memory allocation profiles, thread activity heatmaps. Это существенно более информативно чем классические heap dumps которые показывают только snapshot состояния памяти.

Для диагностики проблем производительности в production JFR является правильным первым инструментом. В отличие от heap dumps которые могут занимать гигабайты и требовать много времени на анализ, JFR recording обычно несколько мегабайт и открывается в JMC мгновенно. Возможность включения профилирования в runtime без рестарта делает JFR идеальным для диагностики уже возникших проблем без необходимости воспроизведения в тестовой среде.

## Metaspace и native memory

Metaspace — область памяти где JVM хранит метаданные загруженных классов. Она отделена от heap и живёт в native memory, что означает не подчиняется настройкам Xmx. По умолчанию Metaspace не ограничен, что может быть источником проблем.

Размер Metaspace растёт при загрузке новых классов. Динамическая генерация классов через ByteBuddy, CGLib для JPA proxies и Spring AOP, MapStruct для мапперов создаёт классы в runtime. Утечка происходит когда ClassLoader создающий классы не выгружается — генерированные классы остаются в Metaspace навсегда. Классические сценарии включают redeploy приложения в application server без корректной очистки старых ClassLoader, использование scripting engines без освобождения, некоторые frameworks с агрессивной генерацией classes.

Ограничение Metaspace через MaxMetaspaceSize защищает от неограниченного роста. Правильный размер зависит от приложения, но двести пятьдесят шесть мегабайт обычно достаточно для типичного Spring Boot микросервиса. Превышение приводит к OutOfMemoryError Metaspace, что явно указывает на проблему требующую расследования.

Native Memory Tracking — механизм отслеживания использования native memory JVM. Включается параметром NativeMemoryTracking summary или detail. Через jcmd можно получить полный breakdown использования — сколько занимает heap, metaspace, code cache, threads stacks, direct memory, GC internal structures. Это критично для диагностики проблем когда контейнер OOMKilled но heap не полный — обычно причина в раздутом metaspace или thread stacks.

Java 16 представила Elastic Metaspace — улучшение уменьшающее overhead и фрагментацию metaspace. Это делает работу с большим количеством классов эффективнее, что особенно важно для приложений с большим количеством dynamic proxies или scripting.

## String deduplication и другие оптимизации

G1 может выполнять deduplication одинаковых строк — если находит несколько String объектов с одинаковым содержимым, заменяет их внутренние char array на общий разделяемый. Активируется параметром UseStringDeduplication. Может дать экономию от пяти до пятнадцати процентов heap для приложений с большим количеством дублирующихся строк, что типично для JSON парсинга где ключи повторяются в каждом объекте.

Реальная выгода зависит от workload. Приложения обрабатывающие много JSON или XML с повторяющимися структурами получают заметный effect. Приложения работающие с уникальными данными от deduplication практически не выигрывают но платят небольшой CPU cost.

## Реальные результаты миграции в КНП

Опыт миграции части сервисов КНП с Java 11 на Java 21 показывает определённые закономерности. Сам Java 21 в production стабилен — ни один из мигрированных сервисов не показал регрессий которые можно было бы отнести именно к переходу на новую версию JVM. Стандартный вывод из практики миграции — Java 21 как базовая платформа готова к продуктовому использованию.

Реальные проблемы возникали не из-за Java 21 самой по себе, а из-за параллельно обновляемых зависимостей. Hibernate 6 который пришёл вместе с миграцией стал строже проверять доступ к lazy полям, что обнажило скрытые проблемы с транзакциями и self-invocation. Spring Security jose и core оказались разных версий из-за транзитивных зависимостей, что привело к NoSuchMethodError в OAuth flow. Hazelcast 5 API кардинально изменился по сравнению с версией 3, что сломало интеграцию Spring Boot Actuator и потребовало exclude auto-configurations.

Практический вывод — миграция на Java 21 в реальном enterprise проекте это не только изменение sourceCompatibility параметра. Это координированное обновление всего стека — Spring Boot 3, Hibernate 6, обновлённые библиотеки безопасности, message broker клиенты. Каждый компонент требует внимания к semantic изменениям и регрессионному тестированию.

## Инструменты диагностики в production

Классический набор инструментов для работы с JVM в production включает несколько категорий. GC логирование через параметры Xlog gc даёт полное представление о работе сборщика мусора — частота срабатываний, длительность пауз, эффективность освобождения памяти. Долгие Full GC паузы, частые Young GC, растущий размер old generation без освобождения — всё это диагностические признаки указывающие на конкретные типы проблем.

Native Memory Tracking для полного breakdown использования native memory. Незаменим для диагностики OOMKilled контейнеров где heap не полный. Показывает точное распределение памяти между всеми внутренними структурами JVM.

Утилита jcmd как универсальный интерфейс для взаимодействия с работающей JVM. Позволяет получить thread dump без остановки приложения, информацию о heap и его использовании, запустить принудительный GC для тестирования, начать JFR recording в runtime. Работает через специальный canonical file interface — быстро и надёжно.

Для проблем производительности JFR recording открытый в JMC даёт максимально полную картину. CPU hotspots показывают где реально тратится время выполнения. GC log profile показывает влияние сборки мусора на общую производительность. Thread activity показывает лок contention и другие concurrency проблемы. Для complex диагностики один JFR recording обычно достаточно для определения root cause большинства production проблем.

## Итоги

JVM подсистема между Java 11 и 21 существенно эволюционировала. Сборщики мусора улучшились — G1 стал эффективнее, ZGC достиг production readiness с generational версией в Java 21. Container awareness стал первоклассной фичей начиная с Java 10 — JVM автоматически видит cgroup limits и адаптируется. Ускорение старта через CDS работает по умолчанию, AppCDS доступен для более серьёзной оптимизации, CRaC как preview технология обещает радикальное сокращение cold start.

GraalVM Native Image как альтернативный путь для случаев требующих сверхбыстрого старта и минимального потребления памяти. Не универсальное решение — ограничения по reflection и dynamic classloading, значительно более долгий build процесс, тонкая настройка совместимости с фреймворками. В КНП массово не применяется.

JIT компилятор постоянно улучшается — C2 стал эффективнее особенно для современного стиля Java кода. Metaspace получил elastic вариант в Java 16 уменьшающий overhead. String deduplication доступен в G1 для приложений с большим количеством повторяющихся строк.

JFR стал бесплатным в OpenJDK с Java 11 — правильный инструмент для профилирования в production с минимальным overhead. JMC для анализа делает работу с performance проблемами значительно эффективнее чем классические heap dumps.

Для КНП контекста миграция на Java 21 оказалась стабильной с точки зрения самой JVM. Проблемы возникали из-за параллельно обновляемых зависимостей — Hibernate 6, Spring Boot 3, обновлённые клиенты Hazelcast и других библиотек. Стандартный подход к миграции включает параллельные ветки master-21, постепенное обновление сервисов, тщательное регрессионное тестирование каждого этапа.

Дальше обсуждается что изменилось в стандартной библиотеке и какие проблемы возникают при миграции с Java 11 на 21 в реальных enterprise приложениях. Это уровень API deprecations, javax к jakarta переезд, множественные мелкие но практически важные изменения.
