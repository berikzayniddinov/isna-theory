# 12. JPA основы: Entity, EntityManager, PersistenceContext

## Работа с базой данных без ORM и с ним

Работа с реляционной базой данных в Java без ORM выглядит достаточно тягостно. Разработчик пишет SQL как строку в коде, открывает JDBC connection через DataSource, готовит PreparedStatement с параметрами, выполняет запрос. Затем итерирует по ResultSet, вручную читает значения колонок по индексу или имени, конструирует Java объекты со всеми присваиваниями полей. Обрабатывает возможный SQLException, аккуратно закрывает все ресурсы через try-with-resources или явные finally блоки. Для одной элементарной CRUD операции получается десятки строк boilerplate кода, повторяющегося от одного метода к другому с минимальными вариациями.

Ситуация усугубляется при работе со связями между таблицами. Реляционная модель строит связи через foreign keys, но объектная модель предполагает навигацию по ссылкам. Загрузил объект User из БД, теперь нужен связанный Address — приходится делать отдельный SQL запрос по foreign key. У Address есть City — ещё один запрос. Каждый шаг навигации по domain модели требует явного SQL, ручной сборки объектов и связывания их между собой. Быстро становится невыносимым для сложной модели с десятками связанных сущностей.

ORM, сокращение от Object-Relational Mapping, — это слой программного обеспечения, автоматизирующий преобразование между реляционной моделью базы данных и объектной моделью приложения. Разработчик описывает Java классы, ORM автоматически генерирует SQL для типовых операций, парсит результаты в объекты, обрабатывает загрузку связанных данных, реализует кэширование для повторных обращений. Разработчик работает с объектной моделью приложения, детали SQL скрыты под абстракцией.

В Java экосистеме есть три взаимосвязанных концепции, которые часто путают. JPA, полное название Jakarta Persistence API (раньше Java Persistence API), — это стандарт, спецификация. Определяет интерфейсы для работы с сущностями через EntityManager и EntityTransaction, набор аннотаций для маппинга Entity на таблицы (@Entity, @Id, @Column), собственный язык запросов JPQL. Сам по себе JPA реализации не предоставляет — это только спецификация. Hibernate — самая распространённая реализация JPA. Существует с 2001 года, задолго до появления JPA стандарта, в определённом смысле сформировал representation того, каким ORM должен быть в Java мире. Даёт полную функциональность JPA плюс свои Hibernate-специфичные возможности — расширения HQL над JPQL, second-level кэш, event listeners, соглашения по connection pooling. Spring Data JPA — это надстройка над JPA от команды Spring. Даёт репозитории-интерфейсы с автоматической реализацией, механизм derived queries по имени метода, интеграцию с Spring транзакциями и audit механизмом. Убирает ещё один слой boilerplate над стандартным JPA API.

В типичном enterprise приложении разработчик обычно пишет код через Spring Data JPA репозитории. Внутри они используют JPA через EntityManager. Реализация — Hibernate через Session. Который в свою очередь использует JDBC для реального общения с базой данных. Знание всех уровней необходимо для senior разработчика, потому что понимание того, что происходит на каждом уровне, критично для диагностики проблем и оптимизации производительности.

## Entity как класс отображённый на таблицу

Основная концепция JPA — Entity, обычный Java класс, помеченный специальными аннотациями и отображённый на таблицу в базе данных. Каждый экземпляр Entity класса соответствует одной строке в этой таблице. Свойства класса маппятся на колонки, связи между Entity классами отражают foreign keys между таблицами.

Есть несколько правил, которым должен соответствовать Entity класс. Он должен быть аннотирован @Entity — без этой аннотации Hibernate не будет считать класс сущностью. Должно быть определено поле-идентификатор с аннотацией @Id, обычно типа Long или UUID, соответствующее первичному ключу таблицы. Класс должен иметь публичный или защищённый конструктор без аргументов — Hibernate использует его для создания экземпляров через reflection при загрузке из БД. Класс не должен быть final — Hibernate создаёт прокси-подклассы через CGLIB для реализации lazy loading, что невозможно для final класса. Рекомендуется, но не обязательно, чтобы класс реализовывал Serializable, полезно для distributed кэшей и сериализации в некоторых сценариях.

Типичная Entity выглядит следующим образом. Класс аннотирован @Entity плюс опционально @Table для указания имени таблицы и схемы, если они отличаются от Java конвенций. Поле идентификатора помечено @Id и обычно @GeneratedValue для указания стратегии автогенерации значения. Обычные поля маппятся аннотацией @Column с параметрами вроде имени колонки, nullable, unique, length. Поля типа enum обрабатываются через @Enumerated с указанием способа хранения. Даты и времена в современных версиях JPA используют java.time классы вроде LocalDateTime без специальных аннотаций. Связи с другими Entity помечаются @ManyToOne, @OneToMany и подобными аннотациями с указанием стратегии загрузки через FetchType и опций каскадирования.

Аннотация @Enumerated требует особого внимания. По умолчанию используется значение ORDINAL — enum сохраняется в БД как числовой индекс своего порядка в декларации. Это опасно, потому что переупорядочивание enum значений или добавление нового в середину списка сломает соответствие между сохранёнными данными и текущим кодом. Правильный подход — явно указывать @Enumerated со значением STRING, тогда enum сохраняется как строковое представление своего имени. Небольшая избыточность в размере данных перевешивается стабильностью и понятностью.

Аннотация @Version реализует механизм оптимистической блокировки. Поле, помеченное этой аннотацией, автоматически инкрементируется Hibernate при каждом UPDATE. Плюс к условию WHERE у UPDATE запроса добавляется проверка что version не изменился с момента чтения. Если version уже другой (потому что параллельная транзакция обновила эту же строку раньше), UPDATE обновит ноль строк, Hibernate выбросит OptimisticLockException. Механизм защищает от потери обновлений при конкурентной модификации одной строки двумя транзакциями.

## Стратегии генерации первичного ключа

Способ автоматической генерации primary key критически влияет на производительность массовых операций и заслуживает отдельного обсуждения.

Стратегия GenerationType.IDENTITY использует auto-increment колонку в БД. Хibernate вынужден выполнить INSERT сразу для получения сгенерированного значения ID — через RETURNING id в PostgreSQL или generated keys mechanism в JDBC. Каждый persist приводит к отдельному INSERT statement. Основная проблема этой стратегии — невозможность JDBC batch insert. Механизм batching отправляет несколько INSERT statements одним round-trip к серверу БД, что ускоряет массовые вставки в пять-двадцать раз. Но batching требует, чтобы все значения были известны на клиенте до отправки batch. При IDENTITY значения генерируются сервером, каждый INSERT нужно выполнять отдельно.

Стратегия GenerationType.SEQUENCE использует database sequence — стандартный механизм PostgreSQL и Oracle. Hibernate заранее запрашивает следующее значение sequence, использует его как ID для нового объекта. Ключевая особенность — можно запрашивать значения пачками через параметр allocationSize. Если он установлен в 50, Hibernate одним запросом получает 50 значений sequence и раздаёт их клиентам без дополнительных обращений к БД. Это позволяет batch insert работать — все ID известны до отправки batch. Для PostgreSQL в enterprise приложениях SEQUENCE — правильный выбор.

Стратегия GenerationType.TABLE использует отдельную таблицу для эмуляции sequence. Медленная из-за необходимости блокировок при обновлении counter в таблице. Не рекомендуется для новых приложений.

Стратегия GenerationType.AUTO позволяет Hibernate самостоятельно выбрать стратегию на основе диалекта БД. Для PostgreSQL выберет SEQUENCE. Явное указание стратегии предпочтительнее для предсказуемости.

В КНП стандарт для всех Entity классов — SEQUENCE с явно указанным SequenceGenerator. Имя генератора в Java и имя sequence в БД должны быть связаны корректно, sequence создаётся через Liquibase миграцию. Параметр allocationSize в Java должен совпадать с INCREMENT sequence в БД, обычно оба установлены в 50. Несовпадение приведёт к конфликтам ID.

## EntityManager как центральный интерфейс

EntityManager — главный интерфейс JPA для работы с сущностями. Через него разработчик выполняет все операции с БД — сохранение новых сущностей, поиск существующих, обновление, удаление, выполнение запросов JPQL или native SQL. Обычно в Spring приложении разработчик не работает с EntityManager напрямую, а использует Spring Data JPA репозитории, которые внутри используют EntityManager. Но полезно понимать что происходит под этой абстракцией, потому что многие проблемы становятся понятнее при знании низкоуровневой механики.

EntityManager получается инъекцией через аннотацию PersistenceContext. Spring связывает его с текущей транзакцией. Основные методы EntityManager включают persist для сохранения новой сущности, find для поиска по идентификатору, merge для обновления detached объекта, remove для пометки на удаление, createQuery для выполнения JPQL запросов, createNativeQuery для native SQL. Плюс методы flush для принудительной синхронизации изменений с БД без commit транзакции и clear для очистки контекста.

Есть важное различие между EntityManager и EntityManagerFactory. EntityManagerFactory — тяжёлый объект, отвечающий за создание EntityManager. Он создаётся один раз при старте приложения через специальный Spring bean обычно называемый LocalContainerEntityManagerFactoryBean, автоматически конфигурируется через Spring Boot auto-configuration. EntityManagerFactory хранит метамодель всех сущностей, конфигурацию Hibernate, connection pool. Является thread-safe и singleton на всё приложение. EntityManager же — лёгкий объект, обычно один создаётся на транзакцию. Не является thread-safe, ответственность за корректную работу с ним лежит на транзакционном механизме Spring. После завершения транзакции EntityManager отбрасывается.

## PersistenceContext как first-level cache

Одна из фундаментальных концепций JPA — PersistenceContext. Это набор managed объектов в рамках текущей транзакции, поддерживаемый EntityManager. Ключевое свойство PersistenceContext заключается в гарантии, что для одного и того же primary key всегда возвращается один и тот же Java объект в рамках одного PersistenceContext.

Практически это работает так. При первом обращении к сущности через find или запрос Hibernate выполняет SELECT, создаёт Java объект и кладёт его в PersistenceContext. При повторном обращении с тем же ID Hibernate находит объект в PersistenceContext и возвращает его же, без обращения к БД. Два таких обращения дают гарантированно один и тот же Java объект — не просто equal, а действительно один и тот же в смысле оператора ==. Это называется first-level cache или session cache и работает только в рамках одной сессии.

Такая идентичность объектов даёт несколько важных практических преимуществ. Identity guarantee — в рамках транзакции невозможно получить два разных Java объекта, представляющих одну и ту же строку БД. Это упрощает работу с сущностями, не нужно специально сравнивать по ID для понимания что это "та же" сущность. Automatic dirty checking — Hibernate помнит исходное состояние каждого managed объекта в момент его загрузки, сравнивает с текущим состоянием при flush, автоматически генерирует UPDATE для изменённых полей. Разработчик не вызывает явное save, просто меняет поля объекта, Hibernate замечает изменения. Lazy loading — прокси на lazy-loaded поля резолвятся при первом обращении пока сессия жива, что позволяет писать код навигации по связям как будто все данные уже загружены. Транзакционная семантика — все изменения managed объектов фиксируются одним commit, откатываются одним rollback.

Есть также важные ограничения PersistenceContext. Он не является кэшем между сессиями — каждая новая транзакция создаёт новый EntityManager с пустым PersistenceContext, для чтения данных придётся снова обращаться к БД. Для меж-сессионного кэша существует second-level cache, обсуждаемый в следующем файле. PersistenceContext не защищает от изменений извне — если другая транзакция обновила строку в БД, эта Session об этом не узнает до явного refresh или до момента следующего запроса, требующего flush.

Существует практическая опасность, о которой нужно помнить при работе с большими датасетами. Если в одну сессию загрузить очень много объектов, например через SELECT ALL на миллион строк, все они удерживаются в PersistenceContext. Heap может исчерпаться, приложение упадёт с OutOfMemoryError. Для батчевой обработки требуется periodic flush для отправки накопленных изменений в БД и clear для освобождения контекста от уже обработанных объектов.

По умолчанию scope PersistenceContext транзакционный — каждая транзакция получает свой EntityManager с собственным PersistenceContext. После завершения транзакции контекст очищается, все managed объекты переходят в состояние detached. Существует также extended scope, при котором контекст живёт дольше транзакции — используется редко, в основном в Stateful контексте EJB, в Spring приложениях обычно не встречается.

## Механизм @Transactional и PersistenceContext

Стандартный Spring подход к работе с JPA заключается в пометке сервисного метода аннотацией @Transactional. Всё что происходит внутри метода работает в одной транзакции с одним PersistenceContext. Понимание что происходит на низком уровне помогает избегать типичных ошибок.

Когда вызывается метод сервиса, помеченный @Transactional, Spring перехватывает вызов через прокси, обсуждавшийся в файле про Spring Framework. Открывается новая транзакция через PlatformTransactionManager — в БД отправляется BEGIN. Создаётся EntityManager, связывается с этой транзакцией, ассоциируется с текущим потоком через ThreadLocal. Вызывается реальный метод сервиса.

Внутри метода при вызове em.find или repository.findById Hibernate выполняет SELECT, загружает объект в PersistenceContext как managed. Одновременно сохраняется копия исходного состояния объекта в snapshot для будущего dirty checking. При изменении полей объекта через setter методы никаких SQL не отправляется — Hibernate помнит что поле "грязное". Ничего не сохраняется в БД до момента flush.

При выходе из метода без исключений Spring commits транзакцию. EntityManager автоматически делает flush перед commit — проходит по всем managed объектам, сравнивает текущее состояние с исходным snapshot, генерирует UPDATE для изменённых полей. Собранные SQL операции отправляются в БД, затем следует COMMIT. После этого EntityManager закрывается, PersistenceContext очищается, ассоциация с потоком удаляется.

Если внутри метода бросается RuntimeException, Spring делает rollback. В БД отправляется ROLLBACK, никакие изменения не сохраняются. PersistenceContext очищается. Важная деталь заключается в том, что по умолчанию Spring откатывает транзакцию только на RuntimeException и Error. Checked exceptions по умолчанию игнорируются — если метод бросает checked exception, транзакция всё равно закомммитится с частичными изменениями. Это частый источник багов и обсуждается подробнее ниже.

## Жизненный цикл сущности

Каждая сущность в JPA находится в одном из четырёх состояний, между которыми переходит через определённые операции. Понимание этих состояний и переходов критично для корректной работы с сущностями.

Transient — это исходное состояние только что созданной сущности через оператор new. Hibernate о таком объекте ничего не знает, объект существует только в памяти приложения, никаких отношений к БД у него нет. Установка полей на transient объекте — обычные Java операции без каких-либо side effects. Transient объект переходит в managed состояние при вызове em.persist на нём.

Managed или persistent — состояние, когда Hibernate активно следит за объектом в рамках текущей сессии. Изменения полей managed объекта будут отслежены dirty checking и сохранены при flush. Managed объект находится в PersistenceContext, гарантированно один экземпляр на primary key. Managed состояние — то, в котором находятся объекты после успешного persist или после загрузки через find.

Detached — это состояние объекта, которое возникает после закрытия сессии, содержавшей его как managed, или после явного вызова em.detach. Объект существует в памяти, но Hibernate за ним больше не следит. Изменения полей не сохраняются автоматически. Возврат Entity из @Transactional метода делает её detached — сессия закрылась при завершении транзакции, всё что вернулось наружу это detached объект.

Removed — состояние объекта, помеченного на удаление через em.remove. При flush будет выполнен DELETE в БД. До flush объект ещё существует в БД, но Hibernate знает что нужно его удалить.

Основные операции EntityManager вызывают эти переходы. Operation persist переводит из transient в managed, планирует INSERT при следующем flush. Operation find выполняет SELECT в БД, возвращает managed объект, или найденный в PersistenceContext если он уже там. Operation getReference возвращает прокси без обращения к БД — SELECT произойдёт только при первом обращении к любому полю кроме идентификатора, что полезно для случаев, когда нужна ссылка на существующую сущность для связывания, но реально читать её данные не требуется.

Operation merge требует особого понимания. Она принимает detached объект и переводит связанное состояние в managed. Ключевая деталь — merge копирует состояние detached объекта в новый managed объект, который возвращается из метода. Оригинальный detached объект остаётся detached. Разработчики часто ошибаются, ожидая что оригинальный объект станет managed после merge. Правильная логика — использовать возвращённый объект для дальнейшей работы.

Operation remove помечает managed объект как removed, планирует DELETE. Operation refresh перечитывает состояние объекта из БД, перезаписывая поля managed объекта в PersistenceContext. Полезно если известно что данные могли измениться извне текущей транзакции. Operation detach переводит managed в detached, убирает из PersistenceContext. Operation clear делает то же для всего контекста — все managed объекты становятся detached, контекст пуст. Operation flush синхронизирует все накопленные изменения с БД без commit транзакции, полезно для батчевой обработки.

## Различие persist и merge

Классический источник путаницы. Правило простое — persist для transient объектов (новых, не существующих в БД), merge для detached (существующих в БД, но не связанных с текущей сессией).

Попытка использовать неправильную операцию приводит к специфическим ошибкам. Если попытаться вызвать persist на detached объекте, Hibernate бросит PersistentObjectException с сообщением про detached entity passed to persist. Правильный подход в такой ситуации — вызвать merge, который создаст новый managed объект с копией состояния и вернёт его для дальнейшей работы.

Альтернативный подход, если detached объект больше не нужен — очистить контекст и загрузить сущность заново через find. Это создаст свежий managed объект без коллизий с detached версией.

Spring Data JPA метод save() умно скрывает эту тонкость. Он проверяет ID переданной сущности — если null или соответствует специальному "new" marker, вызывает persist. Если ID заполнен, вызывает merge. Разработчик не думает о состоянии сущности, save работает в обоих случаях. Внутренние механизмы Spring Data JPA определяют правильную операцию.

## Транзакции JPA и Spring @Transactional

JPA определяет собственный механизм транзакций через интерфейс EntityTransaction. Без Spring работа с транзакциями выглядит многословно — нужно явно получить транзакцию из EntityManager, вызвать begin, обернуть код в try-catch с явным commit при успехе и rollback при исключении. Каждый метод повторяет один и тот же boilerplate.

Spring аннотация @Transactional автоматизирует эту работу через AOP механизм. Метод, помеченный аннотацией, автоматически оборачивается в транзакцию. Разработчик пишет только бизнес-логику, механика транзакций скрыта. Уже обсуждалось в файле про Spring Framework, здесь стоит повторить ключевые опции применительно к JPA контексту.

Параметр propagation определяет как метод участвует в транзакции. Значение REQUIRED, установленное по умолчанию, означает что метод использует существующую транзакцию если она есть, создаёт новую если её нет. Это самый частый случай. Значение REQUIRES_NEW всегда создаёт новую транзакцию, приостанавливая текущую если она была. Используется для "независимых" операций вроде audit log, которые должны сохраняться независимо от исхода основной транзакции. Значение NESTED создаёт savepoint внутри текущей транзакции, что позволяет откатить внутренние изменения без отката всей транзакции. Требует поддержки savepoints в БД, PostgreSQL поддерживает. Значение MANDATORY требует чтобы транзакция уже была открыта, иначе бросает исключение. Значения SUPPORTS, NOT_SUPPORTED, NEVER определяют поведение когда транзакция уже открыта — соответственно работать в ней, работать без транзакции приостановив её, или падать с исключением.

Параметр isolation задаёт уровень изоляции транзакции. PostgreSQL по умолчанию использует READ_COMMITTED, что защищает от dirty reads (чтения незакоммиченных изменений), но допускает non-repeatable reads и phantom reads. Для большинства бизнес-приложений этого достаточно. REPEATABLE_READ гарантирует консистентное чтение в рамках транзакции ценой большей блокировки. SERIALIZABLE — самый строгий уровень, транзакции выполняются как если бы они были последовательными. READ_UNCOMMITTED — самый слабый уровень, разрешает dirty reads, PostgreSQL его на самом деле не поддерживает, все транзакции работают минимум как READ_COMMITTED.

Параметр readOnly установленный в true — важная оптимизация для методов чтения. Hibernate помечает Session как не требующую dirty checking, не создаёт snapshots для сравнения, экономит память и CPU. PostgreSQL может оптимизировать read-only транзакции на своей стороне. Плюс явная документация намерения делает код читабельнее.

Параметр rollbackFor указывает на какие исключения выполнять rollback. По умолчанию Spring откатывает только на RuntimeException и Error. Checked exceptions игнорируются, что приводит к типичному багу — метод бросает checked exception, но транзакция всё равно коммитится с частичными изменениями. Если бизнес-логика может бросать checked exceptions, требующие отката транзакции, нужно явно указать rollbackFor равный Exception.class или конкретному типу exception.

Параметр timeout ограничивает время выполнения транзакции. При превышении транзакция автоматически откатывается. Защищает от долгих транзакций, блокирующих resources.

## Языки запросов JPQL и native SQL

JPA определяет собственный язык запросов, называемый JPQL (Java Persistence Query Language). Синтаксически похож на SQL, но работает с сущностями и их полями, а не с таблицами и колонками. Ключевая особенность — навигация по связям через оператор точки. Запрос про поле связанной сущности автоматически превращается в JOIN в сгенерированном SQL.

Преимущества JPQL несколько. Он портируется между разными базами данных, поскольку диалект-специфичные детали скрыты Hibernate. Проверяется по метамодели на этапе компиляции или старта приложения — опечатки в именах полей ловятся до runtime. Возвращает managed сущности, которые можно изменять с автоматическим сохранением через dirty checking. Однако есть ограничения. JPQL не даёт всей мощи SQL — сложные конструкции вроде recursive CTE, advanced window functions, специфичные для диалекта функции недоступны напрямую.

Для сложных случаев есть native SQL — обычные SQL запросы, специфичные для используемой БД. Полная мощь SQL, полный контроль над планом запроса. Ценой этого является отсутствие типобезопасности (компилятор не проверяет native queries) и привязка к конкретному диалекту БД. Миграция на другую БД потребует переписывания native queries.

Существует также Criteria API — типобезопасный конструктор запросов через Java объекты. Многословный по синтаксису, используется в основном для динамических запросов, когда набор условий определяется в runtime. Например, для поиска с множеством опциональных фильтров в админке. Spring Data JPA предоставляет Specification API поверх Criteria, что делает работу удобнее для типовых сценариев.

Для типовых статических запросов проще писать JPQL через @Query аннотацию Spring Data. Динамические запросы лучше через Specifications. Native SQL только когда действительно необходима функциональность недоступная через JPQL.

## Конфигурация в Spring Boot

Классическое использование JPA требовало создания файла persistence.xml с описанием persistence unit, connection properties, mapped classes. Spring Boot скрывает эту сложность — вся конфигурация происходит через application.yml без специальных XML файлов.

Основные секции конфигурации включают spring.datasource для connection к БД (URL, username, password, настройки connection pool HikariCP), spring.jpa для настроек JPA и Hibernate. Внутри spring.jpa параметр database-platform опционально указывает диалект БД (обычно определяется автоматически). Параметр hibernate.ddl-auto — важнейший, определяет как Hibernate работает со схемой БД. Параметр show-sql контролирует логирование SQL — включён для dev, выключен для prod.

Параметр ddl-auto заслуживает особого внимания. Значение none означает что Hibernate ничего не делает со схемой, всё управляется вручную. Значение validate проверяет что БД схема соответствует Entity классам при старте приложения, при несоответствии падает — это правильный выбор для production. Значение update автоматически модифицирует схему БД до соответствия Entity — категорически не для production, поведение непредсказуемо, может уничтожить данные. Значения create и create-drop создают схему при старте, для тестов с in-memory БД.

Правильный подход в production — ddl-auto равный validate, схема БД управляется отдельно через миграционный инструмент. В Java мире стандарт — Liquibase, менее распространён Flyway. Разработчик пишет миграции в XML, YAML, JSON или SQL, инструмент применяет их в правильном порядке при старте приложения. Каждая миграция имеет уникальный идентификатор и информацию об авторе, применённые миграции сохраняются в специальной таблице databasechangelog. При повторном старте инструмент видит применённые миграции и применяет только новые.

В КНП везде используется Liquibase. Стандартный подход — миграции лежат в src/main/resources/db/changelog, master файл включает остальные changelog файлы. Каждый changeSet содержит один или несколько DDL или DML операций. Настройки Spring Boot указывают путь к master файлу и включают Liquibase.

Дополнительно в spring.jpa.properties.hibernate есть много тюнинг параметров. Параметр batch_size включает JDBC batching для массовых операций. Параметры order_inserts и order_updates сортируют операции по типу перед отправкой в batch, что повышает эффективность батчинга. Параметр default_batch_fetch_size включает батчинг для lazy fetching, что помогает бороться с N+1 проблемой. Параметр time_zone унифицирует timezone для timestamps.

## Cascade и orphan removal

Для связей между сущностями важно определить как операции распространяются с родительской на дочерние. Например, при удалении Fno — что делать с связанными FnoLine.

Параметр cascade у аннотаций связей указывает какие операции каскадируются. Значение PERSIST означает что при em.persist родителя дочерние тоже получат persist. Значение MERGE аналогично для merge. Значение REMOVE каскадирует удаление — em.remove родителя удалит и дочерних. Значение REFRESH перечитывает и дочерних из БД при refresh родителя. Значение DETACH делает detached и дочерних при detach родителя. Значение ALL включает все операции.

Параметр orphanRemoval работает похоже на cascade REMOVE, но с другой семантикой. Он удаляет дочерний объект из БД когда его убирают из коллекции родителя. Например, если у Fno есть коллекция FnoLine с orphanRemoval равным true, удаление одного элемента из списка `fno.getLines().remove(line)` приведёт к DELETE в БД для этой line. Без orphanRemoval line осталась бы в БД со ссылкой на fno, становясь "сиротой" в объектной модели.

Разница между cascade REMOVE и orphanRemoval заключается в trigger операции. Cascade REMOVE работает при em.remove родителя — удаляет всех детей вместе. OrphanRemoval работает при удалении из коллекции — удаляет удалённый элемент.

Правильное использование каскадирования зависит от природы связи. Для агрегатов в терминах DDD (например Fno и его FnoLine живут только вместе) — комбинация cascade ALL и orphanRemoval true подходит. Родитель полностью управляет жизненным циклом детей. Для полу-независимых связей может быть достаточно cascade PERSIST плюс MERGE без REMOVE — родитель управляет созданием и обновлением, но не удалением. Для полностью независимых связей (например Fno и Taxpayer — taxpayer существует независимо от fno) каскадирование не используется вообще.

## Оптимистическая блокировка

Концепция оптимистической блокировки решает проблему конкурентной модификации одной строки двумя транзакциями. Классический сценарий без блокировки выглядит так. Два пользователя одновременно открывают одну сущность на редактирование, оба видят одно и то же состояние. Каждый вносит изменения и сохраняет. Изменения первого записываются в БД. Изменения второго записываются поверх, полностью замещая изменения первого. Никаких ошибок не возникает, но изменения первого пользователя тихо потеряны — это классическая lost update проблема.

Механизм оптимистической блокировки через аннотацию @Version решает эту проблему. Специальное поле version на Entity автоматически инкрементируется Hibernate при каждом UPDATE. К UPDATE запросу добавляется условие проверки что version не изменился с момента чтения. Если version уже другой (потому что параллельная транзакция обновила эту же строку), UPDATE обновит ноль строк, Hibernate поймёт что произошёл конфликт и выбросит OptimisticLockException.

В том же сценарии с двумя пользователями. Оба читают сущность с version равным пяти. Первый пользователь сохраняет — Hibernate генерирует UPDATE с условием WHERE id и version равен пяти, устанавливает новое version равным шести. Одна строка обновлена, версия теперь шесть. Второй пользователь сохраняет — Hibernate генерирует такой же UPDATE, но условие version равен пяти больше не выполняется, обновилось ноль строк. Hibernate бросает OptimisticLockException. Второй пользователь узнаёт что данные протухли, обычно видит сообщение "данные были изменены, перечитайте страницу", повторяет операцию с актуальными данными.

Альтернативный подход — пессимистическая блокировка через SELECT FOR UPDATE. Строка блокируется на уровне БД при чтении, никакая другая транзакция не может её изменить до commit или rollback текущей. Более тяжёлый подход, но проще семантика — не нужно обрабатывать конфликты в приложении. При высокой конкуренции может привести к deadlocks и увеличенной latency.

Правило выбора между этими подходами. Оптимистическая блокировка подходит для read-heavy сценариев с редкими конфликтами. Не блокирует чтение, минимальный оверхед. Пессимистическая блокировка нужна для сценариев с гарантированно конфликтными операциями (счётчики, критичные lookups по популярным записям), где повторы после конфликта нежелательны.

## Заключение

JPA как стандарт Java для ORM с реализацией Hibernate и надстройкой Spring Data JPA — фундамент enterprise persistence в Java. Все три уровня встречаются в реальной работе, каждый требует понимания.

Entity как Java класс отображённый на таблицу через аннотации @Entity, @Id, @Column, связи через @ManyToOne, @OneToMany. Правила про no-arg конструктор и non-final класс важны для работы Hibernate прокси механизма. Стратегия генерации ID через SEQUENCE стандартна для PostgreSQL, IDENTITY ломает batch insert.

EntityManager как центральный интерфейс операций с сущностями. Обычно скрыт за Spring Data репозиториями, но знание его существования и семантики помогает понимать что происходит внутри.

PersistenceContext как first-level cache со свойством "один primary key равен одному Java объекту в сессии". Даёт identity guarantee, dirty checking, lazy loading. Не является кэшем между сессиями и не защищает от изменений извне. Требует внимания при батчевой обработке чтобы избежать OutOfMemoryError.

Lifecycle сущности через четыре состояния — transient, managed, detached, removed. Правильное использование persist для transient и merge для detached, понимание что merge возвращает новый объект — источник частых ошибок.

Аннотация @Transactional со всеми её параметрами — propagation, isolation, readOnly, rollbackFor, timeout. Особенно важна проблема checked exceptions игнорируемых по умолчанию для rollback.

JPQL как основной язык запросов, native SQL для сложных случаев, Criteria и Specifications для динамических запросов.

Конфигурация в Spring Boot через application.yml без persistence.xml. Ddl-auto равный validate в production, схема управляется через Liquibase миграции.

Cascade и orphanRemoval для управления жизненным циклом связанных сущностей в агрегатах. Оптимистическая блокировка через @Version для защиты от lost update проблемы.

Для КНП контекста все сервисы используют JPA плюс PostgreSQL плюс Liquibase. Стандартные паттерны включают SEQUENCE для всех primary key, @Enumerated STRING для enum полей, явное указание FetchType.LAZY для @ManyToOne связей, cascade ALL плюс orphanRemoval для агрегатов, @Version для сущностей требующих защиты от конкурентной модификации.

Дальше обсуждаются внутренности Hibernate, работающие под капотом JPA API. Session и её отличия от EntityManager, механика dirty checking и flush, statement batching для производительности, работа со связями между сущностями и стратегии загрузки.
