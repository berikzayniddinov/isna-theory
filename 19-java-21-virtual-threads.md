# 19. Java 21: Virtual Threads из Project Loom

## Проблема которую решают виртуальные потоки

Классическая модель Java concurrency привязывала каждый Thread к отдельному OS thread. Это удобно концептуально — thread в Java напрямую соответствует thread в операционной системе, планирование делает ядро, всё прозрачно. Но за эту прозрачность приходится платить существенной ценой при масштабировании.

Каждый OS thread потребляет значительные ресурсы. Стек выделяется размером обычно 1 мегабайт по умолчанию — это виртуальная память которая не вся используется, но всё равно резервируется. Переключение контекста между threads требует сохранения регистров процессора, обновления TLB, потенциального сброса кэшей — операция дорогая. Планирование множества threads создаёт нагрузку на планировщик ОС. Практический предел количества OS threads на JVM — несколько тысяч на современном сервере, дальше начинается деградация производительности.

Для web сервисов обрабатывающих множество одновременных запросов это создаёт архитектурную проблему. Каждый запрос требует thread — если thread ждёт ответа от базы данных, вызова другого сервиса, чтения из очереди, он всё это время блокирует OS thread. При тысяче одновременных запросов нужна тысяча threads, каждый большую часть времени просто ждёт I/O. Это неэффективное использование ресурсов и ограничение масштабируемости.

Индустрия ответила на эту проблему асинхронным программированием — reactive frameworks вроде Project Reactor и WebFlux, CompletableFuture с цепочками callback, asynchronous drivers для баз данных и сетевых операций. Философия — thread не блокируется, он передаётся обратно в pool когда операция начинает ожидание, возобновление обрабатывается через callback когда результат готов. Один thread может обслужить тысячи запросов параллельно.

Проблема с асинхронным подходом — колоссальное усложнение кода. Логика запроса разбивается на цепочки колбэков или reactive операторов. Stacktrace становится бесполезным потому что каждая асинхронная точка ломает вызов. Отладка превращается в кошмар — обычные breakpoint не работают предсказуемо, значения переменных теряются между async шагами. Экосистема становится специфической — все библиотеки должны быть reactive иначе весь выигрыш теряется. Один блокирующий вызов в цепочке нейтрализует все преимущества.

Project Loom предложил радикально другой подход. Не менять модель программирования, оставить thread-per-request как есть, но сделать threads настолько дешёвыми что миллионы одновременных концептуально возможны. Разработчик пишет обычный код с прямыми вызовами, JVM берёт на себя эффективное управление ресурсами.

## Что такое виртуальный поток

Виртуальный поток технически представляет собой lightweight thread управляемый JVM, а не операционной системой. Класс наследуется от java.lang.Thread что означает совместимость со всем существующим API — Runnable, ExecutorService, ThreadLocal, CompletableFuture работают одинаково для virtual и platform threads. Разработчик может заменить создание Thread на createVirtual и код продолжит работать без изменений.

Под капотом виртуальный поток связан с несколькими platform threads через механизм называемый carrier threads. Carrier — это обычный OS thread который выполняет код виртуального thread когда тот активен. Когда виртуальный thread выполняет блокирующую I/O операцию, JVM отсоединяет его от carrier, освобождая carrier для другого виртуального thread. Когда операция I/O завершается, виртуальный thread присоединяется к любому доступному carrier для продолжения выполнения.

Количество carrier threads по умолчанию равно количеству процессорных ядер. Виртуальных threads может быть миллионы, они конкурируют за carrier времени. Планирование виртуальных threads делает JVM а не ОС, что позволяет более эффективные алгоритмы специфичные для этого сценария. Переключение контекста между виртуальными threads на одном carrier существенно дешевле чем между OS threads — не нужно вовлекать ядро, достаточно manipulation в user space.

Ключевое поведение — блокирующие I/O операции автоматически освобождают carrier. Когда виртуальный thread вызывает InputStream read, Socket write, JDBC executeQuery, JVM понимает что происходит blocking I/O и передаёт carrier другому виртуальному thread. Реальная работа operating system по ожиданию завершения I/O делается через async примитивы epoll на Linux, kqueue на BSD, IOCP на Windows. Но приложение видит обычный синхронный API, всю асинхронность скрывает JVM.

Виртуальные threads крайне дешёвые по памяти. Начальный стек всего несколько сотен байт, растёт по необходимости, максимум несколько килобайт для типичных use case. Миллион виртуальных threads занимает несколько сотен мегабайт памяти — вполне посильно для современных серверов. Сравните с миллионом OS threads который потребовал бы терабайты виртуальной памяти для стеков.

## Как использовать в коде

Создание виртуального потока делается через Thread ofVirtual builder или Thread startVirtualThread convenience метод. Executor через Executors newVirtualThreadPerTaskExecutor создаёт executor который для каждой задачи создаёт новый виртуальный thread. Это принципиально отличается от классических thread pools где количество threads фиксировано — виртуальные threads настолько дешёвые что pool не нужен, каждая задача получает свой thread.

Для web приложений это означает возможность настроить сервер обрабатывать каждый запрос в отдельном виртуальном thread. Tomcat в Spring Boot 3.2 и выше поддерживает виртуальные threads через опцию spring.threads.virtual.enabled. При включении каждый HTTP запрос обрабатывается в новом виртуальном thread, что снимает ограничение классического thread pool на количество одновременных запросов. Сервер может обрабатывать десятки тысяч concurrent connections на скромном железе.

Аналогичная поддержка для JDBC — каждый запрос получает virtual thread, обращение к базе данных блокирует virtual thread но не carrier. Connection pool продолжает работать нормально, но количество одновременных запросов больше не ограничено размером HTTP thread pool. Ограничение переносится на pool соединений с базой и capacity самой базы данных.

RabbitMQ consumers, Kafka listeners, scheduled jobs — везде где раньше был thread pool с фиксированным количеством threads можно перейти на виртуальные threads. Каждое сообщение обрабатывается в отдельном virtual thread, никаких ограничений на параллелизм со стороны framework.

Существующий код обычно работает без изменений. Обычные synchronized блоки работают с виртуальными threads. ThreadLocal работает — каждый виртуальный thread имеет свой собственный локальный контекст. CompletableFuture работает — можно комбинировать с виртуальными threads. Единственная разница может проявиться в специфических сценариях требующих особой обработки, но большинство кода прозрачно переходит на новую модель.

## Проблема pinning

Существует важное ограничение — виртуальные threads не могут быть отсоединены от carrier во всех ситуациях. Если виртуальный thread находится внутри synchronized блока или выполняет native код через JNI, он pinned к своему carrier — не может передать carrier другому виртуальному thread. Если pinned virtual thread блокируется, весь carrier блокируется вместе с ним, что нейтрализует преимущества виртуальных threads.

В контексте synchronized блоков это ограничение существенно. Многие библиотеки используют synchronized внутренне для обеспечения thread safety. Каждый вызов такой библиотеки внутри synchronized создаёт pinning. Если библиотека делает blocking I/O внутри synchronized, весь carrier блокируется. Один такой pattern способен свести на нет всю масштабируемость виртуальных threads.

JDK решает эту проблему постепенно. В Java 21 многие внутренние synchronized блоки в стандартной библиотеке уже заменены на ReentrantLock который совместим с виртуальными threads. Планируется полное устранение pinning из-за synchronized в будущих версиях. Но для пользовательского кода и сторонних библиотек проблема остаётся актуальной.

JNI пиннинг более фундаментален — native код не может быть suspended JVM потому что JVM не контролирует его выполнение. Виртуальный thread выполняющий JNI вызов остаётся pinned до возврата из native кода. Если native код делает blocking syscall — carrier заблокирован. Для большинства приложений это не проблема потому что JNI используется редко и обычно быстро завершается, но следует помнить об этом ограничении.

Диагностика pinning выполняется через параметр JVM jdk.tracePinnedThreads. При включении JVM печатает stacktrace каждый раз когда виртуальный thread pinned. Это позволяет обнаружить проблемные места в коде — обычно это старые библиотеки с щедрым использованием synchronized. Решение — либо заменить библиотеку на более современную использующую ReentrantLock, либо принять ограничение и понимать что этот компонент не выиграет от виртуальных threads.

Практическая рекомендация — избегать synchronized в новом коде под виртуальные threads, использовать ReentrantLock или другие concurrent примитивы. Проверять существующие критические места на pinning через tracePinnedThreads. Приоритизировать библиотеки с современной архитектурой не полагающиеся на synchronized.

## Взаимодействие с connection pools

Виртуальные threads снимают ограничение количества одновременных запросов на уровне HTTP thread pool. Но нижние уровни — connection pool к базе данных, HTTP client connection pool для внешних сервисов — остаются с фиксированным количеством ресурсов. Это создаёт новую динамику производительности требующую понимания.

Если было ограничение thread pool в 200 threads и pool соединений с базой в 50, то практический предел одновременных запросов идущих в базу — 50. Остальные 150 threads либо обрабатывают запросы не идущие в базу, либо ждут освобождения соединений. С виртуальными threads снимается верхнее ограничение — тысяча запросов может одновременно попытаться получить соединение. Первые 50 получат сразу, остальные 950 будут ждать освобождения. Это может привести к timeout если ожидание превышает настроенное значение.

Практическое решение — увеличить размер connection pool соответственно возросшей concurrency, но это ограничено capacity самой базы данных. Продвижение bottleneck на нижний уровень не решает проблему, только смещает её. Иногда правильное решение — оставить HTTP thread pool в разумных пределах даже с виртуальными threads, чтобы естественный backpressure защищал downstream системы.

Для HTTP client вызовов внешних сервисов аналогичная логика. Существует некая максимальная нагрузка которую downstream может выдержать. Если давать больше concurrent запросов чем downstream может обработать, начинаются timeout, retry, каскадные проблемы. Rate limiting и bulkhead patterns остаются актуальными даже с виртуальными threads.

Мониторинг становится критически важным. Метрики использования connection pools, времени ожидания получения соединения, timeout rates помогают понимать где новые пределы возможностей. Существующие практики observability переносятся на virtual threads без изменений, но необходимо переосмыслить пороги оповещений с учётом новых характеристик системы.

## Structured Concurrency и ScopedValue

Вместе с виртуальными threads Java 21 представила ещё две связанные фичи облегчающие написание concurrent кода. Structured Concurrency в статусе preview и ScopedValue также в preview дополняют картину.

Structured Concurrency решает проблему координации параллельных задач. Классический pattern — один запрос требует данные из трёх разных источников, идёт параллельно к трём микросервисам, ждёт все три ответа, комбинирует результаты. Реализация через CompletableFuture возможна но многословна и подвержена ошибкам с error handling и cancellation.

StructuredTaskScope предоставляет abstraction where все subtasks scope запуска рассматриваются как единое целое. Если родительский task отменён, все subtasks отменяются. Если один subtask падает, другие могут быть отменены в зависимости от policy. Ошибки propagate consistent way. Timeout может быть применён к всей группе. Всё в блоке try-with-resources что гарантирует cleanup ресурсов.

Различные policies работают с разными сценариями. ShutdownOnFailure отменяет остальные задачи при первой ошибке — типичный сценарий когда все результаты необходимы для завершения запроса. ShutdownOnSuccess отменяет остальные при первом успехе — для сценария redundant queries где достаточно любого ответа. Обе policies радикально упрощают код по сравнению с ручной оркестрацией через CompletableFuture.

ScopedValue — замена ThreadLocal более подходящая для виртуальных threads. ThreadLocal имеет несколько недостатков в контексте virtual threads. Каждый виртуальный thread может иметь свой ThreadLocal, но их миллион, потребление памяти растёт. ThreadLocal не наследуется в child threads кроме через специальный InheritableThreadLocal. Модификация ThreadLocal делается императивно, что не всегда очевидно из кода.

ScopedValue immutable — установка значения происходит через runWith метод который принимает callable. Значение доступно во всём callable и в любых виртуальных threads созданных внутри него, но недоступно вне scope. Это делает контекст явным в коде — где начинается видимость, где заканчивается. Хорошо подходит для request context, security context, trace ID и других scoped данных.

Практическое применение — request scoped данные вроде текущего пользователя, correlation ID, database транзакции могут быть переданы через ScopedValue вместо ThreadLocal. Более безопасно потому что нет возможности случайно оставить значение установленным после завершения запроса. Более эффективно потому что не потребляет память в каждом виртуальном thread независимо от того используется ли значение.

## Виртуальные threads против reactive

Появление виртуальных threads не отменяет reactive frameworks мгновенно, но меняет ландшафт выбора. Reactive стек имел уникальное преимущество высокой concurrency при разумном потреблении ресурсов ценой сложности кода. Виртуальные threads предлагают ту же concurrency при сохранении простоты обычного blocking кода.

Для типичных enterprise приложений где основная логика — CRUD операции, интеграции через HTTP и messaging, обработка бизнес правил — виртуальные threads явно лучший выбор. Простота отладки, читаемости, exception handling, интеграции с существующими библиотеками перевешивают потенциальные небольшие преимущества reactive стека в edge cases.

Reactive остаётся релевантным для специфических сценариев. Streaming обработка данных где reactive операторы вроде map, filter, buffer, window выражают логику естественнее чем императивные циклы. Backpressure сценарии где downstream медленный а upstream быстрый и нужен контроль потока — reactive имеет встроенные механизмы. Инфраструктурный код серверов, framework уровня где reactive стек уже используется и переход невыгоден.

Для новых проектов выбор смещается в сторону виртуальных threads по умолчанию, reactive только когда есть конкретная техническая необходимость. Для существующих проектов миграция с reactive на виртуальные threads возможна но не срочна — работающий reactive код может продолжать работать без переписывания. Смешивание в одном приложении практикуемо — некоторые части могут использовать реактивный подход, другие blocking с виртуальными threads.

## Ограничения и подводные камни

Помимо pinning есть другие моменты требующие внимания. Виртуальные threads не подходят для CPU intensive задач. Их преимущество в дешёвом переключении при I/O ожиданиях. Для чисто вычислительной работы количество carrier threads равное CPU cores остаётся пределом — миллион virtual threads делающих расчёты в цикле не даёт никакого преимущества над несколькими platform threads.

Дебаггинг миллиона виртуальных threads может быть сложным. Стандартные thread dumps становятся огромными и неинформативными. Инструменты профилирования должны быть адаптированы для нового мира. JFR и другие инструменты observability постепенно улучшают поддержку виртуальных threads, но некоторая скачка кривой обучения неизбежна.

Некоторые библиотеки могут иметь неявные предположения о конечности количества threads. Кэши размером с количество threads, специфические оптимизации предполагающие ограниченный concurrency, определённые patterns могут ломаться при переходе на виртуальные threads. Тщательное тестирование под нагрузкой обязательно перед продакшн разворачиванием.

Виртуальные threads изменяют динамику garbage collection. Больше threads означает больше объектов connected к stack, потенциально более длительные GC паузы. Современные GC вроде ZGC и Shenandoah спроектированы работать с большим количеством threads, но старые GC могут показывать деградацию. Тестирование производительности с новой моделью необходимо.

## Практическое применение в КНП

В контексте КНП виртуальные threads наиболее применимы к tax-rep и АРМ модулям на Java 21. Эти сервисы обрабатывают формы налоговой отчётности, много интеграционных вызовов через SOAP шину, обращений к базе данных, отправку сообщений в RabbitMQ. Классический I/O bound workload который идеально подходит для виртуальных threads.

Активация через spring.threads.virtual.enabled в Spring Boot 3.2 и выше делается одной строкой в application.yml. Все HTTP запросы автоматически обрабатываются в виртуальных threads. Никаких изменений в код контроллеров и сервисов. Требуется только протестировать под нагрузкой чтобы убедиться в отсутствии проблем pinning.

Компоненты остающиеся на Java 11 — gateway на Zuul базе, некоторые legacy модули не получат виртуальные threads пока не мигрируют. Планирование миграции этих компонентов включает оценку выгоды от виртуальных threads как одного из мотивирующих факторов.

Специфические use case вроде обработки массовых уведомлений через ScheduledJobs могут значительно выиграть от параллелизации через виртуальные threads. Задача обработки миллионов уведомлений где раньше нужна была сложная координация thread pool теперь может быть выражена простым циклом создающим virtual thread на каждое уведомление.

Consumers RabbitMQ могут быть настроены на виртуальные threads. Каждое входящее сообщение обрабатывается в отдельном virtual thread, никаких ограничений на concurrency со стороны consumer framework. Ограничение переносится на throughput RabbitMQ и downstream сервисы что обычно и является правильным bottleneck.

## Итоги

Виртуальные threads Project Loom радикально меняют подход к concurrent Java программированию. Классическая модель thread per request становится масштабируемой до сотен тысяч и миллионов одновременных запросов на скромном железе. Разработчики продолжают писать привычный синхронный blocking код но получают производительность которая раньше требовала сложности reactive стека.

JVM управляет виртуальными threads поверх ограниченного количества carrier threads — обычно равного количеству CPU cores. Блокирующие I/O операции автоматически освобождают carrier для других виртуальных threads. Планирование делает JVM а не операционная система, что позволяет более эффективные алгоритмы.

Активация в Spring Boot 3.2 плюс через одну настройку. Существующий код обычно работает без изменений. Виртуальные threads совместимы с ThreadLocal, synchronized, CompletableFuture и всем существующим API. Проблема pinning из-за synchronized и JNI требует внимания но решается заменой на ReentrantLock или другие concurrent примитивы.

Structured Concurrency упрощает параллельные операции через StructuredTaskScope. ScopedValue заменяет ThreadLocal более безопасной immutable альтернативой. Обе фичи в preview в Java 21 и будут стабилизированы в последующих версиях.

Виртуальные threads не отменяют reactive но смещают выбор по умолчанию для типичных enterprise приложений. Reactive остаётся релевантным для streaming, backpressure сценариев, инфраструктурного кода. Смешивание в одном приложении возможно.

Практические ограничения — виртуальные threads не подходят для CPU intensive задач, connection pools остаются bottleneck, дебаггинг миллиона threads требует новых подходов, тщательное тестирование под нагрузкой обязательно перед продакшн разворачиванием.

Дальше рассматривается инфраструктура передачи сообщений — RabbitMQ и модель AMQP которые составляют критическую часть архитектуры КНП. Понимание как работают exchange, queue, binding, publisher confirms, consumer prefetch помогает правильно проектировать надёжные системы обмена сообщениями.
