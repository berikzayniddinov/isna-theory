# 114. Strangler Fig Pattern: миграция монолита без big bang

## Зачем это знать

У тебя есть большой legacy-монолит. Написан лет 10-15 назад, миллион строк кода, десятки таблиц с спутанными foreign keys, бизнес-логика размазана между stored procedures в БД и Java-кодом, тесты покрывают 20% в лучшем случае. Работает — но каждое изменение занимает недели, добавление нового разработчика в команду — месяцы онбординга, любой релиз это risky event. Все говорят «надо переписать на микросервисы».

Первая мысль — **big bang rewrite**. Забить на монолит, заморозить фичи, команда параллельно пишет новую систему с нуля на модерн стеке, через N месяцев переключаемся. Через N месяцев обычно оказывается что: (1) новая система не готова, ещё N месяцев; (2) бизнес-требования за это время изменились, старую систему всё равно пришлось патчить, теперь два кода вместо одного; (3) новая система не покрывает всё что делала старая (edge cases, скрытые правила, интеграции о которых никто не знал); (4) переключение всё равно big bang и всё равно провал.

Классика IT: Netscape полностью переписал браузер в 90-х, потерял 4 года и рыночную долю. Twitter в 2013 переписывал платформу и практически положил сервис. Netflix — 7 лет разбирал монолит по кусочкам, не переписывая с нуля. Именно последний подход — **Strangler Fig Pattern**, сформулированный Мартином Фаулером в 2004.

Метафора из природы: strangler fig — вид фикусов Юго-Восточной Азии. Семя прорастает на ветке дерева-хозяина, спускает воздушные корни вниз к земле, постепенно оплетает ствол хозяина. Хозяин продолжает жить, фикус растёт. Через 20-50 лет фикус полностью окружает и «удушает» хозяина, тот отмирает, остаётся полая структура из корней фикуса — самостоятельное дерево. Ключевое: **никакого big bang**. Оба дерева живут параллельно, годами, старое постепенно уступает место новому.

Аналогия в софте: новая система растёт **рядом** со старой. Функциональность **постепенно** переносится (по одному use case за раз). Пользователи не замечают миграции — старые пути работают, новые появляются. Через месяцы-годы старая система пуста и удаляется. **Никакого freeze**, **никакого big bang**, **rollback возможен на каждом шаге**.

Разница между «мы делаем миграцию» и «мы понимаем strangler fig» — в способности отвечать: где именно проходит граница между старым и новым **сейчас**; как переключается конкретный запрос; что случится с данными во время dual-write периода; как сделать rollback если новая функциональность сломалась; сколько ждать до удаления старого кода; какие метрики показывают что миграция реально движется, а не имитируется. Без этих ответов «миграция на микросервисы» превращается в вечный проект с расходами на две системы одновременно и никогда не завершается.

Разберём: почему big bang rewrite обычно провал. Метафору strangler fig и её ключевые свойства. Три уровня внедрения — HTTP routing, event interception, database-level. Пошаговый процесс — identify seam, build parallel, route, cutover, delete. Coexistence period — как работать с dual writes и dual reads. Migration стратегии для данных. Тестирование во время миграции. Роль Anti-Corruption Layer. Rollback plans на каждом шаге. Метрики успеха миграции. Типовые ловушки и как их обходить. Альтернативы (big bang, side-by-side) и почему обычно хуже. Реальные примеры (Netflix, Amazon).

Anti-Corruption Layer детальнее — в 113. Микросервисная декомпозиция — 49. Здесь фокус конкретно на strangler fig как процесс миграции.

## Почему big bang rewrite почти всегда провал

Прежде чем разбирать strangler fig, надо понять почему альтернативы плохи. **Big bang rewrite** — переписать с нуля, потом заменить старое разом.

Причины провалов (обычно все сразу):

**Underestimation of complexity**. Старая система накопила знания за годы — edge cases, регуляторные требования, интеграции с partner'ами о которых уже никто не помнит, специальная логика для конкретных клиентов. При «переписывании» команда видит только явную функциональность, скрытое — обнаруживается уже в проде. Классика: система работает, новая — почти работает, но раз в тысячу транзакций что-то падает. Клиенты жалуются. Приходится копаться в старом коде чтобы понять что там реально делалось.

**Moving target**. Пока команда N месяцев пишет новую систему, бизнес не стоит. Требования меняются, регулятор выпускает новые правила, конкуренты добавляют фичи. Старая система патчится, новая ещё не готова. К моменту готовности новая уже отстаёт от старой, приходится добавлять «недостающее». Разрыв никогда не закрывается.

**All-or-nothing switch**. День X — переключение. Что-то ломается — миллионы клиентов affected. Rollback возможен только полный (обратно на старую). Стресс переключения парализует команду, все боятся кнопки «включить».

**Team burnout**. N месяцев без нормальных релизов, только рефакторинг. Мотивация падает, senior engineers уходят («хочу писать код, а не переписывать»). К моменту big bang в команде остаются те кто не смог найти другую работу.

**Ноль validation в проде до launch**. Новая система работает в изоляции — тесты, staging, но реальный prod-нагрузку не видит до самого дня X. Скалирование не проверено. Странные production edge cases не тестировались.

**Реальные кейсы провалов**:
- **Netscape 4→5** (1997-2003). Полный переписывание браузера. 4 года разработки, потеря 90% рыночной доли. К моменту релиза Firefox 1.0 Internet Explorer уже доминировал.
- **Chrysler Comprehensive Compensation** — известный провал extreme programming, полное переписывание payroll system, отменено после 4 лет.

Всё это подтолкнуло индустрию к incremental подходам. Strangler fig — самый цитируемый и практикуемый.

## Метафора и ключевые свойства

Strangler fig как метафора имеет четыре свойства, которые обязательно должны сохраняться в реализации:

**Coexistence**. Старое и новое живут одновременно. Не «сначала одно, потом другое», а параллельно на всё время миграции. Обычно годы, не месяцы.

**Incremental replacement**. Замена по одному use case за раз. Начинаешь с самого простого и низкорискового. Каждый шаг маленький, независимый, тестируемый.

**Reversible steps**. Каждый шаг можно откатить. Переключил один endpoint на новую систему, сломалось — переключаешь обратно. Не нужен полный откат всей миграции.

**Zero user-visible disruption**. Пользователь не видит миграции. URL те же, поведение то же (кроме улучшений). API contracts сохраняются. Клиенты не должны переписывать код.

Что **не** является strangler fig:

- «Big bang через полгода» — это big bang, только позже. Coexistence нет.
- «Держим legacy как read-only» — не удушение, а мумификация. Legacy деградирует, никто его не понимает, но фичи там всё равно требуются.
- «Новые фичи в новом сервисе, старые в старом» — не миграция. Старое никогда не уменьшается, только растёт баланс.
- «Переписываем один сервис в квартал, независимо» — если сервисы независимы, миграция не нужна. Strangler — про переплетённый монолит.

## Уровни внедрения: где проходит граница

Ключевой вопрос при внедрении — **где происходит переключение между старым и новым**. Три основных уровня, каждый со своими trade-off'ами.

### Уровень 1: HTTP-роутинг через facade

Самый распространённый и понятный вариант. Ставим reverse proxy (nginx, Envoy, API Gateway) перед монолитом. Все запросы идут через proxy. Proxy знает какие routes ведут в монолит, какие — в новые сервисы. Постепенно переключает routes.

```
До миграции:
Клиент → [Monolith]

Начало миграции:
Клиент → [Proxy] → [Monolith]  (все routes идут в монолит)

Первый шаг:
Клиент → [Proxy] → /users/*     → [UserService микросервис]
                 → всё остальное → [Monolith]

Через N шагов:
Клиент → [Proxy] → /users/*    → [UserService]
                 → /orders/*   → [OrderService]
                 → /payments/* → [PaymentService]
                 → всё остальное → [Monolith]

Конец миграции:
Клиент → [Proxy] → всё → [микросервисы]
[Monolith] удалён.
```

**Преимущества**:
- Прозрачно для клиентов. URL те же, поведение то же. Клиент даже не знает что часть запросов идёт в новую систему.
- Гранулярность на уровне endpoint. Можно переключить один endpoint, оставить остальные на монолите.
- Легко откатить — изменение конфига proxy, deploy, откат за секунды.
- Работает для любых протоколов HTTP-based.

**Ограничения**:
- Работает только для HTTP-endpoint. Если монолит имеет фоновые задачи, batch jobs, integrations по другим протоколам — их нужно мигрировать отдельно.
- Не решает проблему shared database. Новый сервис и монолит могут читать одни и те же таблицы.

**Технологии**: nginx, Envoy, Spring Cloud Gateway, Kong, AWS API Gateway. В КНП — nginx-based gateway (`isnaknpgateway`).

**Настройка nginx для strangler**:

```nginx
upstream monolith { server monolith.internal:8080; }
upstream user_service { server user-service.internal:8080; }
upstream order_service { server order-service.internal:8080; }

server {
    listen 80;
    
    # Новые сервисы — специфичные пути
    location /api/v1/users/ {
        proxy_pass http://user_service;
    }
    
    location /api/v1/orders/ {
        proxy_pass http://order_service;
    }
    
    # Всё остальное — в монолит
    location / {
        proxy_pass http://monolith;
    }
}
```

При добавлении нового сервиса — добавить location, ничего в монолите не меняется. При проблеме — комментируешь location, всё возвращается в монолит.

### Уровень 2: event interception

Работает когда монолит генерирует события (в БД, message queue, файлы). Новая система подписывается на те же события, обрабатывает параллельно с монолитом. Постепенно монолит перестаёт обрабатывать то что уже делает новая система.

```
До миграции:
Событие → [Monolith] обрабатывает → БД, side effects

Начало:
Событие → [Monolith] обрабатывает
       → [NewService] тоже подписан, но пока shadow (сравнивает, не действует)

Далее:
Событие → [Monolith] обрабатывает часть кейсов (например, только legacy customers)
       → [NewService] обрабатывает другую часть (новые customers)

Конец:
Событие → [NewService] всё обрабатывает
[Monolith] удалён из flow.
```

**Преимущества**:
- Хорошо работает для event-driven систем.
- Shadow mode — новая система работает без риска, только сравнивает свои ответы с монолитом.
- Постепенное переключение по критерию (тип клиента, регион, категория данных).

**Ограничения**:
- Требует чтобы монолит уже был event-driven или поддавался этому.
- Дубли обработки требуют идемпотентности.
- Сложнее откатить чем HTTP routing.

**Типовой use case**: миграция обработки заказов. Монолит публикует `OrderPlaced` в RabbitMQ. Новый сервис подписан на тот же топик. Сначала shadow — новый сервис обрабатывает, но результат не отправляется в БД, только сравнивается с тем что сделал монолит. Через месяц — новый сервис берёт на себя определённые типы заказов, монолит игнорирует те же. Через полгода — новый сервис делает всё, обработчик заказов из монолита удалён.

### Уровень 3: database-level (Branch by Abstraction)

Самый сложный уровень — когда данные в общей БД. Новая система и монолит **читают и пишут одни таблицы**. Миграция сложнее потому что нельзя просто переключить один сервис — данные общие.

**Стратегия dual writes / dual reads**:

**Фаза 1: dual write (новый сервис только пишет)**. Монолит остаётся source of truth. Новый сервис появляется, пишет в новые таблицы (или в те же, с дополнительной колонкой отметки). Читатели всё ещё из старых таблиц (монолит).

**Фаза 2: shadow read (новый сервис читает, сравнивает)**. Клиентский код при запросе идёт в монолит (получает данные из старой схемы), одновременно в новый сервис (получает из новой). Сравнивает — если равны, всё хорошо. Если разошлись — исследовать почему, chalk up ошибки миграции.

**Фаза 3: dual read (клиент выбирает источник)**. Feature flag определяет откуда читать: 5% пользователей из нового, 95% из монолита. Постепенно увеличиваем процент. Мониторим latency, errors, business metrics.

**Фаза 4: cutover**. 100% чтения из нового. Монолит только пишет (для safety). Ждём период (недели-месяцы) чтобы точно быть уверенным.

**Фаза 5: writes off в монолите**. Монолит больше не пишет. Только новый сервис.

**Фаза 6: cleanup**. Удаляем старые таблицы, старый код монолита.

Каждая фаза длится недели или месяцы. Полный процесс — год-два. Но каждый шаг реверсируем, и в любой момент можно вернуться в предыдущую фазу.

## Пошаговый процесс миграции

Идеальный процесс миграции — семь шагов, повторяемых для каждой функциональности.

### Шаг 1: identify the seam

Найти **seam** — линию разреза внутри монолита. Модуль, который можно относительно чисто выделить в отдельный сервис. Хороший seam:

- **Bounded context** (в терминах DDD, файл 113). Одна предметная область с чёткими границами.
- **Мало зависимостей с остальным кодом**. Импорты в модуль и из модуля можно посчитать за час.
- **Собственные таблицы или чёткая часть общих**.
- **Стабильные интерфейсы** — API модуля не менялся часто в последний год.

Плохой seam:
- Модуль связан со всем через shared utility classes.
- Куча запросов JOIN'ит его таблицы со всеми остальными.
- Интерфейсы модуля меняются каждый месяц.

Начинать миграцию нужно с **самого лёгкого** seam'а. Не самого важного, не самого желаемого — самого лёгкого. Первый успешный опыт даст команде понимание процесса и уверенность.

### Шаг 2: introduce facade (seam interface)

Даже если пока не выделили сервис — ввести **абстракцию** для модуля внутри монолита. Клиентский код обращается только через facade interface, не к реализации:

```java
// Было: клиенты напрямую вызывают UserManager, OrderProcessor и т.д.
public class OrderController {
    @Autowired UserManager userMgr;
    @Autowired OrderProcessor orderProc;
    
    public void placeOrder(...) {
        User u = userMgr.getUser(userId);   // прямая зависимость
        orderProc.process(...);
    }
}

// Стало: клиенты через интерфейс, реализация — legacy или new
public interface UserService {
    User getUser(Long id);
}

@Component("legacyUserService")
public class LegacyUserServiceAdapter implements UserService {
    @Autowired UserManager legacyManager;
    public User getUser(Long id) { return legacyManager.getUser(id); }
}

// Через год будет:
@Component("newUserService")
public class NewUserServiceClient implements UserService {
    @Autowired UserServiceGrpcClient client;
    public User getUser(Long id) { return client.getUser(id); }
}
```

Facade — это Branch by Abstraction. Пока обе реализации внутри монолита, но клиентский код уже готов к замене.

### Шаг 3: build parallel implementation

Пишем новую реализацию. Отдельный сервис (микросервис) или отдельный модуль внутри монолита — зависит от масштаба. Тесты, интеграция, deployment infrastructure.

**Ключевое правило**: новая реализация должна поддерживать **тот же контракт** что и старая. Клиентский код не должен знать разницы. Если сохранить контракт невозможно (реально нужны breaking changes) — это отдельная задача **до** миграции, не во время.

### Шаг 4: shadow mode

Прежде чем реально переключать трафик — прогнать новую реализацию в shadow mode. Клиентский код зовёт обе реализации (старую и новую), возвращает результат от старой (unchanged behavior), сравнивает с новой (логирует расхождения).

```java
public class DualUserService implements UserService {
    private final UserService legacy;
    private final UserService modern;
    private final ComparisonLogger logger;
    
    public User getUser(Long id) {
        User legacyResult = legacy.getUser(id);
        
        try {
            User modernResult = modern.getUser(id);
            if (!Objects.equals(legacyResult, modernResult)) {
                logger.logMismatch(id, legacyResult, modernResult);
            }
        } catch (Exception e) {
            logger.logError(id, e);   // но не пробрасываем!
        }
        
        return legacyResult;   // старая версия — source of truth
    }
}
```

Shadow mode — критический шаг. Выясняются реальные различия между новой и старой имплементацией на **реальных данных, реальном трафике**. Часто обнаруживается: старая система имела undocumented edge case, новая обрабатывает по-другому. Или новая быстрее в 90% случаев, но 10% timeout'ит. Или изменилось subtle поведение при null-значениях.

Shadow mode работает недели. Собирается статистика расхождений. Все mismatches разбираются — либо баги в новой имплементации, либо намеренные изменения (тогда документируются).

### Шаг 5: gradual cutover

Когда shadow mode показывает мало mismatches — начинается gradual cutover через feature flag:

```java
public class RoutedUserService implements UserService {
    private final UserService legacy;
    private final UserService modern;
    private final FeatureFlags flags;
    
    public User getUser(Long id) {
        if (flags.isEnabled("use-new-user-service", id)) {
            try {
                return modern.getUser(id);
            } catch (Exception e) {
                // Автоматический fallback на старую
                metrics.incrementFallback();
                return legacy.getUser(id);
            }
        }
        return legacy.getUser(id);
    }
}
```

Процент переключения растёт постепенно: 1% → 5% → 20% → 50% → 100%. На каждом шаге мониторим error rate, latency, business metrics. Если что-то пошло не так — уменьшаем процент.

Feature flag может быть по user_id (для sticky behavior одного пользователя), по region, по type of request. Позволяет тонкую настройку когорт для теста.

### Шаг 6: monolith stops writing

100% чтения из нового. Но записи всё ещё дублируются (`dual write` — и монолит, и новый пишут одни и те же данные, для safety). Через safe period (обычно недели-месяцы) выключаем запись в монолите.

Здесь ключевое — **точка невозврата**. После этого шага rollback становится сложным (данные пишутся только в новую систему, откат требует миграции обратно). До этого шага rollback тривиальный.

### Шаг 7: delete legacy code

Через месяцы после последнего использования — удаляем legacy код монолита. Не сразу — оставить как safety net на случай если обнаружится редкий кейс использования.

Удаление — важно. Иначе legacy код накапливается, никто не понимает что там уже мёртво а что живо, миграция никогда «не заканчивается».

Индикаторы что можно удалять: 0 вызовов в логах за 3 месяца; 0 ссылок в кодовой базе после `git grep`; тесты legacy кода не запускаются никем.

## Coexistence period: dual writes и dual reads

Самая сложная часть strangler fig — период когда старое и новое работают вместе. Обычно годы. Нужно управлять этим состоянием.

**Dual write** — данные пишутся в обе системы одновременно. Проблемы:

**Consistency**. Что если запись в старую систему прошла, а в новую упала? Данные разошлись. Варианты обработки:
- Rollback в старой если новая упала — но старая часто не поддерживает откат отдельной операции.
- Retry новую до успеха — но что если она нескоро восстановится?
- Логировать в failed-writes queue для manual reconciliation — распространённое решение.

**Performance**. Каждая запись теперь делает две операции. Latency растёт, throughput падает. Иногда критично.

**Order of writes**. Пишем сначала в старую или сначала в новую? Обычно сначала в старую (она источник истины пока не закончилась миграция), потом в новую. При крашe между — новая пропустит запись, надо compensating action.

**Dual read** — чтение из обеих систем, comparison. Проблемы:

**Latency = максимум из двух**. Клиент ждёт пока обе системы ответят. Обычно решается async — читаем из старой синхронно (это возвращаем клиенту), из новой асинхронно для сравнения.

**Sampling**. Не обязательно сравнивать 100% запросов. 1% выборка часто достаточна для обнаружения проблем, без 2x нагрузки.

**Comparison logic**. Как определить что результаты «одинаковые»? Ordered lists vs unordered? Precision numbers? Timestamps? Обычно нужны custom equality правила для каждого API.

## Migration стратегии для данных

Отдельная сложная тема — как переносить существующие данные. Три основных подхода:

**Bulk migration up-front**. Копируем все данные из старой БД в новую до начала dual writes. Дальше поддерживаем sync через events или dual writes. Плюс: новая БД сразу готова. Минус: миграция может занять дни для больших данных, во время миграции старая продолжает меняться — надо catch-up.

**On-demand migration**. Данные переносятся при первом обращении. Клиент запросил user_id=42 — сначала проверяем в новой БД, если нет — читаем из старой, копируем в новую, возвращаем. Плюс: не нужен bulk migrate. Минус: сложнее логика, latency при первом обращении, «холодные» данные никогда не мигрируют.

**CDC-based migration** (Change Data Capture). Debezium читает WAL старой БД, стримит изменения в Kafka, новая БД subscribes и применяет. Плюс: real-time sync, никакого dual write code. Минус: инфраструктура сложнее (Debezium + Kafka Connect).

Часто комбинация: bulk migration за weekend maintenance, потом CDC для incremental sync, потом cutover.

## Anti-Corruption Layer: защита нового домена

В процессе миграции новая система должна общаться с legacy (пока legacy жив). Прямая интеграция ведёт к тому что legacy-модель просачивается в новый код — весь смысл миграции теряется.

**Anti-Corruption Layer (ACL)** — слой перевода между legacy и new. Legacy-концепции остаются в ACL, за границей ACL — чистая новая модель.

Пример из tax system:

```java
// Legacy: старая проприетарная структура ФНО
class LegacyTaxDeclaration {
    long declId;             // primary key
    String taxpCode;         // ИИН/БИН налогоплательщика
    String frmCode;          // код ФНО (100, 200, 328, etc)
    String stCode;           // status code, специфичный legacy словарь
    Map<String, Object> metadata;  // untyped bag of properties
    // ... 60 других колонок
}

// Наш domain (новая система):
class TaxDeclaration {
    DeclarationId id;
    TaxpayerId taxpayerId;
    FnoType fnoType;
    DeclarationStatus status;
    Map<String, DeclarationField> fields;
}

// ACL — переводчик:
class LegacyTaxDeclarationAdapter {
    public TaxDeclaration fromLegacy(LegacyTaxDeclaration legacy) {
        return new TaxDeclaration(
            new DeclarationId(legacy.declId),
            new TaxpayerId(legacy.taxpCode),
            FnoType.valueOf("FNO_" + legacy.frmCode),
            mapLegacyStatus(legacy.stCode),
            extractFields(legacy.metadata)
        );
    }
    
    private DeclarationStatus mapLegacyStatus(String legacyCode) {
        return switch (legacyCode) {
            case "N" -> DeclarationStatus.NEW;
            case "P" -> DeclarationStatus.PROCESSED;
            case "A" -> DeclarationStatus.ACCEPTED;
            case "R" -> DeclarationStatus.REJECTED;
            default -> throw new IllegalArgumentException("Unknown status: " + legacyCode);
        };
    }
}
```

Клиенты внутри новой системы работают только с `TaxDeclaration`. Все грязные детали legacy — в ACL. Когда legacy умрёт — ACL удаляется, новая система не меняется.

Без ACL: legacy классы (60 колонок, untyped Map, cryptic codes) просачиваются в новый код. Изменения в legacy schema ломают новую систему. Новая модель загрязнена concepts которые не имеют смысла в новом дизайне.

## Rollback plans на каждом шаге

Ключевое свойство strangler fig — reversible steps. Каждый шаг должен иметь план отката.

**Rollback от HTTP routing**. Изменение конфига proxy обратно на монолит. Секунды. Тривиально.

**Rollback от feature flag cutover**. Уменьшить процент на flag'е обратно к нулю. Секунды. Тривиально.

**Rollback от dual write (новая система)**. Если новая система пишет неправильные данные — просто перестать писать (feature flag). Данные в новой становятся stale, но старая — источник истины. Никаких потерь для клиентов.

**Rollback от monolith stops writing** — сложнее. Данные пишутся только в новую. Откат требует репликации данных обратно в старую (например через reverse CDC). Планировать заранее.

**Rollback от legacy code deletion** — требует git revert и redeploy. Возможно, но болезненно.

Правило: **чем дальше по процессу — тем сложнее откат**. Не спешить проходить точки невозврата (шаги 6-7) без уверенности.

## Метрики успеха миграции

Как понять что миграция реально движется, а не имитируется?

**Продуктовые метрики**:

- **Процент трафика на новой системе** — по количеству endpoint'ов или по объёму запросов. Растёт со временем.
- **Процент кода в новой системе** — LOC монолита уменьшается, микросервисов растёт.
- **Процент таблиц с завершённой миграцией** — new-only, no dual write.

**Процессные метрики**:

- **Time to add feature to new area** vs **to legacy area**. Если фича в новой области раскатывается за неделю, а в legacy — за месяц — миграция даёт value.
- **MTTR (Mean Time To Recovery)** для incident. В новой архитектуре обычно ниже (микросервисы изолируют failure).
- **Deployment frequency** в новых сервисах. Обычно кратно выше чем в монолите.

**Anti-metrics** (плохо когда растут):

- **Количество dual-write ошибок** в логах.
- **Расхождения в shadow mode** после месяцев работы (должны падать, не расти).
- **Fallback rate** на старую систему (если много fallback'ов — новая нестабильна).

**Ключевая метрика** — **общее количество open migration items**. Список того что ещё надо мигрировать. Должен монотонно уменьшаться. Если стоит на месте месяцами — миграция застряла, разбираться почему.

## Типовые ловушки и как их обходить

**Ловушка «feature freeze во время миграции»**. Business говорит «пока мигрируем, никаких новых фич». Через полгода: бизнес сломан, требования накопились, команда деморализована. Правило: миграция **не должна** блокировать новые фичи. Новые фичи идут в новую систему по мере готовности seam'ов. Legacy сохраняет status quo.

**Ловушка «переписать 1:1»**. Соблазн скопировать логику монолита без изменений «чтобы точно работало». Итог: получил тот же плохой дизайн в другой технологии. Новая система должна быть лучше по дизайну — иначе зачем миграция? Правило: во время миграции переосмысливаем модель, не только переписываем.

**Ловушка «не сделали ACL»**. Legacy-структуры просачиваются в новую систему. Через год новая система выглядит как legacy на новом стеке. Правило: ACL с самого начала, всегда.

**Ловушка «не оценили сложность dual write»**. Кажется просто — писать в обе БД. На проде оказывается: consistency проблемы, latency растёт, куча edge cases при failure. Правило: dual write не тривиально. Планировать failure modes до включения.

**Ловушка «слишком большой первый seam»**. Стартовали с самого важного модуля — payments. Сложно, много зависимостей, миграция год не завершается. Команда потеряла мотивацию. Правило: первый seam — самый **лёгкий**, не самый важный.

**Ловушка «не удаляем legacy»**. Мигрировали функциональность, но legacy код остался «на всякий случай». Через 2 года: 30% кода мёртво, никто не знает что живо. Правило: удаляем через 3-6 месяцев после cutover.

**Ловушка «команда не хочет touch legacy»**. Все хотят писать новое, никто не хочет разбираться в старом. Legacy деградирует, миграция стоит. Правило: миграция — общая ответственность команды, ротация людей между legacy и new.

**Ловушка «оценка времени в терминах разработки»**. «Мигрируем модуль за 2 недели». На деле: 2 недели написать, месяц shadow mode, месяц gradual cutover, 6 месяцев waiting to remove legacy. Реальная миграция одного модуля — квартал-полгода. Планировать соответственно.

## Реальные примеры

**Amazon (2000-е)**. Классика. Изначально монолит на Perl. К 2001 году — «two-pizza teams» с независимыми сервисами. Миграция шла через strangler pattern: постепенное выделение сервисов из монолита. Каждый сервис делает одну вещь. Amazon сейчас — тысячи микросервисов, но начиналось всё именно с постепенного удушения монолита.

**Netflix (2008-2015)**. Миграция из monolithic Java приложения на AWS microservices. 7 лет, около 700 микросервисов к концу. Ключевое: не переписывали монолит с нуля, а **постепенно выделяли сервисы**. К концу монолит стал очень тонким, потом удалён.

**Shopify (2016-2020)**. Модуляризация Ruby on Rails монолита. Внутри монолита ввели чёткие boundaries между модулями (packwerk gem enforces boundary rules). Часть модулей выделили в отдельные сервисы, часть осталась в монолите с чёткими интерфейсами. Не полная миграция на микросервисы, а **modular monolith** — тоже вариант.

**GitHub (2020-2023)**. Миграция части функциональности из main Rails монолита на микросервисы. Использовали GraphQL federation для composability. Постепенный процесс.

**Общее**: годы миграции, никакого big bang, gradual extraction. Даже FAANG не решают миграцию за 6 месяцев.

## Альтернативы strangler fig

**Big bang rewrite**. Разобрано в начале — обычно провал. Оправдан только если legacy настолько плох что incremental невозможен (например, legacy на непонятном сейчас языке без документации).

**Side-by-side**. Пишем новую систему полностью параллельно, оставляем legacy жить. Никакой миграции — два продукта. Работает если можно разделить пользователей (legacy — enterprise клиенты, new — SMB). Не работает если пользователи те же.

**Modular monolith**. Не переходим на микросервисы вовсе. Улучшаем структуру монолита — bounded contexts, чёткие module boundaries (Java modules, package private), внутренние SPI. Часто **правильный** ответ вместо микросервисов — команда меньше 30 человек, домен не требует independent scaling. Shopify так делает.

**Backend for Frontend миграция**. Оставляем legacy как есть, но перед ним ставим новый BFF layer. UI работает с BFF, BFF частично проксирует в legacy, частично обрабатывает сам. Позволяет улучшить UX без изменений в legacy. Ограничено — не решает проблему легаси на бэке.

Ключевой вопрос — **действительно ли нужны микросервисы**. Часто «нам нужны микросервисы» — карго-культ, не техническая необходимость. Модерный modular monolith часто лучше для small/medium команд.

## Заключение

**Big bang rewrite** обычно провал: underestimation, moving target, all-or-nothing switch, team burnout, zero prod validation. Netscape, Chrysler, Twitter — известные примеры катастроф.

**Strangler Fig Pattern** — incremental миграция, при которой старое и новое живут параллельно годами, функциональность переносится по одной, каждый шаг реверсируем, пользователи не замечают.

**Ключевые свойства**: coexistence (годы), incremental replacement (по одному use case), reversible steps (rollback на каждом шаге), zero user-visible disruption.

**Три уровня внедрения**:
- **HTTP routing через facade** (nginx, Envoy, Gateway) — самый распространённый, гранулярность по endpoint, тривиальный rollback.
- **Event interception** — для event-driven систем, shadow mode, постепенное переключение.
- **Database-level (Branch by Abstraction)** — самый сложный, dual write / dual read / cutover.

**Пошаговый процесс**: identify seam → introduce facade → build parallel → shadow mode → gradual cutover через feature flag → monolith stops writing → delete legacy. Каждый шаг длится недели-месяцы.

**Coexistence period** — dual writes с consistency проблемами (failed-writes queue для reconciliation), dual reads с sampling (1% для сравнения), performance overhead, порядок записей.

**Migration стратегии для данных**: bulk migration up-front + CDC для incremental sync + weekend cutover — часто комбинация.

**Anti-Corruption Layer** обязателен. Legacy-концепции только внутри ACL, чистая новая модель за границей. Иначе legacy просачивается в новый код и весь смысл миграции теряется.

**Rollback plans**: HTTP routing — секунды, feature flag — секунды, dual write — feature flag off (данные stale но безопасно), monolith stops writing — сложнее (нужен reverse sync), legacy code deletion — git revert. Не спешить к точкам невозврата.

**Метрики успеха**: процент трафика на новой системе (растёт), количество open migration items (уменьшается), MTTR (снижается), deployment frequency (растёт). Anti-metrics: dual-write ошибки, shadow mode mismatches после месяцев, fallback rate.

**Типовые ловушки**: feature freeze во время миграции (не блокировать бизнес); переписать 1:1 (переосмысливать дизайн); отсутствие ACL (легаси просачивается); недооценка dual write сложности; слишком большой первый seam (начинать с лёгкого); не удаляем legacy (мёртвый код накапливается); недооценка времени (реально квартал-полгода на модуль).

**Реальные примеры**: Amazon (early 2000s), Netflix (7 лет 2008-2015), Shopify modular monolith, GitHub GraphQL federation. Даже FAANG не решают миграцию за 6 месяцев.

**Альтернативы**: big bang (обычно провал), side-by-side (только для separable audiences), **modular monolith** (часто правильный ответ вместо микросервисов для small/medium teams), BFF migration (косметика без backend changes).

**Ключевой вопрос**: действительно ли нужны микросервисы. Modular monolith часто лучше для команд <30 человек. Микросервисы стоят операционной сложности только когда есть реальные независимые scaling / deployment / team boundaries.

Anti-Corruption Layer детальнее — в 113. Микросервисная декомпозиция как отдельно — 49. Saga для распределённых транзакций — 50. Outbox для reliable messaging — 51. Здесь была глубина по strangler fig как процесс миграции: почему нельзя big bang, три уровня внедрения, пошаговый процесс, coexistence управление, rollback планы, метрики, ловушки, реальные примеры.
