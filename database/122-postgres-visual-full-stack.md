# 122. PostgreSQL визуально: полный путь от запроса до диска

## Зачем это знать

Файлы 87, 88, 107, 116 разбирают внутренности PostgreSQL текстово. Здесь — визуализация. Все диаграммы связаны между собой: сверху вниз идёт путь запроса от приложения до физических байтов на диске. Разные секции — разные уровни абстракции того же самого.

Читать сверху вниз чтобы увидеть картину целиком. Или сразу перейти к нужному уровню — каждая диаграмма самодостаточна.

**Времена операций** для каждого уровня:
- **Cache hit в shared_buffers**: ~1 микросекунда (memcpy из RAM).
- **Cache hit в OS page cache**: ~5-10 микросекунд (syscall + memcpy).
- **NVMe SSD read**: ~100 микросекунд (100x медленнее RAM).
- **HDD read**: ~5-10 миллисекунд (10000x медленнее RAM).
- **Network round-trip к БД**: 0.5-2 мс.

Отсюда — cache hit rate 99%+ критичен для performance. Каждый miss дороже в 100 раз.

## Memory Layout: где что живёт в RAM

Сервер БД имеет 16 GB RAM. Разбивка кто сколько потребляет:

```
┌──────────────────────────────────────────────────────────────────┐
│                        Physical RAM: 16 GB                       │
├──────────────────────────────────────────────────────────────────┤
│                                                                  │
│  ┌──────────────────────────────────────────────────────────┐    │
│  │ Shared Buffers: 4 GB (~25% RAM)                          │    │
│  │  ┌────┬────┬────┬────┬────┬────┬────┬────┬────┬────┐     │    │
│  │  │p1  │p2  │p3  │p4  │p5  │... │... │... │... │... │     │    │
│  │  └────┴────┴────┴────┴────┴────┴────┴────┴────┴────┘     │    │
│  │  ~524K буферов по 8 KB                                   │    │
│  │  Shared между всеми backend процессами                   │    │
│  └──────────────────────────────────────────────────────────┘    │
│                                                                  │
│  ┌──────────────────────────────────────────────────────────┐    │
│  │ WAL Buffers: 16 MB                                       │    │

│  └──────────────────────────────────────────────────────────┘    │
│                                                                  │

│  └──────────────────────────────────────────────────────────┘    │
│                                                                  │
│  ┌──────────────────────────────────────────────────────────┐    │
│  │ Other PostgreSQL memory: ~100 MB                         │    │
│  │  - autovacuum workers (~40 MB)                           │    │

│  └──────────────────────────────────────────────────────────┘    │
│                                                                  │
│  ┌──────────────────────────────────────────────────────────┐    │
│  │ OS Page Cache: ~10 GB (использует всё свободное)         │    │
│  │  ┌───┬───┬───┬───┬───┬───┬───┬───┬───┬───┬───┬───┐       │    │
│  │  │   │   │   │   │   │   │   │   │   │   │   │   │       │    │
│  │  └───┴───┴───┴───┴───┴───┴───┴───┴───┴───┴───┴───┘       │    │
│  │  Кэширует те же страницы что shared_buffers +            │    │
│  │  другие файлы. Double buffering.                         │    │
│  └──────────────────────────────────────────────────────────┘    │
│                                                                  │
│  ┌──────────────────────────────────────────────────────────┐    │
│  │ Kernel + system: ~500 MB                                 │    │
│  └──────────────────────────────────────────────────────────┘    │
│                                                                  │
└──────────────────────────────────────────────────────────────────┘

     free -h показывает:
     ─────────────────────────────────────
                    total  used  free  shared  buff/cache  available
     Mem:            16G    5G   500M    4G       10G         11G
     ─────────────────────────────────────
     buff/cache = OS page cache
     shared = shared_buffers (виден как shared)
     available = сколько ещё можно захотеть
```

**Ключевая деталь про Double Buffering**. Страница `page X` файла таблицы может быть **одновременно**:
- В shared_buffers (PostgreSQL кэш).
- В OS page cache (Linux кэш).

Обе занимают RAM. «Тратится» ~25% RAM. Компромисс за простоту (PostgreSQL не хочет использовать direct I/O bypass'ая OS cache — сложно, кроссплатформенно).

## Query lifecycle: путь SELECT'а

Что происходит внутри backend процесса при `SELECT * FROM orders WHERE id = 42`:

```
   Client (JDBC)  
      │
      │ TCP: PostgreSQL wire protocol
      │ "Q" message: "SELECT * FROM orders WHERE id = 42"
      ▼
   ┌──────────────────────────────────────────────────────┐
   │                 Backend Process                       │
   │                                                       │
   │  ┌────────────────────────────────────────────┐       │
   │  │ 1. Parser                                  │       │
   │  │    SQL text → Abstract Syntax Tree (AST)   │       │
   │  │                                            │       │
   │  │    SELECT {                                │       │
   │  │      targets: [ * ]                        │       │
   │  │      from: [ orders ]                      │       │
   │  │      where: {                              │       │
   │  │        op: =, left: id, right: 42          │       │
   │  │      }                                     │       │
   │  │    }                                       │       │
   │  └───────────┬────────────────────────────────┘       │
   │              ▼                                        │
   │  ┌────────────────────────────────────────────┐       │
   │  │ 2. Rewriter                                │       │
   │  │    - раскрытие views                       │       │
   │  │    - применение rules                      │       │
   │  │    - подстановка parameters                │       │
   │  └───────────┬────────────────────────────────┘       │
   │              ▼                                        │
   │  ┌────────────────────────────────────────────┐       │
   │  │ 3. Planner / Optimizer                     │       │
   │  │                                            │       │
   │  │    Читает статистику из pg_statistic       │       │
   │  │    Рассматривает возможные планы:          │       │
   │  │                                            │       │
   │  │    План A: Seq Scan (cost=15000.00)        │       │
   │  │    План B: Index Scan (cost=8.30) ✓       │       │
   │  │                                            │       │
   │  │    Выбирает: Index Scan on orders_pkey     │       │
   │  └───────────┬────────────────────────────────┘       │
   │              ▼                                        │
   │  ┌────────────────────────────────────────────┐       │
   │  │ 4. Executor                                │       │
   │  │                                            │       │
   │  │    IndexScan node:                         │       │
   │  │      - open index orders_pkey              │       │
   │  │      - search key = 42                     │       │
   │  │      - find TID (page 4, item 3)           │       │
   │  │      - fetch tuple from heap               │       │
   │  │      - apply MVCC visibility (xmin/xmax)   │       │
   │  │      - return row                          │       │
   │  └───────────┬────────────────────────────────┘       │
   │              ▼                                        │
   │       Response format (rows)                          │
   │              │                                        │
   └──────────────┼────────────────────────────────────────┘
                  │
                  ▼
           TCP response ("T" + "D" + "C" messages)
                  │
                  ▼
                Client (JDBC получает ResultSet)
```

**Детальный шаг 4 Executor — обращение к shared buffers**:

```
   IndexScan asks BufferManager: "нужна страница X таблицы orders"
      │
      ▼
   BufferManager: check buffer hash table
      │
      ├─── Cache HIT (страница уже в buffers)
      │    │
      │    ▼
      │    Pin buffer (защита от eviction)
      │    Return pointer to 8KB page
      │    
      └─── Cache MISS (страницы нет)
           │
           ▼
           Найти пустой/старый buffer (Clock Sweep eviction)
           │
           ▼
           Если evict'нутый buffer dirty → flush на диск
           │
           ▼
           Read страницы с диска (syscall pread)
           │  ┌────────────────────────────────┐
           │  │ 1. Проверить OS page cache     │
           │  │    ├── HIT → memcpy (быстро)   │
           │  │    └── MISS → real disk read   │
           │  └────────────────────────────────┘
           │
           ▼
           Заполнить buffer
           Pin buffer
           Return pointer
```

## Write path: INSERT / UPDATE до диска

Разберём `INSERT INTO orders (id, name) VALUES (42, 'test')` полностью:

```
   Client: INSERT ... COMMIT
      │
      ▼
   ┌──────────────────────────────────────────────────────┐
   │           BACKEND PROCESS                             │
   │                                                       │
   │  ┌────────────────────────────────────────┐          │
   │  │ 1. Parser + Planner (простой INSERT)   │          │
   │  └───────────┬────────────────────────────┘          │
   │              ▼                                        │
   │  ┌────────────────────────────────────────┐          │
   │  │ 2. Executor: ModifyTable node          │          │
   │  │    - Найти страницу с свободным местом │          │
   │  │      (через Free Space Map)            │          │
   │  │    - Записать tuple в heap page        │          │
   │  │      (page становится dirty)           │          │
   │  │    - Обновить индексы                  │          │
   │  │    - Записать WAL запись               │          │
   │  └───────────┬────────────────────────────┘          │
   │              ▼                                        │
   │  ┌────────────────────────────────────────┐          │
   │  │ 3. COMMIT                              │          │
   │  │    - Записать COMMIT WAL entry         │          │
   │  │    - **FSYNC WAL** ← вот здесь ждём диск │       │
   │  │    - Ответить клиенту "OK"             │          │
   │  └────────────────────────────────────────┘          │
   └──────────────────────────────────────────────────────┘
             │
             ▼
   Изменения в памяти:
   ┌──────────────────────────────────────────────────────┐
   │  Shared Buffers                                       │
   │  ┌──────────────────────────────────────┐             │
   │  │ Page 4 (orders):                     │             │
   │  │  Header (LSN обновлён)               │             │
   │  │  Line Pointers: [old..., new_ptr]    │             │
   │  │  Free Space (уменьшилось)            │             │
   │  │  Tuple 4: NEW row (xmin=our_txid)  ✓ │             │
   │  │  Tuple 3, 2, 1: old rows             │             │
   │  │                                      │             │
   │  │  Флаг: DIRTY ⚠                       │             │
   │  └──────────────────────────────────────┘             │
   │                                                       │
   │  Index buffer:                                        │
   │  ┌──────────────────────────────────────┐             │
   │  │ B-tree index orders_pkey:            │             │
   │  │  Добавлена запись (42 → page 4, item 4) │           │
   │  │  DIRTY ⚠                             │             │
   │  └──────────────────────────────────────┘             │
   └──────────────────────────────────────────────────────┘

   Изменения в WAL:
   ┌──────────────────────────────────────────────────────┐
   │  WAL Buffers (in RAM)                                 │
   │  ┌──────────────────────────────────────┐             │
   │  │ LSN 0/1234567:                       │             │
   │  │  XLOG_HEAP_INSERT: table=orders,     │             │
   │  │    tuple=[42, 'test', xmin=our_txid] │             │
   │  │                                      │             │
   │  │ LSN 0/1234580:                       │             │
   │  │  XLOG_BTREE_INSERT: index=orders_pkey│             │
   │  │    key=42 → TID (page 4, item 4)     │             │
   │  │                                      │             │
   │  │ LSN 0/1234600:                       │             │
   │  │  XLOG_XACT_COMMIT: our_txid          │             │
   │  └──────┬───────────────────────────────┘             │
   │         │ FSYNC на COMMIT (обязательно!)              │
   │         ▼                                             │
   └─────────┼─────────────────────────────────────────────┘
             │
             │ WAL сразу пишется на диск
             ▼
   ┌──────────────────────────────────────────────────────┐
   │  DISK: WAL файлы                                     │
   │  /var/lib/postgresql/data/pg_wal/                    │
   │  ┌──────────────────────────────────────┐            │
   │  │ 000000010000000000000001 (16 MB)     │            │
   │  │ 000000010000000000000002 (16 MB)  ✓  │ ← новая    │
   │  │   ...                                │   запись   │
   │  │  LSN 0/1234567: HEAP_INSERT ...      │            │
   │  │  LSN 0/1234580: BTREE_INSERT ...     │            │
   │  │  LSN 0/1234600: COMMIT ...           │            │
   │  └──────────────────────────────────────┘            │
   └──────────────────────────────────────────────────────┘

   Клиент получает "COMMIT OK" когда WAL fsync'нут.
   Данные в heap ещё в RAM (dirty page).


   ПОЗЖЕ (не в момент commit'а):
   ┌──────────────────────────────────────────────────────┐
   │  Background Writer / Checkpointer                     │
   │                                                       │
   │  Периодически (или при checkpoint):                   │
   │  Dirty pages из shared_buffers → диск                 │
   └──────┬───────────────────────────────────────────────┘
          │
          ▼
   ┌──────────────────────────────────────────────────────┐
   │  DISK: heap файлы                                    │
   │  /var/lib/postgresql/data/base/16384/16385           │
   │  ┌──────────────────────────────────────┐            │
   │  │ Page 4 обновлена на диске:           │            │
   │  │  Tuple 4: NEW row (наш INSERT)   ✓   │            │
   │  └──────────────────────────────────────┘            │
   └──────────────────────────────────────────────────────┘
```

**Ключевое понимание**:
- **COMMIT ждёт fsync WAL** — durability гарантирована.
- **COMMIT НЕ ждёт запись heap** — она в RAM, догонит позже.
- Если сервер упадёт до записи heap на диск → recovery через WAL восстановит.

**Timeline COMMIT в миллисекундах**:
```
T=0ms   : INSERT выполнен в памяти (dirty)
T=1ms   : WAL запись в WAL Buffers
T=2ms   : COMMIT → write() WAL в OS
T=2.5ms : fsync() WAL → диск подтвердил
T=3ms   : Backend отвечает клиенту "OK"

T=?     : (несколько минут спустя) checkpointer 
          flush dirty page на диск
```

**TID** (Tuple Identifier) — как «указатель» на строку из индекса:
```

```

Индекс хранит `key → TID`. Executor через TID сразу находит физическое место tuple'а на странице.

## Заключение

Полный путь запроса `SELECT * FROM orders WHERE id = 42`:

**Уровень 1: Application (Java/Spring)**  
JPA → SQL → HikariCP → JDBC → TCP.

**Уровень 2: PostgreSQL Server**  
postmaster → backend process → Parser → Rewriter → Planner (выбирает Index Scan) → Executor.

**Уровень 3: Buffer Manager**  
Cache lookup: hit (~1μs) или miss → clock sweep eviction → read с диска.

**Уровень 4: Linux Kernel**  
syscall pread → page cache lookup: hit (~5μs) или miss → file system → block layer → device driver.

**Уровень 5: Physical Disk (SSD)**  
NVMe read 8 KB страницы (~100μs) → в page cache → в shared buffer → в executor.

**Обратный путь**: 8 KB page → tuple по TID → MVCC visibility check → row → TCP → JDBC → Hibernate → Java object → HTTP.

**Три уровня кэша** между приложением и физическим диском:
1. **Shared Buffers** (PostgreSQL, ~25% RAM) — cache pages.
2. **OS Page Cache** (Linux, оставшийся RAM) — cache files.
3. **Physical SSD/HDD** — persistent storage.

**Write path COMMIT** — ключевая деталь:
- INSERT/UPDATE изменяет страницу в shared_buffers (dirty).
- WAL entry в WAL buffers.
- **COMMIT ждёт fsync WAL** — гарантия durability.
- **НЕ ждёт запись heap** — это позже (background writer / checkpointer).
- Recovery через WAL если сервер упал до записи heap.

**Все компоненты связаны**:
- Application dependency: connection pool → PostgreSQL processes.
- PostgreSQL внутренности: backend → buffer manager → OS → disk.
- Обратный путь: те же уровни в обратном порядке.
