# 122. PostgreSQL визуально: физическая архитектура

## Простая схема

Как всё соединено физически — от приложений до диска.

```
    ┌──────────┐   ┌──────────┐   ┌──────────┐   ┌──────────┐
    │  Прод 1  │   │  Прод 2  │   │  Прод 3  │   │  Прод N  │

                   ┌─────────────────────────┐
                   │      PGBouncer          │
                   │  (connection pooler)    │
                   │                         │

                   │  подключений к БД       │
                   └───────────┬─────────────┘
                               │

      ║   ┌──────────────────────────────────────────┐   ║

      ║   │   ┌──────────────────────────────┐       │   ║
      ║   │   │ Shared Buffers (4 GB)        │       │   ║

      ║   │   │ ┌────┬────┬────┬────┬────┐   │       │   ║

      ║   │   + процессы PostgreSQL                  │   ║

      ║                      │                           ║
      ║                      │  если данных нет в RAM    ║
```

## Что где находится

**Приложения (Прод 1, 2, 3, N)**
- Это твои микросервисы: `orders-service`, `user-service`, `payment-service` и т.д.
- Каждый хочет подключиться к БД.
- Могут быть сотни или тысячи подключений одновременно.

**PGBouncer**
- Прокси между приложениями и БД.
- Тысячи клиентских подключений → 20-50 реальных подключений к PostgreSQL.
- Без него БД захлебнётся от количества connection'ов (каждое = отдельный процесс).

**PostgreSQL Server** (один блок — цилиндр):

**CPU**
- Выполняет SQL: парсит, планирует, выполняет.
- Больше ядер = больше параллельных запросов.

**RAM (shared_buffers, ~25% RAM)**
- Кэш страниц с диска (8 KB каждая).
- Если данные тут — быстро (~1 микросекунда).
- Если нет — идём на диск (~100 микросекунд для SSD).

**HDD/SSD**
- Хранит все данные постоянно.
- Файлы таблиц (`base/16384/16385`).
- Файлы индексов.
- Журнал изменений (WAL) в отдельной папке `pg_wal/`.

## Как это работает пошагово

```
1. Приложение хочет данные
   │
   ▼
2. Открывает подключение к PGBouncer
   │
   ▼
3. PGBouncer выдаёт одно из своих подключений к БД
   │
   ▼
4. Запрос летит в CPU
   │
   ▼
5. CPU думает: "нужна страница X таблицы orders"
   │
   ▼
6. Смотрю в RAM (shared_buffers):
   │
   ├── ЕСТЬ  → беру! (быстро)
   │         │
   │         └─→ возвращаю данные приложению
   │
   └── НЕТ   → иду на диск
             │
             ▼
7. Читаю страницу с HDD/SSD
   │
   ▼
8. Кладу в RAM (на будущее)
   │
   ▼
9. Возвращаю данные приложению
```

## Что физически на диске

Разберём папку с данными PostgreSQL:

```
    /var/lib/postgresql/data/
    │
    ├── base/              ← ВСЕ ТАБЛИЦЫ ЛЕЖАТ ТУТ
    │   │
    │   └── 16384/         ← папка одной базы (myapp)
    │       │
    │       ├── 16385      ← таблица orders (файл)
    │       ├── 16386      ← таблица users (файл)  
    │       ├── 16387      ← индекс orders_pkey (файл)
    │       └── ...
    │
    ├── pg_wal/            ← ЖУРНАЛ ИЗМЕНЕНИЙ
    │   │
    │   ├── 000000010000000000000001   (16 MB)
    │   ├── 000000010000000000000002   (16 MB)
    │   └── ...
    │
    ├── postgresql.conf    ← настройки
    ├── pg_hba.conf        ← кто может подключаться
    └── PG_VERSION         ← версия
```

**Главные две вещи**:

1. **`base/`** — тут все данные (таблицы, индексы).
   - Каждая таблица = **один файл**.
   - Если больше 1 GB — несколько файлов.

2. **`pg_wal/`** — журнал.
   - Каждое изменение сначала пишется сюда.
   - Потом уже в основные файлы.
   - Защищает от потери данных при сбое.

## Что внутри файла таблицы

Файл `16385` (таблица orders, 250 MB) состоит из **страниц по 8 KB**:

```
    Файл 16385:
    
    ┌────────┬────────┬────────┬────────┬────────┬────────┐
    │page 0  │page 1  │page 2  │page 3  │page 4  │page 5  │  ...
    │ 8 KB   │ 8 KB   │ 8 KB   │ 8 KB   │ 8 KB   │ 8 KB   │
    └────────┴────────┴────────┴────────┴────────┴────────┘
    
    Каждая страница — минимальная единица чтения.
    Читаешь одну строку → читается вся страница (8 KB).
```

Внутри одной страницы:

```
    Страница 4 (8 KB):
    ┌───────────────────────────────────────┐
    │  Служебная информация (header)        │
    │  Указатели на строки                  │
    ├───────────────────────────────────────┤
    │                                       │
    │       Свободное место                 │
    │                                       │
    ├───────────────────────────────────────┤
    │  Строка: id=42, name='Иван'           │  ← вот твой заказ!
    │  Строка: id=43, name='Пётр'           │
    │  Строка: id=44, name='Мария'          │
    └───────────────────────────────────────┘
```

## RAM и shared_buffers — это разное!

**Важно**: RAM ≠ shared_buffers. Это часто путают.

**RAM** — это вся физическая память сервера. Например 16 GB.

**Shared Buffers** — это **часть** этой RAM которую PostgreSQL берёт себе под кэш. Обычно 25% от RAM = 4 GB из 16.

**Аналогия**: RAM — это твой холодильник целиком. Shared Buffers — одна полка в холодильнике где PostgreSQL хранит свои продукты. Другие полки используют другие программы и OS.

Визуально:

```
   ═══════════════════════════════════════════════════════
   
                   RAM всего сервера: 16 GB
   
   ═══════════════════════════════════════════════════════
   
   ┌───────────────────────────────────────────────────┐
   │                                                   │
   │  ┌────────────────────────────────────────┐       │
   │  │  Shared Buffers (4 GB)                 │       │
   │  │  = ЭТО ЧАСТЬ RAM что PostgreSQL        │       │
   │  │    берёт под свой кэш страниц          │       │
   │  │  ┌────┬────┬────┬────┬────┬────┐       │       │
   │  │  │page│page│page│page│page│... │       │       │
   │  │  └────┴────┴────┴────┴────┴────┘       │       │
   │  └────────────────────────────────────────┘       │
   │                                                   │
   │  ┌────────────────────────────────────────┐       │
   │  │  Процессы PostgreSQL (~500 MB)         │       │
   │  │  ┌────┐ ┌────┐ ┌────┐ ┌────┐          │       │
   │  │  │b1  │ │b2  │ │b3  │ │... │          │       │
   │  │  └────┘ └────┘ └────┘ └────┘          │       │
   │  └────────────────────────────────────────┘       │
   │                                                   │
   │  ┌────────────────────────────────────────┐       │
   │  │  Другие процессы (~500 MB)             │       │
   │  │  системные утилиты                     │       │
   │  └────────────────────────────────────────┘       │
   │                                                   │
   │  ┌────────────────────────────────────────┐       │
   │  │  OS (Linux) + OS Page Cache (~10 GB)   │       │
   │  │  Linux кэширует файлы в свободной RAM  │       │
   │  │  ┌────┬────┬────┬────┬────┬────┐       │       │
   │  │  │page│page│page│page│page│... │       │       │
   │  │  └────┴────┴────┴────┴────┴────┘       │       │
   │  └────────────────────────────────────────┘       │
   │                                                   │
   │  ┌────────────────────────────────────────┐       │
   │  │  Kernel и служебное (~1 GB)            │       │
   │  └────────────────────────────────────────┘       │
   │                                                   │
   └───────────────────────────────────────────────────┘
   
   Итого 16 GB разделены на:
   - Shared Buffers: 4 GB       (PostgreSQL кэш)
   - Backend процессы: 500 MB   (PostgreSQL процессы)
   - Другие процессы: 500 MB    
   - OS Page Cache: 10 GB       (Linux кэш файлов)
   - Kernel: 1 GB
```

## Разница между Shared Buffers и OS Page Cache

Оба кэшируют одни и те же файлы, но это **два разных кэша**:

```
                          RAM
   ┌─────────────────────────────────────────────────┐
   │                                                 │
   │  ┌─────────────────────────────────────────┐    │
   │  │  Shared Buffers (4 GB)                  │    │
   │  │                                         │    │
   │  │  Кто управляет: PostgreSQL              │    │
   │  │  Что хранит:    страницы БД (8 KB)      │    │
   │  │  Умеет:         MVCC, знает о таблицах  │    │
   │  │                                         │    │
   │  │  ┌────┬────┬────┐                       │    │
   │  │  │p 4 │p 7 │p 9 │  ← копии страниц      │    │
   │  │  └────┴────┴────┘    из файлов БД       │    │
   │  └─────────────────────────────────────────┘    │
   │                                                 │
   │  ┌─────────────────────────────────────────┐    │
   │  │  OS Page Cache (10 GB)                  │    │
   │  │                                         │    │
   │  │  Кто управляет: Linux (kernel)          │    │
   │  │  Что хранит:    любые файлы             │    │
   │  │  Умеет:         кэшировать что угодно   │    │
   │  │                                         │    │
   │  │  ┌────┬────┬────┬────┬────┬────┐        │    │
   │  │  │p 4 │p 7 │p 9 │p 1 │p 2 │... │        │    │
   │  │  └────┴────┴────┴────┴────┴────┘        │    │
   │  │  ↑ те же страницы + другие файлы        │    │
   │  └─────────────────────────────────────────┘    │
   │                                                 │
   └─────────────────────────────────────────────────┘
```

**Одна и та же страница может быть в обоих кэшах одновременно** — это называется **double buffering**. «Тратится» RAM на дубликаты, но это компромисс за простоту.

**Порядок поиска когда PostgreSQL хочет страницу**:

```
   1. Смотрю в Shared Buffers (свой кэш)
      ├── Есть → беру! (~1 микросекунда)
      └── Нет  → иду ниже
                 │
                 ▼
   2. Прошу у OS через syscall read()
      OS смотрит в Page Cache (свой кэш)
      ├── Есть → отдаёт из RAM (~5 микросекунд)
      └── Нет  → читает с диска
                 │
                 ▼
   3. С диска (~100 микросекунд SSD)
   
   ← возвращаемся обратно, копируя страницу
   ← в OS Cache, потом в Shared Buffers
```

## Скорости

Почему кэш так важен — сравнение скоростей:

```
   ┌────────────────────┬────────────────────────┐
   │  RAM (Shared       │   ~1 микросекунда      │  ← быстро
   │      Buffers)      │                        │
   ├────────────────────┼────────────────────────┤
   │  RAM (OS Cache)    │   ~5 микросекунд       │
   ├────────────────────┼────────────────────────┤
   │  NVMe SSD          │   ~100 микросекунд     │
   │                    │   (в 100x медленнее)   │
   ├────────────────────┼────────────────────────┤
   │  SATA SSD          │   ~500 микросекунд     │
   ├────────────────────┼────────────────────────┤
   │  HDD (крутящийся)  │   ~10 000 микросекунд  │  ← очень
   │                    │   (в 10 000x медленнее)│    медленно
   └────────────────────┴────────────────────────┘
```

**Вывод**: попадание в RAM = быстро. Промах = долго. Отсюда всё крутится вокруг кэша.

## Итого простыми словами

**База данных = сервер с CPU + RAM + диском**.

**На диске**:
- Папка `base/` — все таблицы (одна таблица = один файл).
- Папка `pg_wal/` — журнал изменений.

**В RAM**:
- Кэш страниц (shared_buffers) — копии страниц с диска.
- Процессы PostgreSQL — один на каждого клиента.

**Клиенты подключаются через PGBouncer** — иначе БД захлебнётся от количества connection'ов.

**Работа с данными всегда через RAM**:
- Данные в кэше — быстро.
- Данных нет в кэше — читаем с диска, кладём в кэш.
