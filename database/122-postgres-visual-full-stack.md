## Что где находится

### 1. Приложения (Прод 1, 2, 3, N)

Твои микросервисы. Каждый — отдельная программа на другом сервере или pod'e в K8s.

- Могут быть тысячи подключений одновременно (сотни pod'ов × десятки connections каждый).
- Общаются с БД через TCP на порт 5432.

### 2. PGBouncer

Прокси между приложениями и БД.

- Держит **много** подключений от приложений (тысячи).
- Держит **мало** подключений к БД (20-50).
- Мультиплексирует — раздаёт свои 20-50 подключений между тысячами клиентов.
- Без него БД захлебнётся: каждое подключение = отдельный процесс = 5-10 MB RAM. 1000 подключений = 5-10 GB RAM только на процессы.

### 3. PostgreSQL Server — весь остальной блок

Всё внутри цилиндра — **один физический сервер** (или один K8s pod). CPU, RAM и диск на одной машине.

**postmaster** — главный процесс. Слушает порт 5432. Форкает backend процесс на каждое подключение.

**Backend процессы** — по одному на каждое подключение (клиента). Каждый ~5-10 MB. Именно они выполняют SQL для конкретного клиента.

**CPU** — 8-64 ядер. Выполняет всю логику: парсинг SQL, построение плана, выполнение.

**RAM (16 GB всего)** — вся физическая память. Внутри:
- **Shared Buffers (4 GB)** — часть RAM под кэш страниц PostgreSQL. **Это НЕ вся RAM**, только её часть.
- **WAL Buffers (16 MB)** — буфер для журнала перед записью на диск.
- **Backend процессы (~500 MB)** — сами процессы PostgreSQL.
- **OS Page Cache (~10 GB)** — Linux кэширует те же файлы (второй кэш).

**Диск (SSD/HDD)** — постоянное хранилище.
- **`base/16384/`** — папка твоей БД. Каждая таблица = отдельный файл (16385, 16386, ...).
- **`pg_wal/`** — журнал изменений. Каждое изменение сначала сюда, потом в таблицы.
- **`global/`** — служебное (роли, tablespaces).

**Фоновые процессы** — работают параллельно, обслуживают БД:
- **Background Writer** — пишет dirty pages из shared_buffers на диск в фоне.
- **WAL Writer** — пишет WAL из WAL Buffers на диск.
- **Checkpointer** — периодически синхронизирует всё dirty на диск (checkpoint).
- **Autovacuum Launcher** — запускает vacuum для очистки мёртвых строк.
- **Stats Collector** — собирает статистику использования.
- **Logger** — пишет логи в файл.

## Порядок работы при SELECT

Простыми словами что происходит:

```
1. Прод App шлёт SQL → PGBouncer
2. PGBouncer передаёт SQL → backend процесс в PostgreSQL
3. Backend через CPU:
   - парсит SQL
   - строит план
   - выполняет
4. Нужна страница таблицы:
   - смотрю в Shared Buffers (кэш PostgreSQL)
     ├─ есть  → беру! (1 микросекунда)
     └─ нет   → иду дальше
   - смотрю в OS Page Cache (кэш Linux)
     ├─ есть  → отдаётся из RAM (5 микросекунд)
     └─ нет   → читаю с диска
   - читаю с SSD (100 микросекунд)
5. Данные возвращаются: диск → OS Cache → Shared Buffers → backend
6. Backend → PGBouncer → приложение
```

## Порядок работы при INSERT/UPDATE

```
1. Прод App шлёт INSERT → PGBouncer → backend
2. Backend через CPU выполняет INSERT
3. Изменения:
   - меняется страница в Shared Buffers (dirty)
   - пишется WAL запись в WAL Buffers
4. При COMMIT:
   - WAL Writer сбрасывает WAL Buffers на диск (fsync)
   - Клиент получает "OK"
5. Dirty page на диск позже:
   - Background Writer или Checkpointer запишут
   - Клиенту это уже не важно
```

## Скорости — почему кэш всё

```
   ┌──────────────────────┬──────────────────────┐
   │  Shared Buffers      │   ~1 микросекунда    │  ← мгновенно
   │  (RAM, PG)           │                      │
   ├──────────────────────┼──────────────────────┤
   │  OS Page Cache       │   ~5 микросекунд     │
   │  (RAM, Linux)        │                      │
   ├──────────────────────┼──────────────────────┤
   │  NVMe SSD            │   ~100 микросекунд   │
   │                      │   в 100x медленнее   │
   ├──────────────────────┼──────────────────────┤
   │  SATA SSD            │   ~500 микросекунд   │
   ├──────────────────────┼──────────────────────┤
   │  HDD (крутящийся)    │   ~10 000 микросекунд│  ← ужасно
   │                      │   в 10 000x медленнее│    медленно
   └──────────────────────┴──────────────────────┘
```

**Отсюда**:
- Cache hit rate 99%+ — критично для performance.
- Больше RAM → больше кэша → быстрее БД.
- Медленный диск = медленные cache miss'ы = медленная БД.

## Что запомнить

**Всё это работает на одном сервере**:
- PGBouncer — обычно отдельный процесс, может быть на том же сервере или отдельно.
- PostgreSQL Server — процессы + RAM + диск в одной машине.

**Три уровня хранения данных**:
1. **Shared Buffers** — RAM, кэш PostgreSQL, самый быстрый.
2. **OS Page Cache** — RAM, кэш Linux, тоже быстрый.
3. **Диск** — постоянное хранилище, медленный.

**Два вида процессов**:
1. **Backend'ы** — по одному на клиента, выполняют его запросы.
2. **Фоновые** — служебные (writer'ы, checkpointer, autovacuum).

**Два типа файлов на диске**:
1. **Таблицы и индексы** — в `base/`.
2. **Журнал (WAL)** — в `pg_wal/`.
