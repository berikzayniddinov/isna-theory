## Два уровня connection pool

**Важно понимать**: часто в системе есть **ДВА уровня connection pooling**:

```
   ┌────────────────────────────────┐
   │  Прод App (Java)               │
   │                                │
   │  ┌──────────────────────────┐  │
   │  │  HikariCP                │  │  ← ПЕРВЫЙ ПУЛ (в приложении)
   │  │  пул 10-30 connections   │  │
   │  │  (внутри JVM процесса)   │  │
   │  └──────────────────────────┘  │
   └────────────────┬───────────────┘
                    │
                    ▼
   ┌────────────────────────────────┐
   │  PGBouncer                     │  ← ВТОРОЙ ПУЛ (отдельный процесс)
   │  пул 20-50 connections         │
   │  (может быть на другой машине) │
   └────────────────┬───────────────┘
                    │
                    ▼
              PostgreSQL
```

**Зачем два пула** — они решают разные проблемы:

**HikariCP** (внутри приложения):
- Держит открытые connection'ы чтобы не открывать каждый раз (открытие ~30 мс).
- **Пул на инстанс приложения**. 3 pod'а × 20 connections = 60 connections.
- Работает внутри JVM.

**PGBouncer** (отдельный процесс/сервис):
- Принимает много connection'ов от разных app instances.
- Отдаёт мало реальных connection'ов PostgreSQL.
- **Один пул на всё**. 100 app instances × 20 = 2000 clients → 30 real connections.
- Спасает PostgreSQL от исчерпания (max_connections обычно 100-500).

**Пример на 100 микросервисов**:
- Без PGBouncer: 100 pods × 20 HikariCP = 2000 connections к PG → превышение лимита, БД не работает.
- С PGBouncer: 2000 HikariCP → PGBouncer → 30 к PG. Работает.

## Где возникает I/O wait

**I/O wait** — это состояние **процесса в ОС** (не PostgreSQL специфично).

```
   Backend процесс PostgreSQL:
   
   1. Хочу прочитать страницу с диска
   2. Делаю системный вызов read()
   3. Процесс переходит в состояние "D" (uninterruptible sleep)
      ← ЭТО I/O WAIT
   4. OS отправляет команду на диск
   5. Диск читает (~100 микросекунд для SSD, ~10 мс для HDD)
   6. OS будит процесс, возвращает данные
   7. Процесс продолжает работать
```

**Метрика `%iowait`** (в top, iostat):

```
   %iowait = процент времени когда:
   - CPU был idle (простаивал)
   - НО хоть один процесс ждал disk I/O
   
   Высокий %iowait (>30%) = 
   диск медленный, много запросов ждут его
```

**Где физически «стоит» I/O wait**:

```
   ┌─────────────────────────────────┐
   │  Backend процесс PostgreSQL     │
   │  делает read()                  │
   └────────────┬────────────────────┘
                │
                ▼
   ┌─────────────────────────────────┐
   │  Linux kernel                   │
   │                                 │
   │  ⚠ Процесс переходит в "D" ⚠   │  ← I/O wait здесь
   │  Ждёт disk controller           │
   └────────────┬────────────────────┘
                │
                ▼
   ┌─────────────────────────────────┐
   │  Disk controller (SATA/NVMe)    │
   │  Отправляет команду на диск     │
   └────────────┬────────────────────┘
                │
                ▼
   ┌─────────────────────────────────┐
   │  Физический диск (SSD/HDD)      │
   │  Читает биты                    │
   │  100 μs (SSD) - 10 000 μs (HDD) │
   └─────────────────────────────────┘
```

**Симптомы высокого I/O wait**:
- В `top`: `%wa` (или `%iowait`) большой (>30%).
- В `iostat -x`: `%util` близко к 100%, `await` большой.
- Приложения тормозят.
- PostgreSQL долго отвечает на запросы.

**Причины**:
- Медленный диск (HDD вместо SSD).
- Много concurrent запросов к диску.
- Мало RAM → мало кэша → часто читаем с диска.
- Плохие индексы → seq scan всей таблицы.

## Путь запроса — все уровни с временами

Реальные времена от нажатия кнопки в клиенте до ответа:

```
   Пользователь кликнул кнопку в браузере
        │
        │ ~50 мс сеть до app сервера
        ▼
   Прод App: Controller получил HTTP запрос
        │
        │ ~1 мс: обработка, преобразование в SQL
        ▼
   HikariCP: беру connection из пула
        │
        │ ~10 μs (если пул не исчерпан)
        │ ← ЖДУ если пул исчерпан
        ▼
   TCP → PGBouncer
        │
        │ ~1 мс сеть внутри датацентра
        ▼
   PGBouncer: выдаёт connection к БД
        │
        │ ~100 μs (если пул не исчерпан)
        │ ← ЖДУ если пул исчерпан
        ▼
   TCP → PostgreSQL
        │
        │ ~500 μs сеть + protocol
        ▼
   PostgreSQL backend получил SQL
        │
        │ ~1 мс: parse + plan
        ▼
   Executor: нужна страница таблицы
        │
        ├─ Shared Buffers? → есть, ~1 μs
        │
        ├─ OS Page Cache? → есть, ~5 μs
        │
        └─ Disk (I/O WAIT)
              │
              │ SSD ~100 μs
              │ HDD ~10 000 μs (10 ms!) ← жуть
              ▼
        Читаю страницу
        │
        ▼
   Возвращаю данные обратно тем же путём
        │
        │ PostgreSQL → PGBouncer → HikariCP →
        │ Controller → HTTP response
        ▼
   Пользователь видит результат
```

## Что запомнить

**Уровни физической архитектуры сверху вниз**:

1. **App Layer** — Java приложение с HikariCP пулом.
2. **Proxy Layer** — PGBouncer (тоже пул, но глобальный).
3. **PostgreSQL processes** — postmaster + backend'ы + фоновые.
4. **CPU** — выполняет запросы.
5. **RAM** (16 GB) — вся память, внутри:
   - Shared Buffers (4 GB) — кэш PostgreSQL
   - WAL Buffers — буфер журнала
   - Backend процессы (~500 MB)
   - OS Page Cache (~10 GB) — кэш Linux
6. **Linux kernel** — здесь возникает I/O wait когда процесс ждёт диск.
7. **Disk** — SSD/HDD, файлы БД и журнала.

**Два уровня пула**:
- **HikariCP** — в приложении, ускоряет открытие connection'ов.
- **PGBouncer** — перед БД, защищает от исчерпания max_connections.

**I/O wait** — состояние процесса когда ждёт диск. Метрика `%iowait` в top / iostat. Высокий = диск медленный.

**Кэши экономят время**:
- Shared Buffers hit → 1 микросекунда.
- OS Cache hit → 5 микросекунд.
- Disk read → 100 μs (SSD) или 10 000 μs (HDD).

Разница в **100-10 000 раз**. Поэтому кэш решает всё.
