# 116. База данных и PostgreSQL: полная картина простыми словами

## Зачем это знать

Разработчик пишет SQL, ORM генерирует запросы, БД возвращает результаты. Работает. Пока не начинаются вопросы: почему один запрос миллисекунда, а другой на той же таблице секунды. Почему после deploy'а с большой миграцией система тормозит два дня. Почему `SELECT ... FOR UPDATE` иногда виснет. Почему на репликах данные появляются с задержкой. Почему после массового DELETE таблица не уменьшается в размере. Все эти вопросы имеют одни и те же корни — устройство базы данных.

Проблема в том что «база данных» для многих разработчиков — чёрный ящик. SQL известен, но что реально происходит когда запрос уходит в БД — тайна. А без модели этого чёрного ящика невозможно ни диагностировать инциденты, ни писать эффективный код, ни планировать масштабирование.

Разница между «использую БД» и «понимаю БД» — способность за секунду ответить: где физически лежат данные когда я вставил строку через `INSERT`; что такое транзакция и почему она либо есть либо её нет; как БД одновременно обслуживает 100 клиентов не путая их данные; почему UPDATE создаёт новую версию строки а не меняет старую; зачем нужен index и когда он вреден; что случится если сервер БД внезапно выключат из розетки; зачем нужны реплики.

Этот файл — полная картина базы данных и конкретно PostgreSQL. Простыми словами, но глубоко. Отталкиваемся от нуля: что такое БД → как хранит данные → как обрабатывает запросы → как обеспечивает надёжность → как масштабируется. Каждая тема — не «упоминание», а достаточно подробно чтобы построить рабочую модель.

Разберём: что такое БД концептуально (не «программа», а модель данных + engine + transactions). Реляционная модель — таблицы, строки, колонки, ключи, foreign keys. Что такое PostgreSQL как система — процессная архитектура, memory, disk, network. Физическое хранение — heap, pages, tuples, TID. Индексы — B-tree упрощённо, когда помогают. Транзакции и ACID — зачем нужны, что гарантируют. MVCC — как PostgreSQL позволяет много клиентов работать одновременно без конфликтов. WAL — как БД не теряет данные при краше. Shared buffers — как БД кэширует. Connections — как БД работает с клиентами. Query lifecycle — путь SQL от строки до результата (parser → planner → executor). VACUUM — почему нужен и что делает. Locks — как БД координирует concurrent доступ. Backups — как защитить данные. Replication — как масштабировать чтение и обеспечить HA. Troubleshooting — что делать когда медленно.

## Что такое база данных на самом деле

«База данных» — не «программа для хранения данных» (это redis, файлы, что угодно тоже хранит). Настоящая БД — это **три вещи вместе**:

**1. Модель данных.** Как ты **представляешь** свои данные. Реляционная модель (таблицы со строками) — самая распространённая. Есть document (JSON), key-value, graph, time-series модели. Каждая модель диктует какие вопросы легко задавать, какие сложно.

**2. Storage engine.** Как данные **физически лежат** на диске. Как быстро найти нужную строку. Как обеспечить чтобы запись не потерялась при выключении питания. Как эффективно использовать RAM и SSD.

**3. Transaction engine.** Как **много клиентов одновременно** работают с одними данными без коллизий. Как гарантировать что если операция началась — она либо целиком выполнится, либо целиком отменится. Как показать каждому клиенту согласованное состояние даже когда другие клиенты меняют данные.

PostgreSQL — реляционная БД (первое) со своим storage engine (второе) и MVCC-based transaction engine (третье). Все три компонента тесно связаны. Понимать надо все три.

Аналогия для интуиции. Библиотека — тоже своего рода БД. **Модель данных** — карточный каталог: как систематизированы книги (по автору, теме, году). **Storage engine** — как книги физически расставлены на полках (алфавитный порядок? по разделам? индекс где какая книга). **Transaction engine** — как несколько посетителей одновременно берут и возвращают книги без хаоса (один взял, другой ждёт; или два берут разные книги параллельно).

Плохая библиотека — где книги свалены в кучу без каталога, посетители дерутся за одну книгу, и раз в неделю несколько книг «теряется». Хорошая — где всё работает даже когда 100 посетителей одновременно.

PostgreSQL — хорошая библиотека для данных. Разберём как она устроена.

## Реляционная модель: таблицы, строки, колонки, связи

Реляционная модель — данные в виде **таблиц**. Каждая таблица — набор **строк** (rows), каждая строка — набор **колонок** (columns) с типизированными значениями.

Пример: таблица `users`:

```
 id | name        | email             | created_at
----+-------------+-------------------+---------------------
  1 | Иван        | ivan@mail.ru      | 2024-01-15 10:23:00
  2 | Пётр        | petr@example.com  | 2024-01-16 14:45:12
  3 | Мария       | maria@corp.kz     | 2024-01-17 09:12:33
```

**Колонки** имеют **типы**: `id` — целое число (integer), `name` — строка (text), `email` — строка, `created_at` — дата+время (timestamp). Тип определяет что можно хранить и какие операции доступны (для чисел — арифметика, для строк — конкатенация, для дат — сравнение и разности).

**Строки** — конкретные записи. Каждая уникальна, идентифицируется по **primary key** — колонка (или комбинация) которая гарантированно уникальна. Обычно это `id` — синтетический идентификатор (автоинкремент или UUID). Primary key — как номер в паспорте: гарантирует что двух Иванов с одинаковым id не бывает.

**Связи между таблицами** — через **foreign key**. Одна таблица ссылается на строку в другой:

```
Таблица orders:
 id | user_id | total_amount | created_at
----+---------+--------------+-------------------
101 |       1 |       1500.0 | 2024-01-15 11:00
102 |       1 |        250.0 | 2024-01-16 15:30
103 |       2 |       3200.0 | 2024-01-18 09:45
```

`user_id` в orders — foreign key, ссылающийся на `id` в users. Означает «этот заказ принадлежит пользователю с id=1». Позволяет узнать «все заказы Ивана» через **JOIN**:

```sql
SELECT u.name, o.total_amount, o.created_at
FROM users u
JOIN orders o ON u.id = o.user_id
WHERE u.name = 'Иван';
```

Возвращает:
```
 name | total_amount | created_at
------+--------------+-------------------
 Иван |       1500.0 | 2024-01-15 11:00
 Иван |        250.0 | 2024-01-16 15:30
```

БД читает две таблицы, находит совпадения по условию, объединяет в результат.

**Целостность через foreign key**. Если попытаемся вставить order с `user_id = 999` (такого юзера нет) — БД откажется. `INSERT INTO orders (user_id, ...) VALUES (999, ...)` вернёт ошибку `foreign key violation`. Это защищает от «сирот» — заказов без пользователя, потерянных связей.

**Нормализация** — процесс разбиения данных на таблицы так чтобы избежать дублирования. Без нормализации мы бы могли иметь одну таблицу:

```
 order_id | user_name | user_email | total
----------+-----------+------------+------
      101 | Иван      | ivan@...   | 1500
      102 | Иван      | ivan@...   | 250
      103 | Пётр      | petr@...   | 3200
```

Проблемы: имя и email пользователя дублируются в каждом заказе. Иван поменял email — надо обновить в 50 местах, часть можем пропустить, данные разойдутся. Нормализация решает: держим users отдельно, orders ссылается через user_id, изменение email в users автоматически видно во всех запросах.

## Что такое PostgreSQL как система

PostgreSQL — не «одна программа», а **набор процессов** работающих вместе. Понимание процессной архитектуры критично для диагностики.

**Postmaster** — главный процесс, запускается при старте PostgreSQL. Слушает TCP-порт (обычно 5432) на входящие подключения от клиентов. Ничего сам не обрабатывает — только принимает подключения и **форкает** отдельный процесс на каждого клиента.

**Backend process** — процесс обслуживающий одного клиента. Клиент подключился → postmaster создал backend процесс → все запросы этого клиента обрабатываются в этом процессе. Клиент отключился → backend завершается. Значит: 100 подключенных клиентов = 100 backend процессов в OS.

**Фоновые процессы** — служебные, не связанные с клиентами:
- **Writer** — периодически записывает грязные страницы из shared buffers на диск.
- **WAL writer** — записывает WAL (write-ahead log) на диск.
- **Autovacuum launcher + workers** — периодически чистят таблицы от dead tuples (см. ниже).
- **Stats collector** — собирает статистику использования (используется query planner).
- **Checkpointer** — периодически делает checkpoint (полная синхронизация shared buffers с диском).

Всё это можно увидеть через `ps` на сервере:

```bash
ps -ef | grep postgres
postgres  1234  1 0 ... postgres: postmaster
postgres  1235  1234 ... postgres: writer process
postgres  1236  1234 ... postgres: wal writer process
postgres  1237  1234 ... postgres: autovacuum launcher process
postgres  1238  1234 ... postgres: stats collector process
postgres  1245  1234 ... postgres: user1 mydb 10.0.0.5(52345) idle
postgres  1246  1234 ... postgres: user2 mydb 10.0.0.6(52346) SELECT
```

Строки в конце (`user1 mydb ... idle`, `user2 ... SELECT`) — backend процессы. Показывают: кто подключён, к какой БД, с какого IP, что сейчас делает.

**Каждый backend — отдельный процесс OS**. Занимает 5-10 MB памяти. Если подключенных клиентов 100 — уже 500-1000 MB ушло на backend'ы. Отсюда — почему **connection pool** обязателен в приложении (файл 107): один клиент держит один backend, но 1000 клиентов = 1000 backend'ов = катастрофа.

## Физическое хранение: heap, pages, tuples

Данные PostgreSQL хранит на диске в **файлах**. Каждая таблица — один или несколько файлов в директории данных.

Внутри файла данные организованы **страницами** (pages) фиксированного размера — 8 KB. Страница — единица чтения/записи. Меньше — не читаем. Один SELECT одной строки — читаем всю страницу где эта строка лежит.

Внутри страницы — **tuples** (кортежи). Один tuple = одна строка таблицы. Плюс служебные заголовки, свободное место, указатели на tuples.

Схема одной 8 KB страницы:

```
┌───────────────────────────────────────────┐
│  Page Header (24 bytes)                   │
├───────────────────────────────────────────┤
│  Item Pointers (line pointers):           │
│  [ptr1] [ptr2] [ptr3] [ptr4] ...          │  указатели на tuples
├───────────────────────────────────────────┤
│                                            │
│         Free space                         │  свободное место для новых
│                                            │
├───────────────────────────────────────────┤
│                                            │
│         Tuple N                            │
│                                            │
│         Tuple 3                            │  tuples растут снизу
│         Tuple 2                            │
│         Tuple 1                            │
└───────────────────────────────────────────┘
```

**Item pointers** растут сверху, **tuples** — снизу. Свободное место посередине. Когда встречаются — страница полна, новые tuples идут в следующую страницу (или создаётся новая).

**TID (Tuple Identifier)** — физическое расположение строки. Пара `(page_number, item_pointer_index)`. Например `TID = (5, 3)` означает «5-я страница, 3-й указатель в ней». Через TID можно за один seek прочитать конкретную строку. Индексы (см. ниже) хранят именно TID'ы.

**Что происходит при INSERT**:

1. PostgreSQL находит страницу где есть свободное место (или создаёт новую).
2. Пишет новый tuple в свободное место снизу.
3. Добавляет item pointer сверху с указателем на tuple.
4. Обновляет page header (счётчик tuples).
5. Помечает страницу как «dirty» — надо будет записать на диск.

Всё это — в памяти (shared buffers, см. ниже). На диск записывается позже (background writer, checkpoint) — оптимизация для производительности. WAL при этом обязательно записывается на диск сразу (для durability, см. ниже).

**Что происходит при UPDATE** — важная особенность PostgreSQL:

PostgreSQL **не меняет** существующий tuple. Вместо этого:
1. Создаёт **новую версию** tuple с новыми значениями.
2. Помечает старую версию как «устаревшую» (заполняет служебное поле `xmax` — «убил меня transaction ID Y»).
3. Индексы обновляются — теперь могут указывать на две версии.

Старая версия остаётся физически в heap до **VACUUM** (см. ниже). Это фундамент **MVCC** — Multi-Version Concurrency Control. Позволяет параллельным транзакциям видеть согласованные snapshot'ы данных.

**Что происходит при DELETE** — почти как UPDATE:
1. Tuple **не удаляется** физически. 
2. Помечается служебным полем `xmax` — «удалён transaction Y».
3. Индексы остаются.

Место освобождает VACUUM позже. Отсюда классический вопрос новичка «удалил миллион строк, почему таблица не уменьшилась» — физически данные ещё там, ждут VACUUM.

## Индексы: как быстро найти строку

Без индекса найти строку — прочитать всю таблицу. Таблица в миллион строк = 250 000 страниц по 4 строки в среднем = 250 000 read'ов с диска. Медленно (секунды-минуты).

**Индекс** — отдельная структура данных, позволяющая быстро найти где лежит строка по значению колонки. Как алфавитный указатель в конце учебника — вместо перелистывания всей книги, смотришь в указатель, находишь номер страницы.

**B-tree** (balanced tree) — самый распространённый тип индекса в PostgreSQL. Дерево, где:
- Внутренние узлы содержат «поисковые ключи» (значения колонки) + указатели на дочерние узлы.
- Листья содержат ключи + **TID** (указатели на строки в heap).
- Дерево «сбалансировано» — глубина одинаковая от корня до любого листа.

Схема B-tree индекса на `users.email` (миллион строк):

```
                         [m, s]                          ← root (1 узел)
                        /   |    \
                   [c,g] [n,p]  [t,w]                    ← internal (10 узлов)
                   / | \  / | \  / | \
                 ... ...  ... ...  ... ...               ← leaves (тысячи узлов)
                                     │
                       "petr@example.com" → TID (54321, 3)
                       "philip@..."       → TID (98765, 1)
                       ...
```

Найти email `petr@example.com`:
1. Начинаем с корня. Сравниваем: `p` между `m` и `s` → идём в правый узел.
2. В узле `[n,p]`: `p...` попадает между `p` — идём в правый лист.
3. В листе находим `petr@...` → TID (54321, 3).
4. Читаем страницу 54321 heap, item 3 → нужная строка.

Итого: 3 чтения индекса + 1 чтение heap = 4 read'а вместо 250 000. Разница на порядки.

**Стоимость индекса**. Индекс — тоже данные, тоже на диске. На таблицу в 1 GB может быть 100-200 MB индексов. Каждый INSERT/UPDATE обновляет и heap, и индексы — write amplification. Каждая новая версия строки при UPDATE тоже требует обновления индексов.

Правило: индекс полезен когда часто ищем по колонке. Бесполезен когда колонка редко в WHERE. Вреден когда таблица маленькая (планировщик всё равно предпочтёт seq scan) или write-heavy (индексы замедляют INSERT). Детально — файл 109.

## Транзакции: всё или ничего

Транзакция — **группа операций, которые либо все выполняются, либо ни одна**. Классический пример — банковский перевод:

```sql
BEGIN;
UPDATE accounts SET balance = balance - 100 WHERE id = 1;   -- списали с А
UPDATE accounts SET balance = balance + 100 WHERE id = 2;   -- зачислили на Б
COMMIT;
```

Без транзакции: если сервер упал после первого UPDATE и до второго — деньги списали с А, но не зачислили на Б. 100 «исчезли». Катастрофа.

С транзакцией: `BEGIN` открывает транзакцию. Оба UPDATE выполняются но не «финализируются». `COMMIT` — обе операции атомарно применяются. Если что-то пошло не так между BEGIN и COMMIT (упало приложение, ошибка в SQL) — `ROLLBACK` откатывает всё. Либо перевод состоялся полностью, либо не начинался — промежуточных состояний нет.

**ACID** — четыре свойства которые транзакции гарантируют:

**Atomicity (атомарность)**. Всё или ничего. Обсуждено выше.

**Consistency (согласованность)**. После транзакции БД в согласованном состоянии — все constraints (foreign keys, unique, check) выполняются. Транзакция не может оставить БД в невалидном состоянии.

**Isolation (изоляция)**. Параллельные транзакции не видят промежуточных состояний друг друга. Пока одна транзакция активна, её изменения не видны другим (в базовых уровнях isolation).

**Durability (долговечность)**. Закоммиченные данные не теряются даже при краше сервера. Обеспечивается WAL (см. ниже).

**Isolation levels** — насколько строго изолируются транзакции. Классические:

- **Read Uncommitted** — транзакция видит незакоммиченные изменения других. В PostgreSQL нет (внутренне работает как Read Committed).
- **Read Committed** — видит только закоммиченные изменения других. Дефолт в PostgreSQL. Компромисс между performance и корректностью.
- **Repeatable Read** — если прочитал строку в начале транзакции, все последующие чтения той же строки в этой транзакции вернут то же значение (даже если другие транзакции закоммитили изменения).
- **Serializable** — самый строгий. Транзакции ведут себя как будто выполнялись последовательно (одна за другой), хотя реально параллельно. Дороже по performance.

Разбор изоляции в файле 32. Здесь важно понять: **транзакция — фундаментальная гарантия что данные не поломаются** при concurrent доступе и сбоях.

## MVCC: как много клиентов работают одновременно

**MVCC (Multi-Version Concurrency Control)** — механизм PostgreSQL позволяющий множеству транзакций работать одновременно **без блокировок для чтения**. Ключевая инновация PostgreSQL, отличает от многих других БД.

Идея: каждая транзакция видит **snapshot** данных на момент своего старта. Другие транзакции могут менять данные — snapshot не меняется. Только когда транзакция закоммитится, другие увидят её изменения (в новых snapshot'ах).

**Как это работает физически**:

Каждый tuple в heap имеет служебные поля:
- **xmin** — ID транзакции которая создала этот tuple.
- **xmax** — ID транзакции которая удалила/обновила этот tuple (или 0 если жив).

Транзакция при чтении tuple проверяет:
- **xmin** — эта транзакция уже закоммитилась ДО моего старта? Если да — tuple существовал когда я начал.
- **xmax** — эта транзакция удалившая/обновившая tuple уже закоммитилась ДО моего старта? Если да — tuple для меня удалён.

По этим двум полям каждая транзакция может решить для себя видима ли конкретная версия tuple.

**Пример UPDATE с двумя транзакциями**:

```
Начальное состояние: tuple v1: (xmin=100, xmax=0), value = "old"

Транзакция T1 (ID=200) UPDATE'ит:
  - Создаёт tuple v2: (xmin=200, xmax=0), value = "new"
  - Ставит xmax=200 в v1

Параллельно транзакция T2 (ID=201) читает эту строку:
  - Началась после T1 START, но до T1 COMMIT.
  - Смотрит v1: xmin=100 (закоммитилась давно) ✓, xmax=200 (T1 ещё не закоммитилась) ✗
  - Значит для T2 — v1 всё ещё живая. Читает "old".

T1 COMMIT.

Транзакция T3 (ID=202) читает после T1 COMMIT:
  - Смотрит v1: xmax=200 (T1 закоммитилась) → v1 удалена для T3.
  - Смотрит v2: xmin=200 (T1 закоммитилась) → v2 живая. Читает "new".
```

Каждая транзакция получает **консистентную картину** на момент своего старта. Никаких блокировок для чтения — просто фильтрация видимости.

**Плюсы MVCC**:
- Читатели не блокируют писателей. Писатели не блокируют читателей.
- Каждая транзакция видит согласованный snapshot.
- Высокая concurrency — можно иметь тысячи одновременных транзакций.

**Минусы MVCC**:
- **Bloat**. UPDATE не меняет строку, создаёт новую. Старая остаётся до VACUUM. Активно обновляемая таблица растёт быстро.
- **VACUUM необходим**. Без него dead tuples накапливаются, таблица раздувается, производительность деградирует. Autovacuum обычно справляется, но требует настройки для больших таблиц (файл 89, 105).
- **Transaction ID wraparound**. Transaction ID — 32-битное число (4 миллиарда значений). При исчерпании нужен freeze (обновление xmin старых tuples на «замороженное» значение). Ещё одна работа для VACUUM.

Отличие от других БД. Oracle и SQL Server тоже используют MVCC, но по-разному (Oracle через undo log — старые версии живут отдельно, не в heap). MySQL InnoDB — тоже MVCC (undo log). PostgreSQL хранит все версии в heap — простее внутренне, но требует VACUUM.

## WAL: как БД не теряет данные

Проблема: PostgreSQL пишет изменения сначала в shared buffers (RAM), потом асинхронно на диск. Если сервер упадёт между записью в RAM и записью на диск — изменения потеряны. Клиенту сказали `COMMIT ok`, но данных нет.

Решение — **Write-Ahead Log (WAL)**. Каждое изменение сначала записывается в специальный лог (WAL) на диск, потом уже в основные файлы. `COMMIT` гарантирует что WAL записан на диск (fsync). Основные файлы могут догоняться позже.

**Как это спасает от crash'а**:

Сервер упал в момент когда:
- В shared buffers: изменения tuple X сделаны, страница dirty.
- На диске (heap): tuple X ещё старый.
- На диске (WAL): запись «tuple X обновлён на Y, транзакция Z закоммитилась».

При старте PostgreSQL:
1. Читает WAL с последнего checkpoint.
2. Для каждой записи применяет изменение к heap (**recovery**).
3. Tuple X теперь Y в heap. Данные восстановлены.

Гарантия: **что закоммитилось, то не потеряно**. Это **Durability** в ACID.

**Checkpoint** — периодическая полная синхронизация shared buffers с диском. После checkpoint WAL до этой точки уже не нужен для recovery (данные в heap актуальны). Дефолтно раз в 5 минут или каждые 1 GB WAL. Настраивается через `checkpoint_timeout`, `max_wal_size`.

**WAL — единственная критичная операция ввода-вывода**. Всё остальное можно позже. Отсюда — диск под WAL должен быть быстрым (обычно отдельный SSD/NVMe). Если WAL тормозит — тормозит вся БД.

**Практический пример**. Спросишь `pg_stat_wal`:

```sql
SELECT wal_records, wal_bytes, wal_write, wal_sync 
FROM pg_stat_wal;
```

`wal_write` — сколько раз WAL писался (background). `wal_sync` — сколько раз делался fsync (при COMMIT). Много `wal_sync` — много коммитов, каждый ждёт диска. Оптимизация — batch операций в одну транзакцию (10 INSERT в одном COMMIT = 1 fsync вместо 10).

## Shared Buffers: как БД использует память

PostgreSQL держит **кэш страниц** в памяти — **shared buffers**. Дефолт — 128 MB, обычно ставят 25% от RAM сервера (для 16 GB RAM → 4 GB shared buffers).

Когда backend читает страницу heap или индекса:
1. Проверяет shared buffers — есть ли уже эта страница в памяти?
2. **Cache hit** → читает из памяти (микросекунды).
3. **Cache miss** → читает с диска (миллисекунды или десятки миллисекунд для HDD), кладёт в shared buffers.

**Cache hit rate** — процент чтений из кэша. Идеал 99%+ для OLTP. Смотреть:

```sql
SELECT sum(heap_blks_hit) * 100.0 / (sum(heap_blks_hit) + sum(heap_blks_read)) 
    AS cache_hit_ratio
FROM pg_statio_user_tables;
```

< 95% — недостаточно памяти для рабочего набора данных, либо увеличить shared_buffers, либо увеличить RAM сервера.

**Работа write side**. Изменения делаются в shared buffers (страница помечается dirty). На диск пишет **background writer** периодически. **Checkpointer** делает полную синхронизацию dirty pages при checkpoint. Между — данные в памяти, WAL уже на диске.

**OS page cache** — отдельный кэш на уровне Linux. PostgreSQL читает страницы через OS, OS тоже их кэширует. Значит одна страница может быть и в shared buffers, и в OS cache. **Double buffering**. Обычно приемлемо — теряется 25% RAM на дублирование, но упрощает архитектуру.

## Connections: как клиенты подключаются

Клиент открывает TCP-соединение к PostgreSQL на порт 5432. Postmaster принимает, запускает backend процесс, backend аутентифицирует клиента (проверяет пароль, LDAP, certificate).

После аутентификации backend готов принимать запросы. Клиент шлёт SQL, backend выполняет, возвращает результат. Пока клиент подключён — backend живёт.

**Ограничения**:
- Каждый backend = ~5-10 MB памяти в OS + backend-specific memory (work_mem для запросов, temp_buffers).
- `max_connections` (дефолт 100) — предел параллельных соединений. Больше — либо не подключишься, либо получишь `too many connections`.

**Почему нужен connection pool в приложении** (файл 107):
- 1000 клиентов приложения = 1000 подключений к PostgreSQL. Не влезет.
- Connection pool (HikariCP в Spring) держит 10-30 подключений открытыми, приложение переиспользует.
- Каждый веб-запрос берёт connection из пула, работает, возвращает. Клиенты приложения делят пул.

**pgBouncer** — external connection pooler между приложением и PostgreSQL. Приложение подключается к pgBouncer (лёгкий процесс, тысячи соединений), pgBouncer поддерживает маленький пул к реальному PostgreSQL. Полезно когда приложений много.

## Query lifecycle: что происходит с SELECT

Клиент отправил `SELECT * FROM users WHERE email = 'ivan@mail.ru'`. Что происходит:

**1. Parser** — превращает SQL текст в структурированное представление (AST — Abstract Syntax Tree). Проверяет синтаксис. Ошибка синтаксиса → `syntax error` сразу.

**2. Rewriter** — применяет правила переписывания. Views раскрываются в underlying таблицы. Rules применяются (редко используется).

**3. Planner / Optimizer** — самый интересный. Выбирает **как** выполнить запрос:
- Использовать индекс на `email` или seq scan таблицы?
- Если JOIN — какой алгоритм (Nested Loop, Hash Join, Merge Join)?
- В каком порядке JOIN'ить таблицы?

Основа выбора — **cost model** (стоимость каждого плана в абстрактных единицах). Меньший cost = лучший план. Cost основан на **статистике** таблиц (сколько строк, распределение значений колонок). Статистика собирается `ANALYZE` — часть autovacuum.

Пример плана:

```
Index Scan using users_email_idx on users
    (cost=0.29..8.30 rows=1 width=64)
  Index Cond: (email = 'ivan@mail.ru')
```

`Index Scan using users_email_idx` — планировщик выбрал использовать индекс. `cost=0.29..8.30` — оценка стоимости (min..max). `rows=1` — оценка сколько строк вернётся.

Если статистика устарела или сложные запросы — планировщик может ошибаться, выбрать неоптимальный план. Отсюда классический совет «обновите статистику: `ANALYZE table`».

**4. Executor** — выполняет план. Идёт по узлам плана: Index Scan → читает индекс, находит TID → читает heap по TID → применяет фильтр → возвращает строку клиенту.

**5. Возврат клиенту** — строки упаковываются в PostgreSQL wire protocol, отправляются по TCP клиенту.

`EXPLAIN` показывает план без выполнения. `EXPLAIN ANALYZE` — выполняет и показывает реальные времена. Основной инструмент диагностики медленных запросов (файлы 88, 103).

## VACUUM: почему нужен

MVCC оставляет мусор — dead tuples от UPDATE и DELETE. Индексы указывают в том числе на мёртвые версии. Без очистки:
- Таблицы раздуваются (bloat), больше страниц читать.
- Индексы раздуваются, поиск медленнее.
- Transaction ID wraparound угрожает (нужен freeze старых xmin).

**VACUUM** — процесс очистки:
1. Идёт по heap, находит dead tuples (закоммиченные транзакции которые их создали/удалили далеко в прошлом, никому не нужны).
2. Помечает место как свободное (для будущих INSERT'ов).
3. Обновляет индексы — удаляет указатели на dead tuples.
4. При VACUUM FULL — реально переупаковывает страницы (block requires exclusive lock, обычно не используется в prod).

**VACUUM обычный vs VACUUM FULL**:
- Обычный VACUUM — non-blocking, освобождает место для повторного использования внутри таблицы. Таблица не уменьшается на диске, но новые INSERT'ы могут заполнять освобождённое место.
- VACUUM FULL — блокирует таблицу целиком (ACCESS EXCLUSIVE). Реально переписывает файл, таблица уменьшается на диске. Используется редко (обычно `pg_repack` вместо).

**Autovacuum** — фоновый процесс, автоматически запускает VACUUM когда bloat превышает порог (по умолчанию — 20% dead tuples). Обычно достаточно для типовых нагрузок. Для тяжёлых таблиц требует настройки (autovacuum_vacuum_scale_factor, cost_delay — файл 89, 105).

Симптом плохо работающего VACUUM: таблица растёт на диске быстрее чем растёт логически (миллион insert → таблица 10 GB а могла быть 1 GB — 90% bloat). Мониторить `pg_stat_user_tables.n_dead_tup / n_live_tup`.

## Locks: как БД координирует concurrent доступ

Даже с MVCC (читатели не блокируют писателей) — писатели могут блокировать друг друга. `UPDATE` одного tuple двумя транзакциями одновременно — вторая ждёт первую. Нужны locks для координации.

**Levels of locks** в PostgreSQL:

**Table-level locks**. От `ACCESS SHARE` (SELECT берёт) до `ACCESS EXCLUSIVE` (ALTER TABLE, DROP TABLE берут). Между ними — 8 разных уровней с разной степенью совместимости.

**Row-level locks**. `SELECT ... FOR UPDATE` явно блокирует конкретные строки. UPDATE автоматически блокирует затрагиваемые строки. Другая транзакция желающая UPDATE тех же строк — ждёт.

**Deadlock** — две транзакции ждут друг друга по кругу. PostgreSQL автоматически обнаруживает через 1 секунду (`deadlock_timeout`) и убивает одну из транзакций с ошибкой. Приложение должно retry.

Разбор locks и `EXPLAIN` — файл 88.

**Как узнать кто кого блокирует в проде**:

```sql
SELECT blocked.pid, blocked.query AS blocked_query,
       blocking.pid AS blocking_pid, blocking.query AS blocking_query
FROM pg_stat_activity blocked
JOIN pg_stat_activity blocking 
    ON blocking.pid = ANY(pg_blocking_pids(blocked.pid))
WHERE blocked.wait_event_type = 'Lock';
```

Показывает пары «жертва → блокировщик». Если блокировщик — `idle in transaction` (открыл транзакцию и забыл закоммитить) — классический баг приложения, нужен `idle_in_transaction_session_timeout` в конфиге.

## Backups и Point-in-Time Recovery

Данные могут потеряться от разных причин: hardware failure, human error (`DROP TABLE production_data`), софтверный баг. **Backup** — единственная защита.

Типы бэкапов:

**Logical backup** (`pg_dump`). Выгрузка данных как SQL-инструкции. `pg_dump mydb > backup.sql`. Плюс: портативно (можно восстановить в другую версию PostgreSQL), понятно (SQL). Минус: медленно для больших баз (сотни GB — часы), нельзя PITR.

**Physical backup** (`pg_basebackup`). Копирование файлов данных на другой сервер. Быстро (просто copy). Минус: same-version PostgreSQL, файлы прямо копируются.

**Continuous archiving + PITR**. Комбинация `pg_basebackup` + сохранение всех WAL segments. Позволяет восстановиться на **любой момент времени** между backup и текущим. Классика для критичных систем: backup раз в день + WAL непрерывно → recover на «состояние на 14:32 вчера когда админ дропнул таблицу».

Инструменты автоматизации: **pgBackRest**, **Barman**, **WAL-G**, **pgBackWeb**. Enterprise стандарт.

Правило: **backup только если он проверен восстановлением**. Регулярно (раз в квартал минимум) на тестовом сервере восстанавливать из бэкапа и убеждаться что работает. Без этого backup — иллюзия.

## Replication и HA

Один сервер = single point of failure. Умер сервер — данные недоступны (даже если backup есть, восстановление часы). Нужна **replication**.

**PostgreSQL streaming replication**:
- **Primary** (мастер) — основной сервер, принимает writes.
- **Standby** (реплики) — копии primary, синхронизируются через WAL streaming. Читают только (read-only).

Как работает:
1. Primary записал WAL segment.
2. Отправляет по сети standby.
3. Standby применяет WAL к своим файлам.
4. Standby теперь имеет те же данные (с небольшой задержкой = replication lag).

**Synchronous vs Asynchronous replication**:
- **Async** (дефолт) — primary не ждёт standby. COMMIT завершается когда WAL записан локально. Быстрее, но при краше primary до отправки WAL — standby отстанет.
- **Sync** — primary ждёт подтверждения от standby перед COMMIT. Медленнее, но гарантия что данные на двух серверах.

**Failover** — переключение при падении primary. Один из standby становится новым primary. Обычно автоматизировано через **Patroni** или **repmgr**. Downtime — секунды-минуты.

**Read replicas** для scaling reads. Мастер обслуживает writes + часть reads. Реплики только reads. Приложение балансирует запросы. При replication lag — read может вернуть slightly stale данные (обычно допустимо).

Детально — файл 90.

## Что делать когда медленно: базовая диагностика

Симптом «БД тормозит». Пошаговый чек-лист:

**1. Активность сейчас**. `SELECT * FROM pg_stat_activity WHERE state != 'idle'` — что выполняется. Много запросов долго висят → детально смотреть каждый.

**2. Locks**. Кто кого блокирует (query выше). Blocker обычно виноват. `idle in transaction` — приложение забыло закоммитить.

**3. Slow queries**. Включён `pg_stat_statements` — топ по `mean_exec_time`. Медленный запрос → `EXPLAIN ANALYZE` → искать Seq Scan большой таблицы → добавить индекс.

**4. Bloat**. `n_dead_tup / n_live_tup` из `pg_stat_user_tables` — если > 20% на активной таблице, VACUUM отстаёт.

**5. Cache hit ratio**. Если < 95%, недостаточно RAM или неэффективные запросы вычитывают ненужные данные.

**6. Disk I/O на сервере**. `iostat -xz 1` на сервере БД. `await` > 20 мс = диски перегружены. Файлы 88, 107.

**7. Connections**. `pg_stat_activity count > 80% от max_connections` — исчерпан пул. Смотреть кто держит, connection pool в приложении настроен?

**8. Replication lag**. Если реплики — `pg_stat_replication` показывает lag. Растёт = что-то не так.

## Заключение

База данных = модель данных + storage engine + transaction engine. PostgreSQL — реляционная модель (таблицы) + heap-based storage + MVCC-based transactions.

**Реляционная модель** — таблицы со строками и колонками, связи через foreign keys, целостность через constraints. JOIN'ы объединяют данные из разных таблиц.

**PostgreSQL — процессная архитектура**. Postmaster принимает соединения, форкает backend процесс на клиента. Каждое соединение = отдельный OS процесс = ~5-10 MB. Отсюда обязательный connection pool в приложении.

**Физическое хранение** — heap файлы, страницы по 8 KB, tuples внутри. TID = (page, item pointer) = адрес строки на диске. UPDATE не меняет tuple, а создаёт новую версию (для MVCC). DELETE не удаляет, а помечает как удалённый. Физическая очистка — VACUUM.

**Индексы** — B-tree deriverbnbi структура. Быстрый поиск по колонке — 3-4 read'а вместо тысяч. Стоят места и замедляют write. Полезны для часто-искомых колонок с высокой селективностью.

**Транзакции** — ACID гарантии. Атомарность (всё или ничего), Consistency (constraints выполнены), Isolation (параллельные не путают друг друга), Durability (закоммиченное не теряется).

**MVCC** — каждая транзакция видит snapshot данных на момент своего старта. Не блокируется на чтении. Служебные xmin/xmax в tuples для видимости.

**WAL** — все изменения сначала в write-ahead log на диск, потом в heap. COMMIT ждёт fsync WAL. При crash — recovery применяет WAL к heap. Гарантирует durability.

**Shared buffers** — кэш страниц в RAM (обычно 25% от RAM). Cache hit rate 99%+ = быстро. < 95% = проблема.

**Query lifecycle** — Parser → Rewriter → Planner → Executor. Planner выбирает план на основе cost model + статистики. `EXPLAIN ANALYZE` показывает реально что происходит.

**VACUUM** — очистка dead tuples. Autovacuum обычно справляется. Для тяжёлых нагрузок настраивать.

**Locks** — координация concurrent writes. Deadlock автоматически обнаруживается и одна транзакция убивается. `pg_blocking_pids` находит блокировщиков.

**Backups** — logical (pg_dump), physical (pg_basebackup), PITR через WAL archiving. Backup только если проверен восстановлением.

**Replication** — streaming replication через WAL. Primary + standbys. Async (быстро, риск потери) vs sync (гарантия, медленно). Failover через Patroni.

**Медленно** — pg_stat_activity, locks, pg_stat_statements, EXPLAIN ANALYZE, bloat, cache hit ratio, disk I/O.

Все эти вещи взаимосвязаны. MVCC требует VACUUM. VACUUM требует статистики. Статистика влияет на Planner. Planner выбирает индексы. Индексы влияют на write throughput. Write throughput ограничен WAL disk. И так далее. Понимать эти связи — база всей работы с PostgreSQL в проде.
