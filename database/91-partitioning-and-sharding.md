# 91. Партиционирование и шардинг PostgreSQL

## Зачем это нужно

Когда таблица растёт до сотен миллионов записей, начинают проявляться пределы одиночной таблицы на одном сервере. Sequential scan занимает часы. VACUUM тянется бесконечно. Индекс на такой таблице сам занимает десятки гигабайт. Любая операция на всю таблицу — ALTER TABLE, REINDEX — блокирует прод. И это ещё до того, как физические ресурсы сервера (CPU, RAM, IOPS диска) станут узким местом.

Ответ индустрии — разделять данные. На две принципиально разные техники: **партиционирование** и **шардинг**. Они часто путаются, но решают разные задачи.

Партиционирование — это разбиение одной таблицы на несколько подтаблиц (partitions) в пределах **одной базы данных на одном сервере**. Снаружи выглядит как одна таблица, внутри это N физически отдельных таблиц. Плюсы: partition pruning (запросы читают только релевантные partitions), быстрый drop старых данных, независимые операции обслуживания на partitions. Но всё ещё один сервер, ограниченный его ресурсами.

Шардинг — это разбиение данных между несколькими **отдельными серверами**. Каждый шард — своя PostgreSQL инсталляция со своими данными. Приложение (или прокси) знает, к какому шарду обратиться за какими данными. Даёт горизонтальное масштабирование сверх возможностей одной машины. Но существенно усложняет архитектуру: distributed transactions, cross-shard queries, миграция данных при добавлении шардов.

В этом файле разберём обе техники. Начнём с партиционирования: типы (range, list, hash), partition pruning, партиционированные индексы, миграция обычной таблицы на партиционированную без даунтайма. Потом шардинг: стратегии выбора shard key, consistent hashing, distributed transactions, инструменты (Citus, Vitess), когда шардинг оправдан.

## Партиционирование: типы и механика

PostgreSQL с версии 10 поддерживает нативное partitioning (`declarative partitioning`), до этого использовался inheritance-based partitioning (constraints exclusion), который сохраняется для совместимости но не рекомендуется для новых установок.

Идея declarative partitioning проста. Создаётся «родительская» таблица, объявленная как partitioned:

```sql
CREATE TABLE orders (
    id BIGSERIAL,
    user_id BIGINT NOT NULL,
    created_at TIMESTAMP NOT NULL,
    status VARCHAR(20) NOT NULL,
    amount NUMERIC(12,2)
) PARTITION BY RANGE (created_at);
```

Ключевая директива — `PARTITION BY RANGE (created_at)`. Она говорит: эта таблица разбита на партиции по значению `created_at`. Сама parent таблица не содержит данных — это только шаблон и точка входа для запросов.

Дальше создаются конкретные партиции — каждая для своего диапазона значений:

```sql
CREATE TABLE orders_2024_01 PARTITION OF orders 
    FOR VALUES FROM ('2024-01-01') TO ('2024-02-01');

CREATE TABLE orders_2024_02 PARTITION OF orders 
    FOR VALUES FROM ('2024-02-01') TO ('2024-03-01');
```

Физически orders_2024_01 — это отдельная таблица со своим heap файлом, своими индексами, своими статистиками, своим autovacuum циклом. Но логически она — часть orders. `INSERT INTO orders VALUES (..., '2024-01-15', ...)` автоматически попадёт в orders_2024_01, потому что дата попадает в её range.

`SELECT * FROM orders WHERE created_at >= '2024-01-15' AND created_at < '2024-01-20'` — PostgreSQL проанализирует условие, поймёт что нужны только строки из orders_2024_01, и **прочитает только эту партицию**, полностью игнорируя остальные. Это называется **partition pruning** — исключение партиций из плана до execution.

Три основных типа партиционирования:

**RANGE** — по непрерывному диапазону. Каждая партиция определяет FROM и TO. Идеальна для timestamp (по месяцу или дню), для числовых интервалов. Пример выше.

**LIST** — по списку конкретных значений. Каждая партиция определяет набор значений.

```sql
CREATE TABLE orders PARTITION BY LIST (country);
CREATE TABLE orders_kz PARTITION OF orders FOR VALUES IN ('KZ');
CREATE TABLE orders_ru PARTITION OF orders FOR VALUES IN ('RU', 'BY');
CREATE TABLE orders_other PARTITION OF orders DEFAULT;
```

Полезна для географии или категоризации по фиксированным значениям.

**HASH** — по хешу от значения. Каждая партиция определяет modulus и remainder.

```sql
CREATE TABLE orders PARTITION BY HASH (user_id);
CREATE TABLE orders_p0 PARTITION OF orders FOR VALUES WITH (modulus 4, remainder 0);
CREATE TABLE orders_p1 PARTITION OF orders FOR VALUES WITH (modulus 4, remainder 1);
CREATE TABLE orders_p2 PARTITION OF orders FOR VALUES WITH (modulus 4, remainder 2);
CREATE TABLE orders_p3 PARTITION OF orders FOR VALUES WITH (modulus 4, remainder 3);
```

Даёт равномерное распределение (если user_id хорошо распределены). Полезна, когда нет natural range/list ключа, но нужно распределить нагрузку между партициями. Downside: pruning работает только для запросов с точным равенством по partition key (`WHERE user_id = 5` — знаем hash, знаем партицию; `WHERE user_id > 5` — не знаем).

Есть **subpartitioning** — партиции могут сами быть партиционированы. Например: сначала по стране (LIST), внутри каждой страны — по месяцу (RANGE). Полезно, но добавляет complexity.

## Partition pruning — как это работает

Ключевая ценность партиционирования — partition pruning. Запрос читает только релевантные партиции, а не всю «виртуальную» таблицу.

Есть два уровня pruning: planning-time и execution-time.

**Planning-time pruning** происходит на этапе планирования: Optimizer видит условие `WHERE created_at BETWEEN '2024-01-01' AND '2024-01-15'`, знает границы партиций, исключает orders_2023_12 и orders_2024_02 и все остальные, оставляет только orders_2024_01. План строится сразу без ненужных партиций.

**Execution-time pruning** появился в PG 11. Работает для случаев, когда значение partition key неизвестно на планировании — например, оно приходит из параметра или из subquery. План включает все партиции с runtime-фильтром: «пропусти этот узел если условие false». На execution когда значение известно, узлы с false-условиями пропускаются.

Пример execution-time pruning:

```sql
PREPARE q(date) AS 
SELECT * FROM orders WHERE created_at = $1;

EXECUTE q('2024-01-15');
```

При PREPARE неизвестно значение параметра. Plan включает все партиции. При EXECUTE значение известно, читается только orders_2024_01.

Смотреть на pruning в плане:

```
EXPLAIN SELECT * FROM orders WHERE created_at BETWEEN '2024-01-01' AND '2024-01-15';
```

```
Append  (cost=... rows=...)
  ->  Seq Scan on orders_2024_01  (cost=... rows=...)
        Filter: (created_at BETWEEN ...)
```

Только orders_2024_01 в плане — pruning сработал. Если бы `SELECT * FROM orders WHERE user_id = 5` (условие не по partition key), увидели бы все партиции — pruning не работает.

**Условие для pruning**: WHERE должно содержать partition key напрямую. Функции над partition key ломают pruning: `WHERE DATE(created_at) = '2024-01-15'` не сработает, потому что Optimizer не знает как DATE взаимодействует с range партиций. Правильно: `WHERE created_at >= '2024-01-15' AND created_at < '2024-01-16'`.

## Индексы на партиционированной таблице

Индексы работают на partition, не на всей таблице. Когда ты создаёшь индекс:

```sql
CREATE INDEX ON orders (user_id);
```

Это создаёт **partitioned index** — сам индекс тоже партиционирован, физически это отдельный индекс на каждой партиции. Каждый маленький, локально B-tree.

Плюс: индекс на 100M-строчной partitioned таблице фактически 12 индексов по 8M строк (если 12 партиций). Каждый в разы меньше, быстрее ANALYZE, быстрее REINDEX.

Минус: unique constraint на не-partition-key column не работает нативно. Уникальность гарантируется только в пределах партиции. Если хочешь глобальный unique — либо включи partition key в constraint (что часто искажает бизнес-логику), либо решай на уровне приложения.

Для partition key auto-created индексы обычно достаточны. Для frequent WHERE-условий по другим колонкам — создавать явно.

## Миграция обычной таблицы на партиционированную

Реальный кейс: у тебя есть orders на 300M строк, работает медленно, надо партиционировать. Как это сделать без даунтайма?

Простой путь: `ALTER TABLE orders PARTITION BY RANGE (created_at)`. Нельзя. PostgreSQL не поддерживает преобразование обычной таблицы в партиционированную in-place. Нужна миграция.

Стандартный approach:

Шаг 1. Создать новую partitioned таблицу с другим именем.

```sql
CREATE TABLE orders_new (LIKE orders INCLUDING ALL) 
    PARTITION BY RANGE (created_at);

CREATE TABLE orders_2024_01 PARTITION OF orders_new 
    FOR VALUES FROM ('2024-01-01') TO ('2024-02-01');
-- ... остальные партиции
```

Шаг 2. Скопировать существующие данные. Это самая долгая часть — для 300M строк идёт часы. Делать в batch'ах, коммитить, между batch'ами пауза (чтобы autovacuum и другие запросы могли работать):

```sql
INSERT INTO orders_new 
SELECT * FROM orders WHERE created_at >= '2024-01-01' AND created_at < '2024-02-01';
COMMIT;
-- пауза, следующий batch
```

Шаг 3. Настроить триггер на orders, дублирующий INSERT/UPDATE/DELETE в orders_new. Это чтобы новые изменения тоже попадали в новую таблицу пока идёт миграция.

Шаг 4. Когда данные скопированы полностью и sync поддерживается триггером — атомарный swap имён:

```sql
BEGIN;
ALTER TABLE orders RENAME TO orders_old;
ALTER TABLE orders_new RENAME TO orders;
COMMIT;
```

Это быстрая операция, требует ACCESS EXCLUSIVE lock, но занимает миллисекунды. Приложение теперь работает с новой партиционированной таблицей.

Шаг 5. Убрать триггер, удалить orders_old.

Целая процедура сложная, но работоспособная. Автоматизировать можно через **pg_partman** — extension которое помогает управлять партициями (создавать по расписанию, удалять старые).

Для простых случаев — можно принять downtime. Ночью, когда нагрузка минимальна, сделать pg_dump orders, drop, create partitioned, restore. Всё атомарно, но пара часов недоступности.

## Управление партициями в жизненном цикле

Партиционирование по времени — самый частый паттерн. Каждый месяц (или день, или год) — новая партиция для актуального периода. Старые партиции могут удаляться через определённое время (retention policy).

Ручное управление быстро становится утомительным: каждый месяц создать новую партицию, удалить старую. Автоматизировать помогает **pg_partman**:

```sql
SELECT partman.create_parent(
    p_parent_table => 'public.orders',
    p_control => 'created_at',
    p_interval => '1 month',
    p_premake => 6                     -- создавать партиции на 6 месяцев вперёд
);
```

Дальше pg_partman через scheduled job (например, каждый день) сам создаёт новые партиции по мере приближения к их периоду и опционально удаляет старые:

```sql
UPDATE partman.part_config 
SET retention = '12 months', 
    retention_keep_table = false
WHERE parent_table = 'public.orders';
```

Означает: партиции старше 12 месяцев удалять полностью. При исполнении pg_partman выполняет `DROP TABLE partition_name` для старых — это мгновенная операция (не как DELETE миллионов строк).

Retention через drop — одна из главных практических выгод партиционирования. Хранение прод-логов, аудита, метрик — где нужно хранить X месяцев и удалять старое — становится тривиальной задачей.

## Partition-wise join и aggregate

PostgreSQL 11+ поддерживает **partition-wise join** — операция join между двумя партиционированными таблицами с одинаковой партиционной структурой может выполняться параллельно, партиция за партицией.

Пример: `orders` и `order_items` обе партиционированы по order_id с одинаковыми диапазонами. Join между ними может выполняться независимо для каждой пары партиций, потому что строки order_items с order_id в диапазоне партиции orders_1 находятся только в order_items_1.

Включается через `enable_partitionwise_join = on` в PG 12+ (было off по умолчанию). Даёт большой выигрыш для крупных join'ов, но за счёт использования work_mem на каждую партицию — при 100 партициях work_mem умножается на 100.

Аналогично `enable_partitionwise_aggregate` — агрегация выполняется на каждой партиции независимо, потом объединяется.

## Когда партиционирование не помогает

Партиционирование — не серебряная пуля. Есть случаи, когда оно ничего не даёт или даже вредит.

Первое — если запросы **не используют partition key**. Партиционирование по `created_at`, а все запросы `WHERE user_id = X`. Optimizer вынужден проверить каждую партицию (partition pruning не работает без partition key в WHERE). Итог: N мелких запросов вместо одного большого, что даже медленнее.

Fix: либо переpартиционировать по user_id, либо создать глобальный индекс на user_id (не поддерживается в PostgreSQL) — это ограничение и повод пойти в шардинг.

Второе — если таблица **не такая большая**. Партиционирование добавляет overhead: planning дольше, каждая партиция — отдельная точка обслуживания. Для таблицы на 10M строк оно скорее замедлит чем ускорит.

Правило: партиционируй если хотя бы одно из:
- Больше 100 GB.
- Больше 100M строк.
- Есть natural retention policy (удалять старое).
- Есть паттерн запросов, где WHERE всегда содержит partition key.

Третье — если много **cross-partition транзакций**. Например, UPDATE меняет partition key — строка должна переехать из одной партиции в другую. Это дорого, часто требует ручной обработки.

## Шардинг: горизонтальное масштабирование

Партиционирование помогает пока хватает одного сервера. Что дальше?

Один PostgreSQL сервер имеет пределы:
- CPU — определённый параллелизм.
- RAM — сколько поместится shared_buffers + work_mem × concurrent queries.
- Диск — IOPS и storage capacity.
- Network — bandwidth на клиентские соединения и репликацию.

Даже топовое железо (128 CPU cores, 1 TB RAM, NVMe RAID) имеет предел. Если приложение перерастает — надо разбивать данные между разными серверами. Это **шардинг** (sharding).

Идея. У нас 4 сервера PostgreSQL, каждый со своей копией схемы. Данные распределяются между ними по какому-то признаку — **shard key**. Например, users с user_id 1-25M на сервере 1, 25M-50M на сервере 2, и т.д. Или по хешу user_id % 4.

Приложение должно знать, куда пойти за конкретными данными. `SELECT * FROM users WHERE user_id = 12345` — надо определить шард (по правилу распределения) и отправить запрос туда. `INSERT INTO users` — по значению user_id определить шард, вставить туда.

Это называется **application-aware sharding**. Приложение содержит routing logic, знает про топологию шардов. Работает, но связывает приложение с инфраструктурой — при добавлении шарда надо менять код.

Более распространённый вариант — **middleware sharding**: прокси между приложением и шардами, который скрывает топологию. Приложение думает, что работает с одной базой, прокси распределяет запросы. Инструменты: **Citus** для PostgreSQL, **Vitess** для MySQL.

## Стратегии распределения (shard key)

Как выбирать shard key — фундаментальный вопрос. От него зависит всё дальнейшее.

**Hash-based sharding**. Shard = hash(user_id) % N. Плюсы: равномерное распределение (при хорошем hash), простое правило. Минусы: range-запросы (`WHERE user_id > 100000`) требуют обращения ко всем шардам. Добавление нового шарда требует rehash всех данных — почти всё переезжает.

**Range-based sharding**. Shard 1: user_id 1-10M, shard 2: 10M-20M, и т.д. Плюсы: range queries работают на одном шарде. Простое понимание. Минусы: hot spots — если новые пользователи всегда получают последние ID, весь новый traffic идёт на последний shard. Балансировать сложнее.

**Directory-based sharding**. Отдельная таблица mapping — `user_id → shard`. Даёт максимальную гибкость: любые сложные правила распределения, легко перемещать данные (обновить mapping). Минус: extra lookup, single point of failure если mapping недоступен.

**Consistent hashing**. Продвинутый вариант hash-based, минимизирующий rebalancing при добавлении/удалении шардов. Каждый shard занимает диапазон в hash space; при добавлении нового только его соседи переезжают. Используется в Cassandra, Riak, DynamoDB.

Ключевая проблема выбора shard key — избежать **cross-shard queries**. Если запросы часто требуют данных из нескольких шардов (JOIN между таблицами на разных шардах), performance страдает. Идеальный shard key — тот, по которому фильтруются все или большинство запросов.

Классический пример: multi-tenant SaaS. Данные каждого tenant (компания-клиент) шардятся вместе. Все запросы одного tenant'а идут на один шард. Cross-tenant queries редки. Shard key = tenant_id.

Плохой пример: соцсеть, где каждый user связан со всеми через фолловинг. Любой feed запрос трогает друзей, разбросанных по всем шардам. Sharding по user_id даёт много cross-shard запросов — производительность плохая.

## Distributed transactions

Транзакции затрагивающие несколько шардов — сложная и медленная операция. Классическое решение — **two-phase commit (2PC)**:

Фаза 1 (prepare): координатор говорит каждому участнику «подготовься к коммиту». Каждый выполняет транзакцию, но не коммитит окончательно — записывает в WAL prepared state.

Фаза 2 (commit/abort): если все ответили OK — координатор говорит «коммитить». Каждый коммитит и подтверждает. Если хоть один отказал — «откатить».

Проблема 2PC. Если координатор умрёт между фазой 1 и фазой 2, участники остаются в prepared state, держат locks и WAL. Никто не может решить, коммитить или откатить. Требуется manual intervention.

Ещё проблема — латенсия. 2PC — минимум два round-trip до каждого участника, fsync на каждом шаге. Транзакция на 3 шардах занимает 6-10ms там где локальная — 1ms.

Из-за этого микросервисные архитектуры избегают 2PC и используют вместо них **eventual consistency** через Saga или Outbox паттерны (о них в другом файле). Данные согласуются не мгновенно, а через набор компенсирующих действий.

Для шардинга общий подход: **избегать cross-shard транзакций дизайном**. Shard key выбирается так, что типичная транзакция затрагивает один shard. Если действительно нужен cross-shard update — сделай через события (записал в свой шард + сгенерировал событие для другого шарда).

## Citus

Самый популярный инструмент для sharding PostgreSQL — **Citus**. Изначально open-source, куплен Microsoft (стал Azure Cosmos DB for PostgreSQL), но остался open-source.

Citus работает как расширение PostgreSQL. Ты имеешь coordinator node и worker nodes. Coordinator — обычный PostgreSQL с установленным Citus, worker'ы — PostgreSQL с Citus. Приложение подключается к coordinator, тот распределяет запросы по worker'ам.

Distributed table создаётся так:

```sql
CREATE TABLE users (
    user_id BIGINT,
    email TEXT,
    created_at TIMESTAMP
);

SELECT create_distributed_table('users', 'user_id');
```

`create_distributed_table` берёт обычную таблицу и превращает в distributed по shard key `user_id`. Данные разделяются на N shards (по умолчанию 32), каждый shard — physical таблица на одном из worker nodes.

INSERT в distributed table прозрачно идёт на нужный worker. SELECT — coordinator анализирует запрос:

- WHERE по shard key → single-shard query, идёт на один worker, быстро.
- WHERE без shard key → coordinator рассылает на все worker'ы, собирает результаты, объединяет. Медленнее, но работает.
- JOIN между distributed таблицами — если они co-located (шардированы по одинаковому ключу с одинаковым числом шардов) — join выполняется на worker'ах. Иначе — сложные стратегии (broadcast маленькой таблицы, re-shuffle).

Citus добавляет тип **reference table** — маленькие справочные таблицы, реплицируются полностью на каждый worker. JOIN'ы с ними работают локально на worker'е без данных transfer.

```sql
SELECT create_reference_table('countries');
```

Хорошая архитектура на Citus: большие таблицы distributed по бизнес-ключу (tenant_id, user_id), маленькие reference. JOIN'ы работают локально. Cross-shard queries редки.

Citus решает много sharding проблем: rebalancing (перенос shards между workers без даунтайма), high availability (streaming replication каждого shard), distributed transactions (2PC внутри для нужных случаев).

## Vitess и другие

**Vitess** — sharding для MySQL, разработан YouTube, потом open-sourced. Инструмент отдельного класса — прокси/оркестратор перед кластером MySQL. Мощный, но специфический для MySQL мира. Для PostgreSQL нет прямого аналога такой зрелости.

**Postgres-XL** — форк PostgreSQL с встроенным distributed processing. Не активно развивается.

**Spock replication** и другие logical replication решения — не sharding, а cross-cluster sync.

**Amazon Aurora** и **Google AlloyDB** — managed сервисы с cluster-level scaling, но не sharding в буквальном смысле.

Для реального шардинга PostgreSQL на 2024-2026 практически варианты — Citus или application-level sharding (руками).

## Когда шардинг оправдан

Шардинг — сложная тема, часто применяется преждевременно. Правило: **не шарди пока не исчерпал всё остальное**.

Прежде всего попробуй:
- Оптимизацию запросов (индексы, планы).
- Партиционирование внутри одного сервера.
- Vertical scaling (более мощная железка).
- Разделение читающей нагрузки через реплики.
- Кэширование (Redis для hot data).
- Разделение приложения на микросервисы, каждый со своей БД (это тоже sharding, но по бизнес-домену — обычно проще).

Если после всего этого один сервер продолжает не справляться — тогда шардинг. Признаки: один шард данных не помещается в RAM, IOPS диска исчерпаны, CPU на 100% при нормальной нагрузке.

Sharding означает: distributed transactions (медленно, ненадёжно), cross-shard queries (сложно), rebalancing (болезненно), operational overhead (управлять N кластерами вместо 1). Осознанно принимай эту сложность только когда реально нужна.

Для KNP-подобных enterprise систем (миллионы пользователей, но не миллиарды одновременных запросов) обычно партиционирования достаточно. Sharding — для FAANG-масштаба или очень write-heavy систем.

## Заключение

Партиционирование и шардинг решают разные задачи, хотя обе связаны с большими данными.

Партиционирование — разбиение таблицы внутри одного сервера. Даёт partition pruning для быстрых запросов по partition key, независимые операции обслуживания на партициях, retention через простой DROP старых. Три типа: RANGE (для timestamp'ов и непрерывных значений), LIST (для категорий), HASH (для равномерного распределения). Автоматизация через pg_partman. Миграция обычной таблицы на партиционированную требует truancate + trigger + rename swap. Ограничения: unique constraints работают только внутри партиций, cross-partition queries без pruning медленнее.

Шардинг — распределение данных между отдельными серверами. Даёт горизонтальное масштабирование за пределы возможностей одной машины. Стратегии распределения: hash (равномерно, плохо для range queries), range (хорошо для range, hot spots), directory (гибко, extra lookup). Ключевое — выбрать shard key так, чтобы типичные запросы работали с одним шардом. Cross-shard queries и distributed transactions существенно медленнее, часто ненадёжны.

Citus — де-факто стандарт для sharding PostgreSQL. Coordinator + workers, distributed tables + reference tables, автоматический routing запросов, rebalancing без даунтайма. Application-level sharding — альтернатива для простых случаев, но связывает приложение с топологией.

Шардинг применяй только когда всё остальное исчерпано. Оптимизация запросов, партиционирование, vertical scaling, read replicas, кэширование, разделение на микросервисы — всё это проще sharding'а. Только когда одна машина реально не тянет — принимай complexity шардинга.

Для КНП партиционирование — нужно для больших таблиц (orders, audit log, notifications). Шардинг — нет, размера недостаточно. Правильная стратегия: партиционировать по времени большие таблицы + автоматика через pg_partman + retention 12-24 месяца + партиционированные индексы.

Дальше практика. Создай partitioned таблицу по месяцам, вставь миллион строк с разными датами, посмотри как EXPLAIN показывает partition pruning. Установи pg_partman, настрой автоматику. Замерь ANALYZE и VACUUM время на partitioned vs обычной таблице — увидишь разницу. Только через практику приходит понимание, что даёт партиционирование и когда оно оправдано.
