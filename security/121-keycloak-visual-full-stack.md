## JWT — что внутри токена и как проверяется

Пришёл token в API — что там и как валидируется:

```
   Header.Payload.Signature (три части через точку)
   
   ┌────────────────────────────────────────────────────────────┐
   │                    Header (base64)                         │
   │  {                                                         │
   │    "alg": "RS256",   ← алгоритм подписи (RSA + SHA-256)    │
   │    "kid": "abc123"   ← ID ключа в JWKS                     │
   │  }                                                         │
   └────────────────────────────────────────────────────────────┘
                             │
   ┌────────────────────────────────────────────────────────────┐
   │                    Payload (base64) — claims               │
   │  {                                                         │
   │    "iss": "https://keycloak/realms/myapp",                 │
   │    "sub": "user-uuid-12345",                               │
   │    "aud": "backend-api",                                   │
   │    "exp": 1712345678,   ← истекает                         │
   │    "iat": 1712345078,   ← выдан                            │
   │    "email": "ivan@example.com",                            │
   │    "realm_access": {                                       │
   │      "roles": ["ADMIN", "USER"]                            │
   │    },                                                      │
   │    "iin": "800101300123"   ← ИИН (если из ЭЦП)             │
   │  }                                                         │
   └────────────────────────────────────────────────────────────┘
                             │
   ┌────────────────────────────────────────────────────────────┐
   │                    Signature (base64)                      │
   │                                                            │
   │  RSA-подпись( Header + "." + Payload, private_key )        │
   │  ← создаётся Keycloak приватным ключом                     │
   │  ← проверяется публичным ключом из JWKS endpoint           │
   └────────────────────────────────────────────────────────────┘
   
   
   Проверка Spring Security:
   
   1. Извлекает token из Authorization header
   2. Разбирает на 3 части
   3. Смотрит header → берёт alg и kid
   4. GET /jwks (кэшированный)
   5. Находит public key по kid
   6. Проверяет signature:
      RSA-verify( public_key, signature, Header + "." + Payload )
   7. Проверяет claims:
      - exp > now (не истёк)
      - iss == expected issuer
      - aud содержит наш client_id
   8. Успех → создаёт Authentication в SecurityContext
```

## Security Layers — уровни защиты

```
   ┌──────────────────────────────────────────────────────────────────┐
   │  1. Транспорт: HTTPS/TLS                                         │
   │  ← весь трафик зашифрован                                        │
   │  ← защита от man-in-the-middle                                   │
   └──────────────────────────────────────────────────────────────────┘
                                │
                                ▼
   ┌──────────────────────────────────────────────────────────────────┐
   │  2. Аутентификация: Кто ты?                                      │
   │                                                                  │
   │  Способы в Keycloak:                                             │
   │  ┌──────────────┐  ┌──────────────┐  ┌──────────────┐            │
   │  │ Password     │  │ Social Login │  │ ЭЦП (X.509)  │            │
   │  │ (username +  │  │ (Google, FB) │  │ (Kalkan)     │            │
   │  │  password)   │  │              │  │              │            │
   │  └──────────────┘  └──────────────┘  └──────────────┘            │
   │                                                                  │
   │  + 2FA (OTP через Google Auth / SMS)                             │
   │  + WebAuthn (fingerprint, YubiKey)                               │
   └──────────────────────────────────────────────────────────────────┘
                                │
                                ▼
   ┌──────────────────────────────────────────────────────────────────┐
   │  3. Авторизация: Что ты можешь?                                  │
   │                                                                  │
   │  Проверка через JWT claims:                                      │
   │  - realm_access.roles: ["ADMIN"]                                 │
   │  - resource_access.orders-api.roles: ["orders:read"]             │
   │  - scope: "openid email profile"                                 │
   │                                                                  │
   │  Проверяется через:                                              │
   │  - @PreAuthorize("hasRole('ADMIN')")                             │
   │  - @PreAuthorize("hasAuthority('SCOPE_orders:read')")            │
   │  - Spring Security authorizeHttpRequests()                       │
   └──────────────────────────────────────────────────────────────────┘
                                │
                                ▼
   ┌──────────────────────────────────────────────────────────────────┐
   │  4. Целостность данных: JWT signature                            │
   │                                                                  │
   │  Каждый JWT подписан приватным ключом Keycloak                   │
   │  Backend проверяет подпись через public key (JWKS)               │
   │  → Изменение payload → подпись невалидна → 401                   │
   └──────────────────────────────────────────────────────────────────┘
                                │
                                ▼
   ┌──────────────────────────────────────────────────────────────────┐
   │  5. Ротация токенов: короткие access + refresh                   │
   │                                                                  │
   │  Access token: 5-15 минут                                        │
   │  ← если утёк, максимум 15 минут доступа                          │
   │  ← потом клиент делает refresh, чтобы получить новый             │
   │                                                                  │
   │  Refresh token: 7-30 дней                                        │
   │  ← хранится в httpOnly cookie (защита от XSS)                    │
   │  ← при использовании выдаётся новый (rotation)                   │
   └──────────────────────────────────────────────────────────────────┘
                                │
                                ▼
   ┌──────────────────────────────────────────────────────────────────┐
   │  6. Session management                                           │
   │                                                                  │
   │  Keycloak хранит session:                                        │
   │  - Можно посмотреть где user залогинен                           │
   │  - Force logout всех сессий (при инциденте)                      │
   │  - Автологаут после idle timeout                                 │
   └──────────────────────────────────────────────────────────────────┘
```

## Что где хранится

```
   ┌────────────────────────┐   ┌────────────────────────┐
   │      Frontend          │   │      Backend           │
   │                        │   │                        │
   │  Access token:         │   │  НЕ хранит токены!     │
   │  → JavaScript memory   │   │                        │
   │    (variable)          │   │  Проверяет JWT         │
   │    ← защита от XSS     │   │  при каждом запросе    │
   │    (не в localStorage) │   │                        │
   │                        │   │  Кэширует JWKS         │
   │  Refresh token:        │   │  (public keys)         │
   │  → httpOnly cookie     │   │                        │
   │    ← JS не может       │   │                        │
   │      прочитать         │   │                        │
   │                        │   │                        │
   └────────────────────────┘   └────────────────────────┘
   
   ┌────────────────────────────────────────────────────┐
   │              Keycloak (в PostgreSQL)               │
   │                                                    │
   │  - Пользователи (email, password hash, атрибуты)   │
   │  - Клиенты (client_id, secret, redirect_uris)      │

   │  - Sessions (кто сейчас залогинен)                 │
```

## Что запомнить

**Keycloak — это центральный сервер identity**:
- Все приложения проверяют аутентификацию через него.
- Один сервер на всю компанию.

**Три роли в OAuth 2.0**:
- **Frontend/Backend** = Client (просит доступ).
- **Keycloak** = Authorization Server (выдаёт токены).
- **Backend API** = Resource Server (проверяет токены).

**JWT токен = самодостаточный**:
- Backend НЕ ходит в Keycloak на каждый запрос.
- Проверяет подпись локально через кэшированный public key.
- Если подпись валидна и не истёк → доверяет content.

**ЭЦП (Kazakhstan)**:
- Пользователь подписывает challenge приватным ключом (USB-токен / файл).
- Keycloak проверяет через публичный ключ из X.509 сертификата.
- Извлекает ИИН/БИН из сертификата, использует как identity.
- Kalkan CryptoAPI / NCALayer — плагин для браузера.

**Security слои**:
1. HTTPS — транспорт.
2. Authentication — кто ты (password, ЭЦП, 2FA).
3. Authorization — что можешь (roles, scopes).
4. JWT signature — целостность.
5. Token rotation — минимизация impact при утечке.
6. Session management — контроль всех сессий.

**Хранение токенов на клиенте**:
- Access: JS memory (не в localStorage!).
- Refresh: httpOnly cookie (защита от XSS).
