# 89. VACUUM, статистика и практика диагностики медленных запросов

## Зачем это знать

PostgreSQL — единственная из массовых СУБД, которая требует регулярной уборки. Мёртвые версии tuple'ов от UPDATE и DELETE накапливаются в heap и индексах, и без периодической очистки таблица начинает пухнуть, sequential scan замедляется, индексы теряют эффективность. Механизм этой уборки — VACUUM. Понимать его — часть базовой компетенции DBA и senior-разработчика, работающего с PostgreSQL в проде.

Статистика — второй компонент, о котором знают все, но глубоко разбираются немногие. Optimizer выбирает планы на основе оценок, оценки берутся из статистики, статистика может устареть. Одна из самых частых причин «внезапно медленный запрос» — это устаревшая статистика: Optimizer думает, что таблица маленькая, выбирает Nested Loop, а на самом деле таблица уже гигантская. Понимать, как собирается статистика, что в неё входит, почему может врать — это ключ к предсказуемым планам.

Наконец, практика диагностики медленных запросов. Это не отдельная тема, а способ использования всего остального: locks, планы, статистика, VACUUM. В проде типовая ситуация — «пользователи жалуются, кабинет тормозит» — и надо за 30 минут найти конкретный запрос, понять почему он медленный, применить fix. Этот файл сводит всё в конкретный workflow.

## VACUUM — что это на самом деле делает

VACUUM в PostgreSQL — это не одна операция, а целое семейство. Есть просто `VACUUM`, есть `VACUUM FULL`, есть `VACUUM ANALYZE`, есть `VACUUM FREEZE`, есть autovacuum как фоновая версия. Каждый делает своё, и путать их — источник многих проблем.

Начнём с базового. Обычный `VACUUM tablename` (без FULL) выполняет следующее. Проходит по heap таблицы страница за страницей. Для каждой страницы смотрит: какие tuple'ы можно считать «мёртвыми» — это те, чей xmax принадлежит уже закоммиченной транзакции, и при этом никакая активная транзакция не может их увидеть (потому что все snapshot'ы начинают жить позже этого xmax'а).

Найдя dead tuples, VACUUM освобождает их line pointers — помечает как unused. Место в странице теоретически освобождается, но физически пока никто не переписывает: страница остаётся такой же, просто теперь известно, что часть её слотов пустая. Free Space Map таблицы обновляется — там записывается, сколько free space в каждой странице. Это важно, потому что при следующем INSERT'е PostgreSQL заглянет в FSM и найдёт страницу с достаточным местом.

Аналогично VACUUM обрабатывает индексы. Для каждого индекса проходит по нему, находит записи, указывающие на удалённые tuple'ы (те, что VACUUM только что убрал из heap), удаляет эти записи. Это делается в отдельном проходе после heap.

Один тонкий момент — VACUUM обычно не возвращает освобождённое место операционной системе. Файл таблицы остаётся того же размера. Освобождённые страницы просто будут использованы для новых INSERT'ов. Только если VACUUM освободил тысячи страниц **в конце** файла (последовательно), он попробует truncate файл. Это редко бывает при обычной нагрузке — dead tuples разбросаны по всему heap, не сосредоточены в конце.

Для настоящего возврата места есть `VACUUM FULL`. Он работает принципиально по-другому: создаёт полностью новый файл таблицы, копирует туда все живые tuple'ы, потом атомарно заменяет старый файл новым. Никакого bloat в результате — таблица становится максимально плотной. Но за это платят: `VACUUM FULL` берёт `ACCESS EXCLUSIVE` lock на всё время работы, что означает полный downtime для этой таблицы. И работает медленно — фактически перезаписывает всю таблицу. Для сотен гигабайт — часы. В продакшене используется только в specific случаях, обычно в maintenance окно.

Существует `pg_repack` — расширение, которое делает то же самое (уплотняет таблицу и убирает bloat), но без exclusive lock. Он создаёт trigger на исходной таблице, копирует данные в новую таблицу, ведёт diff через trigger, потом атомарно переключается. Требует какое-то время держать двойное место на диске (старая + новая версия), но не блокирует production. Стандартный инструмент для borderline cases в проде.

Есть `VACUUM ANALYZE` — комбинация: сначала vacuum, потом analyze (обновление статистики). Обычно autovacuum делает оба, но вручную удобно совместить.

Есть `VACUUM FREEZE` — принудительная заморозка старых tuple'ов для защиты от XID wraparound. Об этом подробнее ниже.

## Autovacuum — как оно работает

VACUUM вручную запускать неудобно, поэтому у PostgreSQL есть **autovacuum** — фоновый процесс, который сам решает, когда какую таблицу пылесосить.

Autovacuum состоит из двух частей. Первая — **autovacuum launcher**, один процесс на кластер, который раз в `autovacuum_naptime` (по умолчанию 60 секунд) просыпается, смотрит на все базы данных, выбирает одну и запускает воркера для неё. Вторая — **autovacuum workers**, каждый обслуживает одну базу. Одновременно может работать до `autovacuum_max_workers` воркеров (по умолчанию 3).

Worker решает, какие таблицы обрабатывать, по двум критериям. Первый — **пороговая величина мёртвых tuple'ов**:

```
threshold = autovacuum_vacuum_threshold + autovacuum_vacuum_scale_factor × n_live_tup
```

По умолчанию `autovacuum_vacuum_threshold = 50`, `autovacuum_vacuum_scale_factor = 0.2`. Это значит: таблица пылесосится, когда мёртвых tuple'ов больше 50 + 20% от живых. Для маленькой таблицы (100 живых) порог — 70 мёртвых. Для большой (100 миллионов живых) — 20 миллионов мёртвых.

Второй порог — для ANALYZE, аналогичный, только `autovacuum_analyze_scale_factor = 0.1` (10%). Статистика обновляется чаще vacuum'а.

Проблема с этими дефолтами становится очевидна на больших таблицах. 20% от 100M — это 20 миллионов dead tuples перед началом уборки. Пока накопятся, таблица уже сильно заbloat'ится, sequential scan замедлится, индексы разрастутся. Для больших продуктивных таблиц принято сильно снижать scale_factor:

```sql
ALTER TABLE huge_table SET (
    autovacuum_vacuum_scale_factor = 0.02,
    autovacuum_analyze_scale_factor = 0.01
);
```

2% и 1% соответственно — vacuum срабатывает при 2 миллионах мёртвых на 100M-строчной таблице. Гораздо чаще, но каждый vacuum быстрее (меньше работы).

Есть ещё **throttling**. Autovacuum не должен потреблять всю I/O, вытесняя обычную нагрузку. Механизм — cost-based delay. Каждая операция vacuum'а имеет условную стоимость (`vacuum_cost_page_hit = 1`, `vacuum_cost_page_miss = 10`, `vacuum_cost_page_dirty = 20`). Когда накопленная стоимость достигает `autovacuum_vacuum_cost_limit` (по умолчанию 200), процесс засыпает на `autovacuum_vacuum_cost_delay` (по умолчанию 2 мс).

Для обычной нагрузки это норма, autovacuum не мешает. Но на больших таблицах с быстро растущим bloat дефолтные настройки слишком консервативны — autovacuum успевает мало за отведённое время, дефицит растёт. Тогда снижают `autovacuum_vacuum_cost_delay` до 0 или `10 μs`, чтобы дать autovacuum'у работать быстрее. Мониторить нужно `checkpoint_write_time` и общую I/O нагрузку — если autovacuum начинает мешать, поменьше agressive.

Как понять, справляется ли autovacuum. Простой запрос:

```sql
SELECT schemaname, relname, n_live_tup, n_dead_tup,
       n_dead_tup::float / NULLIF(n_live_tup + n_dead_tup, 0) AS dead_ratio,
       last_autovacuum, last_autoanalyze
FROM pg_stat_user_tables
WHERE n_dead_tup > 10000
ORDER BY dead_ratio DESC;
```

Смотришь `dead_ratio` — доля мёртвых. Если больше 20-30% на нагруженной таблице, autovacuum отстаёт. Смотришь `last_autovacuum` — если несколько часов назад или NULL, значит vacuum давно не работал.

## Что мешает autovacuum'у

Autovacuum отстаёт не просто так. Есть несколько типовых причин.

**Long-running transactions**. Транзакция, начатая час назад, держит snapshot. VACUUM не может удалить tuples, чей xmax моложе, чем snapshot этой транзакции — они всё ещё могут ей быть нужны. Итог: dead tuples накапливаются, VACUUM видит их, но не может убрать. Их называют **non-removable rows**.

Как обнаружить. `pg_stat_activity` показывает открытые транзакции:

```sql
SELECT pid, state, xact_start, NOW() - xact_start AS duration, query
FROM pg_stat_activity
WHERE xact_start IS NOT NULL
ORDER BY xact_start;
```

Особенно опасны транзакции в состоянии `idle in transaction` — приложение открыло BEGIN, выполнило запросы, потом ушло делать что-то другое, и забыло commit/rollback. Транзакция висит, snapshot держится, VACUUM бесполезен.

Fix: `SET idle_in_transaction_session_timeout = 60000` — 60 секунд, потом idle транзакции автоматически убиваются с ошибкой. В приложении — вылавливать паттерны, где COMMIT/ROLLBACK может не выполниться (исключения, ранние return'ы). Использовать `@Transactional` вокруг компактных методов, не растягивать транзакции на всю логику.

**Slow autovacuum на большой таблице**. Vacuum большой таблицы — это часы работы. Если параллельно UPDATE-нагрузка продолжает генерировать мёртвых, к концу vacuum'а мёртвых уже накопилось столько, что нужен ещё один vacuum. Гонка вооружений, где VACUUM проигрывает.

Fix: увеличить количество autovacuum workers, снизить cost_delay для быстрой работы, партиционировать большую таблицу на подтаблицы (каждая vacuum'ится независимо).

**Autovacuum отключён**. Иногда его выключают «для производительности», не понимая последствий. Через месяц таблица так пухнет, что читать её становится в 10 раз медленнее, чем должно.

Проверить: `SHOW autovacuum;` должно вернуть `on`. Если `off` — включить. Никогда не отключай autovacuum глобально.

## XID wraparound и VACUUM FREEZE

Отдельная и часто недооценённая проблема — Transaction ID wraparound. XID в PostgreSQL — это 32-битное число, счётчик транзакций. Каждая транзакция получает новый XID при BEGIN. После ~4 миллиардов транзакций (2^32) счётчик переполнится и начнётся с нуля.

Это создаёт проблему для MVCC. Если tuple был создан транзакцией с XID = 100, а сейчас счётчик уже начал новый круг и стал XID = 105, то новая транзакция с XID 105 будет думать, что tuple от XID 100 создан после неё (потому что 100 меньше 105 после wraparound — но контекстно это старая транзакция). Данные внезапно становятся невидимы.

Чтобы этого не случалось, PostgreSQL периодически «замораживает» старые tuple'ы — обновляет их xmin на специальную константу FrozenTransactionId, которая означает «этот tuple видим всегда, безусловно, независимо от wraparound». Frozen tuple переживает любое количество wraparound'ов.

Заморозка происходит в VACUUM, если tuple старше `vacuum_freeze_min_age` XID'ов (по умолчанию 50 миллионов). При обычной работе это делается неспешно, попутно с обычным VACUUM.

Но есть жёсткий лимит. Если возраст самого старого tuple'а в таблице приближается к `autovacuum_freeze_max_age` (по умолчанию 200 миллионов XID), PostgreSQL запускает **aggressive autovacuum** на этой таблице. Он пылесосит **все** страницы (даже те, что не менялись — обычный VACUUM их пропускает через Visibility Map), чтобы гарантированно заморозить всё старое.

Aggressive vacuum на большой таблице — это часы работы, но он критичен. Если игнорировать, приближение к wraparound становится всё опаснее. Начинают появляться warning'и в логе:

```
WARNING: database "knp" must be vacuumed within 12345678 transactions
```

Если полностью проигнорировать, база остановит **все writes** для защиты от wraparound. Единственный путь восстановления — запустить VACUUM в single-user mode, что означает полный downtime.

Мониторинг: смотреть возраст самой старой замороженной xmin в каждой БД:

```sql
SELECT datname, age(datfrozenxid) AS xid_age
FROM pg_database
ORDER BY xid_age DESC;
```

Если приближается к `autovacuum_freeze_max_age`, значит aggressive vacuum скоро сработает. Для больших таблиц лучше запланировать freeze в maintenance окно (специальным `VACUUM FREEZE tablename` вручную), чем ждать пока autovacuum сделает это в неподходящий момент.

## Bloat — что это и как измерить

Bloat — это разница между полезным объёмом данных и реальным размером таблицы (или индекса) на диске. Возникает от мёртвых tuple'ов, которые не были удалены, от разреженных страниц (много удалений в одной странице оставляют её полупустой), от преждевременных splits в B-tree индексах.

Полностью 100% bloat означает: таблица занимает вдвое больше места, чем нужно. Половина — полезные данные, половина — dead tuples. Это плохо потому что sequential scan читает вдвое больше, index scan промахивается кэшем чаще, autovacuum работает дольше.

Точно измерить bloat непросто — нужно знать «идеальный» размер, а он зависит от структуры таблицы, alignment колонок, среднего размера tuple'ов. Есть популярный запрос от pgexperts (Fujitsu), который делает оценку, но она приблизительная. Реально используется расширение `pgstattuple`, которое даёт точную картину:

```sql
CREATE EXTENSION pgstattuple;

SELECT * FROM pgstattuple('orders');
```

Возвращает:
- `table_len` — размер таблицы в байтах.
- `tuple_count` — количество живых tuple'ов.
- `tuple_len` — общий размер живых tuple'ов.
- `tuple_percent` — процент места, занятый живыми (идеально 90%+).
- `dead_tuple_count` — количество мёртвых.
- `dead_tuple_percent` — процент мёртвых.
- `free_percent` — процент свободного места в страницах.

Если dead_tuple_percent больше 20% на нагруженной таблице — есть проблема. Если free_percent 40% — таблица разреженная от удалений.

Аналогично для индексов есть `pgstatindex`. Bloat в индексах часто выше чем в таблицах, потому что B-tree структура не любит удалений.

## ANALYZE — как собирается статистика

Переходим к статистике. Всё, что мы говорили про Optimizer, работает на её основе. Устаревшая статистика — ключевая причина плохих планов.

Что собирается. Для каждой колонки таблицы PostgreSQL хранит в `pg_statistic`:

- `null_frac` — доля NULL-значений.
- `avg_width` — средний размер значения в байтах.
- `n_distinct` — оценка количества уникальных значений. Если положительное — абсолютное число, если отрицательное — доля от общего числа строк (например, -0.5 = половина всех строк уникальны).
- `most_common_vals` (MCV) — массив самых частых значений в колонке.
- `most_common_freqs` — их частоты (доли от общего числа).
- `histogram_bounds` — границы гистограммы для оценки range-запросов.
- `correlation` — корреляция между физическим порядком (position в heap) и логическим (значение колонки). Полезно для оценки cost index scan.

Пример. Колонка `country` в таблице orders. Собранная статистика:

```
n_distinct = 200 (двести уникальных стран)
most_common_vals = ['KZ', 'RU', 'US', ...]
most_common_freqs = [0.4, 0.3, 0.1, ...]
```

Optimizer для `WHERE country = 'KZ'` видит: 'KZ' в MCV с частотой 0.4, значит вернёт 40% таблицы. Для `WHERE country = 'RARE_COUNTRY'` (нет в MCV): (1 - sum(most_common_freqs)) / (n_distinct - len(MCV)) = оценка селективности.

Для number-type колонок дополнительно строится гистограмма. По умолчанию 100 buckets — колонка делится на 100 равных по количеству строк диапазонов, запоминаются границы. Для `WHERE age > 25 AND age < 30` Optimizer смотрит, какие buckets попадают в этот диапазон, и оценивает количество строк.

`ANALYZE table_name` собирает эту статистику. Это НЕ full table scan — берётся случайная выборка (по умолчанию 30000 строк, настраивается через `default_statistics_target`). Быстро, но приблизительно. Оценка n_distinct на выборке в 30000 строк для миллиардной таблицы может быть очень неточной, если данные skewed.

`default_statistics_target = 100` — стандартное значение. Можно повысить до 1000 или 10000 для колонок с сложным распределением, но за счёт большего времени ANALYZE и большего размера pg_statistic. Индивидуально:

```sql
ALTER TABLE orders ALTER COLUMN country SET STATISTICS 1000;
ANALYZE orders;
```

Теперь для country собирается 1000-элементная MCV и 1000-точечная гистограмма — гораздо точнее.

## Extended statistics — коррелированные колонки

Обычная статистика собирается для каждой колонки независимо. Optimizer оценивает `WHERE a = X AND b = Y` как произведение независимых селективностей: если a = X встречается в 10% строк, b = Y в 20%, то оба одновременно — 2%.

Но колонки часто коррелированы. Пример: у нас orders с колонками country и city. `WHERE country = 'KZ' AND city = 'Astana'`. По статистике: 40% в KZ, 5% в Astana. Optimizer думает: 2% строк. На самом деле Astana только в KZ, поэтому все 5% Astana находятся в 40% KZ — то есть реально 5%, не 2%. Разница в 2.5 раза, что может привести к неправильному выбору плана.

Для таких случаев есть `CREATE STATISTICS` (PG 10+):

```sql
CREATE STATISTICS orders_country_city (dependencies, ndistinct) 
ON country, city FROM orders;

ANALYZE orders;
```

Собирает дополнительные типы статистики:
- `ndistinct` — количество уникальных комбинаций колонок.
- `dependencies` — функциональные зависимости (если city = Astana, то с высокой вероятностью country = KZ).
- `mcv` (PG 12+) — MCV для комбинаций колонок.

С extended statistics Optimizer корректно оценит запрос выше.

Стоит создавать extended statistics для колонок, которые часто используются вместе в WHERE и явно коррелируют. Не для всех подряд — увеличит время ANALYZE.

## Практика диагностики медленных запросов

Теперь применим всё это к типичной задаче: пользователи жалуются, приложение тормозит, надо найти виновника.

Первый шаг — понять, где проблема. Приложение тормозит из-за самой БД, или из-за сети, или из-за кода? Смотришь HikariCP-метрики: если много pending, connection wait time большой — узкое место в БД или дальше. Смотришь `pg_stat_activity`: если много активных запросов с большими query_duration — да, БД.

Второй шаг — что именно тормозит. Открываешь `pg_stat_statements` и смотришь топ по времени:

```sql
SELECT query, calls, total_exec_time, mean_exec_time, 
       stddev_exec_time, rows,
       100.0 * total_exec_time / SUM(total_exec_time) OVER() AS pct_time
FROM pg_stat_statements
ORDER BY total_exec_time DESC
LIMIT 20;
```

Читаешь: `total_exec_time` — сколько времени в сумме на этот запрос ушло с последнего reset статистики. `mean_exec_time` — среднее. `calls` — количество вызовов. `pct_time` — доля от общего времени БД.

Один запрос занимает 30% всего времени БД — вот он, кандидат.

Особенное внимание — на запросы с большим stddev_exec_time. Это значит: иногда быстро, иногда медленно. Значит план нестабилен (parameter sniffing?) или конкурирует за ресурсы.

Третий шаг — разобрать конкретный запрос. `EXPLAIN (ANALYZE, BUFFERS)`. Смотришь:

- Estimated vs actual rows. Сильное расхождение → ANALYZE.
- Тип узла. Sequential Scan там где ждёшь Index? → проверь индексы, статистику.
- Nested Loop с большим loops? → возможно wrong plan из-за оценки.
- Buffers много `read`? → cache miss, либо холодный, либо недостаточно RAM.
- `Rows Removed by Filter` большое? → индекс не покрывает условия.
- External Sort на диск? → work_mem мал.

Четвёртый шаг — гипотеза и fix. Часто это один из вариантов:

**Добавить индекс**. Смотришь на WHERE и ORDER BY, выбираешь колонки, создаёшь индекс. `CREATE INDEX CONCURRENTLY` в проде, чтобы не блокировать.

**Обновить статистику**. `ANALYZE tablename;`. Может решить wrong plan.

**Extended statistics для коррелированных колонок**. Если Optimizer сильно недооценивает WHERE с несколькими условиями.

**Переписать запрос**. Часто медленные запросы — от плохого SQL. Underlying паттерны: N+1 (тысяча SELECT'ов вместо одного JOIN), OFFSET на большом номере (`LIMIT 20 OFFSET 100000` — читает 100020 строк), недостаточно селективные условия.

**Партиционировать таблицу**. Для сотен миллионов строк — часто единственный настоящий fix. Partition pruning делает запросы быстрыми даже без индексов.

**Увеличить work_mem для конкретного запроса**. `SET work_mem = '256MB'` перед запросом. Не глобально.

**Переписать через CTE или окно-функции**. Иногда переформулирование даёт Optimizer'у больше информации.

Пятый шаг — verify. После fix'а прогони EXPLAIN ANALYZE снова. Стало быстрее? Насколько? Если не удалось — вернись к третьему шагу, попробуй другую гипотезу.

Шестой шаг — regression prevention. Слишком часто fix «работает пока не сломается». Мониторинг типа Grafana с алертом на `pg_stat_statements`: если запрос внезапно стал медленнее чем обычно на 3σ, alert. Автоматический EXPLAIN через `auto_explain` extension в лог для медленных запросов, чтобы историю ошибок анализировать после факта.

## Типичные проблемы, которые встречаются раз в неделю

Опыт диагностики показывает, что определённые паттерны повторяются. Каждый senior их узнаёт с полу-взгляда.

**«После деплоя всё тормозит»**. Приложение задеплоили с новой версией, метрики упали. Смотришь pg_stat_statements — есть новые запросы (реально новые от новой версии), или старые запросы стали в 100 раз чаще (нагрузка сместилась). Fix: чаще всего разработчик забыл индекс или неудачно переписал запрос через ORM.

**«Ночью работает быстро, днём медленно»**. Ночью нагрузка низкая — cache warm, работа быстрая. Днём нагрузка растёт, работой начинают конфликтовать за I/O, за locks. Fix: обычно масштабирование ресурсов или оптимизация топ-1 запроса.

**«Внезапно медленно стало на конкретном запросе»**. Раньше работал за 10 мс, вдруг 3 секунды. Смотришь EXPLAIN — план изменился, теперь Sequential Scan вместо Index. Причина обычно — устаревшая статистика после большого INSERT'а или UPDATE'а. `ANALYZE` исправляет.

**«После REINDEX стало быстро, но снова тормозит через месяц»**. Классика bloat в индексе. Autovacuum не поддерживает индексы в идеальной форме, они постепенно раздуваются. Через несколько месяцев запросы через них замедляются. Fix: `REINDEX INDEX CONCURRENTLY idx_name` периодически, или использовать `pg_repack` для конкретного индекса, или пересмотреть частоту autovacuum на этой таблице.

**«Только один запрос тормозит, остальные быстро»**. Каскадное усложнение: этот один запрос настолько тяжёлый, что занимает шаред ресурсы (I/O, work_mem, locks), и остальные из-за этого страдают. Убить его через `pg_cancel_backend`, найти виновника (обычно ad-hoc отчёт от бизнеса), переписать.

**«Backup портит производительность»**. `pg_dump` на большой БД читает всё, конкурирует за I/O с prod-нагрузкой. Использовать physical backup через `pg_basebackup` с throttling, или снимать логический с replica.

**«Migration положила прод»**. `ALTER TABLE` на большой таблице ждёт lock, за ним встают все SELECT'ы, вся таблица заблокирована. Всегда `SET lock_timeout` перед миграциями. Всегда безопасные ALTER (nullable → backfill → NOT NULL, отдельно от AddColumn).

**«Autovacuum съел I/O»**. Autovacuum на большой таблице работает много, конкурирует за I/O. Reducing `autovacuum_vacuum_cost_delay` неправильно — надо разбить таблицу на партиции или снизить frequency больших autovacuum через настройки.

**«Replication lag взлетел»**. Большая транзакция на primary → большой WAL → standby долго применяет → отставание. Часто виновник — массовый UPDATE или DELETE. Разбивать на batch'и, размер каждого — сколько может standby переварить за секунду.

## Настройка autovacuum для реальной жизни

Дефолтные настройки autovacuum — консервативные, для маленьких БД и общих ситуаций. Для нагруженных прод-систем нужна настройка.

Для типичной OLTP БД среднего размера (десятки GB):

```sql
autovacuum = on
autovacuum_max_workers = 5              -- default 3
autovacuum_naptime = 15s                -- default 60s
autovacuum_vacuum_cost_delay = 2ms      -- default 2ms, но можно снизить
autovacuum_vacuum_cost_limit = 1000     -- default 200
autovacuum_vacuum_scale_factor = 0.1    -- default 0.2
autovacuum_analyze_scale_factor = 0.05  -- default 0.1
```

Для конкретных больших таблиц дополнительно:

```sql
ALTER TABLE orders SET (
    autovacuum_vacuum_scale_factor = 0.02,
    autovacuum_analyze_scale_factor = 0.01,
    autovacuum_vacuum_cost_limit = 2000
);
```

Логика: агрессивнее vacuum и analyze для больших таблиц, больше workers для параллельной работы, меньше cost_delay если I/O позволяет.

Мониторить:

```sql
-- Активные autovacuum сейчас
SELECT pid, datname, relname, phase, 
       heap_blks_total, heap_blks_scanned, heap_blks_vacuumed,
       index_vacuum_count
FROM pg_stat_progress_vacuum;

-- Статистика по таблицам
SELECT relname, n_dead_tup, 
       last_autovacuum, last_autoanalyze,
       autovacuum_count, autoanalyze_count
FROM pg_stat_user_tables
ORDER BY n_dead_tup DESC LIMIT 20;
```

Если видишь таблицу с большим n_dead_tup и last_autovacuum давно — autovacuum не справляется, нужны более агрессивные настройки для неё.

## Заключение

VACUUM — не «служебная операция, о которой можно не думать». Это фундаментальный механизм PostgreSQL, обеспечивающий здоровье базы. Понимать разницу VACUUM, VACUUM FULL, autovacuum, VACUUM FREEZE, знать что мешает работе, уметь настроить для конкретной таблицы — часть обязательной компетенции.

Bloat накапливается из-за MVCC, VACUUM его убирает. Long-running transactions мешают VACUUM. Autovacuum отстаёт на больших таблицах при дефолтных настройках. XID wraparound — редкая, но катастрофическая проблема, требующая freeze. pg_repack как безопасная альтернатива VACUUM FULL для реального сжатия.

Статистика питает Optimizer. Устаревшая статистика = плохие планы. `ANALYZE` регулярно, `default_statistics_target` для сложных колонок, extended statistics для коррелированных пар. Мониторинг через pg_stat_user_tables — как давно ANALYZE, соответствует ли статистика реальности.

Диагностика медленных запросов — практика применения всего: locks, планы, статистика, VACUUM. Стандартный workflow: pg_stat_activity → pg_stat_statements → EXPLAIN ANALYZE → hypothesis → fix → verify. Типовые проблемы (устаревшая статистика, missing index, plan flip, bloat) повторяются, senior узнаёт их сразу.

Дальше — практика. Открывай pg_stat_statements в своём проекте прямо сейчас, бери топ-5 по времени, прогоняй через EXPLAIN ANALYZE, разбирай каждый узел. Замерь bloat на самых больших таблицах через pgstattuple. Проверь autovacuum settings — соответствуют ли реальности твоей нагрузки. Каждый час, потраченный на это, даёт больше понимания чем недели чтения статей.
