# 86. Архитектура СУБД и таблица на 100 миллионов записей

## Зачем нам понимать устройство СУБД

Разработчик, который пишет `SELECT * FROM users WHERE id = 5`, обычно не задумывается о том, что происходит после того, как он нажал Enter. Приложение отправило текст запроса, получило результат — на этом всё. Но когда таблица разрастается до сотен миллионов записей, когда запросы начинают выполняться минутами вместо миллисекунд, когда база данных внезапно перестаёт отвечать, — приходится открывать капот.

СУБД устроена как многослойный конвейер. Каждый слой решает свою задачу: разобрать SQL, выбрать оптимальный план, найти нужные страницы, прочитать их с диска, сложить в память, вернуть результат. И если один из слоёв упирается в ограничение — тормозит вся система. Понимать где именно упёрлось — это и есть работа senior-инженера.

В этом файле мы разберём классическую архитектуру СУБД по схеме из учебника Ramakrishnan и Gehrke — той самой, которая изображена на первой картинке. Потом наложим на неё реальность PostgreSQL с PGBouncer перед ним, shared_buffers в памяти и диском под ним. Отдельно и подробно разберём connection pools — и клиентские (HikariCP в Spring), и серверные (PGBouncer), потому что это критическая часть картины, которую часто упускают. И в конце возьмём реальный пример — таблицу с сотней миллионов записей — и посмотрим, как всё это работает вместе.

## Кто и как отправляет SQL

Наверху схемы три источника команд: веб-формы для конечных пользователей, backend-приложения на Java, Python или чём угодно, и SQL-интерфейс для DBA. Все они разные снаружи, но одинаковые изнутри: каждый в итоге отправляет в СУБД **текст SQL-запроса**. База данных не различает, откуда пришёл запрос — она работает с текстом одинаково, парсит его, оптимизирует, исполняет и возвращает результат.

В реальном приложении, вроде микросервисов КНП, запрос путешествует так. Java-код в Spring Boot вызывает `userRepository.findById(5L)`. JPA/Hibernate превращает это в SQL: `SELECT * FROM users WHERE id = ?`. Этот SQL через JDBC-драйвер должен уйти по TCP-соединению — но здесь есть тонкий момент. TCP-соединение к PostgreSQL — тяжёлая штука. Установка соединения (TCP handshake, TLS handshake, аутентификация в Postgres, backend процесс на сервере) занимает от десятков до сотен миллисекунд. Если каждый HTTP-запрос к сервису открывал бы новое соединение к БД, приложение работало бы катастрофически медленно.

Поэтому между приложением и базой всегда стоят два уровня пулинга. Первый — **клиентский пул** внутри самого приложения, обычно HikariCP в Spring Boot. Он держит небольшое количество (10-30) уже открытых соединений и переиспользует их для запросов. Второй — **серверный пул**, PGBouncer, который стоит перед PostgreSQL и позволяет тысячам клиентских соединений разделять малое количество реальных backend-процессов. Оба пула — критическая часть архитектуры, и их правильная настройка часто определяет производительность системы больше, чем любые оптимизации запросов.

Разберём оба пула детально, прежде чем идти дальше внутрь СУБД.

## Клиентский пул: HikariCP

HikariCP — де-факто стандарт для Java-приложений на 2020-х. Он появился как замена стареющим Apache DBCP и C3P0, показав в бенчмарках производительность в разы выше при более простом коде. В Spring Boot 2.x он подключён по умолчанию.

Идея простая. При старте приложения пул открывает N соединений к базе и держит их в готовности. Когда бизнес-код делает запрос, JPA/Hibernate вызывает `dataSource.getConnection()` — это возвращает не новое соединение, а одно из существующих в пуле. Работа с базой идёт через это соединение. По окончании транзакции (или явного `connection.close()`) соединение возвращается в пул. Оно не закрывается физически — только помечается как свободное, готовое к выдаче следующему клиенту.

Внутри HikariCP хранит два состояния соединений: активные (используемые прямо сейчас) и idle (свободные). Когда приходит запрос на getConnection(), пул смотрит: есть ли idle? Если да — отдаёт быстрее чем за микросекунду. Если нет и общее количество меньше maximumPoolSize — открывает новое соединение (это долго, ~50-100 мс). Если всё занято и лимит достигнут — блокирует поток на connectionTimeout миллисекунд, ожидая освобождения. Если за таймаут никто не освободился — бросает `SQLException`, приложение видит ошибку.

Ключевые настройки HikariCP, каждая из которых влияет на поведение.

**maximumPoolSize** — самая важная. Это верхний предел количества одновременно открытых соединений. Дефолт 10. Общая ошибка — ставить много (50-100), думая «больше — лучше». На самом деле оптимум обычно небольшой, потому что каждое соединение = один активный backend-процесс PostgreSQL, а параллелизм ограничен количеством CPU-ядер на сервере БД. Есть известная формула для оценки: `pool_size = ((core_count * 2) + effective_spindle_count)`, где spindle_count — количество дисков (для HDD это буквально число шпинделей, для SSD — 1). Для сервера с 8 CPU и SSD это 8*2+1 = 17. Слишком большой пул создаёт contention внутри БД: слишком много одновременных запросов дерутся за locks, RAM, диск.

**minimumIdle** — сколько соединений держать открытыми минимум, даже когда нагрузки нет. По умолчанию равно maximumPoolSize (пул всегда полный). Смысл: избежать latency spikes, когда после простоя резко приходит нагрузка и приходится открывать много соединений одновременно. В prod обычно оставляют равным max — пул стабилен по размеру.

**connectionTimeout** — как долго ждать выдачи соединения, прежде чем бросить исключение. Дефолт 30 секунд. Если сервис быстро отвечающий, лучше поставить 2-5 секунд: fail fast лучше, чем висящие запросы. С обвязкой ретраев на уровне приложения короткий таймаут ловит ситуацию, когда пул исчерпан, и позволяет вернуть 503 быстро.

**idleTimeout** и **maxLifetime** — про lifecycle соединения. idleTimeout удаляет соединение из пула, если оно простаивает дольше указанного времени (дефолт 10 минут). maxLifetime закрывает соединение через это время, независимо от активности (дефолт 30 минут). Второй параметр критически важен: сетевое оборудование, load balancers, файрволы могут молча закрывать долгоживущие TCP-соединения. Если соединение простояло час, оно может уже быть мёртвым с точки зрения сети, но HikariCP этого не знает — и следующий запрос через него упадёт с непонятной ошибкой. maxLifetime гарантирует, что соединения периодически пересоздаются, что предотвращает такие случаи.

**leakDetectionThreshold** — если соединение выдано, но не возвращено в пул за это время, HikariCP логирует warning со stack trace того места, где соединение было взято. Полезно для отладки утечек: кто-то забыл вызвать close(). В prod обычно ставят 30-60 секунд, в тестах — 5 секунд для быстрого поиска багов.

**validationTimeout** и валидационный запрос — как проверять, что соединение живо. HikariCP использует JDBC4 метод `Connection.isValid()`, который отправляет лёгкий ping на сервер. Если соединение из пула отдаётся клиенту и isValid возвращает false, HikariCP тихо удаляет мёртвое соединение и берёт следующее.

Настройка HikariCP в Spring Boot делается через application.yml:
```yaml
spring:
  datasource:
    hikari:
      maximum-pool-size: 20
      minimum-idle: 20
      connection-timeout: 3000
      idle-timeout: 600000
      max-lifetime: 1800000
      leak-detection-threshold: 30000
```

Диагностика HikariCP в проде идёт через JMX-метрики или через Micrometer:
- `hikaricp_connections_active` — активные (в использовании) соединения.
- `hikaricp_connections_idle` — свободные.
- `hikaricp_connections_pending` — потоки, ждущие соединения.
- `hikaricp_connections_timeout_total` — сколько раз клиенты не дождались.
- `hikaricp_connections_acquire_seconds` — гистограмма времени получения соединения.

Если pending регулярно больше нуля, а acquire time растёт — пул исчерпан, нужно либо увеличивать размер, либо разбираться, почему запросы держат соединения долго (медленные запросы, забытые транзакции).

## Серверный пул: PGBouncer

HikariCP решает проблему на клиенте, но не решает её на сервере. Представь: у тебя 50 подов Spring Boot, у каждого HikariCP-пул на 20 соединений. Итого потенциально 1000 соединений к PostgreSQL. И каждое из них — это backend-процесс на сервере БД.

Здесь важно понять модель процессов PostgreSQL. В отличие от многих других СУБД (MySQL, SQL Server), которые используют потоки внутри одного процесса, PostgreSQL — **process-per-connection**. Каждое клиентское TCP-соединение обслуживается отдельным процессом операционной системы. Это дизайн-выбор, унаследованный от 90-х: процессы дают лучшую изоляцию (сбой одного не валит остальных), проще управление памятью. Но за это платят: каждый процесс потребляет 5-15 MB памяти (для процессной структуры, private кеша каталогов, work_mem резерва), и создание нового процесса — операция на несколько миллисекунд.

Тысяча активных backend-процессов даёт следующее: 10-15 GB памяти только на служебные структуры процессов, тысячу активных context switch'ей в OS scheduler'е, тысячу открытых соединений в socket table ядра. Если у сервера 32 GB RAM, треть уходит непонятно куда, ещё не начав работать. Плюс параметр PostgreSQL `max_connections` обычно ограничен сотней-двумя (увеличивать выше — жрёт shared memory, все backend'ы должны видеть общие структуры locks и таблиц). При тысяче попыток соединений большинство просто получит `FATAL: sorry, too many clients already`.

Здесь на сцену выходит PGBouncer. Это лёгкий (5-10 MB памяти) прокси, написанный на C, single-threaded с event loop (как nginx). Приложения (HikariCP-пулы) подключаются к нему на порту 6432 вместо 5432, а он держит **пул реальных соединений к PostgreSQL** — обычно 20-100. Клиентское соединение и серверное соединение разделены: клиент может держать своё «соединение» с PGBouncer постоянно, а реальный backend PostgreSQL выделяется только на время активной работы.

Как это работает механически. HikariCP делает запрос через своё соединение к PGBouncer. PGBouncer видит: клиент начал транзакцию (`BEGIN` или неявно первый оператор). Берёт из пула свободное соединение к настоящему PostgreSQL и «привязывает» его к этому клиенту. Все запросы клиента идут через этот backend. Когда клиент делает `COMMIT` или `ROLLBACK` (в transaction pooling режиме), PGBouncer отвязывает backend от клиента и возвращает его в пул. Следующая транзакция того же клиента может пойти через уже другой backend.

Три режима работы. **Session pooling** — самый безопасный. PGBouncer выдаёт backend клиенту при подключении, забирает при отключении. По сути это эквивалентно прямому подключению, никакой экономии соединений нет; экономится только на TCP-handshake и Postgres-аутентификации, которые PGBouncer делает один раз с сервером и держит.

**Transaction pooling** — основной рабочий режим для микросервисов. PGBouncer держит backend прикреплённым к клиенту только на время одной транзакции. После COMMIT — возвращает в пул. Это даёт огромную экономию: если 100 клиентов в среднем 90% времени idle (между транзакциями), 10 реальных backend'ов покрывают их всех. Но за это платят ограничениями. Prepared statements не работают штатно (они кэшируются per-connection, а следующая транзакция клиента может попасть на другое соединение и запрос упадёт). Session-level переменные (`SET SESSION xxx`) теряются между транзакциями. `LISTEN/NOTIFY` не работает (это session-level механизм). Advisory locks на уровне сессии — тоже.

Для Spring/JPA это в основном работает, но с одной большой оговоркой. Драйвер PostgreSQL JDBC умеет server-side prepared statements: после нескольких выполнений одного и того же запроса создаётся prepared statement на сервере, что ускоряет последующие выполнения. С PGBouncer в transaction mode это ломается. Есть варианты решения. Либо отключить prepared statements в JDBC-драйвере: `prepareThreshold=0` в connection string, но тогда каждый запрос парсится и планируется заново — потеря производительности. Либо использовать PGBouncer 1.21+ с включённой поддержкой протокольных prepared statements: `max_prepared_statements = 100` в конфиге PGBouncer, тогда PGBouncer сам управляет prepared statements через ре-эмиссию `PARSE` при переключении соединений. Либо перейти на session pooling (потеряв главное преимущество PGBouncer).

**Statement pooling** — самый агрессивный режим, backend возвращается в пул после каждого statement. Даже транзакции в несколько statements ломаются. Практически не используется, только для очень специфичных workload'ов вроде read-only fanning.

Настройки PGBouncer в конфиге:
```ini
[databases]
knp = host=postgres-primary port=5432 dbname=knp

[pgbouncer]
pool_mode = transaction
max_client_conn = 1000        ; сколько клиентов одновременно
default_pool_size = 30        ; реальных backend'ов на один pool (database+user)
reserve_pool_size = 5         ; дополнительные при пиковой нагрузке
server_idle_timeout = 600     ; закрывать backend после 10 мин простоя
```

`max_client_conn` × `default_pool_size` определяет, во сколько PGBouncer сжимает соединения. Тысяча клиентов на 30 backend'ов — соотношение 33:1. Это работает, если типичная транзакция короткая (миллисекунды), а между транзакциями клиенты не держат соединение занятым.

Мониторить PGBouncer через админ-консоль (специальный виртуальный database `pgbouncer`):
- `SHOW POOLS` — состояние пулов: активные, ожидающие, idle клиенты и серверы.
- `SHOW STATS` — статистика запросов, latency, throughput.
- `SHOW CLIENTS` — список текущих клиентских соединений.
- `SHOW SERVERS` — список текущих серверных соединений.

Ключевые тревожные сигналы: `sv_idle = 0` при `cl_waiting > 0` означает, что пул исчерпан и клиенты стоят в очереди. `sv_used` близко к `default_pool_size` — работает на пределе, нужно увеличивать.

## Полная картина двух пулов

Теперь можно нарисовать полную картину. У тебя 50 подов Spring Boot. В каждом HikariCP с `maximumPoolSize = 20`. Итого потенциально 50 × 20 = 1000 клиентских соединений к БД. Все они идут в PGBouncer с `max_client_conn = 1000` и `default_pool_size = 30`. PGBouncer сжимает эту тысячу до 30 реальных backend-процессов PostgreSQL.

Почему нужны оба пула, а не только один? На клиенте (HikariCP) — потому что установка TCP-соединения даже до PGBouncer стоит миллисекунды, и держать соединения открытыми выгоднее. Плюс HikariCP отвечает за JDBC-семантику: connection.setAutoCommit(false), timeout настройки, connection validation. На сервере (PGBouncer) — потому что реальные backend-процессы PostgreSQL дорогие, и без серверного пула тысяча клиентов задавит сервер.

Sizing двух пулов — искусство. Общее правило: клиентский пул должен быть чуть больше, чем реально нужно (запас для burst нагрузки, чтобы не ждать), серверный — жёстко ограничен возможностями сервера БД. Формула Хикари pool_size = 2×core+spindle применима к серверному пулу PGBouncer: если у сервера 16 CPU и SSD, разумно поставить 30-40. Клиентские пулы должны в сумме давать соотношение с серверным примерно 5-10:1. Если 50 подов × 20 = 1000 клиентских, серверный 100 — соотношение 10:1, приемлемо.

Мониторинг сквозной: измерять time to acquire connection в HikariCP (это может включать ожидание освобождения PGBouncer-backend'а), количество активных backend'ов на PostgreSQL-стороне через `pg_stat_activity`, время между `query_start` и текущим временем для долгих запросов, wait events для понимания, чего именно ждут.

Теперь, когда мы разобрали, как запрос вообще доходит до СУБД, продолжим вглубь.

## Query Evaluation Engine — четыре компонента, которые превращают SQL в результат

Когда backend-процесс PostgreSQL получил текст запроса, за дело берётся **Query Evaluation Engine** — сердце СУБД. Он состоит из четырёх взаимосвязанных компонентов, каждый из которых передаёт результат следующему.

Первый — **Parser**. Он получает текст SQL и превращает его в структурированное дерево (AST, abstract syntax tree). Сначала лексический анализ разбивает строку на токены: `SELECT`, имя колонки, имя таблицы, `WHERE`, оператор сравнения, литерал. Потом синтаксический анализ проверяет, соответствует ли последовательность токенов грамматике SQL, — если написали `SELCT` вместо `SELECT`, ошибка ловится здесь. Затем семантический анализ обращается к системному каталогу (о нём ниже) и проверяет, что таблица `users` реально существует, что колонка `id` в ней есть, что типы совместимы для сравнения. Если что-то не так, приложение получает `SQLException` вроде `relation "users" does not exist`. Если всё хорошо, получается корректное дерево запроса.

Парсинг — это на самом деле нетривиальная работа. Грамматика SQL сложная: подзапросы, common table expressions (CTE), window functions, lateral joins, complex expressions. Парсер PostgreSQL — сгенерированный из BNF-грамматики через Bison, тысячи строк правил. При каждом запросе парсер снова проходит по тексту. Это одна из причин, почему prepared statements быстрее: парсинг делается один раз при подготовке, потом переиспользуется. Именно поэтому кэш parsed statements существует в HikariCP-соединениях, и именно поэтому PGBouncer transaction mode ломает это.

Дальше в игру вступает **Optimizer** — самая интеллектуальная часть СУБД. Одну и ту же логическую задачу можно решить множеством разных способов. Для запроса с JOIN трёх таблиц существуют разные порядки соединения (сначала A с B, потом с C, или сначала B с C, потом с A), разные алгоритмы соединения (nested loop, hash join, merge join), разные способы доступа к данным (последовательное сканирование или обход индекса). Каждая комбинация — это отдельный план выполнения, и все они дают одинаковый результат, но с разной стоимостью.

Optimizer перебирает планы и оценивает стоимость каждого. Для оценки он использует **статистику** — заранее собранную информацию о таблицах: сколько в них строк, какие значения встречаются чаще, как распределены данные. Эта статистика хранится в системном каталоге и обновляется командой `ANALYZE` (обычно автоматически через autovacuum). Optimizer знает, что случайное чтение страницы с диска стоит одно, последовательное — другое, обработка одной строки в памяти — третье. Складывая эти стоимости для каждого шага плана, он выбирает самый дешёвый вариант.

Для маленького количества таблиц (до 12 по умолчанию) Optimizer использует dynamic programming: он реально перебирает все комбинации порядков соединения и выбирает лучший. Это гарантирует оптимум, но экспоненциально по количеству таблиц (12 таблиц — уже сотни миллионов комбинаций). Для большего количества включается GEQO (genetic query optimizer) — эвристический алгоритм на основе генетических методов, который не гарантирует оптимум, но работает за разумное время.

Именно поэтому устаревшая статистика — одна из самых частых причин медленных запросов в проде. Если Optimizer думает, что в таблице тысяча строк, а на самом деле сто миллионов, он выберет план, катастрофически неоптимальный для реальных данных. Это классический случай, когда `EXPLAIN` показывает Sequential Scan там, где должен быть Index Scan.

Выбранный план передаётся в **Plan Executor**. Это движок, который исполняет план шаг за шагом. Внутри он работает по так называемой модели итератора (или Volcano model, названной по проекту Volcano из 90-х). Каждый узел плана — это оператор с методами `open`, `next` и `close`. Executor вызывает `next` у корневого оператора, тот в свою очередь вызывает `next` у своих детей, и так далее вниз по дереву. Строки текут снизу вверх, от источников (сканы таблиц и индексов) через промежуточные операторы (фильтры, соединения, сортировки) к корню, откуда они уходят клиенту.

Volcano model элегантна, но имеет overhead: каждая строка проходит через много виртуальных вызовов `next()`. Для аналитических запросов, обрабатывающих миллионы строк, это заметно. Современные аналитические СУБД (например, DuckDB, ClickHouse) используют более продвинутые модели: **vectorized execution** (обработка батчей строк вместо по одной, амортизирующая overhead) или **push-based execution** (данные толкаются от источника вверх, а не тянутся). PostgreSQL исторически использует классический Volcano, что делает его лучше в OLTP и хуже в OLAP по сравнению со специализированными аналитическими системами.

Сами операторы — это код, который реализует конкретные алгоритмы. **Operator Evaluator** — общее название для этой библиотеки операторов. Sequential Scan просто читает страницы таблицы по порядку и возвращает строки. Index Scan обходит B-tree, получает идентификаторы строк, читает нужные страницы из heap. Nested Loop Join берёт строку из левого источника и для неё вызывает правый источник в цикле. Hash Join сначала строит хеш-таблицу по одному источнику, потом сканирует второй и делает лукапы. Sort накапливает строки, сортирует их и отдаёт по порядку. Каждый из этих операторов — своя реализация, оптимизированная под свою задачу.

## Files and Access Methods — как СУБД видит данные

Executor не работает с диском напрямую. Между ним и физическим хранилищем находится ещё один слой абстракции — **Files and Access Methods**. Это модуль, который знает, как таблица разложена в файлы на диске и как её оттуда доставать.

Таблица физически хранится как **heap** — набор страниц фиксированного размера, обычно 8 килобайт в PostgreSQL. Каждая страница содержит несколько строк (tuple'ов) плюс служебные метаданные. Индексы хранятся отдельно — обычно как B-tree, сбалансированное дерево, которое позволяет быстро находить нужную строку по ключу. У таблицы может быть много индексов, и каждый — это отдельный файл.

Access Methods предоставляют операторам разные стратегии доступа к данным. Sequential scan просто читает все страницы таблицы одну за другой — это дорого, но эффективно с точки зрения ввода-вывода (последовательное чтение с диска в разы быстрее случайного). Index scan обходит B-tree, находит идентификаторы нужных строк, потом идёт в heap и читает эти строки. Bitmap scan — гибрид: сначала по индексу собираются идентификаторы во внутренний битмап, потом страницы читаются по возрастанию номеров, чтобы получить последовательный доступ. Index-only scan — оптимизация, когда все запрошенные колонки уже есть в индексе: в heap идти не нужно, читаем только индекс.

Выбор между этими стратегиями делает Optimizer на этапе планирования. И вот тут проявляется важное свойство: чем больше данных нужно прочитать, тем более выгодным становится sequential scan по сравнению с index scan. Если запрос затрагивает 1% таблицы — index scan быстрее. Если 90% — sequential scan быстрее, потому что случайные чтения в heap по индексу оказываются дороже, чем один большой последовательный проход.

## Buffer Manager — почему база данных быстрая

Все запросы в конечном счёте упираются в скорость диска. RAM работает в сотни раз быстрее SSD и в десятки тысяч раз быстрее HDD. Если бы каждый запрос действительно шёл на диск, база данных была бы невыносимо медленной. Поэтому у СУБД есть свой кэш страниц в памяти — **Buffer Manager**.

В PostgreSQL этот кэш называется `shared_buffers`. Он разделяется между всеми backend-процессами через общую память операционной системы (реализовано через POSIX shared memory или System V shm — в зависимости от версии и настроек). Обычно его настраивают на четверть оперативной памяти сервера: если на сервере 32 GB RAM, разумно поставить `shared_buffers = 8GB`. Внутри — массив слотов размером 8 KB каждый, и каждый слот может содержать одну страницу таблицы или индекса.

Когда Access Method просит у Buffer Manager страницу номер N таблицы T, тот проверяет, есть ли эта страница уже в кэше. Если да — просто возвращает указатель на память, никакого диска. Если нет — выбирает какую-нибудь малополезную страницу для вытеснения (по алгоритму, приближающему LRU — обычно CLOCK-sweep), выселяет её (если она была изменена — сначала пишет на диск), читает нужную страницу с диска, кладёт в освободившийся слот и возвращает указатель. Все дальнейшие обращения к этой странице будут cache hit.

Соотношение cache hit и cache miss — ключевая метрика производительности OLTP-системы. Для нагруженной базы данных нормальный показатель — больше 99% попаданий в кэш. Если он падает ниже, значит либо `shared_buffers` слишком мал для рабочего набора данных, либо запросы гуляют по всей базе (например, идёт большой аналитический запрос, который вытесняет OLTP-данные из кэша). PostgreSQL, кстати, имеет специальный механизм — ring buffer для больших последовательных сканов, — который защищает основной кэш от такого вытеснения. Он подробнее в следующем файле.

Изменения данных тоже идут через Buffer Manager. UPDATE не пишет напрямую на диск — он модифицирует страницу в памяти и помечает её как «грязную» (dirty). На диск грязные страницы попадают позже: постепенно — через фоновый процесс bgwriter, и полностью — при checkpoint. Между Buffer Manager и диском есть ещё один уровень кэша — page cache операционной системы, о котором ещё поговорим. Получается двухуровневое кэширование: сначала shared_buffers, потом OS page cache, и только потом диск.

## Disk Space Manager и физическое хранение

Под Buffer Manager находится **Disk Space Manager** — самый низкоуровневый слой СУБД. Он ничего не знает про SQL, индексы или транзакции; его задача — читать и писать страницы фиксированного размера на диск. Buffer Manager говорит: «прочитай страницу номер 42 из файла F в этот буфер памяти» — Disk Space Manager делает системный вызов `read(fd, buffer, 8192)`, ждёт, пока данные придут с диска, отдаёт управление обратно.

Организация файлов на диске в PostgreSQL простая: каждая таблица и каждый индекс — это отдельный файл в директории `base/<database_oid>/<relation_oid>`. Если размер файла превышает гигабайт, PostgreSQL сегментирует его: `16389`, `16389.1`, `16389.2`. Внутри файла страницы располагаются последовательно, номер страницы напрямую соответствует смещению в файле (страница 42 — это байты с 344064 по 352255).

Файл таблицы хранит только основные данные (main fork). Но у каждой таблицы есть ещё несколько связанных файлов — так называемых forks. Free Space Map (файл с суффиксом `_fsm`) хранит информацию о том, сколько свободного места в каждой странице — это нужно, чтобы при INSERT быстро найти страницу, куда влезет новая строка. Visibility Map (`_vm`) — битовая карта, где для каждой страницы отмечено, все ли её строки видимы всем текущим транзакциям; это позволяет ускорять index-only scan и делать VACUUM более эффективным. Об этих механизмах подробнее — в следующем файле, посвящённом внутренностям.

## Транзакции, локи и восстановление

Параллельно с основным конвейером — от парсера до диска — в СУБД работают три модуля, обеспечивающих свойства ACID: Transaction Manager, Lock Manager и Recovery Manager.

**Transaction Manager** отвечает за жизненный цикл транзакций. Когда приложение делает `BEGIN`, транзакция получает уникальный номер — XID (transaction ID), монотонно возрастающий счётчик. Каждое изменение строк помечается этим XID: строка «знает», какая транзакция её создала и какая удалила. При COMMIT транзакция записывается как успешная, при ROLLBACK — как отменённая. PostgreSQL при откате не удаляет изменения физически; они просто становятся невидимы для других транзакций, потому что помечены XID отменённой транзакции. Физическая очистка происходит позже, при VACUUM.

**Lock Manager** координирует одновременный доступ. Когда две транзакции пытаются одновременно изменить одну строку, СУБД должна как-то это разрулить: либо серийно (одна ждёт другую), либо через версионирование. PostgreSQL использует комбинированный подход: писатели блокируют друг друга (row-level locks), но читатели не блокируют писателей и наоборот благодаря MVCC — многоверсионной модели. О ней подробнее ниже. Кроме row-level, есть более крупные локи: table-level (при DDL), predicate locks (для SERIALIZABLE изоляции).

**Recovery Manager** обеспечивает выживание данных при сбоях. Основной механизм — **Write-Ahead Log** (WAL). Правило простое: любое изменение сначала записывается в специальный журнал на диске, и только потом (позже) — в основные файлы данных. Это критично, потому что запись в файлы данных — операция случайного доступа (страницы разбросаны), а WAL пишется последовательно, что в разы быстрее. Если сервер упал, при перезапуске Recovery Manager читает WAL и «доигрывает» все зафиксированные изменения, которые ещё не успели попасть в файлы данных. Так гарантируется durability: если приложение получило подтверждение COMMIT, изменения не потеряются даже при внезапном отключении питания.

При каждом COMMIT PostgreSQL записывает commit-record в WAL и вызывает `fsync` — системный вызов, гарантирующий, что данные физически попали на устройство, а не остались в буфере ОС. Это медленная операция (на NVMe SSD — десятки микросекунд, на HDD — миллисекунды), и она напрямую ограничивает пропускную способность транзакций. Отсюда важность настройки `synchronous_commit` и группового коммита (когда несколько транзакций объединяют свои fsync'и в один).

## Системный каталог — метаданные о самих себе

Есть ещё один компонент, который упоминается в схеме отдельно, — **System Catalog**. Это набор таблиц, где хранится информация о самой базе данных: какие есть таблицы, какие у них колонки, какие типы данных, какие индексы, какие права у пользователей, какая статистика собрана для оптимизатора. В PostgreSQL это схема `pg_catalog`, там таблицы вроде `pg_class` (список всех отношений), `pg_attribute` (колонки), `pg_index` (индексы), `pg_statistic` (статистика).

Интересное свойство: системный каталог сам является набором таблиц PostgreSQL. То есть база данных описана в терминах самой себя. Это позволяет использовать обычный SQL для интроспекции: `SELECT * FROM pg_class WHERE relname = 'users'` покажет метаданные таблицы users. Когда вы делаете `\d users` в psql, это просто запрос к `pg_class` и `pg_attribute`.

Каталог используется на всех этапах обработки запроса. Парсер обращается к нему, чтобы проверить существование таблиц и колонок. Оптимизатор читает статистику для оценки стоимости планов. Executor узнаёт из каталога, где физически лежат файлы таблиц. Изменения структуры (DDL) — CREATE TABLE, ALTER TABLE, DROP INDEX — на низком уровне сводятся к INSERT, UPDATE и DELETE в каталоге.

## Как всё это работает вместе на примере одного запроса

Соберём картину целиком. Приложение отправляет `SELECT * FROM users WHERE id = 5`. Java-код вызывает `dataSource.getConnection()` — HikariCP отдаёт готовое соединение (или ждёт освобождения). Через это соединение запрос уходит по TCP в PGBouncer. PGBouncer берёт свободный backend из своего пула и передаёт запрос ему. Backend-процесс PostgreSQL начинает обработку.

Parser разбирает текст, обращается к каталогу, проверяет что таблица `users` есть и колонка `id` тоже, строит дерево запроса. Optimizer читает статистику: в таблице миллион строк, есть уникальный индекс на `id`, значит фильтр вернёт максимум одну строку. Он оценивает: Sequential Scan прочитает миллион строк — дорого. Index Scan на primary key — прочитает пару страниц индекса плюс одну страницу heap — дёшево. Выбирает Index Scan.

Plan Executor запускает Index Scan оператор. Тот через Access Method просит у Buffer Manager корневую страницу B-tree индекса. Buffer Manager проверяет: страница в кэше? Да — возвращает указатель на память. Access Method делает бинарный поиск в корне, находит указатель на промежуточную страницу с ключом 5. Просит её у Buffer Manager — та тоже в кэше. Находит указатель на листовую страницу. Просит её — здесь может быть cache miss, потому что листовых страниц много. Buffer Manager обнаруживает, что нужной страницы в кэше нет. Он выбирает жертву для вытеснения, при необходимости пишет её на диск, затем через Disk Space Manager делает `read` для нужной страницы. Системный вызов уходит в ядро, ядро проверяет page cache, если и там нет — идёт до диска. С диска приходят 8 KB, кладутся в буфер, Access Method получает страницу.

В листовой странице — запись с ключом 5 и TID (page 42, offset 3) в heap. Access Method запрашивает страницу 42 у Buffer Manager — снова через все уровни кэша. Получив страницу, смотрит на line pointer #3, находит смещение tuple, читает его. Executor получает строку от Index Scan, поднимает её в корень плана, отдаёт клиенту. Backend отправляет данные обратно в PGBouncer, тот — в HikariCP, тот — в JDBC-драйвер, тот декодирует в Java-объект, JPA превращает в entity, приложение получает результат.

Всё это занимает миллисекунды, если данные в кэше, — или десятки миллисекунд, если пришлось идти на диск. При десятках тысяч таких запросов в секунду системе есть что делать, но она справляется благодаря кэшированию, индексам, оптимизатору, пулингу соединений и продуманной архитектуре.

## RAM: shared_buffers и OS page cache

Про shared_buffers уже говорили — это внутренний кэш PostgreSQL, обычно 25% RAM сервера. Но есть тонкость: PostgreSQL исторически полагается ещё и на page cache операционной системы. Это второй уровень кэширования.

Работает это так. Когда PostgreSQL читает страницу с диска, она проходит через ядро: сначала попадает в OS page cache, потом копируется в shared_buffers. При следующем чтении, если страница уже не в shared_buffers, но всё ещё в OS page cache, дисковое устройство не тревожится — данные достаются из RAM, просто через ядро. Это существенно ускоряет работу.

Именно поэтому shared_buffers не имеет смысла ставить на 90% памяти сервера. Если поставить, у OS не останется места для page cache, и эффективность двухуровневого кэша упадёт. Классическая рекомендация — 25% RAM: shared_buffers, остальное для page cache и всего прочего.

Кроме shared_buffers у PostgreSQL есть ещё специальные области памяти. **work_mem** — на каждый оператор в запросе (Sort, Hash Aggregate, Hash Join); если результат сортировки не помещается в work_mem, происходит spill на диск во временные файлы (temp files), что резко замедляет операцию. Здесь важно понимать: work_mem это не общая память, а на каждый operator. Один сложный запрос с несколькими sort'ами и hash join'ами может использовать несколько work_mem одновременно. Плюс каждый backend может иметь несколько таких запросов. Итого потребление памяти растёт как `n_backends × n_operators_per_query × work_mem`. Настройка work_mem слишком высоко может привести к OOM при burst нагрузке.

**maintenance_work_mem** — для VACUUM, CREATE INDEX, обычно больше, потому что эти операции разовые и им можно дать много памяти. **wal_buffers** — общий буфер для WAL, обычно 16 MB.

CPU в базе используется на всех этапах: парсинг, оптимизация, исполнение операторов. Для точечных OLTP-запросов CPU практически не нагружен. Но большой Hash Join, сортировка миллионов строк, агрегация — всё это CPU-bound. PostgreSQL умеет параллельные запросы (parallel query): один большой запрос может использовать несколько CPU одновременно, поднимая несколько worker-процессов. Это полезно для аналитики, но не для OLTP.

## Диск: data files и WAL

Внизу схемы — диск. И здесь нужно понимать, что PostgreSQL пишет на диск в двух совершенно разных режимах.

Файлы данных пишутся случайно (random I/O). Когда меняется строка в середине таблицы, страница с этой строкой вытесняется из shared_buffers и пишется на диск в свою позицию в файле. Разные запросы модифицируют разные страницы, — получается много мелких записей в разных местах. HDD от такой нагрузки задыхается: механический seek head перед каждой записью занимает миллисекунды. SSD справляется гораздо лучше — там нет механики.

WAL пишется последовательно (sequential I/O). Это по сути append-only лог: каждый новый record дописывается в конец текущего WAL-сегмента. Никаких случайных позиций. Даже HDD это переваривает быстро — головке не нужно позиционироваться, она уже там, где надо. Именно поэтому запись в WAL не так дорога, как запись данных, — и это одна из причин, почему сама идея WAL работает: мы платим быстрым sequential write при commit, а дорогой random write отложен до checkpoint.

Отсюда важная рекомендация продакшена: **WAL на отдельном диске**. Если у тебя один диск на всё, сильная нагрузка на данные (checkpoint пишет много страниц) конкурирует с WAL за IOPS диска, и latency коммитов растёт. Разнеси их на разные volumes — WAL получит свой sequential-канал без помех.

Синхронность коммитов настраивается параметром `synchronous_commit`. По умолчанию `on` — при COMMIT ждём fsync WAL, только потом отвечаем клиенту. Это гарантирует durability: даже при внезапном обесточивании подтверждённые транзакции переживут. Ценой становится latency: fsync на NVMe SSD занимает 20-100 микросекунд, на SATA SSD — сотни микросекунд, на HDD — миллисекунды. Для приложений, где потеря последних 200 миллисекунд транзакций допустима (не финтех), можно поставить `synchronous_commit = off` и получить 3-10x больше throughput. Для финансовых систем — только `on`.

## Таблица на 100 миллионов записей: как это выглядит физически

Теперь давайте сделаем это конкретным. Представь таблицу `orders` в КНП: идентификатор заказа, идентификатор пользователя, время создания, статус, сумма, страна, описание. Средняя строка занимает около 200 байт. Сто миллионов строк — это примерно 20 гигабайт основных данных (heap). Плюс индексы: первичный ключ занимает пару гигабайт, каждый вторичный индекс — от одного до нескольких гигабайт. С учётом bloat (мёртвые версии строк от UPDATE/DELETE), WAL, временных файлов на диске лежит порядка 50 гигабайт.

Физически это выглядит так. Файл heap таблицы — примерно 2.6 миллиона страниц по 8 KB. Файлы индексов — тысячи или миллионы страниц каждый. B-tree первичного ключа для 100 миллионов записей имеет глубину примерно 3-4 уровня: корень с несколькими сотнями ключей, промежуточные страницы, листья со ссылками на heap. Точечный запрос по PK читает 3-4 страницы индекса плюс одну страницу heap — итого 4-5 страниц, обычно все в кэше, ответ приходит меньше чем за миллисекунду.

Такая таблица в проде — это уже серьёзное хозяйство. Она не помещается в shared_buffers целиком (если только у тебя не сервер с 128 GB RAM, а даже тогда только-только влезет). Значит, любой запрос, который читает существенную часть таблицы, будет упираться в диск. Значит, VACUUM такой таблицы идёт часами. Значит, любой ALTER TABLE, требующий блокировки, — риск задержать всю систему. Значит, статистика должна поддерживаться в актуальном состоянии, иначе Optimizer будет выбирать неверные планы. И значит, каждый запрос нужно продумывать: какие индексы задействует, сколько строк реально нужно прочитать, влезет ли рабочий набор в память.

## Какие запросы дешёвые, а какие дорогие

Самые дешёвые запросы — это те, где условие фильтрации однозначно и селективно, и есть подходящий индекс. Классика: `WHERE id = 42`. Optimizer идёт в B-tree первичного ключа, находит листовую страницу за пару обращений (обычно все в кэше), получает TID, читает одну страницу heap, возвращает строку. Всё вместе — доли миллисекунды. Аналогично для `WHERE id IN (1, 5, 42)` — просто три таких лукапа подряд.

Чуть дороже — запросы с range по индексу. `WHERE id BETWEEN 1000 AND 1100` вернёт сто строк, для этого нужно пройти по нескольким листовым страницам индекса и прочитать сотню страниц heap. Если heap-страницы кучкуются (потому что записи вставлялись подряд), это быстро. Если разбросаны — медленнее из-за случайного I/O, но всё равно приемлемо.

Средние по стоимости запросы — те, где нужен вторичный индекс. `WHERE user_id = 12345` без индекса на user_id — это sequential scan всех двадцати гигабайт, минуты работы. С индексом — если у пользователя 100 заказов, это 100 лукапов в heap, десятки-сотни миллисекунд. Разница катастрофическая. Отсюда правило: любая колонка, по которой часто фильтруют или сортируют, должна быть проиндексирована.

Но индексы — это не бесплатно. Каждый индекс замедляет INSERT, UPDATE и DELETE (нужно обновлять индекс), занимает диск, требует своего VACUUM. Поэтому индексируют только то, что реально используется. Найти неиспользуемые индексы можно через `pg_stat_user_indexes` — те, у которых `idx_scan = 0` за долгое время, кандидаты на удаление.

Дорогие запросы начинаются там, где нужно прочитать значительную часть таблицы. `SELECT COUNT(*) FROM orders WHERE status = 'paid'` — если оплаченных 50 миллионов из ста, ни один индекс не поможет (Optimizer сам это поймёт и выберет sequential scan). Прочесть 20 гигабайт с диска — это минуты. Если такой запрос нужен постоянно, единственный способ его ускорить — заранее посчитанные метрики: materialized view, обновляемое по расписанию, или счётчик, обновляемый триггером на INSERT.

`SELECT * FROM orders ORDER BY created_at DESC LIMIT 100` — если нет индекса на created_at, это катастрофа. Optimizer вынужден прочитать всю таблицу и отсортировать её только чтобы взять первые сто строк. Если work_mem мал, сортировка не помещается в память и уходит во временные файлы на диск, что ещё умножает стоимость. С индексом на created_at такой запрос выполняется мгновенно: обход индекса в обратном порядке, первые сто TID'ов, сто heap-лукапов.

Ещё более коварные запросы — с `LIKE '%something%'`. Ведущий wildcard делает B-tree индекс бесполезным: невозможно за один спуск дерева найти все строки, содержащие подстроку. Только полный проход. Решение — специализированные индексы: GIN с расширением pg_trgm для триграммного поиска, или полнотекстовый поиск с tsvector/tsquery.

Убийственно дорогие запросы — массовые UPDATE и DELETE. `UPDATE orders SET status = 'archived' WHERE created_at < NOW() - INTERVAL '1 year'` может задеть тридцать миллионов строк. Каждая обновлённая строка порождает новую версию tuple'а, WAL-запись, обновление всех индексов. Это генерирует десятки гигабайт WAL, забивает реплики, блокирует VACUUM, держит одну гигантскую транзакцию. Правильный способ — batch: цикл по 10 тысяч строк с COMMIT после каждого батча и небольшой паузой, чтобы система успевала обрабатывать другую нагрузку.

Отдельно упомянем N+1 — паттерн из мира ORM. Приложение сначала запрашивает список из тысячи пользователей, потом для каждого делает отдельный SELECT их заказов. Тысяча запросов вместо одного. Каждый запрос — парсинг, планирование, сетевой roundtrip. Даже если сами запросы быстрые (миллисекунды), в сумме это секунды. Лечится JOIN'ами, batch fetching, IN-запросами.

## Что «колбасит» базу данных в проде

Теперь про типичные проблемы, из-за которых база данных начинает вести себя странно. Каждая из них имеет свою механику, свои симптомы и свой способ лечения.

Первое и самое частое — **устаревшая статистика**. После массовой загрузки данных, после большого UPDATE, после создания нового индекса Optimizer может опираться на данные, которые уже не соответствуют реальности. В результате он выбирает план, оптимальный для миллиона строк, а таблица уже стомиллионная. Симптом: EXPLAIN показывает Sequential Scan там, где явно должен быть Index Scan; или estimated rows сильно отличается от actual rows. Лечение: `ANALYZE table_name`.

Похожая проблема — **parameter sniffing**. Prepared statement закешировал план на основе конкретных значений параметров, потом эти параметры поменялись, а план остался неоптимальным. Симптом: один и тот же запрос иногда работает быстро, иногда медленно. Настройка `plan_cache_mode = force_custom_plan` заставляет пересматривать план каждый раз.

Дальше — **long-running transactions**, которые блокируют VACUUM. MVCC оставляет мёртвые версии строк в heap, и VACUUM должен их подчищать. Но VACUUM не может удалить строку, которая ещё может быть видна какой-то транзакции. Если у тебя есть открытая транзакция, начатая час назад, — её snapshot держит живыми все мёртвые строки, накопившиеся с тех пор. Таблица пухнет, sequential scan замедляется, индексы растут. Симптом: в `pg_stat_activity` висит старая транзакция (`xact_start` был давно), размер таблицы растёт быстрее, чем должен. Лечение: убить транзакцию (`pg_terminate_backend`), настроить `idle_in_transaction_session_timeout`.

**Autovacuum не успевает** — родственная проблема. Если writes идут интенсивно, dead tuples накапливаются быстрее, чем autovacuum их вычищает. Особенно это касается больших таблиц: дефолтный трешолд — 20% таблицы должно стать мёртвым, чтобы autovacuum сработал. Для стомиллионной таблицы это двадцать миллионов dead tuples перед началом уборки. К этому моменту таблица уже сильно замедлена. Лечение: `ALTER TABLE huge SET (autovacuum_vacuum_scale_factor = 0.02)` — снизить порог до 2%.

**Checkpoint I/O storm** — характерный спайк latency, повторяющийся с определённой периодичностью. Причина: в checkpoint момент нужно записать на диск все dirty pages из shared_buffers, что даёт мощный burst записи. Пока диск обслуживает этот burst, все запросы, требующие I/O, тормозят. Симптом: графики latency пилообразные, спайки каждые 5 минут. Лечение: `checkpoint_completion_target = 0.9`, чтобы растянуть запись на 90% интервала между чекпоинтами, и увеличение `max_wal_size`.

**Lock contention** и **deadlocks** — когда транзакции стоят друг у друга в очереди. Много одновременных UPDATE'ов одной и той же строки (счётчик просмотров, глобальный агрегат) сериализуются на row lock, и по сути система работает как однопоточная. Симптом: в `pg_stat_activity` много `wait_event_type = 'Lock'`. Deadlock — когда две транзакции ждут друг друга по кругу; Postgres автоматически определяет и убивает одну из них. Лечение: избегать hot rows (шардировать счётчик по нескольким строкам), правильный порядок захвата локов в приложении, короткие транзакции.

**Connection storm** — когда приложение открывает слишком много соединений. `max_connections` в PostgreSQL по умолчанию 100. Приложение при burst нагрузке может попытаться открыть тысячу. Симптом: `FATAL: sorry, too many clients already`. Лечение: PGBouncer с transaction pooling.

**Проблемы с pool exhaustion**. HikariCP-пул в приложении может быть исчерпан из-за долгих запросов, забытых транзакций, деградации БД. Симптом: `hikaricp_connections_pending > 0`, потоки в приложении блокируются в getConnection, RTT запросов растёт лавиной. Причины часто снаружи БД — деградация сети, деградация PGBouncer, деградация самого PostgreSQL. Диагностика: смотреть в двух местах одновременно — pending threads в HikariCP и pool status в PGBouncer.

**WAL full** — когда генерация WAL опережает возможности checkpoint. Много writes → wal-файлы растут, но старые нельзя переиспользовать, пока checkpoint не завершится. В критической ситуации PostgreSQL начинает тормозить writes. Симптом: latency спайки на записи, `pg_stat_bgwriter.checkpoints_req` растёт (checkpoint триггерится по размеру, а не по времени). Лечение: увеличить `max_wal_size`, быстрее checkpoint (что тоже болезненно).

**Replication lag** — реплика отстаёт от primary. Большая транзакция на primary → большой блок WAL → реплика долго его применяет. Симптом: `pg_stat_replication.replay_lag` растёт. Особенно неприятно если приложение читает с реплики — начинает получать устаревшие данные. Лечение: следить за размером транзакций на primary, разбивать большие операции.

## Диагностика: что смотреть и в каком порядке

Когда база «колбасит», нужно быстро локализовать проблему. Порядок действий примерно такой.

Сначала — активные запросы прямо сейчас. `pg_stat_activity` показывает всех клиентов: что они делают, как долго, чего ждут. Отсортируй по `NOW() - query_start` — увидишь самые долгие. Если много запросов с `wait_event_type = 'IO'`, значит проблема на диске. Если с `wait_event_type = 'Lock'` — блокировки. Если с `state = 'idle in transaction'` — забытые транзакции.

Дальше — статистика по конкретным запросам. Расширение `pg_stat_statements` собирает статистику по всем выполненным запросам: сколько раз, сколько времени в сумме, среднее время. Топ-20 по `total_exec_time` показывает, куда уходит время работы базы. Это основной инструмент постфактум-анализа.

Для конкретного медленного запроса — `EXPLAIN (ANALYZE, BUFFERS)`. Он не только показывает план, но и реально запускает запрос с замерами: сколько времени каждый узел плана занял, сколько строк реально пропустил, сколько страниц прочитал из кэша (`shared hit`) и с диска (`shared read`). Если много `shared read` — cache miss, проблема с shared_buffers или тем что запрос гуляет по данным. Если много времени в конкретном узле — например Sort с большими `Rows Removed by Filter`, — можно точно указать, что оптимизировать.

Для оценки здоровья системы в целом — `pg_stat_bgwriter` (как часто чекпоинты, сколько pages они пишут), `pg_stat_database` (транзакции, кэш hit ratio), `pg_stat_user_tables` (bloat, autovacuum stats). Если cache hit ratio ниже 95%, нужно либо больше RAM, либо оптимизировать запросы. Если `n_dead_tup` большое и `last_autovacuum` старое — autovacuum не справляется.

Отдельно — connection pools. На стороне приложения: HikariCP-метрики. На стороне PGBouncer: `SHOW POOLS`, `SHOW STATS`. Если приложение видит pending connections, а PGBouncer видит `sv_used = default_pool_size` — узкое место в PGBouncer, нужно либо увеличить пул, либо разбираться, почему запросы держат соединение долго. Если приложение видит pending, а в PGBouncer `sv_idle > 0` — проблема между приложением и PGBouncer (сеть, DNS, TLS handshake).

На уровне OS — `top`, `iostat -x`, `vmstat`. Если `%wa` больше 20% — процессы висят на I/O. Если `%util` диска близко к 100% — диск saturated. Если swap используется — не хватает памяти.

## Заключение

СУБД устроена как многослойный конвейер. Приложение через свой connection pool (HikariCP) отправляет SQL, который проходит через серверный пул (PGBouncer) к backend-процессу PostgreSQL. Внутри PostgreSQL парсер разбирает SQL в дерево, оптимизатор выбирает дешёвый план, executor запускает операторы, операторы через access methods запрашивают страницы у buffer manager, buffer manager проверяет кэш, при промахе идёт на диск через disk space manager. Параллельно работают transaction manager (координирует транзакции), lock manager (управляет блокировками), recovery manager (пишет WAL для durability). Системный каталог хранит метаданные и статистику, которыми пользуются все остальные компоненты.

Connection pooling — критическая часть картины, которую часто недооценивают. Клиентский пул (HikariCP) переиспользует соединения внутри приложения, чтобы избежать оверхеда установления при каждом запросе. Серверный пул (PGBouncer) сжимает тысячи клиентских соединений в десятки реальных backend'ов PostgreSQL, что делает возможной работу микросервисных архитектур с сотнями подов. Настройка обоих пулов, понимание их взаимодействия и мониторинг — работа, которую senior делает при каждой новой инсталляции.

Под всем этим — двухуровневый кэш (shared_buffers плюс OS page cache) и диск, желательно разделённый на data и WAL, желательно SSD. Все запросы в конечном счёте упираются либо в CPU (сложная логика операторов), либо в RAM (кэш промахи), либо в диск (полный проход по данным). Понимание, куда именно упёрлось, — половина успеха оптимизации.

Когда таблица дорастает до сотен миллионов записей, начинает проявляться физика. Точечные запросы по индексу остаются быстрыми, потому что дерево B-tree мелкое, а листья с ключом плюс страница heap — это 4-5 обращений к памяти. Но любые операции, задевающие значительную часть таблицы, — sequential scan, массовый UPDATE, count(*), сортировка без индекса — становятся долгими, потому что нужно перекачать десятки гигабайт. Правильные индексы, актуальная статистика, настроенный autovacuum, партиционирование больших таблиц, батчинг больших операций — вот что позволяет системе оставаться отзывчивой.

Проблемы в проде обычно возникают на стыках. Sequential scan вместо index scan — устаревшая статистика. Периодические спайки latency — checkpoint I/O storm. Таблица пухнет — long transaction блокирует VACUUM или autovacuum отстаёт. Все запросы медленные — cache miss из-за нехватки RAM. Много ожиданий Lock — hot rows или неправильный порядок операций. Приложение зависло — pool exhaustion в HikariCP или PGBouncer. Каждая проблема имеет свою причину и свой fix, но общая методология одна: смотри `pg_stat_activity` для текущего состояния, `pg_stat_statements` для истории, HikariCP и PGBouncer метрики для пулов, `EXPLAIN ANALYZE` для конкретного запроса, `top` и `iostat` для системы.

Понимать всё это — и есть работа senior-инженера, работающего с базами данных. Не заучивать команды, а видеть картину целиком: как запрос идёт через все слои от Java-кода до диска, где может застрять на каждом уровне, как это диагностировать. Дальше — практика. Возьми одну реальную slow query из своего проекта, прогони EXPLAIN ANALYZE, разбери каждый узел плана, найди узкое место, придумай оптимизацию, замеряй результат. Каждый такой цикл добавляет реального понимания больше, чем десять прочитанных статей.
