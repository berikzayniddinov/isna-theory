## Как работает Platform Thread

Один в один с OS thread. Когда создаёшь `new Thread()`:

```
   Java код:
   new Thread(() -> {
       System.out.println("Hello");
   }).start();
   
                          │
                          ▼
   
   JVM говорит OS: "создай мне OS thread"
                          │
                          ▼
   
   Linux: pthread_create()
                          │
                          ▼
   
   Создан OS thread с ~1 MB stack памяти
                          │
                          ▼
   
   Kernel scheduler начинает планировать
                          │
                          ▼
   
   На каком-то CPU core запускается наш код
```

**Проблемы**:
- **Дорого**: 1 MB stack × 10 000 threads = 10 GB RAM только на стеки.
- **Ограничено**: OS не любит когда много threads (~1000-4000 максимум).
- **Медленный context switch**: kernel scheduler переключает ~10 μs на каждый switch.

## Как работает Virtual Thread (Java 21)

Совсем другая модель. **Java сама** управляет планированием.

```
   Java код:
   Thread.startVirtualThread(() -> {
       System.out.println("Hello from VT");
   });
   
                          │
                          ▼
   
   JVM создаёт объект в heap ~5 KB
   (это не OS thread, это просто объект!)
                          │
                          ▼
   
   JVM Scheduler (ForkJoinPool):
   "нужно выполнить этот VT"
                          │
                          ▼
   
   Берёт свободный Carrier Thread (обычный OS thread)
   Монтирует VT на этот carrier
                          │
                          ▼
   
   VT выполняется на carrier'e
                          │
                          ▼
   
   Если VT делает blocking операцию (I/O, sleep):
     - VT unmount с carrier'а
     - Carrier свободен, берёт другой VT
     - VT ждёт завершения I/O в heap
     - Когда I/O готово → mount на любой свободный carrier
     - VT продолжает выполнение
```

**Ключевое отличие**: пока OS thread ждёт I/O (в состоянии "D" wait), он ЗАБЛОКИРОВАН. Ничего не делает.

Virtual thread ждёт I/O → **carrier thread освобождается** → берёт другой VT → делает полезную работу.

Отсюда — можно иметь миллион VT на 8 carrier threads. Пока одни ждут I/O, другие работают на carrier'ах.

## Взаимодействие потоков — общая память

Все потоки одного JVM работают в **общей heap памяти**:

```
   ┌───────────────────────────────────────────────────────────┐
   │                    Heap (общая память)                    │
   │                                                           │
   │  ┌──────────────────┐        ┌──────────────────┐         │
   │  │  Object counter  │        │  Object list     │         │
   │  │  value = 42      │        │  [1, 2, 3, 4]    │         │
   │  └────────┬─────────┘        └────────┬─────────┘         │
   │           │                           │                   │
   │           │  ВСЕ потоки видят         │                   │
   │           │  эти объекты              │                   │
   │           │                           │                   │
   └───────────┼───────────────────────────┼───────────────────┘
               │                           │
       ┌───────┼───────┐           ┌───────┼───────┐
       │       │       │           │       │       │
       ▼       ▼       ▼           ▼       ▼       ▼
   ┌──────┐┌──────┐┌──────┐    ┌──────┐┌──────┐┌──────┐
   │Thread││Thread││Thread│    │Thread││Thread││Thread│
   │  1   ││  2   ││  3   │    │  4   ││  5   ││  6   │
   └──────┘└──────┘└──────┘    └──────┘└──────┘└──────┘
   
   Проблема: если два потока одновременно меняют counter,
             могут получить неправильный результат (race condition).
```

## synchronized — как работает

`synchronized` = каждый объект имеет **monitor lock**. Только один поток одновременно держит lock.

```
   Java код:
   synchronized(sharedObject) {
       counter.value++;
   }
   
                          │
                          ▼
   
   Thread хочет войти в блок
                          │
                          ▼
                          
   Проверяет monitor lock у sharedObject:
     
     ├── LOCK свободен → берёт себе, входит в блок
     │
     └── LOCK занят другим потоком → ЖДЁТ
              │
              │ Thread уходит в состояние BLOCKED
              │ OS thread не работает, ждёт
              ▼
         Тот кто держит lock, выходит из блока
              │
              ▼
         Освобождает lock
              │
              ▼
         Ожидающий thread просыпается, берёт lock, входит
```

**Схема двух потоков на одном lock**:

```
   Thread A                                Thread B
   
   1. Входит в synchronized     
   2. Получил lock              
   3. Делает работу...          |  Хочет войти в synchronized
                                |  Lock занят → BLOCKED
                                |  Ждёт...
   4. Выходит                   |  Ждёт...
   5. Отпускает lock            |  Ждёт...
                                |  Просыпается!
                                |  Берёт lock
                                |  Входит в блок
                                |  Делает работу...
```

## volatile — как работает

Обычные переменные могут кэшироваться в CPU registers/L1 cache. Разные потоки видят разные значения.

```
   БЕЗ volatile:
   
   int counter = 0;
   
        Thread A                     Thread B
        │                             │
        ▼                             ▼
   ┌──────────┐                  ┌──────────┐
   │ CPU core │                  │ CPU core │
   │    0     │                  │    1     │
   │ ┌──────┐ │                  │ ┌──────┐ │
   │ │ L1   │ │                  │ │ L1   │ │
   │ │ cache│ │                  │ │ cache│ │
   │ │ =5   │◄─── читал 5        │ │ =0   │◄─── ещё не читал
   │ └──────┘ │                  │ └──────┘ │
   └──────────┘                  └──────────┘
        │                             │
        └─────────────┬───────────────┘
                      │
                      ▼
              ┌────────────┐
              │    RAM     │
              │  counter=5 │
              └────────────┘
   
   Проблема: Thread B не видит обновление 5 сделанное Thread A.
             Возможно вечно будет читать 0 из своего кэша.
```

С `volatile`:

```
   С volatile:
   
   volatile int counter = 0;
   
        Thread A                     Thread B
        │                             │
        │ пишет counter = 5           │ читает counter
        ▼                             ▼
   ┌────────────────────────────────────────┐
   │           РАМ напрямую                 │
   │           counter = 5                  │
   │  (memory barrier — обход кэша CPU)     │
   └────────────────────────────────────────┘
   
   Thread B видит новое значение сразу.
   
   volatile гарантирует:
   - Visibility (видимость) между потоками
   - Не гарантирует atomicity! counter++ всё равно небезопасно
```

## Blocking operations — что происходит

Когда thread делает blocking операцию (read с диска, wait на lock):

**Platform Thread**:
```
   Thread делает socket.read()
        │
        ▼
   syscall read() → Linux kernel
        │
        ▼
   Kernel: "жди пока данные придут по сети"
        │
        │ OS thread переходит в состояние WAITING/BLOCKED
        │ CPU core свободен, берёт другой OS thread
        │
        │  ..........  данные пришли  ..........
        │
        ▼
   Kernel будит OS thread
        │
        ▼
   Thread получает данные, продолжает работу
```

Пока thread ждёт — **весь OS thread заблокирован**. Занимает 1 MB памяти, ничего не делает.

**Virtual Thread**:
```
   VT делает socket.read()
        │
        ▼
   JVM перехватывает: "это blocking, я обработаю по-своему"
        │
        ▼
   VT unmount с carrier thread
   Carrier свободен, JVM даёт ему другой VT
        │
        ▼
   Наш VT: JVM просит kernel уведомить когда данные готовы
        │
        │  ..........  данные пришли  ..........
        │
        ▼
   JVM: "теперь mount этот VT на свободный carrier"
        │
        ▼
   VT продолжает работу на carrier'e
```

Пока VT ждёт — **carrier thread делает другую работу**. Ресурсы не простаивают.

## Context switch — переключение потоков

**Context switch** — переключение CPU с одного thread на другой.

```
   На CPU core сейчас Thread A:
   ┌──────────────────────────┐
   │  CPU регистры            │
   │  IP = 0x1234 (в коде A)  │
   │  RAX = ...               │
   │  RBX = ...               │
   │  ...                     │
   └──────────────────────────┘
                │
                │ scheduler решил переключить
                ▼
   1. Сохраняем регистры Thread A в его stack
   2. Загружаем регистры Thread B из его stack
   3. Прыгаем на IP Thread B
                │
                ▼
   Теперь CPU выполняет Thread B:
   ┌──────────────────────────┐
   │  CPU регистры            │
   │  IP = 0x5678 (в коде B)  │
   │  RAX = ...               │
   │  ...                     │
   └──────────────────────────┘
   
   Context switch занимает ~1-10 μs
   Много переключений = потеря производительности
```

**Разница для Virtual Threads**:
- Platform thread context switch: kernel делает, ~10 μs.
- Virtual thread mount/unmount: JVM делает, ~1 μs. В **10 раз** быстрее.

## Полная картина — путь запроса через потоки

Пример: HTTP request приходит, обрабатывается, идёт в БД, возвращает ответ:

```
   1. HTTP request приходит на server socket
        │
        ▼
   2. Netty / Tomcat принимает запрос
      Кладёт задачу в thread pool
        │
        ▼
   3. Thread pool берёт свободный thread:
      
      Platform threads (Tomcat classic):
      - Взял OS thread T1
      - T1 обрабатывает запрос
      - Пока T1 работает — 1 OS thread занят
      
      Virtual threads (Tomcat with VT):
      - Создал VT
      - Смонтировал на carrier
      - Carrier может обрабатывать много VT
        │
        ▼
   4. Обработка: вызов Service, Repository
        │
        ▼
   5. Repository делает SQL запрос
      HikariCP выдаёт connection
      JDBC делает blocking read()
        │
        ├─ Platform: OS thread BLOCKED, ждёт ответ БД
        │  1 MB памяти простаивает
        │
        └─ Virtual: VT unmount, carrier свободен
           carrier берёт другой VT, делает полезную работу
        │
        ▼
   6. БД ответила
        │
        ├─ Platform: OS thread просыпается
        │
        └─ Virtual: VT mount обратно
        │
        ▼
   7. Формируем HTTP response
      Отправляем клиенту
        │
        ▼
   8. Thread возвращается в pool (или VT завершается)
```

## Что запомнить

**Иерархия**:
```
   JDK (для разработки)
     └── JRE (для запуска)
           └── JVM (виртуальная машина)
```

**Три уровня потоков**:
1. **OS threads** (pthreads) — kernel планирует, ~1 MB stack, максимум ~1000-4000.
2. **Platform threads** — Java threads 1:1 с OS threads. Классика до Java 21.
3. **Virtual threads** (Java 21+) — миллионы возможны, M:N на carrier threads.

**Platform vs Virtual**:
- Platform: дорогой (~1 MB), OS thread 1:1, kernel scheduler.
- Virtual: дешёвый (~5 KB), M:N на carrier'ах, JVM scheduler.

**Взаимодействие**:
- Все потоки видят общий **heap**.
- **synchronized** = monitor lock на объекте, только один поток.
- **volatile** = visibility между потоками (обход CPU cache).

**Blocking operations**:
- Platform: OS thread блокируется, простаивает.
- Virtual: VT unmount, carrier делает другую работу.

**Context switch**:
- Platform: kernel, ~10 μs.
- Virtual: JVM, ~1 μs.

**Правило Java 21**:
- Для CPU-bound работы — platform threads (не будет profit от VT).
- Для I/O-bound (много блокировок) — virtual threads (огромный win).
