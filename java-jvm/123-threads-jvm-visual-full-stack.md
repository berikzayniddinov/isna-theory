## JDK, JRE, JVM — что это

Часто путают. Простыми словами:

```
    ┌────────────────────────────────────────────┐
    │              JDK (Java Development Kit)    │
    │              ─────────────────────         │
    │   всё что нужно ДЛЯ РАЗРАБОТКИ:            │
    │                                            │
    │   - javac (компилятор Java → bytecode)     │
    │   - jshell, jconsole, jstack, javadoc      │
    │                                            │
    │   ┌────────────────────────────────────┐   │
    │   │       JRE (Java Runtime Env)       │   │
    │   │       ───────────────────          │   │
    │   │  всё что нужно ДЛЯ ЗАПУСКА Java:   │   │
    │   │                                    │   │
    │   │  - стандартные библиотеки Java     │   │
    │   │  - команда java                    │   │
    │   │                                    │   │
    │   │  ┌──────────────────────────────┐  │   │
    │   │  │    JVM (Virtual Machine)     │  │   │
    │   │  │    ─────────────────         │  │   │
    │   │  │  сама виртуальная машина     │  │   │
    │   │  │  что выполняет bytecode:     │  │   │
    │   │  │                              │  │   │
    │   │  │  - интерпретатор             │  │   │
    │   │  │  - JIT компилятор            │  │   │
    │   │  │  - Garbage Collector         │  │   │
    │   │  │  - memory manager (heap)     │  │   │
    │   │  └──────────────────────────────┘  │   │
    │   │                                    │   │
    │   └────────────────────────────────────┘   │
    │                                            │
    └────────────────────────────────────────────┘

    Правило: JVM ⊂ JRE ⊂ JDK
    
    - Хочешь просто запускать программы → нужен JRE.
    - Хочешь разрабатывать → нужен JDK.
    - С Java 9+ обычно ставят JDK (jlink делает custom JRE).
```

## Два вида Java Threads — Platform и Virtual

### Platform Thread (классический, до Java 21)

**Один Java Thread = один OS thread** (1:1).

```
    JVM (Java)                    Linux OS
    
    ┌─────────────┐              ┌────────┐
    │   Java      │──────1:1─────│   OS   │
    │  Thread 1   │              │thread 1│
    └─────────────┘              └────────┘
    
    ┌─────────────┐              ┌────────┐
    │   Java      │──────1:1─────│   OS   │
    │  Thread 2   │              │thread 2│
    └─────────────┘              └────────┘
    
    ┌─────────────┐              ┌────────┐
    │   Java      │──────1:1─────│   OS   │
    │  Thread N   │              │thread N│
    └─────────────┘              └────────┘
    
    Каждый занимает ~1 MB памяти под stack.
    
    Проблема: если тебе нужно 10 000 потоков:
              10 000 × 1 MB = 10 GB памяти только на стеки!
              OS ограничивает ~1000-4000 потоков.
```

**Когда thread блокируется** (например ждёт ответ от БД):

```
    Java Thread → syscall read() → Kernel: "жду данные"
    │
    ▼
    OS thread → состояние WAITING (не работает, не потребляет CPU)
    Но ЗАНИМАЕТ 1 MB памяти всё это время.
    
    ← 1000 потоков ждут БД = 1 GB RAM простаивает
```

### Virtual Thread (Java 21+)

**Много Java Virtual Threads → мало Carrier Threads → OS threads** (M:N).

```
    JVM (Java)                                    Linux OS
    
    Virtual Threads (миллион):                    OS threads (только 8):
    ┌──┬──┬──┬──┬──┬──┬──┬──┬──┬──┐               ┌────┬────┬────┬────┐
    │v1│v2│v3│v4│v5│v6│v7│..│..│vN│               │os1 │os2 │os3 │os4 │
    └──┴──┴──┴──┴──┴──┴──┴──┴──┴──┘               └────┴────┴────┴────┘
    каждый ~5 KB                                  каждый ~1 MB
        │                                            ▲
        │  JVM монтирует virtual thread              │
        │  на свободный carrier для выполнения       │
        ▼                                            │
    ┌────────┬────────┬────────┬────────┐            │
    │Carrier │Carrier │Carrier │Carrier │────────────┘
    │thread 1│thread 2│thread 3│thread 4│  1:1 с OS thread
    └────────┴────────┴────────┴────────┘
    (обычно = число CPU cores)
```

**Ключевая магия**: когда virtual thread делает **blocking** операцию (I/O, sleep):

```
    Virtual Thread 5 делает socket.read()
    │
    ▼
    JVM говорит: "это blocking, я обработаю по-своему"
    │
    ▼
    Virtual Thread 5 → отмонтирован (unmount) с carrier
    Carrier thread освобождается
    │
    ▼
    Carrier берёт другой virtual thread (например VT 42)
    и работает с ним!
    │
    ▼
    Данные пришли от сети → JVM монтирует VT 5 обратно
    на любой свободный carrier → продолжает работу
    
    Итог: пока одни virtual threads ждут I/O,
          carrier threads работают с другими VT.
          Ничего не простаивает!
```

## Простое сравнение

```
   Задача: обработать 10 000 HTTP запросов одновременно.
   Каждый запрос делает вызов в БД (~100 мс ожидания).

    Platform Threads:
    ┌──────────────────────────────────┐
    │  10 000 Java threads             │
    │                                  │
    │  = 10 000 OS threads             │
    │  = 10 GB памяти (1 MB × 10K)     │
    │  = OS не выдержит (max ~4000)    │
    │                                  │
    │  9 998 потоков ЖДУТ ответа БД    │
    │  занимая ресурсы впустую         │
    └──────────────────────────────────┘

    Virtual Threads (Java 21):
    ┌──────────────────────────────────┐
    │  10 000 virtual threads          │
    │                                  │
    │  = только 8 carrier threads      │
    │  = 50 MB памяти (5 KB × 10K)     │
    │  = OS довольна                   │
    │                                  │
    │  Пока одни ждут БД, carrier'ы    │
    │  работают с другими VT           │
    │                                  │
    │  Реально ждут: 0 carrier threads │
    └──────────────────────────────────┘
```

## Взаимодействие потоков через общую память

Все потоки в JVM видят один heap:

```
    ┌──────────────────────────────────────┐
    │           Heap (общий)               │
    │                                      │
    │        ┌─────────────┐               │
    │        │ counter = 5 │               │
    │        └─────────────┘               │
    │              ▲                       │
    │              │  все потоки видят     │
    │              │  этот объект          │
    └──────────────┼───────────────────────┘
                   │
       ┌───────────┼───────────┐
       │           │           │
    Thread A   Thread B   Thread C
    хочет      хочет      хочет
    counter++  counter++  counter++
```

**Проблема**: три потока одновременно делают `counter++`. Может получиться 6 вместо 8 (потеря обновлений).

**Решение 1 — synchronized**:

```
    synchronized(counter) {
        counter++;
    }
    
    Как работает:
    - У каждого объекта есть замок (monitor lock).
    - synchronized блок = "хочу этот замок".
    - Только один thread может держать замок.
    - Остальные ждут.
    
    Thread A: получил замок → counter++ → отпустил
    Thread B: ждал → получил замок → counter++ → отпустил
    Thread C: ждал → получил замок → counter++ → отпустил
    
    Итого: 8. Правильно.
```

**Решение 2 — volatile**:

```
    volatile int counter = 0;
    
    Зачем: обычные переменные могут кэшироваться в CPU регистры.
    Разные потоки могут видеть разные значения.
    
    БЕЗ volatile:
    Thread A: counter = 5 → пишет в свой CPU cache
    Thread B: читает counter → берёт из своего cache → всё ещё 0!
    
    С volatile:
    Thread A: counter = 5 → пишет в RAM напрямую
    Thread B: читает counter → из RAM → видит 5
    
    Важно: volatile НЕ защищает от race condition (counter++).
           Только от невидимости изменений между потоками.
```

## Что запомнить

**Иерархия**:
```
    JDK (для разработки)
      └── JRE (для запуска)
            └── JVM (виртуальная машина)
```

**Три уровня потоков**:

```
    1. OS threads (Linux)
       ─────────────────
       ~1 MB каждый
       max 1000-4000
       управляет kernel
       
              ▲
              │ Platform 1:1
              │ Virtual M:N (через carriers)
              │
    2. Java threads (внутри JVM)
       ────────────────────────
       Platform thread: 1:1 с OS thread, ~1 MB
       Virtual thread:  ~5 KB, миллионы возможны (Java 21+)
              
              ▲
              │
              │
    3. Ваш Java код
       ─────────────
       Thread t = new Thread(...)          ← Platform
       Thread.startVirtualThread(...)      ← Virtual (Java 21+)
```

**Общая память (heap)**:
- Все потоки видят одни и те же объекты.
- Проблема: race conditions.

**Решения**:
- **synchronized** — только один поток в блоке (замок на объекте).
- **volatile** — изменения видны сразу всем потокам (обход CPU cache).

**Когда что использовать**:
- **CPU-bound** (тяжёлые вычисления) → platform threads (VT не помогут).
- **I/O-bound** (много ждут БД, сеть, диск) → virtual threads (огромный win в Java 21).
