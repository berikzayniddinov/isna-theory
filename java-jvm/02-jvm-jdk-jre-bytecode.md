# 02. JVM, байткод, classloading, JIT и модель памяти

## Зачем разработчику понимать JVM

Java-разработчик может годами писать код, не задумываясь о том, что происходит внутри JVM. Пишешь классы, запускаешь через IDE, дебагишь, деплоишь. Работает. Пока производительность не становится проблемой, пока приложение не начинает падать с OutOfMemoryError, пока startup не замедляется до неприемлемого. Тогда возникают вопросы, на которые без понимания JVM ответить нельзя. Почему приложение стартует минуту? Почему heap dump в 4 гигабайта? Почему GC внезапно занимает 30% CPU? Почему после перезапуска первые запросы медленные?

Все эти вопросы упираются в детали работы JVM: как байткод исполняется, как JIT его оптимизирует, как работает GC, как организована память процесса. Знание этих деталей отличает senior от middle. Middle пишет код и надеется что "оно работает". Senior пишет код с пониманием как оно работает, может диагностировать проблемы, знает как настроить JVM под свой workload, умеет читать GC логи и heap dumps.

В этом файле разберём JVM изнутри: как байткод исполняется через интерпретатор и JIT, как classloader организован иерархически, что такое области памяти (heap, metaspace, stack, direct memory), как работают разные GC алгоритмы (Serial, Parallel, G1, ZGC), почему reflection и proxy — фундамент Spring. Всё это на уровне достаточном, чтобы разбираться с реальными production проблемами.

## Из чего состоит инсталляция Java

Термины JVM, JRE, JDK часто путают. Это три вложенных уровня, каждый содержит предыдущий.

**JVM (Java Virtual Machine)** — движок, реально исполняющий байткод. Это не абстракция, а конкретный процесс операционной системы, реализующий спецификацию Java Virtual Machine. Внутри JVM: интерпретатор байткода, JIT-компилятор, garbage collector, classloader system, thread scheduler, JNI (интерфейс к native коду). Существует несколько реализаций JVM. Самая распространённая — HotSpot от Oracle, входит в OpenJDK и коммерческий Oracle JDK. Amazon Corretto — сборка OpenJDK от Amazon с long-term support, стандарт в КНП. Есть альтернативы: OpenJ9 от IBM/Eclipse (компактная память, быстрый старт), GraalVM (полиглот, AOT-компиляция в native), Azul Zing (специализация на low-latency).

**JRE (Java Runtime Environment)** — JVM плюс стандартная библиотека классов. Standard library — это всё что в пакетах `java.lang`, `java.util`, `java.io`, `java.net`, `java.time` и многих других. `String`, `HashMap`, `File`, `Socket`, `LocalDateTime` — все они реализованы в JRE. Без JRE JVM бесполезна: даже элементарные операции вроде создания строки требуют классы стандартной библиотеки.

JRE достаточно для **запуска** готовых Java-приложений. Раньше JRE поставлялась отдельно от JDK — можно было установить только среду для запуска, без инструментов разработки. Начиная с Java 11 отдельный JRE больше не поставляется — есть только JDK. Внутри JDK структурно всё есть, включая JRE-компоненты.

**JDK (Java Development Kit)** — JRE плюс инструменты разработчика. Ключевые инструменты: `javac` — компилятор Java-исходников в байткод, `jar` — упаковщик JAR-архивов, `javadoc` — генератор документации, `jshell` — интерактивный REPL, `jstack`, `jmap`, `jcmd`, `jstat` — диагностические утилиты. Для написания и сборки кода нужен JDK. Для запуска — достаточно JRE (или JDK, что то же самое в современных версиях).

Одна операционная система может иметь несколько версий JDK одновременно. Переменная среды `JAVA_HOME` указывает "текущую активную", команды `java` и `javac` в PATH используют её. Gradle читает `JAVA_HOME` при запуске. В Docker-контейнерах каждый несёт свою JDK через base image (`FROM amazoncorretto:21-alpine`), никаких конфликтов между приложениями.

В КНП используется Amazon Corretto как стандарт: Corretto 11 для сервисов на master, Corretto 21 для нового кода на master-21 ветке. Плюс легаси-сервис isna-knp-gateway остаётся на Java 11 потому что использует Zuul, который не мигрирован на Java 21.

## Зачем вообще виртуальная машина

Понимание "почему Java устроена как виртуальная машина" помогает понять её сильные и слабые стороны. Сравним с C++ подходом.

В C++ ты пишешь код, компилятор превращает его в **машинный код** конкретной архитектуры процессора. Инструкции ADD, MOV, JMP — реальные команды x86 или ARM, которые процессор напрямую исполняет. Финальный executable работает только на той архитектуре и той ОС, под которую собран. Хочешь запустить на другой платформе — пересобирай.

Java сделала иначе. `javac` компилирует `.java` файлы не в машинный код, а в **байткод** — инструкции для абстрактного виртуального процессора, который не существует физически, только описан в спецификации. Байткод хранится в `.class` файлах.

При запуске JVM (реализация которой существует для каждой платформы) читает байткод и исполняет его. Может интерпретировать (по одной инструкции за раз, медленно) или компилировать в машинный код на лету (JIT, быстро). Байткод один и тот же на всех платформах — JVM разная. Отсюда лозунг Java "write once, run anywhere".

Плюсы этого подхода. Портативность — один JAR работает на Windows, Linux, Mac, x86, ARM. Управляемая память — GC освобождает от ручного malloc/free. Безопасность — нет прямых указателей, нет buffer overflow в user code. Мощный runtime — reflection, dynamic classloading, hot-swap для отладки. JIT-оптимизации — компилятор во время работы знает реальные паттерны использования, может оптимизировать лучше static AOT-компилятора.

Минусы. Startup slow — JVM инициализируется, стандартные классы грузятся, first-time JIT компиляция. Для быстро запускаемых утилит и serverless функций это проблема. Overhead памяти — сам JVM занимает 50-200 MB даже до загрузки приложения. Уровень абстракции — можно писать безопасный код, но нельзя опуститься до низкого уровня как в C.

Для типичного enterprise бэкенда, работающего годами непрерывно, минусы малозаметны. Startup slow — раз в час деплой, потом работает. Overhead memory — на серверных мощностях терпимо. Java-приложения после warmup работают почти как native.

## Байткод и стековая машина

Разберём как выглядит байткод. Простой Java метод:

```java
public int add(int a, int b) {
    return a + b;
}
```

После `javac Add.java` получаем `Add.class`. Через `javap -c Add.class` смотрим байткод:

```
public int add(int, int);
  Code:
     0: iload_1
     1: iload_2
     2: iadd
     3: ireturn
```

Четыре инструкции. Разберём каждую. `iload_1` — загрузить (l**oad**) целое число (**i**nteger) из локальной переменной с индексом 1 на operand stack. `iload_2` — то же с локальной 2. `iadd` — сложить два верхних int на стеке, результат положить обратно. `ireturn` — вернуть верхний int со стека как результат метода.

Ключевой момент: JVM — **стековая машина**. У неё нет регистров как у реального процессора (x86, ARM). Все операции работают с **operand stack** — рабочей областью памяти для промежуточных значений. Инструкции кладут значения на стек и снимают их для операций. Это упрощает генерацию байткода (компилятору не нужно распределять регистры) и делает код независимым от целевой архитектуры.

Локальные переменные хранятся в отдельной таблице, доступ по индексу. Индекс 0 обычно `this` для нестатических методов. Индексы 1, 2, ... — параметры и локальные. Загрузка на стек: `iload`, `aload` (для references), `fload` (float), `lload` (long) и другие в зависимости от типа. Сохранение обратно: `istore`, `astore`.

Спецификация JVM определяет около 200 opcode'ов. Основные категории. Loading/storing — `iload`, `istore` и вариации. Arithmetic — `iadd`, `isub`, `imul`, `idiv`, `irem` для int; аналогичные для других типов. Type conversion — `i2l`, `i2f`, `l2i` (integer to long, integer to float, long to integer). Control flow — `ifeq`, `if_icmpne`, `goto`, `tableswitch`. Object manipulation — `new`, `getfield`, `putfield`, `getstatic`, `putstatic`. Method invocation — `invokevirtual`, `invokestatic`, `invokespecial`, `invokeinterface`, `invokedynamic`. Exception handling — `athrow`.

Заучивать все opcode'ы не нужно. Но понимание что байткод — низкоуровневые инструкции стековой машины, а не "compressed text of Java", важно для нескольких сценариев. Работа с bytecode manipulation библиотеками (ByteBuddy, ASM, Javassist) — они генерируют или модифицируют байткод, знание opcode'ов необходимо. Понимание работы Lombok — он генерирует байткод для `@Getter`, `@Setter` во время компиляции. Понимание Hibernate lazy-loading — proxy классы генерируются во время runtime через bytecode manipulation. Отладка сложных ошибок вроде `VerifyError` — байткод не проходит валидацию JVM.

Каждый метод имеет несколько метаданных помимо самого байткода. `max_stack` — максимальная глубина operand stack (нужна для валидации). `max_locals` — количество слотов в таблице локальных переменных. `exception_table` — какие блоки покрыты какими catch. `line_number_table` — маппинг между байткодом и строками исходника (для stack trace'ов). Всё это в class file, `javap -v` покажет.

## Как работают методы

Разные instructions вызова методов отражают разную семантику. `invokestatic` — вызов статического метода, простой lookup по имени и сигнатуре. `invokespecial` — вызов конструктора, приватного метода или super-метода, точный класс определён на этапе компиляции. `invokevirtual` — вызов обычного метода, требующий виртуальный dispatch (реальная реализация зависит от runtime типа объекта). `invokeinterface` — вызов через интерфейс, требует поиск в vtable. `invokedynamic` — динамический вызов через bootstrap method, используется в lambdas, method references.

Виртуальный dispatch — важная тема. Пример:

```java
Animal a = new Dog();
a.makeSound();  // вызывается Dog.makeSound(), не Animal.makeSound()
```

Compile-time тип `a` — Animal, но runtime тип — Dog. Байткод: `invokevirtual Animal.makeSound`. При исполнении JVM смотрит на реальный класс объекта (Dog), находит в его method table `makeSound`, вызывает. Это стандартный OOP polymorphism.

JIT существенно оптимизирует эту операцию через **inlining**. Если анализ показывает, что в конкретном месте кода `a` всегда Dog (или чаще всего), JIT встраивает тело `Dog.makeSound` прямо в вызывающий метод, убирая накладные расходы vtable lookup. Если позже придёт объект другого типа — deoptimization, JIT откатывается к обычному вызову.

`invokedynamic` — специальная инструкция, введённая в Java 7 для поддержки динамических языков на JVM (JRuby, Jython). Позже использована для lambdas в Java 8. При первом вызове invokedynamic запускается bootstrap method, возвращающий CallSite — указатель на реальный код для вызова. Дальнейшие вызовы используют этот CallSite напрямую. Это позволяет реализовывать различные механизмы выбора implementation динамически.

## Classloader: иерархия и делегирование

Класс становится доступным для использования только после того, как JVM его **загрузит** — прочитает `.class` файл, разберёт байткод, инициализирует статические поля. Загрузка происходит **лениво**: класс загружается только когда он первый раз реально нужен. Это ускоряет startup — не грузим то что не используется.

Загрузкой занимаются **classloader'ы**. В классическом Java (до 9) иерархия такая:

- **Bootstrap ClassLoader** — самый низкий уровень, реализован в native коде C++. Загружает core-классы JDK: java.lang, java.util, java.io. Не имеет parent classloader'а — он root.

- **Extension ClassLoader** (или Platform в Java 9+) — загружает расширения JDK: некоторые дополнительные модули, ранее — JAR-ы из `jre/lib/ext`.

- **System ClassLoader** (Application ClassLoader) — загружает классы твоего приложения из classpath. По умолчанию именно он используется для main метода.

Ключевой принцип — **delegation model**. Когда classloader просят загрузить класс, он сначала **делегирует** запрос своему parent'у. Parent пробует загрузить. Если parent не смог (класс не в его области), запрос возвращается вниз, classloader пробует сам. Если ни один не может — ClassNotFoundException.

Смысл делегирования — безопасность и целостность. Никто не может подсунуть свою реализацию `java.lang.String`, потому что запрос дойдёт до bootstrap classloader'а, тот найдёт настоящий String, вернёт его. Custom classloader не получит шанса подгрузить свою "поддельную" версию.

С Java 9 система изменилась из-за модулей (JPMS). Bootstrap теперь загружает только `java.base`. Появился Platform ClassLoader для остальных JDK модулей. System ClassLoader как раньше. Идея делегирования сохранена.

**Custom classloader'ы** используются для специфичных задач. **Tomcat** создаёт отдельный classloader на каждое web-приложение — чтобы одно приложение не могло влиять на другое (изоляция классов). **Spring Boot** — LaunchedURLClassLoader, умеющий читать JAR внутри JAR (обсуждали в файле 04). **OSGi** — сложная модульная система, каждый bundle со своим classloader'ом. **Hot-reload инструменты** (JRebel) — пересоздают classloader при изменении файлов.

Разработка custom classloader'а сама по себе не сложна: расширяешь `ClassLoader`, переопределяешь `findClass()`, реализуешь чтение bytecode из своего источника. Но правильно интегрировать с delegation model, обрабатывать edge cases (loaded classes visibility, native libraries) — нетривиально.

## Классические ошибки classloading'а

Знание типичных ошибок помогает диагностировать. **ClassNotFoundException** — класс отсутствует в classpath. Приложение пытается загрузить класс, ни один classloader не находит `.class` файл. Причина обычно — забыли добавить dependency, неправильный classpath, версия зависимости другая.

**NoClassDefFoundError** — класс был доступен при компиляции, но в runtime не найден. Это отличается от ClassNotFoundException: там просят найти, тут по ссылке пытаются использовать. Обычно возникает при отсутствии одной из транзитивных зависимостей.

**LinkageError** и подтипы (NoSuchMethodError, NoSuchFieldError, IncompatibleClassChangeError) — класс есть, но у него другая сигнатура. Классический случай — версии библиотек конфликтуют. Compile-time код собран с одной версией, runtime подхватил другую, метод который вызывается не существует в загруженной. Реальный кейс в КНП: `knp-form-hz5-actuator-cache-nosuchmethod` — Spring Boot 2.2 Actuator вызывал `Cache.getNativeCache()`, которого в Hazelcast 5 API уже нет.

Диагностика этих ошибок начинается с полного анализа classpath. `jcmd <pid> VM.system_properties | grep classpath` покажет что реально в classpath. `./gradlew dependencies --configuration runtimeClasspath` — дерево зависимостей. Если есть подозрение на конфликт версий — искать в BOOT-INF/lib/ несколько JAR-ов с одним классом.

Правило: не переопределять версии из Spring Boot BOM без крайней необходимости. BOM держит совместимые версии всех библиотек — обходить это через явные версии — прямой путь к LinkageError.

## Interpreter и JIT

JVM не сразу компилирует байткод в машинный. Она **интерпретирует** его — читает инструкцию, выполняет соответствующее действие (обычно короткий C++ код внутри JVM), переходит к следующей. Это медленно: overhead на декодирование инструкций, отсутствие оптимизаций.

Но у JVM есть **JIT (Just-In-Time)** компилятор. Пока метод выполняется мало раз, JVM его интерпретирует. JIT профилирует выполнение: считает вызовы метода, замеряет какие ветки чаще выполняются, какие типы приходят в полиморфные вызовы. Когда метод пересекает **порог компиляции** (обычно 10 тысяч вызовов), JIT компилирует его байткод в машинный код процессора. Дальнейшие вызовы идут через скомпилированный код напрямую, минуя интерпретатор.

В HotSpot JVM две реализации JIT. **C1 (client compiler)** — быстрая компиляция, слабые оптимизации. Даёт быстрый первичный buildup. **C2 (server compiler)** — долгая компиляция, агрессивные оптимизации. Дает максимальную производительность для стабильно горячего кода. Современные JVM используют **tiered compilation** — сначала интерпретатор, потом C1, потом C2. Каждый уровень — компромисс между временем компиляции и качеством кода.

Оптимизации JIT впечатляют. **Inlining** — тело маленького метода вставляется в место вызова, убирая overhead вызова. **Escape analysis** — если объект создан внутри метода и не "убегает" за его пределы, его можно аллоцировать на стеке или даже полностью устранить (scalar replacement). **Dead code elimination** — код, который не влияет на результат, выбрасывается. **Loop unrolling** — циклы разворачиваются в несколько итераций подряд для лучшей branch prediction. **Constant folding** — вычисления с константами делаются на этапе компиляции.

Одна особенность — **deoptimization**. JIT делает предположения на основе профилирования: "этот метод всегда возвращает int > 0", "этот виртуальный вызов всегда на класс X". Оптимизирует под эти предположения. Если предположение оказывается неверным (пришёл int < 0, вызов на другой класс), скомпилированный код становится некорректным. JIT отмечает эту компиляцию как invalid, метод возвращается к интерпретации, потом перекомпилируется с учётом новой информации.

Для разработчика JIT незаметен большую часть времени — просто "код работает быстро". Но есть заметные эффекты. **Cold start slow** — первые запросы в свежий Spring Boot pod могут быть 5-10× медленнее прогретых. Пока JIT не скомпилировал горячий код, всё интерпретируется. Отсюда важность startupProbe и warm-up requests при deployment.

**Benchmark trickery** — простой `System.nanoTime()` в цикле для замера производительности почти всегда обманчив. JIT прогреется в середине цикла, замеры до и после разные. Правильный benchmark через JMH (Java Microbenchmark Harness) — учитывает warm-up, deоptimization, dead code elimination.

**AOT (Ahead-of-Time compilation)** и GraalVM Native Image — альтернативный подход. Всё компилируется в native binary заранее, без JIT в runtime. Плюсы: startup за десятки миллисекунд, малый memory footprint. Минусы: нет profile-guided optimization runtime, часть Java-фич не работает (reflection, dynamic loading) без явного конфигурирования. Хорошо для короткоживущих serverless-функций, для traditional long-running server — обычная JVM с JIT остаётся правильным выбором.

## Модель памяти JVM

JVM-процесс использует несколько отдельных областей памяти, каждая с своим назначением. Понимание их структуры критично для диагностики OOM и настройки размеров.

**Heap** — куда идут все объекты, созданные через `new`. Общий на все потоки процесса. GC управляет его выделением и освобождением. Это самая большая область, обычно основной target настройки (`-Xms`, `-Xmx`).

Heap разделён на поколения (generations) — реализация generational GC hypothesis. **Young generation** — где живут новорождённые объекты. Разделен на Eden (куда попадают новые объекты) и два survivor space (S0, S1). **Old generation** (tenured) — куда переезжают долгоживущие объекты после нескольких GC-циклов.

Идея поколений основана на наблюдении: **большинство объектов умирают молодыми**. Локальные переменные метода, промежуточные результаты — короткая жизнь. Долгоживущие — сессии, кэши, singletons — меньшинство. GC оптимизирован под это: minor GC (только young) быстрый и частый, major GC (весь heap включая old) медленный и редкий.

**Metaspace** (заменивший PermGen с Java 8) — хранит metadata классов: имена, поля, байткод методов, constant pool. Не в heap, отдельная область. Размер растёт по мере загрузки классов. Классический баг — динамическая генерация классов (proxy, reflection-heavy code) без выгрузки — Metaspace растёт, OOM `Metaspace`.

**Stack** — у каждого потока свой. Хранит **frame**'ы — записи о вызванных методах. Каждый вызов метода = новый frame, содержащий локальные переменные, аргументы, operand stack, return address. Возврат из метода — frame удаляется. Размер стека `-Xss` (по умолчанию около 1 MB на поток). Классический баг — бесконечная рекурсия, stack переполняется — `StackOverflowError`.

**Native stack** — для JNI-вызовов и внутренних C++ потоков JVM. Отдельно от Java stack.

**Direct memory** — off-heap память, управляется вручную через `ByteBuffer.allocateDirect()`. Используется NIO, Netty (для zero-copy IO), memory-mapped files. GC не трогает direct memory. Лимит `-XX:MaxDirectMemorySize` (по умолчанию = Xmx). Утечка direct memory — плохо, потому что GC не может её восстановить.

**Code cache** — где JIT хранит скомпилированный машинный код. Размер `-XX:ReservedCodeCacheSize` (обычно 240 MB). Если переполняется, JIT перестаёт компилировать новые методы — производительность деградирует.

Понимание всех этих областей важно для правильной настройки JVM в контейнере. Раньше JVM смотрела на всю доступную RAM хоста и брала процент из неё. В K8s это часто = OOM: контейнер имеет лимит 2 GB, JVM берёт 24 GB как процент от 32 GB хоста. Java 10+ понимает cgroup limits контейнера и адаптируется. Но принято явно задавать: `-Xms1g -Xmx1g -XX:MaxRAMPercentage=75` — фиксирует размеры и защищает от неожиданностей.

## Garbage Collection

GC — механизм автоматического освобождения памяти в JVM. Разработчик не пишет `free`, GC сам находит объекты, на которые никто не ссылается, освобождает их. Это упрощает код, устраняет целые классы багов (use-after-free, memory corruption), но добавляет накладные расходы: GC работает в runtime, требует CPU и создаёт паузы.

Как GC понимает что объект "мёртвый". Через понятие **GC roots** — точек, от которых считается "живость". Roots — активные потоки и их локальные переменные, статические поля классов, JNI references, синхронизированные монитор-ссылки. Всё, до чего можно дойти по ссылкам от какого-то root'а — **live** (достижимо). Остальное — **garbage**.

Разные GC алгоритмы отличаются тем, как эффективно они находят garbage и освобождают память.

**Serial GC** — простейший, один поток делает всю работу. Stop-the-world (STW) — все application threads замораживаются пока GC работает. Хорош для маленьких приложений с одним CPU. Не для production enterprise.

**Parallel GC** (Throughput Collector) — параллельные потоки для GC работы. Тоже STW, но короче. По умолчанию до Java 9. Оптимизирован под пропускную способность (максимум работы за минимум времени), не под latency (низкие паузы).

**G1 (Garbage First)** — по умолчанию с Java 9. Region-based: heap разбит на регионы фиксированного размера, GC выбирает регионы с максимальным количеством garbage для сборки (отсюда название). Incremental: не собирает весь heap разом, только часть за проход. Целевые паузы через `-XX:MaxGCPauseMillis`. Хорошо для средних heap (4-32 GB), баланс throughput и latency.

**ZGC** — специализирован на низкие паузы. Concurrent, использует colored pointers (специальные биты в указателях для отметок GC работы), паузы <10 ms даже на heap в терабайты. Хорош для low-latency сервисов (финансы, gaming). Немного дороже по throughput. Стал production-ready в Java 15+.

**Shenandoah** — аналог ZGC от Red Hat. Concurrent compaction. Работает аналогично.

Выбор GC зависит от workload. Для стандартных Spring Boot микросервисов на средних heap — G1 из коробки хорош. Не менять если нет конкретных причин. Для low-latency (тревога паузами >100 ms) — ZGC. Для batch processing (максимум throughput) — Parallel.

Параметры GC настраиваются через `-XX:` флаги. `-XX:+UseG1GC` — включить G1. `-XX:MaxGCPauseMillis=200` — целевая максимальная пауза 200 ms. `-Xlog:gc*:file=gc.log` — логировать GC события в файл. GC логи — ключевой источник информации для диагностики.

**Stop-the-world** — фундаментальное понятие. Пауза, когда все Java threads замораживаются, чтобы GC мог безопасно работать со структурами heap. Даже concurrent-GC (ZGC, Shenandoah, G1) имеют короткие STW-фазы (обычно для root scanning). Длинная STW в production = пользователи видят "зависание". Мониторинг GC пауз через метрики Actuator (`jvm.gc.pause`).

## Симптомы GC проблем

Типовые проблемы, вокруг которых крутится диагностика.

**`OutOfMemoryError: Java heap space`** — heap исчерпан. Причины: реальная утечка (объекты не освобождаются потому что где-то держится ссылка), слишком маленький Xmx для рабочего набора, burst нагрузка создающая много объектов. Диагностика — heap dump, анализ в Eclipse MAT.

**`OutOfMemoryError: GC overhead limit exceeded`** — GC жрёт >98% CPU и освобождает <2% памяти. Значит утечка на пределе Xmx: сборщик работает без пользы, приложение простаивает. Действие — увеличить Xmx (краткосрочно) и найти утечку (долгосрочно).

**`OutOfMemoryError: Metaspace`** — метадата классов заполнили Metaspace. Обычно динамическая генерация классов без выгрузки. Настройка `-XX:MaxMetaspaceSize` (default unlimited — плохо для production).

**`OutOfMemoryError: Direct buffer memory`** — off-heap исчерпан. Обычно Netty или NIO buffer leak.

**Long GC pauses** — замечаются через метрики или GC логи. Причины: слишком большой heap для алгоритма (Parallel GC на heap 30 GB — паузы могут быть секунды), fragment (fragmentation), плохо настроенные регионы G1. Действие — тюнинг GC параметров или смена алгоритма.

**Frequent Full GC** — Full GC (весь heap) должен быть редким событием. Если он частый — приложение живёт под давлением, большинство создаваемых объектов долгоживущие. Действие — heap dump, анализ.

Диагностический workflow. Heap dump: `jcmd <pid> GC.heap_dump /tmp/heap.hprof`. Открыть в Eclipse MAT или VisualVM. Смотреть "Dominator Tree" — какие объекты держат больше всего памяти. Смотреть "Leak Suspects" — MAT сам подсвечивает подозрительные структуры.

Thread dump: `jcmd <pid> Thread.print` или `jstack <pid>`. Показывает состояние всех потоков, что они делают. Полезно для диагностики зависаний, deadlock'ов, contention'а. Реальный кейс из КНП — `knp-filter-sent-documents-perf`: доказали блокировку потока на synchronized методе через thread dump.

GC logs: `-Xlog:gc*:file=gc.log:time,level,tags`. Каждый GC event записывается с длительностью, размерами до/после. Анализировать через GCEasy или GCViewer. Показывает динамику: как heap растёт, как часто GC срабатывает, какие паузы.

## Многопоточность и Java Memory Model

Java с самого начала поддерживает многопоточность. `Thread` — базовая абстракция. Каждый поток имеет свой stack, но все делят heap.

Управление потоками руками (`new Thread().start()`) — плохая практика. Правильный подход — `ExecutorService` и thread pools. Позволяют управлять количеством потоков, переиспользовать (без cost создания), встроенный queueing.

**Synchronization** — механизмы координации потоков. `synchronized` блок — блокировка на мониторе объекта. В байткоде — инструкции `monitorenter`/`monitorexit`. Атомарность и видимость гарантируются. Долгосрочно held synchronized блокирует другие потоки — contention.

`volatile` — модификатор поля. Гарантирует видимость изменений между потоками (запись в volatile сразу видна всем потокам). НЕ гарантирует атомарность — операции типа `counter++` не атомарны даже для volatile int.

`AtomicInteger`, `AtomicReference` и другие Atomic-классы — атомарные операции через CAS (compare-and-swap) инструкции CPU. Быстрее synchronized для simple counters.

`java.util.concurrent` — большой пакет: `ConcurrentHashMap`, `CopyOnWriteArrayList` (thread-safe коллекции), `ReentrantLock` (гибче synchronized), `Semaphore`, `CountDownLatch`, `CyclicBarrier`, `CompletableFuture` (async programming).

**Java Memory Model (JMM)** — формальная спецификация того, что один поток видит из действий другого. Ключевое понятие — **happens-before** отношение. Определённые события формируют это отношение: конец synchronized-блока happens-before начало следующего на том же мониторе; запись volatile happens-before чтение того же volatile; `Thread.start()` happens-before любых действий в запущенном потоке; конец потока happens-before `Thread.join()` возвращения.

Понимание JMM критично для написания корректного многопоточного кода. Много тонкостей — reordering (JIT и CPU могут переупорядочивать инструкции), visibility (без happens-before не гарантировано что изменение одного потока видно другому), atomicity vs visibility (volatile гарантирует одно, но не другое).

С Java 21 — **Virtual Threads (Project Loom)**. Миллионы легковесных потоков, шедулятся JVM на пул платформенных. Хорошо для IO-bound задач: обычные thread pools ограничены (тысячи threads = гигабайты памяти на stacks), virtual threads — сотни тысяч, каждый занимает килобайты. Революция для HTTP серверов, где каждый request — свой thread.

## Reflection и dynamic proxy

**Reflection** — API для inspection и manipulation классов и объектов в runtime. Можешь получить `Class<?>` объекта, посмотреть его методы и поля, вызвать метод по имени, создать инстанс без известного класса.

```java
Class<?> cls = Class.forName("kz.gov.kgd.isna.knp.SomeService");
Method m = cls.getMethod("doWork");
Object instance = cls.getDeclaredConstructor().newInstance();
m.invoke(instance);
```

Медленнее прямого вызова (несколько раз), но необходима для универсального кода: Spring (создание beans, DI), Jackson (сериализация arbitrary объектов), JPA (работа с annotated entities), тестовые фреймворки.

**Dynamic proxy** — генерация класса в runtime, реализующего указанный интерфейс, с делегированием вызовов в handler. Стандартный API: `java.lang.reflect.Proxy.newProxyInstance(...)`. Плюс InvocationHandler, вызываемый на каждый метод.

Ограничение — работает только для интерфейсов. Для классов (без интерфейса) используется **CGLIB** (Code Generation LIBrary) или **ByteBuddy**. Оба генерируют подкласс таргета, переопределяют методы, добавляют вокруг них логику. Ограничение — не может проксировать `final` классы/методы (нельзя переопределить).

Spring активно использует dynamic proxy для реализации `@Transactional`, `@Async`, `@Cacheable`, security и других AOP-аспектов. Когда ты помечаешь метод `@Transactional`, Spring вместо оригинального объекта отдаёт proxy. Proxy содержит логику "открыть транзакцию, вызвать оригинальный метод, commit/rollback". Все места, где ты используешь этот бин, получают proxy — все вызовы идут через логику транзакций.

Это ведёт к классической проблеме **self-invocation**. Метод одного класса вызывает другой метод того же класса через `this.method()`. Такой вызов не идёт через proxy — proxy находится "снаружи" оригинального объекта. Аннотация на вызываемом методе не срабатывает. Реальный кейс из КНП: `knp-fo-sync-notification-bugs` — метод `processAll()` вызывал `this.processOne()`, где `processOne` был `@Transactional(REQUIRES_NEW)`. Ожидалась отдельная транзакция на каждую итерацию, но её не было — все шло в одной транзакции внешнего метода. Следствие — LazyInitializationException при обработке большого количества элементов.

Fix'ы: вынести метод в отдельный bean, инжектировать себя (`@Autowired MyService self;`), использовать `AopContext.currentProxy()` (страшно и требует `@EnableAspectJAutoProxy(exposeProxy=true)`).

## Диагностика в production

Полезные утилиты для отладки Java-приложений в production, доступные внутри контейнера через `kubectl exec`:

`jps` — список запущенных Java-процессов с их PID.

`jstack <pid>` или `jcmd <pid> Thread.print` — thread dump. Стек-трейсы всех потоков в текущий момент. Показывает где приложение сейчас работает, кто ждёт что.

`jmap -dump:format=b,file=/tmp/heap.hprof <pid>` или `jcmd <pid> GC.heap_dump /tmp/heap.hprof` — heap dump. Может быть очень большим (гигабайты) — осторожно с диском.

`jcmd <pid> VM.native_memory summary` — сводка использования native памяти (metaspace, code cache, direct memory).

`jcmd <pid> GC.heap_info` — общая информация о heap.

`jstat -gc <pid> 1000` — статистика GC каждую секунду. Показывает динамику: как быстро young заполняется, как часто GC срабатывает, сколько времени тратится.

`jcmd <pid> VM.system_properties` — все system properties процесса. Полезно для проверки classpath, JVM args, timezone.

`jcmd <pid> GC.run` — принудительно запустить GC. Только для отладки, не в production под нагрузкой.

`jcmd <pid> JFR.start filename=recording.jfr duration=60s` — записать Java Flight Recorder trace на минуту. Открывать в Java Mission Control для детального анализа: методы hotspots, allocations, locks, IO.

Все эти утилиты доступны в JDK, включаются в Corretto image по умолчанию. Некоторые managed сервисы вроде Aurora ограничивают доступ к JVM tools — но для standard Spring Boot deployment всё работает.

## Заключение

JVM — сложная система, о которой можно писать книги. Мы прошли по основным темам: разница JVM/JRE/JDK, зачем виртуальная машина, как устроен байткод, как работают classloaders, JIT-компиляция, области памяти, garbage collection, многопоточность, reflection и proxy. Каждая тема — глубокая, здесь лишь ключевые концепции.

Практическое значение этих знаний — способность отвечать на реальные production вопросы. Почему приложение стартует минуту — cold start, JIT ещё не разогрелся, много классов загружается, много auto-configuration работает. Почему heap dump 4 гигабайта — размер Xmx, живые объекты, оценка memory pressure. Почему internal API вызов медленный первые несколько раз — JIT warmup. Почему после обновления зависимости NoSuchMethodError — конфликт версий, LinkageError, надо проверять classpath.

Для КНП контекста особенно важно понимать. Настройка JVM в контейнере: `-Xms=-Xmx` для стабильности, `-XX:MaxRAMPercentage=75` в container для safety, choice G1GC vs ZGC. Диагностика утечек через heap dumps и Eclipse MAT. Понимание proxy для правильной работы `@Transactional`. Мониторинг GC пауз через Prometheus + Grafana. Использование virtual threads (Java 21) для IO-bound сервисов.

Дальше — практика. Возьми любой Spring Boot сервис в КНП, включи JFR запись на 5 минут под типичной нагрузкой, открой в Java Mission Control, изучи. Сгенерируй heap dump, анализируй в MAT. Померь startup time, разбей на фазы через `/actuator/startup` (Boot 2.4+). Каждое такое упражнение даёт больше понимания, чем ещё одна прочитанная статья.
