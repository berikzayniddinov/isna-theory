# 14. Spring Data JPA: репозитории, queries, projections

## Что даёт Spring Data JPA над стандартным JPA

Работа с JPA напрямую через EntityManager получается многословной. Даже элементарные CRUD операции требуют boilerplate — явные вызовы persist, find, createQuery с типизированными параметрами, обработка Optional и списков вручную для каждого случая. Для каждой Entity класса приходится писать похожий код с минимальными вариациями. При десятках сущностей в enterprise приложении объём такого кода становится существенным.

Spring Data JPA как надстройка над JPA устраняет большую часть этого boilerplate. Основная идея заключается в том что разработчик описывает только интерфейс репозитория с нужными методами, а Spring генерирует реализацию через reflection и парсинг имён методов. Никакого implementation писать не нужно для типовых операций. Для более сложных запросов есть механизм @Query с явным JPQL или native SQL, но и здесь нужен только интерфейс, реализация не пишется.

Ключевые возможности Spring Data JPA включают несколько взаимосвязанных механизмов. Иерархию базовых репозиториев с готовыми методами — extend JpaRepository интерфейс и получаешь тридцать с лишним методов CRUD плюс batch операции. Механизм derived queries — Spring парсит имена методов вроде findByEmail и генерирует соответствующий JPQL запрос автоматически. Аннотация @Query для случаев когда derived queries не хватает, поддерживает как JPQL так и native SQL. Specifications API для формирования динамических запросов через Criteria когда условия определяются в runtime. Готовая поддержка pagination и sorting через объекты Page, Pageable, Sort. Механизм projections для возврата только нужных полей вместо полной сущности. Автоматический audit для заполнения createdAt, updatedAt, createdBy, updatedBy без ручного кода. Всё это существенно ускоряет разработку типовых операций и делает код чище.

В КНП Spring Data JPA используется во всех сервисах для работы с PostgreSQL. Знание его возможностей и подводных камней входит в базовую компетенцию разработчика.

## Иерархия базовых репозиториев

Spring Data определяет иерархию базовых интерфейсов, идущих от общего к специфичному. Каждый уровень добавляет функциональность.

На самом верху находится интерфейс Repository, параметризованный типом сущности и типом идентификатора. Это пустой маркерный интерфейс, обозначающий что имплементация относится к Spring Data репозиториям. Практически не используется напрямую, только как основа для более конкретных интерфейсов.

CrudRepository расширяет Repository, добавляя базовые CRUD операции — save, saveAll, findById, existsById, findAll, findAllById, count, deleteById, delete, deleteAll. Универсальный для любого Spring Data — работает не только с JPA, но и с MongoDB, Cassandra, Redis. Если приложение может потенциально переходить между хранилищами, использование CrudRepository даёт большую портируемость.

PagingAndSortingRepository расширяет CrudRepository добавляя пагинацию — методы findAll принимающие Pageable для страничного чтения и Sort для сортировки. Возвращает Page объекты с метаинформацией о страницах.

JpaRepository расширяет PagingAndSortingRepository, добавляя JPA-специфичные методы — flush для явной синхронизации с БД, saveAndFlush для сохранения с немедленным flush, getReferenceById для получения proxy ссылки без загрузки, batch операции для массовой обработки. Обычно это то что нужно для типичного JPA приложения.

На практике для JPA сервисов КНП стандартный подход — extend JpaRepository с параметрами Entity и типом её ID. Пустой интерфейс уже имеет тридцать с лишним готовых методов. Никакой implementation писать не нужно, готово к использованию сразу.

Механика генерации реализации работает через AOP и proxy. При старте приложения Spring Boot автоматически обнаруживает через @EnableJpaRepositories аннотацию (включённую в auto-configuration), сканирует пакеты на предмет интерфейсов наследующих Repository. Для каждого создаётся прокси, реализующий интерфейс. Прокси делегирует стандартные методы SimpleJpaRepository — базовой реализации от Spring Data. Регистрирует прокси как Spring bean под именем интерфейса. Инъекция через @Autowired получает этот прокси, разработчик работает с ним как с обычным репозиторием.

## Derived queries через имена методов

Одна из самых элегантных фич Spring Data JPA — автоматическая генерация запросов из имён методов интерфейса. Разработчик пишет метод с определённым по правилам именем, Spring парсит имя и генерирует соответствующий JPQL запрос.

Простые методы работают интуитивно. Метод findByRegNum принимающий String parses в запрос SELECT f FROM Fno f WHERE f.regNum = ?1. Возвращаемый тип Optional указывает Spring что искать один результат. Метод findAllByStatus возвращающий List автоматически ищет все записи со статусом равным параметру. Метод findAllByStatusAndCreatedAtAfter парсится в запрос с составным условием через AND.

Правила именования разработаны так чтобы охватить типичные операции. Префиксы определяют тип операции — findBy, getBy, readBy, queryBy для SELECT, countBy для SELECT COUNT, existsBy для SELECT EXISTS, deleteBy или removeBy для DELETE (требует @Transactional на методе или на классе). Модификаторы вроде Top10 или First5 ограничивают количество результатов. Модификатор Distinct добавляет DISTINCT в SQL. Модификатор IgnoreCase делает сравнение строк case-insensitive.

Условия задаются через специальные ключевые слова. And и Or для логических комбинаций условий. Between для диапазонов. LessThan, GreaterThan, LessThanEqual, GreaterThanEqual для сравнений. Like, NotLike, StartingWith, EndingWith, Containing для строковых операций. In и NotIn для проверки принадлежности множеству. IsNull, IsNotNull для проверки null. True, False для boolean полей.

Навигация по связям между сущностями работает через нижнее подчёркивание в имени метода. Метод findByTaxpayer_RegNum генерирует JPQL с навигацией f.taxpayer.regNum, что превращается в JOIN в сгенерированном SQL. Хорошо работает для типичных сценариев когда нужно фильтровать по полю связанной сущности.

Преимущества derived queries очевидны. Быстро писать — не нужно писать JPQL руками, только имя метода. Проверка на этапе старта приложения — если метод не может быть распарсен из-за опечатки в имени поля или неподдерживаемого условия, Spring падает при инициализации, не в runtime. Type safety через возвращаемый тип.

Недостатки также известны. Длинные имена методов быстро становятся нечитаемыми, что-то вроде findByFirstNameAndLastNameOrEmailContainingIgnoreCaseOrderByCreatedAtDesc сложно понять с первого взгляда. Ограниченная выразительность — сложная логика с приоритетами операторов не всегда работает как ожидается. Легко напороться на неоднозначность парсинга — метод findByAAndBOrC может интерпретироваться как (A AND B) OR C или A AND (B OR C) в зависимости от того что Spring решит.

Практическое правило — использовать derived queries для условий из двух-трёх полей. Для более сложной логики переходить на @Query с явным JPQL, что даёт полный контроль над запросом.

## Аннотация @Query для явных запросов

Когда derived queries не хватает по выразительности или получаются слишком длинные имена методов, используется @Query аннотация с явным JPQL или native SQL запросом.

С JPQL пишется обычный запрос с параметрами. Параметры могут задаваться через именованные placeholders вроде двоеточия и имени, привязываясь через @Param аннотацию на параметре метода. Альтернатива — позиционные placeholders через знак вопроса и номер. Именованные читабельнее, позиционные короче. В КНП обычно используются именованные для лучшей читаемости кода.

Для native SQL нужен параметр nativeQuery равный true. Запрос выполняется как обычный SQL диалекта БД, полная мощь PostgreSQL включая window functions, recursive CTE, специфичные для диалекта функции. Ценой является привязка к конкретной БД и отсутствие типобезопасности.

Constructor projection через SELECT new позволяет возвращать DTO напрямую из запроса вместо Entity. Указывается полное имя DTO класса и порядок аргументов конструктора. Полезно когда не нужна managed сущность, только данные.

Для операций изменения данных — UPDATE и DELETE — требуется дополнительная аннотация @Modifying на методе. Без неё Spring попытается выполнить запрос как SELECT, что для UPDATE или DELETE невозможно и приводит к ошибке. Возвращаемый тип int указывает количество затронутых строк.

Критический gotcha с bulk UPDATE и DELETE операциями заключается в том что они не проходят через first-level cache. Managed объекты в текущей сессии остаются со старым состоянием после bulk операции. Пример проблемы — читаем сущность через findById, получаем managed объект со status равным NEW. Затем выполняем bulk update через @Modifying запрос, устанавливающий status для группы записей. В БД status изменён, но managed объект в first-level cache всё ещё показывает старое NEW значение. Обращение к f.getStatus вернёт NEW, что не соответствует реальности. Стандартное решение — явный em.clear после bulk операции или использование @Modifying с параметром clearAutomatically равным true, что делает clear автоматически.

Spring Expression Language поддерживается внутри строк запросов через специальный синтаксис. Позволяет обращаться к полям параметров или использовать выражения. Полезно для сложных подстановок, но с осторожностью — SpEL evaluation имеет свою стоимость, для критичных по производительности запросов лучше избегать.

## Specifications API для динамических запросов

Для динамических запросов, где условия формируются в runtime — сложные фильтры в админке, отчёты с опциональными параметрами — ни derived queries, ни @Query не подходят напрямую. Нужен механизм композиции условий на лету. Spring Data предоставляет Specification API как обёртку над JPA Criteria API.

Идея заключается в том что каждый фильтр представляется отдельной Specification, которые комбинируются через логические операции. Одна Specification — это лямбда-функция, принимающая Root, CriteriaQuery и CriteriaBuilder, возвращающая Predicate. Может возвращать null, что означает "не применять этот фильтр". Такие спецификации собираются в один комбинированный запрос через методы where, and, or.

Для использования Specifications репозиторий должен extend JpaSpecificationExecutor интерфейс дополнительно к JpaRepository. Этот интерфейс добавляет методы findAll, findOne, count принимающие Specification.

Практическая работа с Specifications выглядит так. Разработчик определяет статические методы фабрики Specifications для отдельных фильтров — hasStatus, createdAfter, hasTaxpayerRegNum и подобные. Каждый метод проверяет что параметр не null и возвращает соответствующий Predicate, или возвращает null если параметр не указан. Такие спецификации комбинируются в цепочку через where, and для формирования полного запроса. Ноль параметров — все спецификации возвращают null, запрос без фильтров. Один параметр — только соответствующая Specification применяется. Все параметры — полный набор условий.

Плюсы такого подхода — гибкость композиции условий, возможность тестировать каждую Specification отдельно, повторное использование в разных запросах. Минусы — многословность синтаксиса Criteria API, необходимость понимания generic типов JPA metamodel.

Существуют альтернативы Specifications с потенциально более удобным синтаксисом. Querydsl — типобезопасный query builder с автогенерируемыми Q-классами для каждой Entity. Позволяет писать запросы вроде QFno.fno.status.eq(status).and(QFno.fno.createdAt.after(t)), что более читаемо чем Specifications. Требует annotation processor и code generation, что усложняет build. jOOQ — полностью типобезопасный SQL DSL, если хочется писать близко к SQL но с type safety. Требует изучения нового DSL.

В КНП обычно используется Specifications — не требует дополнительной инфраструктуры, встроен в Spring Data. Для сложных случаев с большим количеством динамических фильтров вложение времени в Querydsl или jOOQ может окупиться.

## Pagination и Sort

Пагинация результатов — стандартная функциональность для отображения больших списков. Spring Data предоставляет её через несколько связанных концепций.

Объект PageRequest создаётся через статический фабричный метод of с номером страницы, размером страницы и опционально Sort объектом для указания сортировки. Возвращает Pageable, который передаётся в метод репозитория.

Возвращаемый тип Page содержит не только сами данные но и метаинформацию — общее количество элементов, общее количество страниц, наличие следующей и предыдущей страницы, номер текущей. Полезно для отображения pagination controls в UI. Под капотом Spring выполняет два SQL запроса — основной SELECT с LIMIT и OFFSET для получения текущей страницы, и SELECT COUNT для получения общего количества.

Второй запрос за COUNT может быть медленным для больших таблиц, где COUNT требует прохода по всей таблице. Для случаев когда total count не нужен есть альтернативный тип Slice. Он не выполняет COUNT запрос, но предоставляет только методы hasNext и hasPrevious для навигации. Быстрее для больших датасетов, но не даёт totalElements. Slice используется для infinite scroll или простой навигации вперёд/назад без показа общего числа страниц.

В контроллере можно принять Pageable напрямую как параметр метода. Spring парсит query параметры page, size, sort из HTTP запроса в Pageable объект. Клиент передаёт что-то вроде ?page=0&size=20&sort=createdAt,desc, Spring автоматически формирует правильный Pageable. Настройки по умолчанию и максимальные значения задаются через spring.data.web.pageable в application.yml. Ограничение max-page-size защищает от атак, где клиент пытается запросить страницу с миллионом элементов и переполнить память сервера.

Sort может задаваться отдельно от pagination для случаев когда нужна сортировка без пагинации. Строится через Sort.by указывая поля и направление. Может комбинироваться с Pageable через PageRequest.of с Sort параметром.

## Projections для оптимизации чтения

Часто разработчик не нуждается в полной сущности, только в паре полей. Загружать всю Entity избыточно — тратится время на чтение всех колонок и память на создание полных Java объектов. Projections позволяют возвращать только нужные данные.

Interface projection — самый чистый подход через определение интерфейса с getter методами для нужных полей. Spring генерирует прокси реализацию этого интерфейса. При выполнении запроса тянутся только колонки соответствующие getter методам интерфейса. Меньше данных из БД, меньше памяти в приложении. Возможны вложенные projections для проекций связанных сущностей — интерфейс может содержать метод возвращающий другой projection интерфейс, что рекурсивно применяет ту же логику к связанной сущности.

Class-based projection через явный DTO класс с constructor — второй подход. Пишется обычный Java класс с полями и конструктором, принимающим их значения. В @Query запросе используется JPQL constructor expression SELECT new с полным именем класса и порядком аргументов. Запрос возвращает список DTO напрямую, Entity даже не создаются. Более многословно чем interface projection, но явно и понятно, полная типобезопасность.

Dynamic projection позволяет определить тип projection параметром метода. Метод репозитория принимает Class параметр указывающий на тип возвращаемых объектов. Один метод может возвращать разные projections в зависимости от передаваемого типа — полную Entity, interface projection, DTO. Гибко для случаев когда разным потребителям нужны разные объёмы данных.

Правило применения projections простое — использовать их для read операций где не нужны все поля сущности. Особенно важно для широких таблиц с многими колонками, где загрузка всей строки существенно медленнее чем нескольких нужных полей. Экономит нагрузку на БД, сеть и heap приложения. Плюс даёт архитектурное преимущество — DTO явно определяет что нужно контроллеру, лучше документирует API.

## Audit механизм

Автоматическое заполнение полей createdAt, updatedAt, createdBy, updatedBy — стандартная потребность в enterprise приложениях. Spring Data JPA предоставляет audit механизм для этого без ручного кода.

Активация происходит через аннотацию @EnableJpaAuditing на конфигурационном классе. Дополнительно нужен bean реализующий AuditorAware интерфейс, возвращающий текущего пользователя. Обычно это извлечение имени из Spring Security context — SecurityContextHolder.getContext().getAuthentication().getName(). Если пользователь не аутентифицирован, возвращает Optional.empty что означает "нет текущего пользователя".

На Entity классах используется аннотация @EntityListeners с AuditingEntityListener для активации audit механизма. Поля помечаются аннотациями @CreatedDate, @LastModifiedDate, @CreatedBy, @LastModifiedBy. При persist новой сущности заполняются @CreatedDate и @CreatedBy. При каждом update — @LastModifiedDate и @LastModifiedBy. Всё автоматически, без явного кода в бизнес-логике.

Для унификации audit полей на многих Entity классах можно вынести их в mapped superclass с @MappedSuperclass аннотацией. Все Entity наследующие этот класс автоматически получают audit fields. Один @EntityListeners на superclass работает для всех наследников.

## Custom repository implementations

Иногда derived queries и @Query не покрывают потребности — нужна кастомная логика с прямым использованием EntityManager. Например, сложные Criteria queries формирующиеся программно, native queries с ResultSetMapping для нестандартных проекций, batch операции с явным контролем flush и clear.

Spring Data поддерживает custom implementations через специальный паттерн. Разработчик определяет отдельный интерфейс с суффиксом Custom, например FnoRepositoryCustom, содержащий кастомные методы. Пишет класс реализации с суффиксом Impl, например FnoRepositoryImpl, реализующий этот интерфейс. Внутри реализации инъектирует EntityManager через @PersistenceContext и работает с ним напрямую.

Главный репозиторий extend и JpaRepository и custom интерфейс. Spring Data обнаруживает custom implementation по конвенции naming (класс должен называться как интерфейс плюс Impl) и подмешивает его методы в основной репозиторий. Разработчик работает с главным репозиторием, где доступны и стандартные методы от JpaRepository и кастомные методы от custom implementation.

Такой подход позволяет добавить произвольную сложную логику к репозиторию без потери стандартной функциональности. Полезно для методов не укладывающихся в стандартные паттерны derived query или @Query, но не требующих отдельного сервиса.

## Семантика метода save

Метод save имеет тонкую семантику, которую разработчики часто понимают неправильно. Для новой сущности он вызывает em.persist, что планирует INSERT при следующем flush. Для managed сущности (уже загруженной из БД в текущей сессии) save фактически ничего дополнительного не делает — dirty checking сам заметит изменения при flush и сгенерирует UPDATE. Для detached сущности (например переданной извне) save вызывает em.merge, что копирует состояние в новый managed объект.

Практическое следствие — не нужно вызывать save на managed сущностях. Пример типичной ошибки — метод сервиса загружает сущность через findById, изменяет поля, вызывает save. Save для managed объекта избыточен — dirty checking сам всё сохранит. Правильный код просто изменяет поля без явного save.

Массовые операции требуют внимания. Метод saveAll принимающий список работает через batch если правильно настроен hibernate.jdbc.batch_size. Метод saveAllAndFlush аналогично плюс явный flush сразу. Опасность вызова save в цикле по большому списку — все persist накапливаются в first-level cache, для миллиона объектов происходит OutOfMemoryError. Правильный подход — либо saveAll для не очень больших batches, либо явный flush и clear каждые пятьдесят или сто итераций.

## Транзакции в репозиториях

Каждый метод JpaRepository уже помечен @Transactional внутри SimpleJpaRepository реализации. Для read методов используется @Transactional(readOnly = true), для write — обычный. Это означает что простой вызов findById вне явной транзакции работает — Spring открывает read-only транзакцию для этого вызова.

Внутри @Transactional метода сервиса вызов репозитория подключается к текущей транзакции через propagation REQUIRED. Не создаёт новую, что было бы неправильно. Всё что делает репозиторий происходит в контексте транзакции сервиса.

Правильное архитектурное правило — сервис является границей транзакции. @Transactional на service методе задаёт границу, всё внутри работает в этой транзакции. Не полагайся на transactionality репозитория для сложных операций затрагивающих несколько репозиториев или комбинирующих чтение с записью — граница транзакции должна быть явно определена на service уровне.

## Заключение

Spring Data JPA как надстройка над JPA существенно упрощает работу с типовыми операциями через механизм автоматической реализации репозиториев. Разработчик описывает интерфейс, Spring генерирует прокси реализацию.

Иерархия репозиториев от Repository как маркерного интерфейса до JpaRepository с JPA-специфичной функциональностью. Обычно extend JpaRepository — стандартный подход в Spring Boot приложениях.

Derived queries парсят имена методов в JPQL запросы. Хорошо работают для условий из двух-трёх полей, для более сложных случаев переходят на @Query.

Аннотация @Query для явных JPQL или native SQL запросов. @Modifying для UPDATE и DELETE. Осторожность с bulk операциями не проходящими через first-level cache.

Specifications API для динамических запросов через Criteria. Каждая Specification представляет отдельный фильтр, комбинируются через логические операции. Альтернативы Querydsl и jOOQ дают более удобный синтаксис, но требуют дополнительной инфраструктуры.

Pagination через Page и Pageable. Slice как более быстрая альтернатива без COUNT запроса. В контроллере можно принимать Pageable напрямую с автоматическим парсингом query параметров.

Projections для оптимизации чтения — interface projection через прокси, class-based через DTO constructor, dynamic через Class parameter. Экономят нагрузку на БД и приложение.

Audit механизм через @EnableJpaAuditing плюс AuditorAware bean. Автоматическое заполнение createdAt, updatedAt, createdBy, updatedBy без ручного кода.

Custom implementations через паттерн Custom интерфейс плюс Impl класс. Позволяет добавлять произвольную сложную логику к репозиторию.

Save имеет тонкую семантику — для managed сущности избыточен, dirty checking сам сохранит изменения. Для batches использовать saveAll с периодическим flush и clear.

Транзакции — репозитории имеют собственные @Transactional, но правильная граница на service уровне.

Для КНП контекста стандартный подход — extend JpaRepository с derived queries для простых операций, @Query для сложных, Specifications для динамических фильтров. Projections для read операций, audit включён на всех Entity через common parent class.

Дальше обсуждается производительность JPA — самая обширная и важная тема в реальной работе. N+1 проблема, LazyInitializationException, connection pool, second-level cache — типичные источники проблем в production и способы их решения.
