# 109. Индексы в БД: когда создавать, когда нельзя, что если везде

## Зачем это знать

Индекс кажется бесплатной оптимизацией: запрос был медленным — добавил индекс — стал быстрым. Отсюда типовая ловушка джуна: увидел медленный запрос → CREATE INDEX. Ещё один медленный → ещё один INDEX. Через год в проде 15 индексов на одной таблице, INSERT'ы тормозят в разы, диск раздут, VACUUM не успевает, а половина индексов вообще не используется.

Индексы — не бесплатны. Каждый индекс = отдельная структура на диске (обычно B-tree), которая должна поддерживаться при каждом INSERT/UPDATE/DELETE. Индекс на write-heavy таблице замедляет запись в разы: одна вставка = запись в heap + обновление всех индексов. Индекс размером с саму таблицу — не редкость. Индекс, который никто не использует — чистый overhead без выгоды. А если запрос сформулирован неправильно (функция вокруг колонки, wrong type для сравнения) — индекс есть, но planner его не использует, и запрос всё равно медленный.

Разница между «пишу CREATE INDEX когда что-то тормозит» и «понимаю индексы» — это про **экономику**. Индекс — инвестиция: платишь стоимостью записи и диском, получаешь скорость чтения. Хорошая инвестиция — когда селективность высокая (индекс сужает много) и таблица часто читается. Плохая — когда селективность низкая (boolean, gender), таблица маленькая (planner всё равно seq scan сделает), или таблица write-heavy а читается редко.

Разберём: что такое индекс на самом деле (структура на диске, вторичная относительно heap). Стоимость индекса — write amplification, диск, VACUUM, планирование. Когда создавать (high-selectivity WHERE, JOIN, ORDER BY, FK — да, PostgreSQL их **не** индексирует автоматически). Когда не создавать (low cardinality, никогда не запрашиваемые, маленькие таблицы, write-heavy). Типы индексов подробно: B-tree (default), Hash, GIN (jsonb/FTS/arrays), GiST (геометрия, ranges), SP-GiST, BRIN (time-series). Специальные формы: partial (`WHERE`), expression (функциональные), covering (`INCLUDE`), composite (порядок колонок важен), unique. Что произойдёт если проиндексировать всё — конкретные цифры по замедлению записи, размеру, VACUUM. Диагностика в проде: `pg_stat_user_indexes` для usage, поиск дублирующих и unused, bloat индексов, REINDEX CONCURRENTLY. Типовые ошибки: индекс на всё, wrong order в composite, функция вокруг колонки ломающая использование индекса, забытые old indexes.

Как planner выбирает между index scan и seq scan — в файле 103. Locks и EXPLAIN мастерство — в 88. Здесь — про сами индексы: жизненный цикл, экономика, дизайн.

## Что такое индекс на самом деле

Индекс — отдельная структура на диске, поддерживающая быстрый поиск по колонке (или комбинации колонок). Живёт **параллельно** с самой таблицей (heap), не заменяет её. Heap хранит все строки в порядке вставки (примерно), индекс — упорядоченную ссылку на них.

Классический B-tree индекс — сбалансированное дерево, где каждый узел содержит отсортированные ключи + указатели на страницы (внутренние узлы) или на строки heap (листья). Поиск по ключу — O(log n) операций (обычно 3-4 уровня дерева даже для сотен миллионов строк).

Пример структуры (упрощённо) для индекса на `orders(user_id)`:

```
              [500, 1000, 1500]         ← root
             /       |         \
    [100,300]    [700, 850]   [1200, 1400]  ← internal
     /    |      /    |     \    ...
   ...  ...    ...  ...    ...             ← leaf → (heap page, tuple offset)
```

Каждый leaf ссылается на **TID** (Tuple Identifier) — пара (page number, offset), физическое расположение строки в heap.

Найти `WHERE user_id = 900`: 3 чтения (root → internal → leaf) в индексе, дают TID → 1 чтение из heap → 4 IO вместо 10000 (полное сканирование heap таблицы в миллион строк). Разница на порядки.

**Ключевой момент**: индекс дублирует данные. Значения колонки хранятся и в heap, и в индексе. Отсюда — стоимость.

## Экономика индекса: что платишь и что получаешь

**Получаешь**: скорость чтения. `SELECT ... WHERE indexed_col = ...` — миллисекунды вместо секунд. `ORDER BY indexed_col` — не требует сортировки, чтение прямо по индексу. `JOIN ... ON a.id = b.indexed_col` — nested loop с O(log n) probe на каждую строку.

**Платишь** — четырьмя ресурсами:

**1. Место на диске.** Индекс на колонку BIGINT в таблице с 100 млн строк — примерно 3 GB (8 байт ключ + служебные данные, накладные расходы B-tree ~50%). Индекс на TEXT колонку — в несколько раз больше. Composite индекс на (a, b, c) — сумма размеров каждой колонки + служебное. Сложение по десяти индексам легко даёт индексы суммарно **больше** самой таблицы.

**2. Замедление INSERT/UPDATE/DELETE.** Каждая вставка в таблицу = вставка в heap + вставка в каждый индекс. У таблицы 10 индексов → INSERT делает 11 операций записи вместо 1. Пропускная способность падает в 5-10 раз. UPDATE — сложнее: если UPDATE меняет проиндексированную колонку → удаление из индекса + вставка нового значения. Если не меняет (HOT update) — можно избежать index touch, но только при выполнении условий (см. ниже).

**3. Overhead на VACUUM.** VACUUM должен обойти все индексы и удалить оттуда ссылки на dead tuples в heap. Больше индексов → дольше VACUUM. При bloat'е индексов — операция становится долгой и тяжёлой. Autovacuum может отставать (см. файл 89).

**4. Overhead на планирование.** Planner учитывает все существующие индексы при выборе плана. Много индексов → медленнее planning (тщательнее анализ). Для OLTP с миллионами простых запросов заметно даже при 20+ индексах.

**Правило экономики**: индекс окупается когда **выигрыш чтения × частота чтения > потеря записи × частота записи + место + VACUUM overhead**. Для read-heavy таблиц окупается почти любой полезный индекс. Для write-heavy — надо считать.

## Когда создавать индекс

Есть несколько классов колонок, где индекс почти всегда оправдан.

**Колонки в WHERE с высокой селективностью**. Селективность = сколько строк отфильтруется. `WHERE email = 'x@y.com'` — обычно 0 или 1 строка (уникально), селективность 100%. `WHERE status = 'ACTIVE'` где 60% строк active — селективность 40% (отсеет 40%), низкая. Индекс полезен когда селективность >90% (сузит до <10% строк).

Пример: таблица `users` в 10 млн строк. `WHERE email = ?` без индекса — seq scan, читаем всё, секунды. С индексом — 4 IO, миллисекунды. Индекс окупается за один запрос.

**Колонки в JOIN**. `SELECT * FROM orders JOIN users ON orders.user_id = users.id`. Индекс на `orders.user_id` позволяет nested loop с O(log n) probe вместо hash join с построением hash table на всю users. При большой orders и маленькой users — nested loop с индексом обычно быстрее.

Обратная сторона: `users.id` (PRIMARY KEY) уже проиндексирован (unique index создаётся автоматически для PK). Индекс нужен на «внешнюю» сторону — `orders.user_id`. **PostgreSQL не создаёт индекс на FK колонки автоматически** (в отличие от MySQL InnoDB). Это одна из самых частых причин медленных JOIN'ов у новичков в Postgres.

**Колонки в ORDER BY и GROUP BY**. B-tree индекс хранит данные упорядоченно. `ORDER BY created_at DESC LIMIT 10` — вместо сортировки миллиарда строк, идём по индексу с конца, берём 10 первых. Мгновенно.

Особенно важно для pagination и «показать последние N». Без индекса на sort key — sort всей таблицы в памяти или (плохо) на диске (external merge, см. файл 88).

**FK колонки** — специально. `CREATE TABLE order_items (order_id BIGINT REFERENCES orders(id), ...)`. PostgreSQL проверяет FK при DELETE родителя: удаляешь Order → надо найти все `order_items WHERE order_id = ?`. Без индекса на order_id — seq scan order_items на каждую DELETE. Массовая чистка родителей превращается в часы работы. **Создавай индекс на каждую FK колонку** (правило почти всегда истинно, кроме случая когда родительскую таблицу вообще никогда не удаляют).

**Уникальные колонки** — через unique index (создаётся автоматически при `UNIQUE constraint`). Не только для скорости, но и для гарантии уникальности. `email`, `username`, `phone` — типовые кандидаты.

**Композитные индексы** для запросов, часто фильтрующих по нескольким колонкам одновременно. `WHERE user_id = ? AND created_at > ?` — композитный индекс `(user_id, created_at)` покрывает оба условия в одном обращении. Порядок колонок — критически важен (об этом ниже).

## Когда НЕ создавать индекс

Обратная сторона. Часто джуны создают индексы там, где они не помогают или даже вредят.

**Колонки с низкой cardinality**. `gender` (значений 2-3), `is_active` (boolean), `status` (5-10 значений). Индекс на такую колонку почти бесполезен: `WHERE gender = 'M'` отфильтрует 50% строк, planner всё равно выберет seq scan (быстрее чем читать половину heap через индекс с random I/O).

Исключение — partial index на редкое значение: `CREATE INDEX ON users(id) WHERE is_active = false` — если active обычно true, а нужно быстро найти inactive (например, для регулярной чистки). Индекс покрывает только 1% строк, крошечный, полезный.

**Колонки, никогда не участвующие в WHERE/JOIN/ORDER BY**. Логи изменений, метаданные для аудита, поля для дальнейшей обработки. Индекс на такую колонку — чистый overhead. Проверить через `pg_stat_user_indexes.idx_scan = 0` за длительный период.

**Маленькие таблицы**. Справочники в тысячи строк, конфигурации, статические lookup-таблицы. Planner всё равно выберет seq scan (полное сканирование быстрее, весь heap помещается в один-два блока shared_buffers). Индекс не используется, только место занимает.

**Write-heavy таблицы с редким чтением**. `audit_log`, `events_raw`, `queue_messages`. Записи миллион в час, чтение — раз в день дампом. Индекс замедлит запись, не сильно ускорит редкий batch-read (там всё равно seq scan оптимальнее). Часто такие таблицы держат вообще без индексов кроме PK.

**Колонки с частым UPDATE**. Каждый UPDATE проиндексированной колонки требует обновления индекса. Если колонка меняется часто (например, `updated_at` при каждом изменении строки), индекс на неё создаст постоянную нагрузку. Смотреть на access patterns: индекс нужен для `WHERE updated_at > ?` или только для отслеживания? Если только для audit — не индексируй.

## Типы индексов в PostgreSQL

B-tree — default, покрывает 90% случаев. Но есть специализированные типы для особых задач.

**B-tree** — сбалансированное дерево, поддерживает =, <, >, BETWEEN, IN, LIKE 'prefix%', IS NULL. Работает для любого типа с определённым ordering. Стандарт.

Тонкость с `LIKE`: `WHERE name LIKE 'John%'` — индекс работает (prefix match). `WHERE name LIKE '%John'` (suffix) или `LIKE '%John%'` (contains) — B-tree не помогает. Для полнотекстового или substring поиска нужен GIN.

**Hash** — только для точного равенства (=). Быстрее B-tree на большом объёме для чисто equality запросов. Раньше не был WAL-logged (не поддерживал crash recovery), с Postgres 10 исправлено. Практически используется редко — B-tree покрывает те же случаи с сопоставимой скоростью и большей универсальностью.

**GIN** (Generalized Inverted Index) — для колонок с несколькими значениями внутри одной строки: массивы, jsonb, tsvector (full-text search). Идея как в поисковых системах: для каждого «слова» (элемента массива, ключа JSON, лексемы) хранится список строк где оно встречается. Поиск `WHERE tags @> ARRAY['urgent']` — идёт напрямую в inverted list для 'urgent', возвращает список строк. Быстро.

Реальный кейс: JSON-документы. `CREATE INDEX ON orders USING GIN (metadata)` — можно быстро искать `WHERE metadata @> '{"payment": "card"}'` даже по миллиону документов.

Минусы GIN: медленные INSERT/UPDATE (нужно обновлять inverted lists для каждого значения), большой размер. Есть `fastupdate` для отложенной вставки в pending list с последующим flush.

**GiST** (Generalized Search Tree) — для геометрических типов, range types, exclusion constraints. `CREATE INDEX ON reservations USING GIST (during)` где `during` — tsrange. Поиск пересечений `WHERE during && '[2024-01-15, 2024-01-20]'::tsrange` — эффективно.

Также используется для FTS (tsvector), но обычно GIN лучше (быстрее чтение, медленнее запись; для FTS обычно преобладает чтение).

**SP-GiST** (Space-Partitioned GiST) — для данных с естественной пространственной кластеризацией: IP-адреса (по префиксам сети), геокоординаты, phone numbers по кодам стран. Реже используется.

**BRIN** (Block Range Index) — для очень больших таблиц с естественным порядком физического расположения. Хранит min/max значения для каждого блока (или группы блоков) — не для каждой строки. Крошечный по размеру (мегабайты вместо гигабайтов), но менее точный.

Идеально для time-series: логи, метрики, события — где `created_at` строго возрастает и данные лежат в heap примерно по порядку вставки. `WHERE created_at > NOW() - INTERVAL '1 hour'` — BRIN мгновенно определяет какие блоки могут содержать нужное, читает только их.

Плохо работает если данные пишутся не по порядку (UPDATE меняющий физическое расположение) или порядок вставки не совпадает с порядком partition key.

## Специальные формы B-tree индексов

Помимо простого «индекс на колонку», B-tree поддерживает несколько специальных форм — часто более эффективных.

**Partial index** — индекс не на все строки, а только на удовлетворяющие условию:

```sql
CREATE INDEX orders_pending_idx ON orders (created_at) 
WHERE status = 'PENDING';
```

Если в таблице 100 млн заказов, но `PENDING` только 10 тысяч — partial index в 10 000 раз меньше полного. Поиск `WHERE status = 'PENDING' ORDER BY created_at` — идёт по крошечному индексу.

Классические use cases: soft-delete (`WHERE deleted_at IS NULL`), обработка очередей (`WHERE processed = false`), редкие статусы (`WHERE priority = 'HIGH'`).

**Expression index (функциональный)** — индекс на результат функции, не на саму колонку:

```sql
CREATE INDEX users_email_lower ON users (lower(email));
-- работает: WHERE lower(email) = 'x@y.com'
```

Без такого индекса `WHERE lower(email) = ?` игнорирует обычный индекс на `email` (planner не знает что `lower()` детерминированная). Expression index решает.

Другой пример: индекс на `date_trunc('day', created_at)` для быстрого group by day. Или на `EXTRACT(YEAR FROM birthdate)` для запросов по годам рождения.

Ограничение: функция должна быть `IMMUTABLE`. Функции с `now()`, `random()`, `nextval()` внутри — не подходят (значение не воспроизводимо).

**Covering index (INCLUDE)** — индекс с дополнительными колонками, не участвующими в поиске, но включёнными в индекс:

```sql
CREATE INDEX orders_user_idx ON orders (user_id) INCLUDE (created_at, status);
```

Запрос `SELECT created_at, status FROM orders WHERE user_id = ?` может получить всё нужное **прямо из индекса**, не обращаясь в heap. Это называется **Index Only Scan** (см. файл 103) — самый быстрый режим чтения.

INCLUDE колонки не участвуют в сортировке индекса, только «прицеплены» к leaf-записям. Полезно когда часто запрашиваются те же несколько колонок.

**Composite index (составной)** — индекс на несколько колонок сразу:

```sql
CREATE INDEX orders_user_created_idx ON orders (user_id, created_at);
```

**Порядок колонок критичен**. Индекс `(user_id, created_at)` эффективен для:
- `WHERE user_id = ? AND created_at > ?` — оба условия покрыты.
- `WHERE user_id = ?` — работает, использует префикс индекса.
- `WHERE user_id = ? ORDER BY created_at` — работает, читаем по индексу.

Но **не работает эффективно** для:
- `WHERE created_at > ?` — только вторая колонка, префикс не задан, seq scan индекса.

Правило: **сначала колонки с equality, потом range, потом ORDER BY**. `WHERE user_id = ? AND created_at > ? ORDER BY score` → индекс `(user_id, created_at, score)`.

**Unique index** — гарантирует уникальность значений. Создаётся автоматически при `UNIQUE` constraint или `PRIMARY KEY`. Может быть составным.

Дополнительно: unique index можно сделать partial. `CREATE UNIQUE INDEX ... ON users (email) WHERE deleted_at IS NULL` — email уникален только среди активных пользователей. Soft-deleted могут переиспользовать email.

## Что произойдёт если проиндексировать всё

Конкретные последствия по числам, чтобы прочувствовать масштаб.

**Замедление INSERT'ов**. Таблица `orders` с 5 индексами (PK + user_id + created_at + status + composite (user_id, created_at)):

- 1 INSERT без индексов = 1 write в heap ≈ 0.1 ms.
- 1 INSERT с 5 индексами = 1 write в heap + 5 index updates ≈ 0.5-1 ms.

5-10x замедление на write. При bulk INSERT миллиона строк — вместо 100 секунд получается 500-1000 секунд. Плюс каждый индекс потребует своей WAL записи → WAL растёт → replication lag.

**Дисковое пространство**. Реальный пример из прод-системы (данные по памяти). Таблица `document_events`, 50 млн строк, размер heap — 12 GB. Индексы: PK (id, BIGINT) — 1.1 GB; user_id — 1.1 GB; created_at — 1.1 GB; document_id (BIGINT) — 1.1 GB; type + status composite — 800 MB; JSONB metadata (GIN) — 3.5 GB. Итого индексов — 8.7 GB, почти столько же сколько сама таблица. Общий footprint удвоился.

**VACUUM overhead**. VACUUM должен пройти по всем индексам и удалить dead tuples. Времена (примерные, для 100 млн строк с 20% dead):

- 0 индексов: VACUUM ~5 минут (только heap scan).
- 5 индексов: ~15-20 минут (heap + 5 index scans).
- 15 индексов: ~40-60 минут.

При active OLTP autovacuum отстаёт. Bloat растёт. Порочный круг.

**Cache pressure**. `shared_buffers` (типично 25% RAM) хранит горячие страницы heap и индексов. Больше индексов → больше страниц конкурируют за место → hot working set вытесняется чаще → cache hit rate падает → больше disk I/O → всё медленнее.

**Planning overhead**. При каждом запросе planner рассматривает все возможные комбинации индексов. С 20 индексами это заметно (миллисекунды на запрос). Для OLTP с 10 000 QPS — 10 секунд CPU на planning в секунду, целое ядро.

**Диагностический сценарий** (реальный анти-паттерн). Разработчик боится «пропустить» медленный запрос → создаёт индекс на каждую WHERE-колонку из access log. Через полгода: 25 индексов, INSERT'ы стали медленнее в 8 раз, диск переполнен, autovacuum отстаёт на дни, `pg_stat_user_indexes` показывает что 12 из 25 индексов `idx_scan = 0` (не использовались ни разу). Half of them были дубликатами (например, index на `(user_id)` и на `(user_id, created_at)` — второй покрывает первый).

## Как понять что индекс работает

`EXPLAIN ANALYZE` для конкретного запроса — покажет использовался ли индекс. Смотреть на:

- `Index Scan using idx_name on table` — да, планировщик выбрал этот индекс.
- `Bitmap Index Scan on idx_name` — тоже использовался (для non-selective или combined conditions).
- `Seq Scan on table` — индекс не использован. Причины: селективность плохая (планировщик решил seq быстрее); индекс не подходит по типу; функция вокруг колонки; type mismatch (`WHERE id = '42'` где `id` — integer, string vs integer — не работает без явного cast).

`Rows Removed by Filter: N` — сколько строк отфильтровано **после** чтения из heap. Большое число = индекс дал слишком много кандидатов, потом фильтр отсёк. Значит нужен более специфичный индекс или composite.

## Диагностика в проде

**Неиспользуемые индексы** — найти через `pg_stat_user_indexes`:

```sql
SELECT 
    schemaname,
    relname AS table,
    indexrelname AS index,
    idx_scan,
    pg_size_pretty(pg_relation_size(indexrelid)) AS size
FROM pg_stat_user_indexes
WHERE idx_scan = 0
  AND indexrelname NOT LIKE '%_pkey'    -- PK не трогаем даже если не используется
ORDER BY pg_relation_size(indexrelid) DESC;
```

Индексы с `idx_scan = 0` за долгий период (недели-месяцы) — кандидаты на удаление. **Осторожно**: reset статистики (`pg_stat_reset()`) обнуляет счётчики. Проверять что stats собирается достаточно долго.

Также осторожно с индексами используемыми только для констрейнтов (unique constraints, FK checks). Они могут иметь `idx_scan = 0` но нужны системе. `pg_constraint` покажет какие индексы используются в constraint'ах.

**Дублирующие/redundant индексы**. `(user_id)` и `(user_id, created_at)` — первый избыточен, второй покрывает. Найти:

```sql
SELECT 
    a.indexrelid::regclass AS index1,
    b.indexrelid::regclass AS index2,
    a.indrelid::regclass AS table_name
FROM pg_index a
JOIN pg_index b ON a.indrelid = b.indrelid 
    AND a.indexrelid != b.indexrelid
    AND array_to_string(a.indkey, ' ') LIKE array_to_string(b.indkey, ' ') || ' %'
WHERE a.indpred IS NULL AND b.indpred IS NULL;
```

Найдёт пары где ключевые колонки одного — префикс другого. Первый можно удалить.

**Bloated индексы**. Индекс который вырос сильно больше своей «оптимальной» величины (обычно из-за большого числа UPDATE'ов и dead tuples).

```sql
SELECT 
    schemaname,
    tablename,
    indexname,
    pg_size_pretty(pg_relation_size(indexrelid)) AS size,
    idx_scan,
    idx_tup_read,
    idx_tup_fetch
FROM pg_stat_user_indexes
WHERE pg_relation_size(indexrelid) > 100 * 1024 * 1024   -- > 100 MB
ORDER BY pg_relation_size(indexrelid) DESC;
```

Дальше — `pgstattuple` extension даёт точный bloat:

```sql
SELECT * FROM pgstatindex('my_index');
-- avg_leaf_density, leaf_fragmentation
```

`avg_leaf_density < 50%` = серьёзный bloat. Reindex восстановит.

**REINDEX без даунтайма**:

```sql
REINDEX INDEX CONCURRENTLY my_index;
-- Postgres 12+, не блокирует DML на таблице
```

Работает как `CREATE INDEX CONCURRENTLY` — двойной проход, немного медленнее обычного REINDEX, но без блокировки. Для больших индексов может занимать часы, но система при этом отвечает.

**Активные запросы и планы**. Понять что реально выполняется:

```sql
SELECT pid, query, state, wait_event
FROM pg_stat_activity
WHERE state = 'active' AND query NOT LIKE '%pg_stat_activity%';
```

Для медленных запросов запустить `EXPLAIN ANALYZE` вручную, посмотреть используется ли ожидаемый индекс. Часто выясняется что созданный «правильный» индекс не берётся planner'ом из-за типа условия или устаревшей статистики (ANALYZE давно не был).

## Типовые ошибки

**Индексировать всё**. Уже разобрано выше. Правило: сначала анализ access patterns (`pg_stat_statements`), потом целевые индексы под конкретные медленные запросы. Не создавать «на всякий случай».

**Неправильный порядок в composite индексе**. Написали `(created_at, user_id)` вместо `(user_id, created_at)` для запроса `WHERE user_id = ? AND created_at > ?`. Индекс не работает эффективно — первый столбец `created_at` не задан equality. Правило: сначала equality, потом range.

**Функция вокруг колонки в WHERE**. `WHERE lower(email) = 'x@y.com'` — обычный индекс на `email` не работает. Нужен expression index на `lower(email)`. То же с `WHERE date_trunc('day', created_at) = ...`, `WHERE CAST(id AS TEXT) = ...`.

**Type mismatch**. `WHERE id = '42'` где `id` — integer. Postgres иногда справляется через implicit cast, иногда — нет (зависит от типа). Всегда лучше явно правильный тип: `WHERE id = 42`.

**FK колонки без индекса**. PostgreSQL не создаёт автоматически. `DELETE FROM parent WHERE id = ?` — при FK на дочерней делает seq scan дочерней. На больших дочерних — часы. Всегда индексировать FK колонки.

**Забытые indexes после рефакторинга**. Раньше был запрос по `status`, добавили индекс. Потом бизнес-логика изменилась, запрос больше не выполняется, индекс остался. Периодически чистить через `pg_stat_user_indexes` анализ.

**Индекс на low-cardinality boolean**. `is_active` — 90% true, 10% false. Индекс на всю таблицу не помогает (selectivity низкая). Лучше **partial index**: `CREATE INDEX ON users(id) WHERE is_active = false` — крошечный, для редких запросов inactive users.

**Слишком много колонок в composite**. `(a, b, c, d, e)` — работает только для запросов начинающихся с `WHERE a = ?`. Каждая колонка добавляет размер индекса. Три колонки — обычно предел. Больше — переосмыслить нужно ли.

**Не проверять что индекс реально используется**. Создали → успокоились. А `EXPLAIN` показывает Seq Scan. Всегда проверять `EXPLAIN (ANALYZE, BUFFERS)` после создания что planner берёт индекс, `idx_scan` в статистике растёт.

## Практический алгоритм: как решать нужен ли индекс

Пришла задача — медленный запрос. Не бросаться `CREATE INDEX`. Пройти алгоритм:

**1. Собрать факты**. `EXPLAIN (ANALYZE, BUFFERS)` для запроса. Понять что именно тормозит: Seq Scan большой таблицы, Sort на диске (external merge), Nested Loop с большим объёмом.

**2. Оценить селективность**. Если WHERE фильтрует до 1% строк — индекс полезен. До 30% — сомнительно. Больше — почти никогда индекс не поможет, seq scan оптимален.

**3. Проверить существующие индексы**. Может есть уже похожий, но planner не берёт (устаревшая статистика — `ANALYZE table`; type mismatch; функция вокруг колонки — expression index; wrong order в composite).

**4. Оценить стоимость нового индекса**. Размер таблицы, число индексов уже, write load. Если write-heavy и индексов уже много — дважды подумать.

**5. Создать индекс в staging, замерить**. `CREATE INDEX CONCURRENTLY` (безопасно для DML). Прогнать тот же запрос — `EXPLAIN` должен показать index scan. Смотреть на реальное ускорение.

**6. Мониторить в prod**. После деплоя следить за `pg_stat_user_indexes.idx_scan` — растёт ли счётчик. Если через неделю всё ещё 0 — индекс не работает как задумано, разобрать почему.

## Заключение

Индексы — инвестиция, не бесплатная оптимизация. Каждый индекс — отдельная структура на диске (обычно B-tree), поддерживается при каждом write, увеличивает VACUUM overhead, создаёт cache pressure. Хорошая инвестиция окупается на read-heavy колонках с высокой селективностью и частым использованием. Плохая — низкая cardinality, никогда не используется, дублирует существующий.

**Когда создавать**: WHERE с высокой селективностью (email, phone, id), JOIN колонки (особенно FK — Postgres их **не** индексирует автоматически), ORDER BY / GROUP BY, uniqueness constraints, composite для многоколоночных фильтров (порядок: equality → range → sort).

**Когда не создавать**: low cardinality (boolean, статусы) — только partial для редких значений; никогда не запрашиваемые колонки; маленькие таблицы (справочники); write-heavy с редким чтением; часто UPDATE'ящиеся колонки.

**Типы**: B-tree (default, 90% случаев), Hash (редко полезен), GIN (jsonb, arrays, FTS), GiST (геометрия, ranges), SP-GiST (специфичное), BRIN (time-series, наименьший размер).

**Специальные формы**: partial (`WHERE` в CREATE INDEX) — для soft-delete, редких статусов; expression — для `lower()`, `date_trunc()`; covering (`INCLUDE`) — для Index Only Scan; composite — с правильным порядком; unique.

**Если проиндексировать всё**: INSERT'ы в 5-10x медленнее, диск удваивается, VACUUM отстаёт, cache вытесняется, planning тормозит. Реальный пример: 25 индексов → 12 неиспользуемых, INSERT'ы в 8x медленнее, autovacuum отстаёт на дни. Индексы — не защитная стратегия «на всякий случай», а целевая оптимизация под конкретные запросы.

**Диагностика в проде**: `pg_stat_user_indexes` для usage (idx_scan = 0 = кандидат на удаление, кроме constraint indexes); поиск дублирующих через pg_index; bloat через pgstattuple; REINDEX CONCURRENTLY для восстановления без даунтайма.

**Типовые ошибки**: индекс на всё; неправильный порядок в composite (сначала equality, потом range); функция вокруг колонки ломающая обычный индекс (нужен expression); FK колонки без индекса (Postgres не индексирует); забытые старые индексы после рефакторинга; low-cardinality boolean без partial.

Алгоритм принятия решения: EXPLAIN → оценить селективность → проверить существующие индексы → оценить стоимость → создать в staging → замерить → мониторить в prod через `pg_stat_user_indexes`.

Как planner выбирает между index scan и seq scan — в файле 103. EXPLAIN и locks в 88. VACUUM и статистики в 89. Здесь была экономика и дизайн индексов: что создавать, что не создавать, что случится если переборщить.
