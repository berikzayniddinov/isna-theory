# 15. JPA производительность: N+1, LazyInit, кэш, транзакции

## Почему производительность JPA критически важна

Enterprise Java приложения проводят большую часть времени работая с базой данных. Бизнес-логика обычно относительно простая — прочитать данные, применить бизнес-правила, записать результат обратно. Реальную нагрузку создают SQL запросы, генерируемые JPA слоем, и время их выполнения определяет user experience. Плохо написанные запросы — медленное приложение, независимо от того насколько эффективный Java код в бизнес-логике.

JPA как абстракция скрывает многое от разработчика. Простая строка вроде цикла по списку сущностей с обращением к связанному полю в теле цикла может тихо превратиться в тысячу SELECT запросов через N+1 проблему. Помеченный @Transactional метод может выполняться минутами из-за неоптимальной длительности транзакции. Возврат Entity из сервиса приводит к LazyInitializationException в контроллере при попытке сформировать response. Абстракция утекает, детали проступают в самые неудобные моменты работы приложения в production.

Знание производительности JPA — это не оптимизация ради оптимизации, а базовая корректность приложения. Без понимания N+1 приложение работает тридцать секунд там где должно работать триста миллисекунд. Без правильной работы с транзакциями возникают deadlocks и потеря данных в prod. Без понимания LazyInit контроллер крашится при попытке отдать response пользователю. Все эти проблемы регулярно встречаются в реальных enterprise приложениях, и senior разработчик должен уметь распознавать и предотвращать их.

## N+1 проблема как главный враг

Самая частая причина медленных JPA приложений называется N+1 проблемой. Возникает в конкретном сценарии — разработчик загружает список сущностей одним запросом, потом в цикле для каждой из них обращается к lazy-loaded связанной сущности. Для каждого обращения Hibernate генерирует отдельный SELECT.

Классический пример выглядит так. Метод сервиса помечен @Transactional. Загружает через репозиторий список Fno через простой findAll. Затем в цикле для каждого Fno обращается к связанному Taxpayer через getTaxpayer, читает его name. По умолчанию @ManyToOne на taxpayer должен быть указан LAZY, поэтому загрузка отложена до первого обращения.

Что реально происходит в базе данных. Первый запрос — SELECT star FROM fno возвращает все Fno записи. Затем на каждое обращение к связанному taxpayer выполняется отдельный SELECT star FROM taxpayer WHERE id равен нужному значению. Для тысячи Fno получается тысяча дополнительных SELECT — итого одна тысяча один запрос вместо одного или двух. Отсюда название N+1: один запрос на родителей плюс N запросов на детей.

Практические последствия ужасающие. Каждый SELECT запрос требует round-trip к серверу БД. В типичной production сети round-trip занимает от одной до десяти миллисекунд в зависимости от расстояния и загрузки. Тысяча round-trips по пять миллисекунд — это пять секунд только на сетевые задержки, ещё до времени обработки на стороне БД. Приложение отвечает пять секунд там где должно отвечать пятьдесят или сто миллисекунд. Пользователь видит зависшую страницу.

## Как обнаружить N+1

Есть несколько подходов к обнаружению этой проблемы. Простое включение логирования SQL показывает проблему сразу — вместо ожидаемых одного-двух запросов в логах появляется длинная простыня одинаковых SELECT с разными идентификаторами. Достаточно однократно взглянуть на логи после выполнения проблемного метода чтобы диагностировать проблему.

Механизм statistics в Hibernate даёт агрегированную статистику по сессии. Включается через параметр generate_statistics в конфигурации. По окончании сессии в логах появляется сводка — сколько entities загружено, сколько statements выполнено, сколько времени потрачено на JDBC connection и на выполнение statements. Соотношение statements и entities — прямой индикатор N+1. Если тысяча statements при пятидесяти entities загруженных, это явный признак проблемы в коде.

Автоматическая защита от регрессий возможна через специальные библиотеки в тестах. Библиотека datasource-proxy перехватывает JDBC calls на низком уровне и позволяет посчитать количество запросов. В интеграционном тесте можно вызвать метод сервиса, потом assert-ить что количество SELECT не превышает разумное значение вроде двух. Такой тест ловит регрессии производительности когда кто-то добавляет обращение к lazy полю без правильной настройки fetch стратегии.

В production обнаружение работает через мониторинг. Метрики базы данных показывают количество запросов в секунду, средняя latency запросов. Резкий рост QPS при обычной нагрузке указывает на N+1 в новом коде. APM инструменты вроде Datadog, New Relic, Elastic APM автоматически детектируют N+1 паттерн через анализ traces и подсвечивают проблемные endpoints.

## Как решить N+1

Существует несколько подходов к решению, каждый со своими сценариями применения.

Самый прямой способ — JOIN FETCH в JPQL запросе. Явно указываем что связанные данные должны быть загружены вместе с родительскими одним SQL. Один SQL запрос с JOIN между двумя таблицами возвращает все данные сразу. Работает отлично для @ManyToOne связей и других single-value ассоциаций.

Существует важный нюанс с коллекциями и pagination. JOIN FETCH для @OneToMany коллекции вместе с pagination даёт проблему — Hibernate не может правильно применить LIMIT в SQL когда есть JOIN на коллекцию, потому что LIMIT ограничивал бы количество строк в результате, а не количество родительских сущностей. Hibernate вытягивает все данные в память и применяет pagination там, что даёт warning HHH000104 в логах. Для больших датасетов это неприемлемо — все данные грузятся в память несмотря на пагинацию. Для коллекций с пагинацией нужны другие подходы.

Аннотация @EntityGraph предоставляет декларативную альтернативу JOIN FETCH. Разработчик указывает пути по графу сущностей которые должны быть загружены eagerly для конкретного метода репозитория. Hibernate автоматически строит JOIN FETCH для указанных путей. Более чисто чем ручной JOIN FETCH в JPQL строке, работает похожим образом. Один SQL запрос со всеми нужными JOIN.

Стратегия batch fetching через @BatchSize не использует JOIN, вместо этого группирует lazy загрузки в пачки. При обращении к первому lazy полю в цикле Hibernate замечает что есть много объектов ожидающих такой же загрузки, генерирует один SELECT с условием IN на список идентификаторов размером batch_size. Все объекты этого batch загружаются одним запросом. Затем следующий batch и так далее. Вместо N дополнительных запросов получается N делить на batch_size, что для batch_size равного пятидесяти даёт двадцать один запрос вместо тысячи одного для тысячи объектов.

Batch fetching можно включить глобально через параметр default_batch_fetch_size в application.yml, что применяется ко всем lazy связям автоматически. Или локально через аннотацию @BatchSize на конкретной Entity или связи. Работает автоматически без изменения кода бизнес-логики.

DTO projection — принципиально другой подход. Не загружаем Entity вообще, а формируем DTO с нужными полями напрямую в запросе. JPQL с constructor expression SELECT new создаёт DTO объекты из результатов запроса без промежуточного создания Entity в PersistenceContext. Экономит и время БД (не читаются все колонки Entity, только нужные) и время приложения (не создаются полные Java объекты, только компактные DTO).

Выбор подхода зависит от контекста. Для чтения связанных данных с целью отображения — JOIN FETCH или @EntityGraph работают хорошо. Для сложных сценариев с непредсказуемой глубиной связей — глобальный default_batch_fetch_size даёт автоматическое решение. Когда сущности не нужны, только данные — DTO projection самый эффективный. Для действительно сложных случаев можно писать native SQL с полным контролем над запросом.

## Проблема LazyInitializationException

Классическая проблема JPA приложений возникает при попытке обратиться к lazy loaded полю после закрытия сессии. Прокси на связанное поле помнит что нужно загрузить, но сессии больше нет, SELECT выполнить некуда, Hibernate бросает LazyInitializationException.

Типичный сценарий выглядит так. Сервисный метод помечен @Transactional, читает Fno через em.find, возвращает эту сущность как результат метода. При возврате Spring коммитит транзакцию, EntityManager закрывается, сессия завершается, возвращённая сущность становится detached. Контроллер получает detached сущность, пытается обратиться к lazy полю taxpayer для формирования response. Прокси пытается выполнить SELECT для загрузки, но сессии нет — LazyInitializationException.

Правильное решение — использование DTO проекций в сервисе. Сервис не возвращает Entity наружу, вместо этого читает нужные данные внутри транзакции и формирует DTO содержащий именно те поля которые нужны контроллеру. Все обращения к lazy полям происходят внутри транзакции, где сессия активна и данные могут быть загружены. Плюс архитектурная чистота — Entity является внутренней деталью implementation слоя persistence, не должна утекать в API слой. Точный контроль над тем какие данные загружаются даёт возможность оптимизировать под конкретный use case.

Альтернативные решения через JOIN FETCH или @EntityGraph заранее загружают нужные связи, делая данные доступными после закрытия сессии. Работают когда известно какие связи будут нужны, менее гибко чем DTO проекции для сложных сценариев.

Существует также open-session-in-view паттерн который Spring Boot включает по умолчанию. Сессия держится открытой на весь HTTP запрос включая контроллер и рендеринг response. LazyInitializationException не возникает потому что сессия всегда активна. Однако у этого подхода серьёзные проблемы. Он скрывает N+1 — SELECT запросы летят из контроллера или сериализатора, разработчик не видит их в коде сервиса. Держит БД connection занятым на всё время обработки HTTP запроса, что при медленных клиентах может исчерпать connection pool. Правильная практика в prod — отключать open-in-view в конфигурации, тогда LazyInit возникает в тестах и разработчики вынуждены правильно грузить данные в сервисе.

Использование FetchType.EAGER как способ борьбы с LazyInit — самое ленивое решение. Убивает производительность в общем случае, потому что связанные данные грузятся всегда, даже когда не нужны для конкретного вызова. Не решает проблему архитектурно, а маскирует её.

## Изменения в Hibernate 6

Отдельно стоит упомянуть про изменения при миграции части сервисов КНП на Java 21 и соответствующий Hibernate 6. Новая версия стала строже проверять доступ к lazy полям — LazyInitializationException проявляется в местах, где Hibernate 5 иногда прощал. Плюс комбинация с self-invocation проблемой @Transactional может дать неочевидные баги.

Реальный кейс из КНП, названный knp-fo-sync-notification-bugs, иллюстрирует ситуацию. Метод помечен @Transactional, но вызывается через this.method внутри того же класса. Spring proxy минуется, транзакция не открывается, сессия не создаётся. Любое обращение к lazy полю внутри такого метода сразу даёт LazyInitializationException. При этом Hibernate 5 в аналогичной ситуации мог работать благодаря дополнительным механизмам вроде open-session-in-view. Миграция вскрыла шесть багов в одной feature из-за этой комбинации проблем.

Урок общий — миграция на новую версию любой инфраструктурной библиотеки требует тщательного regression testing. Semantic изменения могут не быть очевидными по документации, ловятся только на реальном выполнении. Хорошее покрытие тестами включая интеграционные с реальной БД помогает обнаруживать такие проблемы до prod.

## Различие findById и getReferenceById

Два похожих метода с тонкой семантической разницей регулярно становятся источником багов. Метод findById возвращает Optional и внутри вызывает em.find, который делает SELECT в БД сразу при вызове. Возвращаемая сущность (если найдена) находится в managed состоянии, все её поля загружены. Метод getReferenceById возвращает Entity напрямую и внутри вызывает em.getReference, который возвращает proxy без обращения к БД. SELECT произойдёт только при первом обращении к любому полю proxy кроме идентификатора.

Использование getReferenceById оправдано в конкретном сценарии — когда нужна ссылка на существующую сущность для связывания в отношении, но реально читать её данные не требуется. Пример — создаём новый Fno и хотим установить связь с существующим Taxpayer. Нам нужен объект Taxpayer только для установки в поле fno.setTaxpayer, никакие данные Taxpayer читаться не будут. GetReferenceById возвращает proxy, никакого лишнего SELECT нет, экономится одна БД операция.

Опасность возникает при попытке использовать getReferenceById для чтения данных. Если proxy используется вне транзакции с последующим обращением к полям — LazyInitializationException. Внутри транзакции при обращении к полю proxy выполнится SELECT, что часто неожиданно.

Реальный кейс из КНП называется taxreport21-java21-runtime-regressions. Код использовал getById (устаревший метод, эквивалент getReferenceById), передавал полученный объект в маппер вне транзакции. Маппер обращался к полям объекта для формирования DTO, что приводило к LazyInit. Fix — заменить getById на findById, что делает SELECT сразу и возвращает полностью загруженную сущность.

Правило — getReferenceById только для связывания сущностей, никогда для использования их данных. Для чтения — findById или полноценные запросы через репозиторий.

## Оптимизация через readOnly

Аннотация @Transactional со значением readOnly true даёт существенную оптимизацию для read методов. Всегда указывать её для методов только читающих из БД.

Механически что даёт эта настройка. Hibernate помечает Session как имеющую FLUSH_MODE MANUAL — не делает автоматический flush перед queries. Не создаёт snapshots для загруженных сущностей — не будет dirty checking. Не будет генерации UPDATE при commit транзакции даже если поля были изменены (что не должно происходить в read методах, но защищает от случайных изменений).

Экономия ресурсов заметная. Snapshot для каждой загруженной сущности требует памяти пропорциональной количеству полей. Для больших запросов возвращающих тысячи сущностей это существенно. Сравнение snapshots с текущим состоянием при flush тратит CPU. Для read-only транзакции это чистые потери.

Дополнительно PostgreSQL может оптимизировать read-only транзакции на своей стороне. Read-only транзакция не требует WAL записей для операций чтения, что снижает нагрузку. Некоторые типы блокировок могут не устанавливаться. Практическая разница на нагруженной системе заметна.

Явная документация намерения через readOnly также ценна для читаемости кода. Разработчик читающий код видит "это read метод" сразу по аннотации, не разбираясь в логике. Кроме того, случайная ошибка вроде добавления модификации в read метод часто обнаруживается на этапе тестирования — Hibernate явно ругается на попытку изменения в read-only транзакции.

Правило — всегда указывать readOnly true на всех read методах. Стоимость применения нулевая (просто параметр аннотации), польза заметная.

## Self-invocation в JPA контексте

Проблема self-invocation @Transactional уже обсуждалась в контексте Spring Framework. В JPA контексте она особенно болезненна потому что связана с механизмом сессий Hibernate.

Метод помечен @Transactional, вызывается через this.method из того же класса. Spring proxy минуется (потому что this ссылается на реальный объект, не на proxy). Транзакция не создаётся. EntityManager не связывается с текущим потоком. При попытке выполнить любую JPA операцию внутри метода получается ошибка либо отсутствия транзакции либо LazyInit при обращении к lazy полям.

Реальный кейс knp-fo-sync-notification-bugs показал масштаб проблемы. Метод processAll помечен @Transactional, в цикле вызывает processOne через this.processOne. Метод processOne помечен @Transactional propagation REQUIRES_NEW с намерением создать отдельную транзакцию для каждой итерации. Но вызов через this минует proxy, propagation REQUIRES_NEW не срабатывает. Всё выполняется в одной транзакции внешнего processAll.

Последствия многослойные. Одна ошибка в processOne откатывает весь processAll, теряется прогресс. Если ожидалась независимость транзакций для audit или checkpoint логики — не работает. Long transaction держит locks дольше чем следовало. Плюс если внутри processOne ожидается свежая сессия для загрузки данных — её нет, происходит LazyInit при обращении к связанным полям.

Стандартное решение — вынести метод в отдельный bean. Создать NotificationProcessor класс с методом processOne, injected в NotificationService. Внутри processAll вызывать processor.processOne — через injected reference на другой bean, что идёт через proxy. Аннотация @Transactional на processOne теперь срабатывает корректно, propagation REQUIRES_NEW создаёт отдельную транзакцию для каждой итерации.

Правило — если метод внутри @Transactional класса нужно вызывать с propagation REQUIRES_NEW или другими семантически важными настройками транзакций, он должен быть в отдельном bean.

## Batch операции для массовой обработки

Массовая вставка или обновление большого количества записей требует особого подхода из-за проблемы накопления объектов в first-level cache.

Наивный подход — цикл по списку с вызовом persist или save на каждой итерации. Проблема очевидна — все persist накапливаются в first-level cache, для миллиона объектов происходит OutOfMemoryError задолго до завершения цикла. Даже если heap хватает, dirty checking на большом количестве объектов работает медленно.

Правильный паттерн включает периодический flush и clear. В цикле после каждых пятидесяти или ста итераций вызывается em.flush для отправки накопленных SQL в БД и em.clear для очистки first-level cache от уже обработанных объектов. Управляемое количество объектов в памяти на протяжении всей обработки.

Включение JDBC batching через настройки Hibernate многократно ускоряет отправку SQL. Параметр hibernate.jdbc.batch_size устанавливается в значение согласованное с размером batch в цикле — обычно двадцать или пятьдесят. Параметры order_inserts и order_updates включают сортировку операций по типу перед batch, что улучшает эффективность батчинга. Ускорение в пять-двадцать раз для массовых операций.

Критичное напоминание — стратегия IDENTITY для primary key полностью ломает батчинг. Hibernate вынужден делать отдельный INSERT для каждой сущности чтобы получить auto-incremented ID. Для использования batching обязательна стратегия SEQUENCE. Проверить настройку @GeneratedValue на всех Entity участвующих в массовых операциях.

## Second-level cache через Hazelcast

Первый уровень кэша работает внутри одной сессии. Второй уровень существует между сессиями на уровне SessionFactory. Разные транзакции могут делить кэшированные данные, что полезно для конкретных сценариев.

Классический подходящий случай — справочники. Тип налогоплательщика может иметь двадцать значений, читается тысячи раз в день, обновляется раз в год. Кэширование этих данных между сессиями устраняет ненужную нагрузку на БД.

Настройка требует нескольких шагов. Подключение зависимостей hibernate-jcache и провайдера кэша — в КНП используется Hazelcast как distributed кэш между несколькими JVM. В application.yml включаются параметры hibernate.cache.use_second_level_cache и use_query_cache. Аннотация @Cache на Entity классе включает кэширование конкретной сущности с указанием concurrency стратегии — READ_ONLY, NONSTRICT_READ_WRITE, READ_WRITE, TRANSACTIONAL.

Query cache для кэширования результатов запросов работает через @QueryHints на методах репозитория. Осторожно — query cache инвалидируется при любом изменении в кэшируемой таблице, что часто делает его больше проблемой чем пользой для активно меняющихся данных.

В КНП использование Hazelcast как distributed second-level cache позволяет сервисам делить кэшированные справочники между инстансами, что снижает общую нагрузку на БД. Реальный кейс knp-form-hz5-actuator-cache связан с миграцией с Hazelcast 3 на Hazelcast 5 — API кардинально изменился, Spring Boot Actuator CacheMetricsAutoConfiguration вызывал удалённый метод getNativeCache. Пришлось исключать проблемные auto-configurations чтобы приложение стартовало на новой версии Hazelcast.

## HikariCP как connection pool

Spring Boot использует HikariCP по умолчанию — это самый быстрый JDBC connection pool в Java мире. Настройки в application.yml контролируют поведение пула. Параметр maximum-pool-size — максимальное количество соединений. Параметр minimum-idle — минимальное количество соединений в состоянии idle. Параметры idle-timeout и max-lifetime контролируют время жизни соединений. Параметр connection-timeout — сколько ждать получения соединения из пула до выброса исключения. Параметр leak-detection-threshold предупреждает если соединение не возвращено в пул за указанное время, помогает обнаруживать утечки.

Правильный размер пула — тема отдельного рассуждения. Классическое правило рассчитывает размер как 2 умножить на количество CPU cores плюс количество дисков. Для современных SSD и cloud окружений обычно значения десять-тридцать соединений достаточно. Больший пул не значит быстрее — большой пул создаёт contention на стороне БД (много активных сессий конкурируют за locks и resources), что может замедлить всю систему. Меньший пул иногда работает быстрее.

Реальный кейс из КНП про отравление пула — knp-e2e-runner-hikari-isolation-poisoning. E2E runner брал соединения с параметром isolation равным минус единице (специальное значение opt-in). Пул отравлялся — соединения возвращались в пул с странным isolation значением. Следующий клиент получал такое отравленное соединение, что приводило к cascade errors на уровне pgbouncer. Fix — явно указать transaction-isolation в конфигурации HikariCP на TRANSACTION_READ_COMMITTED, что нормализовало поведение всех соединений в пуле.

## Специфика PostgreSQL

Работа с PostgreSQL в enterprise setup обычно включает pgbouncer — connection pooler между приложением и настоящим PostgreSQL сервером. Pgbouncer экономит соединения на стороне БД, что критично когда десятки приложений подключаются к одному PostgreSQL. В КНП стандартно то что приложение называет БД (например db-knp) на самом деле является pgbouncer, PostgreSQL сервер стоит за ним.

Pgbouncer работает в одном из трёх режимов. Режим session — соединение выдаётся клиенту на всю его сессию, полная функциональность включая prepared statements и session variables. Режим transaction — соединение возвращается в пул после каждой транзакции. Более эффективное использование соединений, но не поддерживает server-side prepared statements, что Hibernate использует по умолчанию, приводит к ошибкам. Режим statement — соединение возвращается после каждого statement, самый агрессивный вариант, работает только для очень специфических сценариев.

Работа с pgbouncer в transaction mode требует специальной настройки Hibernate чтобы не использовать server-side prepared statements. Параметр prepareThreshold в JDBC URL или свойствах контролирует это. Настройка неправильно приводит к странным ошибкам, которые сложно диагностировать без понимания что pgbouncer в цепочке.

Batch settings для PostgreSQL включают параметр reWriteBatchedInserts который заставляет PostgreSQL JDBC driver переписывать множественные INSERT в один INSERT VALUES с несколькими наборами значений. Существенно быстрее чем N отдельных INSERT statements. Плюс параметры cachePrepStmts и prepareThreshold контролируют кэширование prepared statements.

## Индексы для производительности запросов

Индексы не являются частью JPA как такового — они создаются на стороне БД через миграции Liquibase. Но критично влияют на производительность запросов, генерируемых JPA. Разработчик JPA приложения должен понимать когда и какие индексы нужны.

Общие правила простые. Индекс на любой foreign key колонке обязателен — иначе JOIN операции медленные, потому что БД делает full scan одной из таблиц для каждой строки другой. Индексы на колонках которые часто используются в WHERE условиях и в ORDER BY. Composite индексы для комбинированных фильтров — но порядок колонок важен, потому что индекс работает по префиксному правилу. Первая колонка индекса может использоваться отдельно, комбинация первой и второй тоже, но не может использоваться только вторая колонка.

Например индекс на fno по колонкам status и created_at работает для запросов с WHERE status равен и WHERE status равен AND created_at больше. Не работает для запроса только с WHERE created_at больше — status не в условии, префикс не совпадает.

Проверить реально используется ли индекс можно через EXPLAIN ANALYZE запроса. Ищем в выводе индикаторы вроде Index Scan или Bitmap Index Scan — они означают что индекс используется. Присутствие Seq Scan для больших таблиц — плохо, нужно full table scan, значит индекс отсутствует или не подходит для запроса.

## Длинные транзакции как проблема

Открытая транзакция занимает ресурсы. Держит connection в пуле — исчерпаешь пул при высокой нагрузке. Держит row locks на изменённых строках — блокируешь другие транзакции пытающиеся обновить те же строки. Раздувает undo logs и WAL в БД. Длинные транзакции — источник проблем производительности и стабильности.

Правило простое — транзакции должны быть короткими. Только чтение и запись в БД, минимальная бизнес-логика внутри @Transactional метода. Никаких обращений к внешним API вроде HTTP запросов или отправки email внутри транзакции — эти операции могут затянуться на секунды или минуты, всё это время транзакция остаётся открытой с занятым connection.

Плохой паттерн — метод сервиса помечен @Transactional, выполняет save сущности в БД, затем вызывает externalApi.call. Пока внешний API отвечает (потенциально до тридцати секунд с настройками по умолчанию), транзакция открыта. Connection занят. Другие запросы к этой же сущности могут блокироваться. При таймауте внешнего API получается забавная ситуация — данные записались в БД (если БД успела commit), но статус транзакции неопределён на стороне приложения.

Правильный подход — разделить сохранение в БД и вызов внешнего API на разные операции. Один метод с @Transactional только для сохранения. Другой метод без @Transactional для вызова API. Порядок вызова в service слое ясно виден. Транзакция короткая, connection освобождается быстро.

Для гарантированной доставки внешним системам используется outbox pattern — обсуждалось в отдельном файле. Сохраняются данные плюс запись о необходимости отправить событие в одной короткой транзакции. Отдельный job в фоне читает outbox таблицу и отправляет накопленные события во внешние системы с retry и обработкой ошибок. Основная транзакция короткая, гарантия доставки обеспечивается механизмом.

## Инструменты диагностики

Практическая работа с производительностью JPA требует умения использовать инструменты диагностики. Логирование SQL уровня DEBUG для logger org.hibernate.SQL показывает все запросы. Логирование уровня TRACE для BasicBinder показывает значения bind параметров. Statistics механизм даёт сводку по каждой сессии. Всё это для dev и test окружений — в production логи слишком шумные при таких уровнях.

Библиотека datasource-proxy в тестах позволяет asserting количество SQL запросов. Тест выполняет метод сервиса, потом проверяет что количество SELECT не превышает разумное значение. Автоматическая защита от регрессий N+1 при code changes.

В PostgreSQL расширение pg_stat_statements предоставляет статистику всех выполненных запросов на стороне БД. Топ запросов по времени выполнения, по количеству вызовов, средняя latency. Инструмент DBA для оптимизации, но полезен и разработчику для понимания реальной нагрузки в prod.

APM инструменты — Datadog, New Relic, Elastic APM — предоставляют distributed tracing и автоматическую детекцию проблем. N+1 подсвечивается автоматически. Slow queries отслеживаются с историей. Полная картина взаимодействия приложения с БД. Существенно ускоряет диагностику проблем в prod.

## Заключение

Производительность JPA — обширная тема где абстракция ORM утекает и приложение начинает падать. Знание типичных проблем и способов их решения — базовая компетенция для работы с enterprise Java.

N+1 проблема как главный враг. Симптом — много одинаковых SELECT запросов в логах. Решения включают JOIN FETCH для single-value связей, @EntityGraph декларативно, @BatchSize или default_batch_fetch_size для автоматического батчинга lazy loading, DTO projection когда нужны только данные.

LazyInitializationException при обращении к lazy полю вне сессии. Правильное решение — DTO проекции в сервисе внутри транзакции. Не EAGER который убивает производительность, не open-in-view который скрывает N+1 и держит connection.

FindById против getReferenceById — findById делает SELECT сразу, getReferenceById возвращает proxy для связывания. Использование getReferenceById для чтения приводит к LazyInit.

Аннотация @Transactional readOnly true на всех read методах — существенная оптимизация без cost.

Self-invocation в JPA контексте особенно болезненна из-за связи с сессиями. Fix через вынос метода в отдельный bean.

Batch операции требуют периодического flush и clear в цикле плюс включение JDBC batching через настройки Hibernate. SEQUENCE для primary key обязательна для batch.

Second-level cache для справочников. Hazelcast как distributed кэш в КНП. Осторожно с миграцией версий провайдера кэша.

HikariCP настройки — правильный размер пула, leak detection, явный transaction isolation. Реальный кейс отравления пула из практики КНП.

PostgreSQL специфика — pgbouncer в transaction mode требует специальной настройки Hibernate, reWriteBatchedInserts для batch, cachePrepStmts для prepared statements.

Индексы на foreign keys и WHERE/ORDER BY колонках. Composite индексы с правильным порядком колонок.

Длинные транзакции как источник проблем. Никаких external API вызовов внутри @Transactional. Outbox pattern для гарантированной доставки.

Диагностика через SQL логи, statistics, datasource-proxy в тестах, pg_stat_statements в PostgreSQL, APM в prod.

Для КНП контекста все эти проблемы регулярны в реальной работе. Знание паттернов и типичных решений позволяет писать эффективный код и быстро диагностировать регрессии производительности. Стандарты команды включают readOnly транзакции для чтения, DTO проекции в сервисах, open-in-view отключён, явные fetch стратегии, SEQUENCE для всех сущностей, использование Testcontainers для интеграционных тестов с реальным PostgreSQL.

Дальше обсуждается блок Java 11 к Java 21 — актуально для миграции модулей КНП на новую версию LTS. Синтаксические изменения, API updates, JVM оптимизации, virtual threads. Понимание что изменилось помогает эффективно использовать возможности новой версии платформы.
