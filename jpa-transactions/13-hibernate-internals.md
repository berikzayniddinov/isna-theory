# 13. Hibernate внутри: Session, dirty checking, flush, связи

## Зачем разбираться в деталях Hibernate

JPA как спецификация определяет только API — интерфейсы и аннотации, которые видит разработчик. Как реально работает загрузка сущности из БД, как отслеживаются изменения, как формируются SQL запросы для связанных данных, как оптимизируется массовая вставка — всё это определяется реализацией. В подавляющем большинстве Java приложений реализацией является Hibernate, и понимание его внутренней механики критично для senior разработчика.

Первая причина знать внутренности заключается в оптимизации производительности. JPA API скрывает то, что реально происходит с базой данных. Одна строка Java кода `fno.getStatus()` может тихо выполнить SELECT если объект был получен через getReference и это первое обращение к полю. Простой цикл по списку с обращением к связанным сущностям может незаметно превратиться в тысячу запросов через N+1 проблему. Только понимание что делает Hibernate под капотом позволяет писать эффективный код и заранее распознавать потенциальные проблемы производительности.

Вторая причина — диагностика ошибок. Специфические Hibernate исключения вроде LazyInitializationException, PersistentObjectException, StaleObjectStateException возникают по конкретным причинам, связанным с механикой Session и proxy объектов. Без понимания lifecycle сессии, semantics flush operations, работы dirty checking — эти exceptions выглядят загадочно, диагностика занимает много времени. С пониманием внутренностей проблема локализуется за минуты.

Третья причина — использование Hibernate-специфичных возможностей когда JPA стандарта не хватает. Batch fetch для оптимизации lazy loading, second-level cache для кэширования между сессиями, event listeners для реагирования на события lifecycle, custom types для нестандартных маппингов — всё это Hibernate функциональность за пределами JPA стандарта. Знание доступных возможностей расширяет toolkit разработчика для решения сложных задач.

## Отношение Session и EntityManager

Hibernate существовал задолго до появления JPA стандарта — с 2001 года, когда стандартом для persistence в Java был EJB Entity Beans, устаревшая и сложная технология. Hibernate предложил элегантную альтернативу с собственным API, центрированным вокруг интерфейса Session. Когда в 2006 году появился JPA стандарт, во многом вдохновлённый именно Hibernate, команда разработки добавила поддержку JPA API, реализовав EntityManager поверх существующего Session.

Практически это означает следующее. EntityManager — интерфейс JPA стандарта, стандартизированный набор методов для работы с сущностями. Session — интерфейс Hibernate, расширяющий EntityManager дополнительными методами специфичными для Hibernate. Через метод unwrap класса EntityManager можно получить нижележащий Session и использовать Hibernate-специфичные возможности.

Session предоставляет несколько дополнительных возможностей, отсутствующих в стандартном JPA. Метод saveOrUpdate — умный сохранение, автоматически определяющий transient или detached состояние переданного объекта и выбирающий правильную операцию. Механизм event listeners позволяет подписаться на события pre-insert, post-load, post-delete и другие, что даёт возможность реализовать аудит или кастомную логику без специальных аннотаций. Filters — механизм фильтров на entities, автоматически применяемых ко всем запросам. Custom query hints для тонкой настройки поведения конкретных запросов.

Правило подхода — писать код через стандартный EntityManager API. Unwrap в Session только когда действительно нужна Hibernate-специфичная функциональность, недоступная через JPA стандарт. Это даёт лучшую портируемость, легче миграции между JPA реализациями. Хотя в реальности мало кто мигрирует между Hibernate и, скажем, EclipseLink — Hibernate доминирует на рынке настолько, что альтернативы редко рассматриваются.

Аналогичная иерархия существует на уровне фабрик. SessionFactory — тяжёлый Hibernate объект, содержащий метамодель всех сущностей, кэши metadata, connection pool конфигурацию. Является thread-safe, singleton на всё приложение. EntityManagerFactory — JPA обёртка над SessionFactory, предоставляющая стандартизированный интерфейс. Spring Boot создаёт один LocalContainerEntityManagerFactoryBean на старте через auto-configuration, все инъекции через @PersistenceContext работают через него. Разработчику не приходится создавать EntityManagerFactory вручную.

## First-level cache в деталях

Внутри Session находится структура, играющая роль first-level cache — это Map ассоциирующий пары (класс сущности, primary key) с managed объектами. При каждой операции чтения Hibernate сначала проверяет этот кэш, и только если объект не найден в кэше, обращается к БД. Все загруженные сущности удерживаются в кэше до конца сессии.

Практическое поведение выглядит очевидным. Первый вызов session.get с указанием класса и ID выполняет SELECT в БД, создаёт Java объект, кладёт его в first-level cache. Все последующие вызовы с теми же аргументами возвращают тот же объект из кэша без обращения к БД. Гарантируется что это буквально один и тот же Java объект в смысле оператора равенства ссылок, не просто equal объекты.

Такой механизм даёт несколько важных преимуществ. Identity map — гарантированно один Java объект на пару класс плюс primary key в пределах сессии. Это упрощает работу с сущностями, не требует специальной защиты от дубликатов в коде. Dirty checking — Hibernate помнит исходное состояние загруженных сущностей и может определить какие изменились для генерации UPDATE. Read cache — повторные чтения не идут в БД, что экономит время на сетевых round-trips. Write-behind — операции persist, update, remove накапливаются в специальной ActionQueue и не отправляются в БД по мере вызова, что позволяет объединить их в batch и оптимизировать порядок выполнения.

Есть также важные ограничения first-level cache. Он не является кэшем между сессиями — каждая новая транзакция создаёт новый Session с пустым кэшем. Прочитанная в предыдущей транзакции сущность не поможет — придётся снова делать SELECT. Для меж-сессионного кэширования существует second-level cache, обсуждаемый ниже. First-level cache также не защищает от изменений извне — если другая транзакция изменила строку в БД, эта Session этого не увидит до commit или явного refresh.

Существует практическая опасность при работе с большими датасетами. Если в один Session загрузить очень много объектов через большой SELECT, все они удерживаются в first-level cache. Heap может исчерпаться, приложение упадёт с OutOfMemoryError. Для батчевой обработки требуется периодическое flush для отправки накопленных изменений в БД и clear для освобождения кэша от уже обработанных объектов. Типичный паттерн — цикл по большому набору данных с em.flush и em.clear каждые пятьдесят или сто итераций.

## Механика dirty checking

Магия автоматического сохранения изменений в JPA — "изменил поле, сохранилось при commit" — не бесплатна. Она реализуется через механизм dirty checking, требующий чтобы Hibernate помнил исходное состояние каждого managed объекта и сравнивал с текущим при flush.

Что происходит при загрузке сущности через em.find или JPQL запрос. Hibernate выполняет SELECT, создаёт Java объект, инициализирует его поля значениями из результирующего set. Затем копирует все значения полей в отдельную структуру — snapshot, обычно массив Object[]. Объект кладётся в first-level cache, snapshot тоже сохраняется в связанной структуре EntityEntry.

С этого момента любые изменения полей объекта потенциально отслеживаются, но реального сравнения не происходит до момента flush. Разработчик просто изменяет поля через setter методы, никакого SQL при этом не выполняется. Ничего не отправляется в БД, но Hibernate знает что при следующем flush нужно проверить эти объекты на изменения.

При flush Hibernate проходит по всем managed объектам в first-level cache. Для каждого сравнивает текущие значения полей с сохранённым snapshot. Если находит расхождения — генерирует UPDATE только для изменившихся полей (или всех, в зависимости от настройки). Собранные UPDATE операции вместе с INSERT и DELETE из ActionQueue отправляются в БД в порядке зависимостей — сначала родительские сущности при inserts, дочерние при deletes.

Пример работы dirty checking. Метод сервиса помечен @Transactional. Внутри метода em.find загружает сущность Fno по идентификатору, состояние status равно NEW. Hibernate сохраняет snapshot с полем status=NEW. Метод изменяет f.setStatus(SUBMITTED) — обычное присваивание Java, никакого SQL. При выходе из метода Spring commits транзакцию. Перед commit автоматически вызывается flush. Hibernate сравнивает snapshot status равен NEW с текущим status равен SUBMITTED, обнаруживает изменение, генерирует UPDATE fno SET status равен SUBMITTED WHERE id равен нужному. SQL отправляется в БД, транзакция коммитится.

Обратите внимание что три обращения к коду — em.find, setter, выход из метода — привели к одному UPDATE в БД. Никакого явного save или persist в коде не требуется. Это удобно и естественно, но за этой простотой скрывается серьёзная механика.

Существуют определённые ограничения dirty checking. Он не заметит изменение внутри mutable коллекции если тип элементов не является Entity — например, добавление в HashMap, хранящуюся как @ElementCollection, может не быть замечено в некоторых конфигурациях. Обычно это не проблема для типичных сценариев, но стоит помнить. Собственная реализация equals на Entity с mutable полями может создавать странные баги, потому что Hibernate использует equals для сравнения в коллекциях.

Для read-only операций dirty checking является ненужным оверхедом — метод только читает, не изменяет. Указание readOnly в @Transactional отключает создание snapshots и dirty checking для загруженных объектов, экономит память и CPU. Правило — всегда помечать read-only методы соответствующей аннотацией.

## Flush против commit

Часто путают операции flush и commit, но семантически они очень разные. Flush отправляет накопленные SQL операции в БД, но транзакция остаётся открытой. Commit фиксирует транзакцию, изменения становятся видны другим транзакциям.

Механика типичного сценария. Метод сервиса делает несколько операций — persist новой сущности, изменение полей managed сущности, ещё один persist. Все эти операции накапливаются в ActionQueue внутри Session, никакого SQL пока не отправляется в БД. При явном или автоматическом flush Hibernate генерирует все накопленные INSERT и UPDATE операции, отправляет их в БД одним batch (при правильной настройке). Транзакция всё ещё открыта, изменения видны только в рамках этой транзакции. При commit транзакция коммитится, изменения фиксируются, становятся видны другим сессиям.

Между flush и commit могут быть ещё операции — чтения, дополнительные изменения. БД видит изменения в рамках открытой транзакции, что позволяет читать свои собственные writes.

Hibernate поддерживает три режима flush определяющих когда flush происходит автоматически. Режим AUTO, установленный по умолчанию, делает flush перед commit транзакции и перед выполнением JPQL запросов чтобы запрос увидел актуальные изменения текущей сессии. Также перед find для другой сущности, если предыдущие изменения могут повлиять. Режим COMMIT делает flush только при commit — запросы могут возвращать устаревшие данные, не видящие изменения текущей сессии. Режим MANUAL требует явного вызова em.flush разработчиком, полезно для fine-grained контроля в специфических случаях.

Для батчевой обработки массовых операций явный flush в цикле — стандартный паттерн, о котором уже упоминалось. Без периодического flush все создаваемые объекты накапливаются в first-level cache и ActionQueue, что приводит к исчерпанию heap для больших датасетов.

## Statement batching для производительности

Одна из самых важных Hibernate performance возможностей — механизм отправки нескольких INSERT или UPDATE операций одним round-trip к серверу БД. Механически это работает через JDBC batch API.

Без batching для тысячи INSERT операций получается тысяча отдельных запросов к БД. Каждый запрос — сетевой round-trip, обычно от одной до десяти миллисекунд в зависимости от сетевой топологии. Тысяча round-trips по пять миллисекунд — это пять секунд только на сеть, даже без учёта времени обработки на стороне БД. Массовая вставка становится невыносимо медленной.

С batching все INSERT операции сначала подготавливаются локально через PreparedStatement.addBatch, накапливаются в памяти. Затем PreparedStatement.executeBatch отправляет их одним round-trip. Ускорение массовых вставок составляет от пяти до двадцати раз в зависимости от сетевой топологии и характера данных.

Настройка Hibernate batching происходит через несколько параметров в application.yml. Параметр hibernate.jdbc.batch_size устанавливает максимальный размер одного batch. Обычно двадцать или пятьдесят даёт хороший баланс между эффективностью и потреблением памяти. Слишком большие значения могут привести к проблемам с некоторыми JDBC driver.

Параметры order_inserts и order_updates включают сортировку операций по типу сущности перед отправкой в batch. Batch более эффективен когда все операции однотипные — все INSERT в таблицу fno, затем все INSERT в таблицу fno_line. Без сортировки Hibernate может чередовать типы, что снижает эффективность батчинга. Практически всегда стоит включать эти параметры.

Параметр batch_versioned_data включает batching для сущностей с @Version. Более специальный случай, полезный если optimistic locking широко используется.

Есть критически важное ограничение — стратегия GenerationType.IDENTITY для primary key ломает batching полностью. Причина понятна — Hibernate вынужден выполнить INSERT сразу для получения auto-incremented ID, не может отложить операцию в batch. Все INSERT становятся отдельными round-trips, batching не работает вообще, даже если batch_size настроен. Для использования batching необходимо использовать GenerationType.SEQUENCE, что и является стандартом в enterprise Java приложениях на PostgreSQL.

## Диалекты БД

Разные базы данных имеют разный SQL синтаксис для одних и тех же операций. Hibernate абстрагирует эти различия через концепцию Dialect — специального класса, знающего специфику конкретной БД.

Основные диалекты в мире enterprise Java включают PostgreSQLDialect для PostgreSQL, MySQLDialect и MariaDBDialect для соответствующих БД, OracleDialect для Oracle, SQLServerDialect для Microsoft SQL Server. Для тестов часто используется H2Dialect с in-memory базой H2 database.

Что именно знает диалект. Синтаксис pagination — LIMIT и OFFSET в PostgreSQL и MySQL против OFFSET FETCH NEXT в SQL Server и Oracle. Механизм sequence — синтаксис получения следующего значения, специфичный для БД. Стандартные функции — lower, now, current_timestamp имеют разное поведение и синтаксис. Маппинг Java типов на SQL типы — String становится VARCHAR разных размеров, boolean хранится по-разному в разных БД, timestamp имеет разную precision. Locking hints — синтаксис для SELECT FOR UPDATE и связанных операций.

В Spring Boot диалект обычно определяется автоматически по JDBC URL — Hibernate знает какая БД используется по префиксу URL и подключает соответствующий диалект. Иногда нужно явное указание через параметр spring.jpa.database-platform, например при использовании кастомного диалекта или для явности конфигурации.

Реальный gotcha из КНП связан с миграцией на Hibernate 6. Старое имя класса диалекта PostgreSQLDialect стало deprecated. Hibernate 6 может автоматически определить нужную версию (PostgreSQL 10+, 12+, 14+) и предпочитает соответствующие специализированные диалекты. Старое имя продолжает работать, но с warning в логах. Не критично, но при разборе логов может путать.

## Ассоциации между сущностями

Реляционная модель строит связи между таблицами через foreign keys. Hibernate представляет эти связи в объектной модели через специальные аннотации на полях Entity.

Аннотация @ManyToOne — самая частая связь. Много детей ссылаются на одного родителя через FK. Например, много Fno могут принадлежать одному Taxpayer. Foreign key колонка находится в таблице many-стороны, в данном случае fno. Аннотация @JoinColumn указывает имя FK колонки. Правильное использование требует всегда явно указывать FetchType.LAZY, потому что стратегия по умолчанию для @ManyToOne — EAGER, что приводит к автоматической загрузке связанной сущности при каждом чтении, даже когда она не нужна. Это опасное значение по умолчанию, регулярный источник проблем производительности.

Аннотация @OneToMany представляет обратную сторону @ManyToOne — один родитель имеет много детей. Собственный FK у этой стороны не создаётся, связь известна только через FK на дочерней стороне. Атрибут mappedBy указывает поле дочерней сущности, ссылающееся обратно на родителя. Без mappedBy Hibernate ошибочно решит что это двунаправленная independent связь и создаст лишнюю join таблицу для её представления. Всегда указывайте mappedBy для bidirectional связей. По умолчанию @OneToMany использует FetchType.LAZY, что логично — коллекции обычно большие, автоматическая загрузка всегда неэффективна.

Аннотация @OneToOne представляет связь один к одному. Владелец связи — сторона с @JoinColumn, где FK колонка. Другая сторона использует mappedBy для указания на владельца. По умолчанию @OneToOne использует FetchType.EAGER, что опасно как и с @ManyToOne. Явное указание LAZY правильная практика.

Аннотация @ManyToMany представляет связь многие ко многим. Требует связующей таблицы для представления связи в реляционной модели. Аннотация @JoinTable указывает имя и структуру связующей таблицы. Практика показывает что почти всегда лучше моделировать такие связи через две @OneToMany связи с explicit промежуточной сущностью. Это даёт возможность добавлять атрибуты к связи — когда была добавлена, кем, с какими параметрами. @ManyToMany оправдан только в случаях когда связь совсем без атрибутов, что редкость.

## Стратегии загрузки LAZY и EAGER

Фундаментальный вопрос ORM — когда загружать связанные данные. Сразу вместе с родительской сущностью через EAGER или лениво при первом обращении через LAZY. От правильного выбора зависит производительность приложения.

Стратегия LAZY откладывает загрузку до первого обращения к связанному полю. Hibernate создаёт proxy объект — обычно CGLIB subclass реальной сущности для одиночных связей или специальный PersistentBag для коллекций. Proxy знает только ID связанной сущности, всё остальное неизвестно. При первом обращении к любому полю proxy кроме ID Hibernate выполняет SELECT для загрузки данных. Все последующие обращения работают с уже загруженными данными.

Стратегия EAGER загружает связанные данные всегда при чтении родительской сущности. Для одиночных связей типа @ManyToOne и @OneToOne это реализуется через JOIN в SQL запросе — родительская и связанная сущности загружаются одним запросом. Для коллекций может использоваться отдельный запрос или JOIN в зависимости от настроек.

Преимущества EAGER очевидны — нет проблемы LazyInitializationException при обращении к связанным данным вне сессии, простая семантика (всегда всё загружено). Недостатки существеннее — лишние JOIN в запросах, даже когда связанные данные не нужны для конкретного вызова. При модели с несколькими уровнями связей это приводит к сложным JOIN, замедляющим все запросы. На больших моделях EAGER просто убивает производительность.

Преимущества LAZY заключаются в загрузке только того что действительно нужно для конкретного вызова. Экономия ресурсов сети, БД, приложения. Недостаток — риск LazyInitializationException при обращении к lazy полю вне активной сессии, что часто случается при возврате Entity из сервиса в контроллер. Также риск N+1 проблемы при непреднамеренном обращении к lazy полям в цикле.

Правило простое и однозначное — использовать LAZY везде, явно указывать fetch=FetchType.LAZY даже там где это значение по умолчанию, для документирования намерения. EAGER только когда есть очень специфическая причина, точно известно что связь всегда нужна, а альтернативные подходы вроде явного JOIN FETCH не подходят.

## Проблема LazyInitializationException

Классическая проблема JPA приложений возникает при попытке обратиться к lazy loaded полю после закрытия сессии, содержавшей объект как managed. Прокси помнит что нужно загрузить, но сессии больше нет, SELECT выполнить некуда, Hibernate бросает LazyInitializationException.

Типичный сценарий возникновения. Сервисный метод помечен @Transactional, читает сущность через em.find, возвращает её как результат. При возврате метода Spring коммитит транзакцию, EntityManager закрывается, сессия завершается. Возвращённая сущность становится detached. Контроллер получает эту detached сущность, пытается обратиться к lazy полю для формирования response — например, вызывает fno.getTaxpayer().getName(). Прокси на taxpayer пытается выполнить SELECT для загрузки данных, но сессии уже нет — LazyInitializationException.

Существует несколько способов решения этой проблемы, различающихся по правильности архитектурного подхода.

Самое правильное решение — использовать DTO проекции в сервисе. Сервис не возвращает Entity наружу, вместо этого читает нужные данные внутри транзакции и формирует DTO, содержащий именно то что нужно контроллеру. Все обращения к lazy полям происходят внутри транзакции, где сессия активна и данные могут быть загружены. Плюс архитектурная чистота — Entity является внутренней деталью implementation слоя persistence, не должна утекать в API слой контроллера. Плюс точный контроль над тем какие данные загружаются, никаких неожиданных лишних запросов.

Альтернативное решение — использовать JOIN FETCH в запросе или @EntityGraph для явной eager загрузки нужных связей. Это делает загруженные данные доступными после закрытия сессии. Работает если известно заранее какие связи будут нужны. Менее гибко чем DTO проекции, но проще в реализации для простых случаев.

Существует также open-session-in-view паттерн, который Spring Boot включает по умолчанию. Сессия держится открытой на весь HTTP запрос, включая контроллер и рендеринг response. LazyInitializationException не возникает потому что сессия всегда активна. Однако у этого подхода серьёзные проблемы. Он скрывает N+1 проблему — SELECT запросы летят из контроллера или сериализатора, разработчик не видит их в коде сервиса. Держит БД connection занятым на всё время обработки HTTP запроса, что при медленных клиентах может исчерпать connection pool. Правильная практика — отключать open-in-view в конфигурации, тогда LazyInitializationException возникает в тестах и разработчики вынуждены правильно грузить данные в сервисе.

Использование FetchType.EAGER — это самое ленивое решение, о котором уже упоминалось. Убивает производительность в общем случае, не решает проблему архитектурно.

Отдельно стоит упомянуть про изменения в Hibernate 6, актуальные для миграции части сервисов КНП на Java 21. Hibernate 6 стал строже проверять доступ к lazy полям — LazyInitializationException проявляется в местах, где Hibernate 5 иногда прощал. Плюс комбинация с self-invocation проблемой @Transactional может дать неочевидные баги. Метод помечен @Transactional, но вызывается через this.method внутри того же класса, proxy минуется, транзакция не открывается, сессия не создаётся. Любое обращение к lazy полю сразу даёт LazyInitializationException. Реальный кейс из КНП назывался knp-fo-sync-notification-bugs — шесть багов в одной feature из этой комбинации проблем.

## Second-level cache между сессиями

First-level cache работает только в рамках одной сессии. Second-level cache существует на уровне SessionFactory и работает между сессиями. Разные транзакции могут делить кэшированные данные.

Second-level cache полезен для конкретного набора сценариев. Много чтений одних и тех же данных из разных запросов и сессий. Данные редко меняются, что делает кэш эффективным (частые изменения инвалидируют кэш, снижая пользу). Хочется распределённого кэша между несколькими JVM, чтобы сервисы делили кэшированные данные.

Классический пример подходящих данных — справочники. Тип налогоплательщика может иметь два десятка значений, читается тысячи раз в день, обновляется раз в год. Загружать эти двадцать записей из БД для каждого запроса — бессмысленная нагрузка. Second-level cache кэширует их между сессиями, любой сервис делает лишь один SELECT в БД при старте кэша, дальше все читают из кэша в памяти.

Настройка second-level cache в Spring Boot требует нескольких шагов. Подключение зависимостей на Hibernate JCache и провайдер кэша — популярные варианты Ehcache для локального кэша в одной JVM, Hazelcast для распределённого кэша между несколькими JVM, Infinispan как альтернатива Hazelcast. В application.yml включаются параметры hibernate.cache.use_second_level_cache и указывается region factory class.

Аннотация @Cache на Entity классе включает кэширование для этой конкретной сущности. Параметр usage указывает стратегию concurrency, которая определяет как обрабатываются конкурентные изменения. Значение READ_ONLY означает что сущность никогда не изменяется — самый быстрый вариант, но нельзя обновлять. Значение NONSTRICT_READ_WRITE не гарантирует консистентности, устаревшие данные возможны. Значение READ_WRITE использует локи для гарантии консистентности. Значение TRANSACTIONAL интегрируется с JTA транзакциями.

Существует также query cache для кэширования результатов запросов не только сущностей. Он инвалидируется при любом изменении в таблице, что часто делает его больше проблемой чем пользой, если таблица активно меняется. Использовать query cache стоит осторожно, только для действительно read-heavy запросов на редко меняющихся данных.

В КНП используется Hazelcast как distributed second-level cache. Позволяет сервисам делить кэшированные справочники между инстансами. Реальный кейс knp-form-hz5-actuator-cache связан с миграцией с Hazelcast 3 на Hazelcast 5 — API кардинально изменился, что сломало Spring Boot Actuator CacheMetricsAutoConfiguration, вызывавший удалённый метод getNativeCache. Пришлось исключать эту auto-configuration чтобы приложение стартовало.

## Cascade и orphan removal детально

Управление жизненным циклом связанных сущностей через cascade и orphanRemoval уже обсуждалось на уровне JPA. Здесь стоит углубиться в детали, специфичные для практики.

Типы cascade определяют какие операции распространяются на связанные сущности. Значение PERSIST каскадирует сохранение — при em.persist родителя все дочерние получают persist. Значение MERGE каскадирует обновление detached объектов. Значение REMOVE каскадирует удаление — em.remove родителя удаляет всех детей. Значение REFRESH перечитывает и родителя и всех детей из БД. Значение DETACH делает detached и родителя и детей одновременно. Значение ALL включает все операции.

Различие между cascade REMOVE и orphanRemoval часто путают, но оно важное. Cascade REMOVE работает при явном вызове em.remove на родителе — удаляет родителя, каскадно удаляет всех детей вместе с ним. OrphanRemoval работает при удалении дочернего объекта из коллекции родителя — если вызвать collection.remove на конкретной line, Hibernate удалит эту line из БД, потому что она стала "сиротой" без ссылки на родителя.

Практическое использование каскадирования зависит от природы связи в domain модели. Для агрегатов в терминах Domain-Driven Design, где родитель и дети живут как единое целое, стандартная комбинация — cascade ALL плюс orphanRemoval true. Пример — Fno с коллекцией FnoLine. Каждая line существует только в контексте своего fno, не имеет самостоятельной жизни. Удаление fno должно удалить все его lines. Убирание line из коллекции fno должно физически удалить эту line из БД. cascade ALL плюс orphanRemoval true реализует эту семантику.

Для полу-независимых связей может быть достаточно cascade PERSIST плюс MERGE без REMOVE. Родитель управляет созданием и обновлением дочерних, но не отвечает за их удаление. Классический пример — Order с OrderItems, где items могут иметь audit значение и не должны физически удаляться при удалении Order (soft delete pattern).

Для полностью независимых связей каскадирование не используется. Пример — Fno имеет ссылку на Taxpayer, но Taxpayer существует независимо от Fno. Удаление Fno не должно затрагивать Taxpayer. Создание Fno не должно каскадно создавать Taxpayer — он должен быть создан отдельным процессом. Никакого cascade на этой связи.

## Equals и hashCode на Entity

Тонкая тема, регулярно вызывающая проблемы. Если Entity объекты хранятся в HashSet или используются как ключи HashMap, нужны корректные реализации equals и hashCode. Стандартные реализации от Object работают по ссылке, что часто не соответствует ожидаемой семантике.

Наиболее интуитивное решение — включить в equals идентификатор ID. Кажется логичным — две сущности равны если у них одинаковый primary key. Но это приводит к серьёзной проблеме с только что созданными объектами, у которых ID равен null. Создание нового Fno и добавление его в HashSet, потом вызов persist — ID меняется с null на реальный после INSERT, hashCode меняется соответственно. HashSet ищет объект в bucket по старому hash, не находит его в новом bucket. Объект тихо "теряется" в HashSet, что создаёт непонятные баги.

Правильные решения зависят от того, есть ли у сущности natural key. Natural key — это поле, идентифицирующее сущность в бизнес-домене, не зависящее от технического primary key БД. Например, regNum для Fno является таким natural key — не может быть двух Fno с одинаковым regNum. В этом случае equals и hashCode реализуются через natural key, что работает корректно и до и после persist.

Если natural key нет, используется приём с константным hashCode. Все объекты этого класса возвращают одинаковый hashCode, например тридцать один. Все они попадают в один bucket любой HashMap, что резко деградирует производительность до линейной, но семантически корректно — hashCode стабилен, объекты не теряются в коллекциях. Equals реализуется через сравнение по ID для persisted объектов, по ссылке для transient.

Через Lombok это можно кратко записать как @EqualsAndHashCode(of = "regNum") для natural key. Без Lombok — ручная реализация с проверкой на null для случая когда natural key ещё не установлен.

Стоит отметить что многие Java приложения работают без явного equals и hashCode на Entity, используя стандартные ссылочные реализации. Это работает пока Entity не попадают в HashSet или HashMap как ключи. Если такой сценарий предполагается — нужна корректная реализация. В КНП обычно ситуации требующие equals редки, стандартных ссылочных реализаций достаточно для большинства сервисов.

## Инструменты отладки SQL

Практический навык — умение посмотреть какие SQL реально генерирует Hibernate для конкретного метода. Инструментов несколько.

Простое логирование SQL включается через несколько параметров конфигурации. Параметр spring.jpa.show-sql равный true выводит SQL в stdout в компактной форме. Параметр hibernate.format_sql включает форматирование SQL для читабельности. Уровень логирования DEBUG для logger org.hibernate.SQL направляет SQL через logging framework, что правильнее для production через централизованное логирование ELK. Уровень TRACE для logger org.hibernate.type.descriptor.sql.BasicBinder показывает значения bind параметров — иначе видишь SQL с placeholders вместо реальных значений.

Statistics механизм даёт общую статистику работы Session. Включается через параметр hibernate.generate_statistics. По окончании сессии в лог выводится метрики — сколько времени потрачено на получение JDBC connection, сколько statements выполнено, сколько entities загружено. Соотношение statements и entities выявляет N+1 проблемы — если тысяча statements при пятидесяти entities, это явный признак N+1 в коде.

Внешние инструменты вроде p6spy и datasource-proxy перехватывают JDBC на уровне ниже Hibernate, логируют реальный SQL с подставленными параметрами вместо placeholders. Даёт возможность видеть SQL буквально в том виде, в котором он отправляется в БД. Особенно полезно для отладки сложных случаев где Hibernate logs могут быть неоднозначными.

В КНП практика использования зависит от окружения. В dev и test окружениях DEBUG уровень для org.hibernate.SQL включён, разработчики видят SQL непосредственно при работе с приложением. В production используется WARN или ERROR уровень чтобы не забивать логи. Для диагностики конкретных проблем можно временно поднять уровень через POST на actuator/loggers endpoint без рестарта приложения — Spring Boot Actuator поддерживает динамическое изменение уровней логирования.

## Заключение

Hibernate под капотом JPA представляет собой сложную систему с многочисленными механизмами оптимизации и абстракциями. Понимание внутренностей необходимо для работы с performance проблемами и диагностики нетривиальных ошибок.

Session и EntityManager отражают исторический контекст — Session более старый Hibernate API, EntityManager — стандарт JPA. Session даёт дополнительные Hibernate-специфичные возможности через unwrap. SessionFactory как тяжёлый singleton на приложение и EntityManager как лёгкий объект на транзакцию.

First-level cache как центральный механизм JPA гарантирует identity объектов в сессии, реализует dirty checking и write-behind. Ограничения включают отсутствие кэша между сессиями и опасность OutOfMemoryError при больших датасетах без периодического flush и clear.

Dirty checking через snapshot сравнение при flush автоматизирует UPDATE операции. Не бесплатно — требует памяти на snapshots и CPU на сравнение. Отключается через readOnly для оптимизации read операций.

Flush и commit — разные операции. Flush отправляет накопленные SQL в БД, транзакция остаётся открытой. Commit фиксирует транзакцию. AUTO flush mode работает автоматически перед queries и commit.

Statement batching через hibernate.jdbc.batch_size и order_inserts/updates даёт значительное ускорение массовых операций. Критично использовать SEQUENCE вместо IDENTITY для primary key, иначе batching не работает вообще.

Ассоциации @ManyToOne, @OneToMany, @OneToOne, @ManyToMany представляют реляционные связи в объектной модели. Обязательно явное указание LAZY для @ManyToOne и @OneToOne, потому что по умолчанию EAGER — источник проблем производительности. Обязательно mappedBy для bidirectional связей чтобы избежать лишней join таблицы.

Стратегии загрузки LAZY по умолчанию для новых связей, EAGER только в специфических случаях. LazyInitializationException правильно решается через DTO проекции в сервисе внутри транзакции, не через EAGER и не через open-in-view.

Second-level cache между сессиями через Hazelcast или Ehcache для redko меняющихся справочников. Требует настройки и правильных стратегий concurrency. В КНП используется через Hazelcast.

Cascade и orphanRemoval различаются по trigger — cascade REMOVE при em.remove родителя, orphanRemoval при удалении из коллекции. Для агрегатов стандартная комбинация cascade ALL плюс orphanRemoval true.

Equals и hashCode на Entity через natural key где возможно, константный hashCode иначе. Стандартные ссылочные реализации подходят когда сущности не хранятся в HashSet.

Отладка SQL через show-sql и логирование org.hibernate.SQL. Statistics для общей картины. p6spy и datasource-proxy для детальной диагностики.

Для КНП контекста понимание всего этого критично для работы с Hibernate в production. Стандарты команды включают явное указание LAZY, DTO проекции в сервисах, open-in-view отключён, PostgreSQL диалект, Liquibase миграции. Мониторинг через show-sql в dev, statistics для оптимизации.

Дальше обсуждается Spring Data JPA как надстройка над JPA. Как репозитории-интерфейсы упрощают работу с БД через derived queries, Specifications, projections и другие механизмы, устраняющие ещё один уровень boilerplate.
